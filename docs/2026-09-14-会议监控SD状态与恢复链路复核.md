## 1. P1：SD 写入状态覆盖实际会议/监控 UI 状态（已证实）

位置：`main/nuwax_ai_partner_main.c` 的 `sync_exclusive_audio_mode_ui_state`；
`main/nuwax_ui_v28/nuwax_drawer.c` 的 `meeting_active` 和菜单点击处理。

同步函数读取控制器状态后，只要 `nuwax_offline_audio_is_active()` 为真就进入
离线覆盖分支。该 API 实际返回全局归档 active，在线镜像同样满足条件。
队列满使 `s.degraded=true`，UI 被改为 ERROR，而会议控制器仍为 ACTIVE。

日志：81.709 秒 UI=2；84.249 秒首个 SD 拒收；84.259 秒 UI=4；之后在线持续上传。
界面仅把 ACTIVE 当作开关开启，因而显示关闭/失败。

衍生缺陷：点击目标由 `!meeting_active()` 计算，误显示 ERROR 时再次点击会
发送“开启”，无法通过该次点击表达关闭。并非仅视觉问题。

整改：业务运行状态决定开关；真正离线接管由独立 lease/capture 状态决定；
SD 降级留在内部诊断，不发布为业务模式 ERROR。

## 2. P1：历史离线模式可污染另一在线模式（源码可达，待实机复现）

上述覆盖分支使用 `offline_mode_kind()` 选择显示会议还是监控。
其存储变量启动默认为会议，只有断线接管时调用 `offline_mode_kind_store` 更新。
在线监控开始 SD 归档时，历史 kind 可能仍为会议，导致 UI 显示会议 ACTIVE、
监控 DISABLED。反向切换也可能被上次离线监控污染。

整改不能只屏蔽 degraded：必须禁止用历史离线 kind 推导在线模式。
覆盖测试应包括首次开机在线监控、会议→监控、监控→会议及两种历史离线顺序。

## 3. P1：归档收尾被当作需要运行音频的请求（已证实）

位置：主文件的 `exclusive_audio_mode_blocks_normal_audio`、
`wait_for_cloud_updates` 中的 background listen 分支，以及正常 listen 等待入口。

阻止普通录音的条件包含 archive active；云端等待循环却用这个条件调用
`run_audio_source`。控制器已关闭、只有文件待收尾时，没有独占模式可执行，
普通录音入口又因同一条件立即退出；外层 continue 没有等待，反复重入。

日志：205.629 秒控制器关闭，206.759 秒文件收尾，中间 78 次 background listen
失败。当前是暂时空转；若介质 I/O 更慢，空转窗口会变长，并增加调度和日志负担。

整改：区分“有模式待运行”“麦克风被占用”“仅文件待关闭”。仅归档收尾时
保留控制消息处理并有界等待；检查主循环和云端等待循环两处入口。

## 4. P1：SD 冷启动/长 I/O 超过缓冲容量（丢帧已证实，慢操作待计时）

位置：`main/offline_audio_spool.c` 的 `begin_archive`、`writer_task`、
`append_locked`、`open_segment_locked`。

buffered begin 先开放入队，文件由 writer 消费首帧时创建。开文件路径在持有
spool lock 时执行 FAT 空间查询、fopen、头部 fwrite/fflush/fsync；writer 优先级 3。
128 帧仅能容纳约 2.56 秒。阻塞超过缓冲窗口就拒绝新帧，实时上传仍继续。

日志从 sequence=128 开始拒收，断网前 accepted=659/rejected=209，少存 4.18 秒。
启动段集中积压、之后可追上，符合初始化或 I/O 长尾，不能据此断言卡持续带宽不足。

本地 IDF 的 `esp_vfs_fat_info` 调用 `f_getfree`；空闲簇缓存无效时 FatFs 扫描 FAT。
这是具体候选慢路径，但现有日志未分别计时，不能断言这 209 帧全部由 FAT 扫描造成。

整改：增加空间查询、建文件、同步、锁等待耗时及最大队列深度诊断；提前准备
介质和首段资源，再根据实测长尾配置缓冲。不能只加大队列后宣称无丢帧。

## 5. P1：镜像未接入期间的帧缺失没有进入拒收统计（已证实）

位置：`mirror_service`、`mirror_append`、`begin_archive` 及会议采集循环。

旧段 active/closing 或锁忙时，新镜像 begin 失败，按 500 ms 间隔重试。
mirror 未 started 时 append 直接返回 NOT_FINISHED，不增加 rejected_frames；
会议调用方忽略返回值并继续上传。接入成功又将镜像计数清零。

日志恢复后在线 1555 帧、SD accepted=1402/rejected=0，差 153 帧，即 3.06 秒。
源码解释了为什么缺口不体现在 rejected 中；其中每个等待阶段的精确耗时仍需诊断。
旧文件完成关闭之前新线上模式已经开始，是产生该窗口的一条实际路径。

因此 `complete=1` 或 `rejected=0` 不能证明整个业务会话从头到尾完整。
整改：分别统计采集、归档未接入、入队拒绝、落盘失败，并保存会话级连续性信息；
交接期间用明确归属的缓冲接续，或维持同一归档生产入口，避免靠轮询重挂吞帧。

## 6. P1：恢复申请成功发送被当作恢复完成（源码可达，待超时场景验证）

位置：主文件 `service_offline_audio_handoff` 的 controller_claimed/
claimed_after_request，以及 `meeting_mode_request_ui`、`reset_to_disabled`。

会议 request_ui 先将状态置 STARTING 再发送请求；主流程只检查状态非 DISABLED
或有待处理事件，随后释放离线 lease 并清空恢复计时。此时还没拿到开启授权，
也未保证麦克风启动成功。之后若 start_timeout，控制器清理身份并关闭，主流程
已无 lease 可继续该次恢复。当前正常 ACK 路径通过，未覆盖这个边界。

整改：分开恢复申请、等待授权、采集启动三个阶段；只有明确成功启动或业务
明确终止才结束恢复事务。等待期间保留用户模式意图和原身份，但必须避免因
保留 lease 而在下一轮把新启动的采集再次当成旧离线采集停掉。显式云端拒绝
应按业务终止处理，不做无条件无限重试。

## 7. P1：固定会话 ID 改变了 8 小时计时语义（源码可达）

位置：`offline_audio_spool.c` 的 `s_limit_session`、`s_limit_start_us`、
`start_capture_continuation` 和 reader 的 `nuwax_offline_limit_elapsed`。

仅在 session_id 改变时更新 limit_start；reader 比较当前开机时间与该起点。
保留同一 session_id 后，多次离线之间的在线时长也计入 8 小时。
例：首次离线 1 分钟，在线 8 小时后再次断网，第二次离线会立即触发上限，
尽管累计离线录音仅约 1 分钟。这不等于支持累计 8 小时离线录音。

整改：明确采用累计离线采集时长还是每次连续离线时长；若要求同一会话累计
8 小时，应累计真正离线采集的时长，在线暂停计时。两种策略都不能用当前
“第一次离线后的墙钟时间”隐式替代。

## 对接及验证边界

- 正式云端仍下发新 audio_session_id，设备保留旧值仅证明设备行为，不能证明
  服务端会话合并完成。
- 测试网关未连通，只能确认本地保留文件，不能推断归档上传或持久化成功。
- 本轮主机测试补上了真实生产入队函数，但 writer、FatFs、UI 状态组合、
  main 恢复事务与计时仍缺集成场景覆盖，不能以模块测试全过替代全链路验收。
- 在线 NA 时间为流内相对时间，SD 为开机时间，同会话 ID 不提供精确时间映射。
  补传归档组织与在线音频去重仍须遵守协议中的对齐约束。

修复顺序：先拆分业务/采集/归档状态并修正 UI 和收尾调度，再修复恢复事务与
计时，最后完善归档接入缓冲、落盘诊断和质量统计。验证需覆盖拒绝、超时、
重复断网、慢卡、立即关闭再开启及跨模式切换；不改变现有补传二进制格式。
