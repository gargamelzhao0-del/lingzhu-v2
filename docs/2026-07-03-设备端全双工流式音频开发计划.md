# 2026-07-03 设备端全双工流式音频开发计划

> 本文档为 7.0 工程新的设备端开发主线。既有工作计划、智能打断旧路线、阶段编号仅作为历史资料，不再约束当前优先级。当前重心改为设备端全双工音频出入口、设备端第一轮音频清洗、低延迟状态执行；网关仅作为测试桥，后续生产 URL 由云端工程师提供。

## 1. 目标定义

设备端的最合适职责不是做智能决策，而是做稳定的音频出入口和第一层保守过滤：

- 播放云端下发音频。
- 播放时同时采集麦克风音频。
- 设备端先做第一轮 AEC，尽量去除自身扬声器回声。
- 设备端再做第一层杂音过滤、门限判断和 VAD 标记。
- 将处理后的音频流式上传云端。
- 收到云端状态、表情、播放控制命令后立即执行。
- 休眠态不向云端上传音频，只在本地跑唤醒词。
- 唤醒态进入聆听流程，采集、过滤、上传用户音频。

云端负责第二轮 AEC、人声/声纹/用户声音过滤、语义相关性判断、是否打断当前播放、智能体决策。设备端不在本地做复杂语义判断，也不因本地疑似人声直接停止播放，除非收到云端明确控制命令。

### 2.2 当前配置暴露的问题

当前检出的 `sdkconfig` 不能直接代表目标全双工固件：

- `CONFIG_NUWAX_SPEAKER_ENABLE` 当前未启用，导致播放代码实际为 stub。
- `CONFIG_NUWAX_WAKE_WORD_ENABLE` 当前未启用，休眠态无法靠本地唤醒词唤醒。
- `CONFIG_NUWAX_VOICE_UPLINK_CODEC_PCM16=y`，Opus 上行路径存在但当前未启用。
- VOCAT 目标下 `CONFIG_NUWAX_VOICE_OUTPUT_SAMPLE_RATE` 当前仍为 `24000`，而 VOCAT shared I2S/ES8311 目标应优先固定为 `16000`。
- VOCAT 目标下当前 VAD 阈值仍为旧值 `avg_abs=3600 / peak=12000`，与 VOCAT 实测低幅度麦克风不匹配；Kconfig 中已经有更合理的 VOCAT 目标值 `avg_abs=400 / peak=1500`。
- P5/P6/AEC 相关路径当前主要是诊断、灰度、手动命令入口，不是默认 speaking 主链路。

因此第一阶段必须先修正目标固件配置，否则后续开发结论会被错误配置干扰。

## 3. 新目标架构

### 3.1 设备状态

设备端主状态建议明确为：

| 状态 | 行为 | 是否上传音频 |
| --- | --- | --- |
| `SLEEPING` | 本地唤醒词检测；屏幕显示休眠/等待唤醒 | 不上传 |
| `AWAKE_LISTENING` | 本地采集、VAD/门禁、speech confirmed 后上传 | 条件上传 |
| `SPEAKING_FULLDUPLEX` | 播放 TTS，同时采集、AEC、过滤、上传 | 上传处理后音频 |
| `THINKING` | 等待云端文本/音频响应 | 不主动上传，除非进入预聆听 |
| `IDLE` | 短暂空闲，可进入 follow-up 或超时休眠 | 不主动上传 |
| `ERROR/RECONNECTING` | 停止音频链路，等待恢复 | 不上传 |

### 3.2 音频下行链路

云端下发：

1. JSON `playback_begin` / `text_response` / 状态命令。
2. NA binary PCM16 audio frame。
3. JSON `playback_end` 或 NA END marker。

设备处理：

1. WebSocket RX task 解析 binary。
2. `nuwax_speaker_playback_handle_audio_frame()` 入播放队列。
3. speaker task 写 ES8311/shared TX。
4. 播放样本同步进入 software reference ring，供 AEC fallback 或诊断使用。
5. 播放 START 后进入 `SPEAKING_FULLDUPLEX`。
6. 播放 END 后根据云端/本地策略进入 follow-up listening 或 idle/sleep。

### 3.3 播放时上行链路

播放期间设备必须同时采集：

1. 采集 `mic` 和可用 reference。
2. 先做设备端 AEC。
3. 对 AEC 输出做本地能量门限、短噪声过滤、VAD 标记。
4. 保守上传疑似人声段，避免误杀用户声音。
5. 通过 NA binary frame 持续上传云端。
6. 不在设备端决定是否打断播放。
7. 云端若决定打断，下发 `stop_playback` / `cancel_turn` / 状态命令，设备立即执行。

### 3.4 非播放唤醒态上行链路

无播放时进入唤醒/聆听：

1. 本地麦克风采集。
2. 自适应噪声底估计、能量门限、peak 门限、最短语音时长判断。
3. speech confirmed 后开始云端 `listen start`。
4. 上传 speech 前 preroll，避免用户开头被截断。
5. 尾静音稳定后发送 END 和 `listen stop`。
6. no-speech 超时则回到 sleep 或保持短暂 follow-up。

### 3.5 休眠态链路

休眠态只允许本地唤醒：

1. 不发送 `listen start`。
2. 不上传 NA audio frame。
3. 本地 wake detector 可以读取麦克风，但数据不得出设备。
4. 唤醒词命中后切到 `AWAKE_LISTENING`，并可先播放/显示唤醒反馈。

### 3.6 命令平面

命令平面必须独立于音频平面：

- WebSocket RX task 不能被播放、采集、AEC 阻塞。
- `device_command` 入队后应尽快执行。
- 表情、状态、音量、停止播放属于高优先级命令。
- 播放期间收到 `set_emotion` / `set_state` 应立即刷新 UI。
- 播放期间收到 `stop_playback` 应立即停止本地播放并清 stale audio。

## 4. 开发阶段计划

### D0. 目标配置收敛

目标：先得到一个能代表目标产品方向的固件配置。

修改范围：

- `sdkconfig.defaults` 或新增目标配置文件。
- 必要时保留 `sdkconfig.debug` / `sdkconfig.opus` 作为调试配置。

任务：

- 开启 VOCAT 目标板。
- 开启 `CONFIG_NUWAX_AUDIO_SOURCE_I2S_MIC`。
- 开启 `CONFIG_NUWAX_SPEAKER_ENABLE`。
- 开启 `CONFIG_NUWAX_WAKE_WORD_ENABLE`。
- 将 VOCAT 输出采样率固定为 `16000`。
- 将 VOCAT VAD 阈值改为 `avg_abs=400 / peak=1500` 起步值。
- 默认先保留 PCM16 上行，降低变量；Opus 作为 D9 后优化项。
- P3/P5/P6 诊断开关不默认启用，避免把诊断路径误当产品路径。

验收：

- `hello.features.audio_playback=true`。
- `hello.audio_params.wake_word=true`。
- `hello.audio_params.output_sample_rate=16000`。
- `hello.audio_params.aec=false`，直到 AEC 主链路实测通过。

### D1. 播放主链路启用与稳定

目标：让当前播放代码真实参与运行，并稳定播放云端下发 PCM16。

涉及模块：

- `main/conversation/speaker_playback.c`
- `main/speaker_output.c`
- `main/board/audio_board.c`
- `main/board/vocat_audio_board.c`
- `main/session_protocol.c`

任务：

- 启用 speaker 后验证 ES8311 shared TX 初始化。
- 验证 NA PCM16 下行帧解析、排队、播放、END marker。
- 验证 `stop_playback` 立即清队、fade/cancel、stale drop。
- 验证播放期间 JSON 命令仍能被处理。
- 修正当前 `output_sample_rate` 与 VOCAT 16k shared I2S 的一致性。

验收：

- 连续播放 10 分钟无崩溃、无 I2S hang。
- START/END 日志完整。
- `stop_playback` 到本地静音目标延迟小于 200 ms。
- 播放中 `set_emotion` 可在 200 ms 内反映到 UI 状态。

### D2. 休眠态与唤醒词主链路

目标：休眠态不上传音频，本地唤醒词命中后进入聆听。

涉及模块：

- `main/wake_word_detector.c`
- `main/nuwax_ai_partner_main.c`
- `main/mic_input.c`

任务：

- 启用 WakeNet 或 MultiNet backend。
- 明确 wake detector 和 conversation capture 的麦克风 owner 互斥关系。
- 睡眠时启动 wake detector。
- 进入聆听/播放/断线时停止 wake detector。
- 唤醒后进入预聆听窗口，不立即上传唤醒词尾音。

验收：

- 休眠 5 分钟无 NA audio uplink。
- 唤醒词命中后进入 listening。
- 唤醒词尾音不作为用户输入上传，或只在 preroll 策略允许范围内上传。
- 误唤醒/漏唤醒记录进入测试报告。

### D3. 统一全双工音频会话管理

目标：把“普通聆听上行”和“播放中上行”统一成一个可控 audio session 框架。

涉及模块：

- `main/nuwax_ai_partner_main.c`

- `main/conversation/p5_fullduplex_overlap_probe.c`

任务：

- 新增或整理统一的 capture session 状态结构。
- 区分 session mode：
  - `listen_wake`
  - `listen_touch`
  - `auto_followup`
  - `during_playback`
- 保证每个 session 有明确 start/stop/final frame。
- 保证播放 START 后可自动启动 `during_playback` capture。
- 保证播放 END 后可结束或切换到 follow-up capture。
- 保留 P5 probe 作为诊断测试入口，但产品链路不依赖远程手动命令触发。

验收：

- 播放开始后 200 ms 内启动播放中采集。
- 播放结束后播放中采集正常 stop，且没有残留 upload task。
- 连续多段 TTS 不产生重复 session、错乱 END、队列泄漏。

### D4. 播放时采集产品化

目标：将 P5 诊断能力转为默认 speaking 状态能力。

涉及模块：

- `main/conversation/p5_fullduplex_overlap_probe.c`
- `main/nuwax_ai_partner_main.c`
- `main/mic_input.c`
- `main/conversation/audio_uplink.c`

任务：

- 从 P5 probe 中抽离可复用的播放中采集循环。
- speaking 状态默认启动采集，不需要云端额外发 probe command。
- 采集音频统一进入 AEC + noise gate。
- 上传帧保留 `NUWAX_AUDIO_FLAG_VAD_SPEECH`。
- 记录 playback_id / audio_session_id / overlap_ms 供云端关联。
- 播放中若没有人声，只允许低频率/低成本上传或不上报，具体由 D6 gate 决定。

验收：

- 播放纯 TTS 时，云端收到的回声残留显著下降。
- 播放中用户说话时，云端能收到连续近端语音。
- 设备端不因本地 near-end candidate 自行停止播放。

### D5. 设备端第一轮 AEC

目标：设备端完成第一轮保守 AEC，并只在实测通过后声明 AEC active。

优先路线：

1. 硬件 reference 路线：
   - `mic_input_read_vocat_mr_pcm16()` 读取 slot0 mic + slot2 ref。
   - 接入 esp-sr AFE/AEC。
   - AEC 输出替换 raw mic，进入 VAD/Opus/ASR uplink。
2. software reference fallback：
   - speaker 输出写入 `p3_software_ref`。
   - `p3_afe_l3.c` 用 software ref 做低成本 AEC。
   - 作为硬件 reference 不稳定时的 fallback 或诊断路径。

涉及模块：

- `main/mic_input.c`
- `main/p3_afe_l3.c`
- `main/p3_software_ref.c`
- `main/p3_softref_aec_diag.c`
- `main/nuwax_ai_partner_main.c`
- `main/session_protocol.c`

任务：

- 修复 `stream_microphone_audio()` 中 AFE MR TODO，使其进入真实处理路径。
- 明确 AEC 初始化、处理、销毁生命周期。
- 引入 ref health gate，reference 不合格时自动 fallback 到 mono raw。
- 记录 ERLE、ref_rms、mic_rms、out_rms、read_timeout、heap。
- 确保 AEC 不明显损伤近端用户声音。
- 通过实测后再将 `hello.audio_params.aec` 改为 true。

初始验收：

- 播放无近端语音时，AEC 输出相对 raw mic 有可测回声下降。
- 播放中近端说话时，用户语音不被明显压制。
- AEC 开启后无连续 read timeout、无 heap 崩溃。
- 未通过前 `hello.audio_params.aec` 必须保持 false。

### D6. 第一层杂音过滤和门禁

目标：设备端做保守过滤，减少明显环境噪声和短促杂音上传，但不承担最终人声/语义决策。

涉及模块：

- `main/conversation/mic_level.c`
- `main/nuwax_ai_partner_main.c`
- 可新增 `main/conversation/noise_gate.c`

策略：

- 固定能量门限：avg_abs + peak。
- 自适应底噪：持续估计 quiet floor。
- 最短语音时长：避免瞬态噪声触发。
- hangover/trailing silence：避免用户尾字被截断。
- preroll：speech confirmed 后补发前若干帧。
- clipping 检测：异常爆音可标记或衰减。
- 播放中 gate 与非播放 gate 分开调参。

重要原则：

- 过滤容错高一点。
- 允许一部分噪声上传给云端二次过滤。
- 不允许因为设备端门限过严导致用户声音被吞。

验收：

- 静音/低底噪环境下不持续上传。
- 轻微环境声不频繁触发上传。
- 正常近距离说话能稳定触发。
- 播放中近端说话能稳定上传。
- 用户开头和尾音不被明显截断。

### D7. 命令平面低延迟和状态执行

目标：音频任务高负载时，状态/表情/停止播放命令仍然快速执行。

涉及模块：

- `main/ws_transport.c`
- `main/session_protocol.c`
- `main/conversation/session_dispatch.c`
- `main/nuwax_ai_partner_main.c`
- UI/状态桥相关模块

任务：

- 给 `set_emotion`、`set_state`、`stop_playback`、`set_volume` 定义高优先级处理路径。
- 避免命令只依赖 100 ms polling。
- 播放中 stop/cancel 直接触发 speaker cancel。
- UI 状态更新不被 AEC 或 uplink 阻塞。
- 记录 command_rx_ms、command_apply_ms、latency_ms。

验收：

- 播放中切表情小于 200 ms。
- 播放中 stop_playback 小于 200 ms。
- AEC/uplink 高负载时命令不丢失。

### D8. 云端 URL 和协议协同

任务：

### D9. Opus 上行优化

目标：在 PCM16 全链路稳定后，再评估启用 Opus 上行降低带宽。

- 队列无持续堆积。

- Wi-Fi 抖动/云端断开重连测试。

## 6. 验收门槛

进入下一阶段前必须满足：

- speaker/wake/AEC/full-duplex 相关配置与目标一致。
- 当前固件不再出现 speaker disabled 但文档声称支持播放的情况。
- 休眠态无音频上传。
- 播放时采集成为默认 speaking 行为，而不是只靠 P5 手动命令。
- AEC 未实测通过前，`hello.audio_params.aec` 不得改为 true。
- 本地过滤必须保守，不能为了少上传噪声牺牲用户语音。
- 设备端不做复杂打断决策，打断由云端决定。
- 命令平面延迟有日志和实测数据支撑。

## 7. 风险和处理策略

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 当前 `sdkconfig` 与目标不一致 | 测试结论失真 | D0 先收敛配置 |
| VOCAT VAD 阈值过高 | 用户语音不上传 | 使用 VOCAT 校准阈值并实测 |
| output sample rate 错误 | 播放变速/协议误导 | 固定 VOCAT 16k |
| AEC 吞近端语音 | 用户插话丢失 | AEC gate + near-end 保真测试 |
| AEC heap/CPU 不够 | 崩溃或丢帧 | 资源预算和 fallback |
| reference slot 不稳定 | AEC 效果差 | ref health gate + software ref fallback |
| 命令被音频阻塞 | 表情/停止播放延迟 | 命令高优先级队列 |
| 设备端过滤过严 | 用户声音被误删 | 保守过滤，云端二次判断 |
| 本地误打断 | 体验不可控 | 设备端不做最终打断决策 |

## 8. 建议优先级

### 8.1 优先级分层(2026-07-03 修订)

| 分层 | 任务 | 说明 |
|---|---|---|
| **基础层**(必须先打通) | D0, D1, D2 | 配置、播放、唤醒,设备能 boot + 能讲 |
| **核心层**(设备端定位答案) | **D6, D7** | **保守过滤 + 状态命令执行——这是设备端最该做的两件事** |
| **全双工层**(核心层的下一棒) | D3, D4, D5 | 全双工采集产品化 + AEC 主链路接入 |
| **优化层**(生产质量) | D8, D9 | 云端协议协同 + Opus 优化 |

### 8.2 任务顺序

1. D0 目标配置收敛(基础)
2. D1 播放主链路启用(基础)
3. D2 唤醒词和 sleep/listen 状态闭环(基础)
4. **D6 保守杂音过滤(核心 — 设备端做"录音后的保守清洗")** ⭐
5. **D7 命令低延迟保障(核心 — 设备端做"状态消息的实时执行")** ⭐
6. D3/D4 全双工采集产品化
7. D5 AEC 主链路接入
8. D8 云端 URL/协议协同
9. D9 Opus 优化

**当前最不应该先做的是复杂本地语义打断**。正确顺序是先把设备端音频出入口做稳，再把保守清洗做好，再保证云端命令秒级执行，最终把是否打断交给云端。

**D6/D7 在 D1/D2 基础打通后立即执行**——这是设备端定位的两大主轴。

> **修订原因**:产品负责人 2026-07-03 明确 "设备端最合适的功能是音频出入口,做一轮过滤,过滤容错可以高一点,把音频传至云端,对于是否打断决策由云端决定"——这意味着 D6/D7 是设备端的**唯一核心价值**,不能放在 D3-D5 全双工链路之后。

## 9. 工程师修订明细(2026-07-03)

### 9.1 D4 修订:P5 复用边界明确

**修订前**:"将 P5 诊断能力转为默认 speaking 状态能力"

**修订后**:
- **复用**现有 P5 probe loop 在 `main/conversation/p5_fullduplex_overlap_probe.c`
- **不重写** P3/P5 精判代码
- P5 在新流程中的角色仅为"采集期参考标志",不参与决策
- D4 实现路径:提取 P5 的 `nuwax_p5_fullduplex_overlap_probe_run_ex` 到 `audio_uplink.c::during_playback()` 调用点
- 与产品负责人 D6 "保守过滤" 一致——P5 输出是参考,不是 gate

### 9.2 D3 修订:session start 规则

**修订前**:未明确"播放 START"的具体触发器

**修订后**:
- **session start 触发器**:`NA frame` 二进制帧的 `FLAG_START=0x01` 标记(bit 0 of header flags)
- **不依赖** JSON `playback_begin` 消息(可能延迟 100-300ms)
- **不依赖** speaker DMA 启动事件
- 实现位置:`main/audio_frame.c::nuwax_audio_frame_build_pcm16()` 的 `start_seq` 跟踪 + `main/conversation/audio_uplink.c::during_playback()` 入口
- 与 `audio_frame.h:8 NUWAX_AUDIO_FLAG_START = 0x01` 严格对齐

### 9.3 D5 修订:ref health gate 阈值具体化

**修订前**:"ref health gate" 描述存在,阈值未给

**修订后**:
- **ref_rms 阈值**:`< 1000` 持续 > 1s → **自动切换 software ref fallback**
- **ref_rms = 0** 持续 > 5s → **自动切换 mono raw(无 AEC)**
- **ref 恢复正常**(ref_rms > 2000 持续 3s)→ **自动升级回 hardware reference**
- 实现位置:`main/board/audio_board.c::audio_board_ref_health_check()`(新增,300ms 周期)
- **风险**:回退到 mono raw 时延迟 50-200ms,需要缓冲对齐

### 9.4 D6 修订:验收标准量化

**修订前**:定性描述

**修订后**:
| 场景 | 量化指标 | 测试方法 |
|---|---|---|
| 静音环境(50dB 以下) | 上传帧数 **< 5 帧/min** | 真机+脚本统计 |
| 50dB 轻环境声 | 上传帧数 **< 10 帧/min** | 粉噪 + 真机 |
| 50cm 正常说话 | 触发延迟 **< 300ms** | 高速摄像机同步 |
| 100cm 正常说话 | 触发延迟 **< 500ms** | 高速摄像机同步 |
| 播放中近端说话 | 用户声音频谱保持 **> 80%** | 频谱对比 + 真机 |
| 键盘 / 鼠标敲击 | 触发次数 **0** | 高速摄像机 + 脚本 |

> **重要原则**:本表 D6 阈值**仅给"高容错"目标**——超过阈值视为设备端粗过滤失败,**需要 D6 二次调参**,**不阻塞**云端二次过滤。
