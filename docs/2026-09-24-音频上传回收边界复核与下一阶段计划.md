## AU04：清理移交失败的责任链

代码依据：`main/conversation/audio_uplink.c:1275` 的 destroy_owned 在队列接管失败时保留 owner 并返回 TIMEOUT；移交成功才清空 owner，返回 NOT_FINISHED 表示异步清理已接管，不能当作未移交。

调用端 `main/nuwax_ai_partner_main.c:29282` 忽略返回值；会议 `meeting_mode.c:894/897/1140/1148` 和监控 `monitoring_mode.c:1153/1156/1173/1234` 也有同类调用，监控收尾随后清除 uplink_ready。失败后保留的指针是否仍由持久对象保存并重试，没有形成统一保证。

限制：sender 的静态任务资源只允许一个活 owner，reaper 初始化先于 sender，接管队列长度为1。正常唯一owner没有队列满证据，不能宣称泄漏已经发生。重复接管同一地址同样需要验证，不能通过简单覆盖队列解决。

下一步：抽取生产移交函数并注入拒绝，联动实际调用端检查；分别验证 OK、NOT_FINISHED、TIMEOUT、sender已完成但删除暂不可行、重复清理。先证明正常单例路径的不变量，再决定使用持久失败owner或专用接管槽。接管必须唯一，内存释放必须发生在任务停止之后。

## AU05：心跳不能代替本地退出进度

代码依据：`audio_uplink.c:1085` 后台回收循环持续设置 capture_done/send_failed 并通知sender；250ms后的连接关闭和90000ms后的最后兜底同时受 !heartbeat_healthy 限制（1115、1138附近）。

如果sender始终未完成且对应epoch心跳持续健康，这两个升级条件均不成立，后台循环可以持续占有sender单例。条件行为由代码确认；尚无此组合的实机证据。sender实际网络调用和取消检查有自身边界，仍须验证如何进入这一条件。

已有基础：sender_stage、stage_since、packet sequence及WebSocket发送阶段可用于诊断；连接关闭使用绑定epoch，避免旧清理任务关闭新连接。不能只依赖阶段时间刷新证明真正发送有进展，也不能把250ms直接改为健康连接强制关闭阈值。

下一步验证矩阵：

| 故障/交错 | 验收要求 |
| --- | --- |
| 正常取消、较慢但持续进展 | 正常回收，不误断连接 |
| 心跳健康、sender无进展 | 有界升级，不能永远占有单例 |
| 心跳不健康 | 保留现有故障恢复能力 |
| 连接epoch已变化 | 不关闭新连接；旧资源仍有明确回收责任 |
| deadline边界恰好完成 | 不重复释放、不误触发最终兜底 |
| 删除暂时不安全 | 保留内存和owner，继续受控回收 |

## 实施顺序和效果边界

1. AU04生产故障注入及单例/调用方责任复核。
2. AU05生产循环注入，测量正常取消最大预算，再设计进度与绝对期限分层恢复。
3. 分开修复、运行音频生命周期/产品/对话回归，再独立构建和镜像身份检查。
4. 实机覆盖普通对话、摇晃/摸头打断、会议/监控退出、掉网重连、休眠。保持旧固件可回退。

预期收益是异常后的可恢复性，不承诺正常对话提速。最大新增风险是重复释放、误关闭新epoch和将正常慢退出判为故障；这些必须成为负例测试。不得直接删除运行中sender或在其退出前释放队列/缓冲。

W04的373ms事件排队及正常休眠后“lost owner event”措辞保留为随后审查项；不把下行播放事件延迟归因于本轮上行reaper。UI继续按用户要求暂缓提帧。AP兼容性、SD提速、WSS/凭据迁移仍保持此前边界。
