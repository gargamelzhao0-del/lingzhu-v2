# 云端恢复与唤醒生命周期优化

日期：2026-09-23。修订标识：`20260923-cloud-resume-v1`。

## 本轮依据

输入为附件 `c581efbf-a9e9-4c25-9e35-d82025fed7de/已粘贴的文本.txt`。日志包含两次启动，第二次是用户点击配网触发的软件重启；未见 panic 或 watchdog。原 AP WPA3 联网和重新配网成功，上轮接管、停止广播及成功响应退出修复已有一次实机证据，但不等于热点掉线、电池/USB 黑屏及长稳全部完成。

两次云端就绪后，音量 owner 事件分别等待 529 ms、538 ms。代码在同步音量、恢复会话后无条件等待 500 ms，期间无法消费该队列。此外，睡眠唤醒请求把 WebSocket epoch 纳入“是否同一请求”，离线 epoch 0 转在线 epoch 1 会触发没有必要的停止/重建。会议、监控的 `has_pending` 又把关闭同步和 ACK 队列算作待运行模式，使云端就绪收敛与唤醒恢复被无录音占用的控制事件阻挡。

## 修改与预期

| 修改 | 修改前 | 修改后 |
| --- | --- | --- |
| 云端恢复固定等待 | 同步音量后盲等 500 ms | 立即消费 speaker owner 事件，再进入正常控制循环 |
| 休眠唤醒请求 | WebSocket epoch 变化即可停止现有 detector | 相同本地睡眠请求保留 token 和 detector；命中时绑定当前连接 |
| 模式占用判断 | 关闭同步或 ACK 排队也阻止睡眠唤醒 | 睡眠恢复使用已有 `has_audio_claim`：真实启用请求、活动模式及离线采集仍阻止普通唤醒 |
| 重复睡眠转换 | 云端就绪已收敛后再次提交 boot_ready | 已处于 SLEEPING 时跳过重复转换 |

这移除的是代码中确定存在的 500 ms 等待，不能保证任何情况下的恢复总耗时都减少 500 ms：Flash 暂停、模型恢复、音频释放等真实等待仍可能存在。

## 保护边界

- 未删除、清空或重排会议/监控控制队列；普通录音入口继续使用严格的 `has_pending` 栅栏。
- 等待启用的事件、已经活动的模式、离线模式 lease、离线录音仍阻止睡眠唤醒。
- 播放打断仍绑定 WebSocket epoch 和 speaker generation；普通唤醒事件在命中时绑定当前 epoch，消费时继续拒绝旧 epoch 和过期事件。
- OTA、配网接管、通知音频、正常对话录音及 Flash 操作保护保留。必要的 Flash 暂停恢复仍可能产生唤醒启停日志。
- 协议、SD 上传路由、表情资源及 UI 样式未因本轮改动而变化。正式云端配置继续生效，测试网关关闭。

## 实机验收

1. 正常开机联网：确认启动出现 `cloud resume revision=20260923-cloud-resume-v1 local_wake=epoch_independent settle_delay_ms=0`，观察云端就绪附近的音量 owner 延迟。
2. 空闲状态关闭热点并恢复：断网显示正确；离线/在线 epoch 改变本身不应重启同一睡眠 detector。`mode=1 ws_epoch=0` 是本次设计的本地睡眠监听，不代表未联网。
3. 云端同步会议/监控关闭：控制仍应应答，设备最终保持睡眠且可唤醒。实际开启会议/监控则必须取得麦克风，不能同时启动普通录音。
4. 播放中掉线重连、唤醒后立即掉线：旧事件不得启动新连接的录音或打断新播放。
5. 连不上 AP 时点击配网，分别使用电池和 USB：检查接管完成、重启 PG2 保持、BLE 成功退出与恢复唤醒；仍需验证此前黑屏现象。
6. OTA 及连续对话回归：允许必要的 Flash 暂停，不应出现持续无法唤醒、麦克风双占用、panic 或 watchdog。
