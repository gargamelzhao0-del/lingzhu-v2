# AU04 上传清理接管修复与验证

## 真实性与范围

上一版 `destroy_owned` 在 xQueueSend 拒绝接管时返回 TIMEOUT，并保留 owner。对话、会议及监控存在忽略返回值的调用，缺少失败重试责任。生产函数提取测试注入队列拒绝后，旧实现不能满足“调用结束后已完成释放或后台接管”的契约。

正常 sender 单例、预先初始化 reaper、长度1队列限制了自然触发条件；没有证据说明最近实机日志发生过队列满或泄漏。此项是故障路径修复，不归因于最近373ms下行事件排队。

本轮另外确认：旧实现入队后读取 ctx->ws_connection_epoch 打日志。对象可能已被后台回收，这是独立的交接后访问竞态。通过“发布后立即模拟后台取走并改写对象”的交错测试验证，日志必须使用交接前快照。

## 修复设计

- 每个堆对象内增加私有 cleanup_next，静态头尾指针和专用临界区维护待回收链表。入链不分配内存，没有队列容量拒绝路径。
- 调用方在发布前保存 epoch、清空唯一 owner；发布后只用局部快照，不再访问对象。
- 后台先取节点，无节点时等待任务通知。发布在取空和等待之间发生时，通知保持待消费；通知只用于唤醒，节点链表才是回收责任的依据。
- 临界区只维护指针，不包含日志、I/O、内存释放或任务删除。后台取走节点后执行原有安全回收。
- 正常唯一 owner 是接口前提。重复清理已置空 owner 无操作；不允许保留指针别名并发重复交接。链表不是允许多owner并发访问同一对象的机制。
- 返回 OK 表示释放完成，NOT_FINISHED 表示后台已接管；有效唯一owner不再遇到队列移交失败。业务调用点无需增加阻塞等待或自行释放。

没有改变AU05后台取消、关闭连接、90000ms最终兜底循环；新旧该部分逐字对比一致。AU05仍开放。

## 验证

`tools/test-uplink-cleanup-handoff.py` 直接提取生产入链、出链和destroy_owned函数，模拟调度、日志和任务删除边界。

覆盖：活动sender取消并保留内存、FIFO多节点、重复清理空owner、已完成但暂不可删除、完成后同步释放、无任务对象释放、发布后后台立即取得对象及日志身份快照。

负例：旧队列拒绝、先发布后清空owner、交接后读取ctx、断开链表尾节点。上述负例必须失败。旧实现保存在 `tools/fixtures/uplink-cleanup-before-au04.c`，避免依赖临时工作文件。

产品回归已更新旧队列特定源码断言，并纳入上述行为测试。最终构建及完整回归结果见本文件末尾与审计目录。

## 效果与剩余风险

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 队列拒绝接管 | 返回错误、部分调用方无重试责任 | 无容量失败点，节点保留后台回收责任 |
| 后台先完成回收 | 调用方日志可能读取失效对象 | 使用交接前快照 |
| 正常对话/模式退出 | 同步完成或后台清理 | 保持同样业务语义 |
| sender未退出 | 不能安全释放 | 同样保留，未放宽释放条件 |
| 心跳健康但sender长期无进展 | AU05条件风险 | 本轮未改变，仍待处理 |

主机测试不是实机长稳证明。需实测普通对话、快速摸头/摇晃、会议/监控停止、掉网恢复和休眠；重点检查双重释放、回收单例卡住及下一轮上传无法启动。不能承诺零新问题。当前稳定固件目录保留用于回退。
