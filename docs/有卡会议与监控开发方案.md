# 有卡会议与监控开发方案

本文件保留早期方案及历次开发背景，不作为当前接口契约。当前消息、字段和字节格式以 [SD 会议监控场次上传协议](SD会议监控场次上传协议.md) 为准，当前设备行为见 [功能逻辑与异常处理](SD会议监控功能逻辑与异常处理.md)。下文的短文件、旧逐文件 begin 和时长／容量描述不能直接用于当前固件验收。

日期：2026-10-13｜状态：设备端及本机测试网关已实现，待实机验收

有卡时，音频先保存到 SD，再按文件上传。会议结束后上传整场；监控边录边传，断网时留存，恢复后优先传当前音频，再补历史。

SD 专用 `hello` 和能力回复检查已经取消。新流程在 7.0.118 本机网关测试版启用；普通云端认证、`hello` 和心跳保持现状。

## 录音规则

| 情况 | 处理方式 |
| --- | --- |
| 无可用 SD | 保持原流程：在线实时上传，离线停止 |
| 有卡会议 | 在线、离线都完整录到本地，整场结束并落盘后才上传 |
| 有卡监控 | 沿用现有人声筛选；在线上传刚封存的短文件，离线保存，恢复后分别上传当前和历史音频 |

每次开启时检查 SD 是否可写、空间是否足够，并确定本场的数据路径。录音途中不自动切换有卡、无卡流程。有卡时不再重复发送旧实时音频流。

一次开启到停止为一个场次，使用固定的 `audio_session_id`。断网、重连、人声暂停都不换场次、不重开麦克风、不重置采集序号；停止后再次开启才生成新 ID。离线也能生成唯一 ID，不依赖网络时间。

App 操作和现有控制 ACK、状态回报保留，离线启停使用本地操作。开启成功以采集和存储实际就绪为准；停止录音不等待上传，补传也不把模式开关重新打开。暂不增加 SD 状态页面。

## 会议流程

1. 开启会议，建立场次记录，连续写入 SD，按现有文件大小分段保存。
2. 会议进行中只录音，本场任何分段都不上传；恢复联网也继续原场录音。
3. 停止会议，排空本场录音缓存，封存最后一个文件，保存分段总数和结束状态。
4. 在线时上传，离线时排队等待。多场会议分别保存，按结束顺序上传，不串场。
5. 各文件提交成功后发送场次结束记录，云端确认收齐后生成整场结果。

“完整一场”可以由多个文件组成，不要求设备生成一个大文件。开始上传前，本场全部有效音频必须已经落盘。

## 监控流程

1. 在线时，有声录音约每秒封存一个文件并上传；持续说话也按时切分，无声不生成空文件。前置缓冲和句尾沿用现有策略，跨文件不重复音频。
2. 断网后继续录音，使用较大的分段文件保存历史音频。
3. 恢复连接时封存离线尾段，新音频进入实时队列，旧音频进入历史队列。本场 ID 保持不变。
4. 优先上传实时文件，空闲时补传历史；停止监控后继续上传剩余文件，最后确认场次结束。

在线以已认证的云端业务连接可用为准。断网前未确认的文件、重启恢复的文件，以及开始上传时距最后一帧已超过 3 秒的文件，都转为历史。同一文件转为历史时不更换 ID、不改内容。

这里的实时是约一秒文件上传，另有写卡和网络延迟。云端保存历史音频并按原采集时间处理，不补发过时的即时告警；实时文件传输途中超过有效期，也按历史处理。

## 上传协议

三类业务共用一套上传流程，只用 `type` 前缀区分，不增加 SD 握手或能力协商。

| 用途 | `type` 前缀 |
| --- | --- |
| 会议 | `meeting_audio` |
| 监控实时 | `monitoring_audio_realtime` |
| 监控历史 | `monitoring_audio_history` |

统一流程：`前缀_begin → begin_ack → 二进制分片 / chunk_ack → 前缀_commit → commit_ack`。各 ACK 使用相同前缀，例如 `meeting_audio_begin_ack`。v1 收到当前片 ACK 后再发下一片；已有 v2 窗口扩展允许一个窗口内连续发送，窗口末尾统一确认持久化偏移。

7.0.120 本机测试版将已结束会议、空闲时的历史监控接入已有 v2 通路。原 begin 附带 `replay_version:2`、`replay_revision:2`、`window_bytes:524288`，网关在 begin ACK 中返回支持的版本和窗口上限；设备实际每窗口最多发送 128 KiB。没有额外 hello，也不等待单独的能力回复。网关不返回窗口字段、内存不足或监控正在运行时，继续使用 v1。正式云端共享连接仍走 v1。

二进制继续使用现有 `NWXCH1`，归档头尾、NA 音频帧、CRC 和续传规则不变。二进制没有 `type`，由当前已确认的 begin 确定所属文件。新类型不再携带 `mode:"archive_only"`。

begin 只保留以下信息，提交和 ACK 复用现有字段结构，不重复携带场次元数据：

| 字段 | 用途 |
| --- | --- |
| `type`、`request_id` | 请求类别和本次请求 ID；重试可使用新请求 ID |
| `segment_id` | 文件唯一 ID，重试及实时转历史都不变 |
| `total_bytes`、`crc32` | 原文件长度和校验值 |
| `audio_session_id`、`segment_index` | 所属场次及本场从 0 开始的文件编号，与归档头一致 |
| `capture_start_ms`、`capture_end_ms` | 相对本场开始的采集区间，64 位毫秒数，左闭右开，不受校时影响 |
| `capture_age_ms` | 仅实时类型携带：发送 begin 时距最后一帧的时间，重试时重算 |

不另加 `capture_origin`，实时和历史直接由类型区分。云端用 `capture_age_ms` 加本次事务耗时判断实时文件是否过期；过期仍正常保存并回复原类型 ACK。时间未校准的离线场次保留相对时间，不伪造准确日期。

每个文件遵守三条确认规则：

- begin ACK 返回实际持久化的连续偏移 `next_offset`；分片 ACK 只确认已可靠保存的字节。
- commit ACK 成功前，云端必须校验文件长度、归档格式、帧数和 CRC。设备收到匹配的成功 ACK 后，先保存确认记录，再删除文件。
- 云端按 `device_id + segment_id` 去重；同 ID 的内容和场次信息必须一致。跨类型重试不重复保存，也不重复触发分析或告警。

单文件确认不能代表整场结束。所有可恢复文件上传后，发送 `meeting_audio_session_end` 或 `monitoring_audio_session_end`，字段只需 `request_id`、`audio_session_id`、`segment_count`、`recording_complete`；异常场次另附已知缺段或缺口信息。云端回复对应 `_ack`，原样关联请求和场次，并返回 `ok`。

`segment_count` 为本场应有的分段总数。正常场次只有从 0 到最后编号全部提交，才确认收齐；异常场次确认已收到可恢复内容并标为部分录音。结束请求可重试，不能重复生成结果。设备保留本地场次清单和确认记录，直到结束 ACK 成功。

云端按场次、分段编号和采集时间组织音频，不按到达顺序拼接。会议真实缺口明确标记；监控静音间隔保留时间位置，生成连续音频时补静音。

## 调度和异常处理

复用现有认证 WebSocket，同一时刻只发送一个文件事务。控制和心跳优先，其次监控实时，最后历史监控和已结束会议；两类后台数据轮换上传。

历史上传需要让位时，等当前完整分片确认后暂停，上传实时文件，再对原文件重新 begin，按 `next_offset` 继续。若监控在批量窗口上传中启动，先等当前窗口确认，再释放预读资源、转入短分片调度。云端切换文件时保留旧文件的可靠前缀和元数据。ACK 超时走重试或重连；不截断发送中的帧，不接受旧连接或不匹配请求的 ACK。

SD 写入优先。只上传已封存文件，网络等待不占 SD 锁，缓存和读写批量有上限。监控录音期间允许读取已封存文件，写入压力升高就暂停后台读取；会议录制期间暂停后台上传。

| 情况 | 处理 |
| --- | --- |
| 上传失败、ACK 丢失 | 保留未确认文件，续传并去重，不阻塞录音 |
| SD 短时写慢或读写失败 | 有限重试，未写成功的帧仍由缓存持有；临时读错不直接判文件损坏 |
| 拔卡、满卡、持续写失败 | 停止本场并通过现有状态及错误通道报告，保留可恢复内容，不假装仍在录音 |
| 正常或低电量关机 | 有限时间内排空缓存、封存场次 |
| 突然掉电 | 重启后恢复有效文件前缀和场次记录，标记异常结束，不自动开麦 |
| 停止后收到旧开启回复 | 丢弃过期回复，不能重新开启已停止或到期的场次 |
| 解绑、换绑或换入其他设备的卡 | 核对数据归属，旧归属录音不自动上传到新账号 |

继续支持八小时离线录音，容量检查扣除已有积压；不自动格式化 SD，不删除未确认数据腾空间。时长上限沿用产品设置，不因本方案给所有在线会议增加八小时强制停止。

## 7.0.120 速度优化与边界

7.0.119 的新会议实测约 123.93 KiB/s，主要限制是新业务类型仍逐片等待 ACK，未接入已有窗口预读通路。7.0.120 同时放开对应 begin 请求和 ACK 解析，使用两块最多 128 KiB 的预读缓冲，最多合并四个 WebSocket 帧写出。读卡、校验和发送可重叠，CRC、可靠落盘确认及删除条件保持不变。

批量上传给新录音保留至少 768 KiB PSRAM，覆盖 768 帧录音暂存及额外运行空间，并在分配后再检查一次；内部 DMA 保留线仍为 16 KiB。分配失败只允许在尚未发送数据时退回小分片，不能在半个窗口发送后擅自改变格式。新会议录音优先，监控运行期间以实时音频和可抢占性为先。恢复扫描只在实际有未完成场次时启动上传，避免全部完成后的无效重连。

500 KiB/s 按“所有文件字节 / 第一条 begin 到整场结束 ACK 的耗时”验收，包含元数据、确认和结束开销，不能只取瞬时峰值。首轮验收场景为会议结束后的后台上传或监控停止后的历史上传；活跃监控期间另验实时延迟和录音完整性。主机模拟可检验协议吞吐与错误处理，不能代替设备 SD、Wi-Fi 和任务调度的实测。

## 本机网页接收与试听

### 7.0.121 恢复与上传修正

- 新场次先写临时清单，落盘后发布；损坏的场次清单单独保留，不让其他正常场次一并失效。物理读写故障仍走 SD 恢复流程。
- 某场上传被拒绝时，本轮暂缓该场，继续其他场次，下轮再重试。确认损坏或不存在的文件标为缺失，场次标为部分录音，不能当作完整录音确认。损坏原文件保留。
- 每次历史调度最多检查 16 条分段记录，释放存储锁后继续推进；当前实时监控直接读取当前场次的最近 8 条记录。此限制针对分段索引，历史场次目录的扫描仍随场次数增加。
- 新场次只由场次清单判断待传状态，保留的损坏文件及其他归属文件不再计入旧归档待传数量，避免没有可传内容时反复连接。
- 按实际内存占用选择 4、3、2、1 帧批量发送，再按需缩小预读窗口。保留 768 KiB PSRAM 和 16 KiB 读任务余量，分配后复查；内部 DMA 保留线不变。
- 网关用独立线程整理整场清单，相同结束请求合并处理；已确认的场次直接读持久化结果回复。整场结束 ACK 允许等待 60 秒，普通分片仍为 2.5 秒，等待期间每 100 ms 检查取消、断网和录音压力。
- 新版网关记录整场确认时间，吞吐统计包含整场整理耗时；没有完整传输记录或整场确认，不宣称达到 500 KiB/s。App 控制和现有消息字段不变，没有增加 SD hello。

主机回归已验证 3 万片（按 960 ms 一片计为 8 小时）的元数据整理、重复确认和网络线程响应，未替代实机 8 小时录音及吞吐验收。

- 电脑打开 `http://127.0.0.1:8810/`，其他设备使用页面底部显示的当前电脑 IP 和端口 8810。

- 点击场次，再点击“准备并播放录音”。独立线程按分片编号读取已确认文件，复核 CRC，提取 PCM16 并生成 WAV；浏览器支持播放、拖动进度和下载。
- **网页试听采用紧凑播放**：只连接收到的音频，不给监控静音或缺失数据补静音。原始文件、时间戳和场次清单保留，不改变服务端正式时间线规则。持续上传时，播放器使用点击时的快照，新文件需重新加载。
