## 3. 已实施优化

### 3.1 正常对话上行

底层 audio_uplink 增加按实例开启的低延迟策略，默认仍为四帧批量。只有正常对话的 start_mic_cloud_upload() 在发送任务启动后、第一帧前显式开启：

- 第一批：1 个 20 ms 帧立即入队；
- 后续批次：每 2 个 20 ms 帧入队；
- final 帧：无条件及时刷新；
- 首批入队失败：不推进到稳态；
- 第一帧后：拒绝切换策略；
- packet buffer 容量仍可容纳原四帧，帧格式不变。

因此确定性的封包等待理论上由首包约 80 ms 降至约 20 ms，稳态发送粒度由 80 ms 降至 40 ms。该数字不包含麦克风、任务调度、TLS、网络和云端处理时间。

会议模式和监控模式直接调用底层 nuwax_audio_uplink_start()，不调用低延迟开关，继续使用原四帧策略。

### 3.2 WebSocket 发送

- plain TCP 和 TLS 的真实 socket 均设置 TCP_NODELAY=1；
- WebSocket header、mask 和首段 masked payload 合并为一次底层写入；
- 大帧剩余内容继续按原 mask offset 分块；
- FIN、opcode、长度编码、掩码、全帧超时、发送锁和失败断连语义不变；
- 常见 662、1324 和 2648 字节音频 payload 可减少一次 TLS application write。

### 3.3 下行首帧播放

- START 成功取得当前播放代次的 action claim 后立即更新逻辑 SPEAKING 状态，但不再同步等待 50/500 ms 的 LVGL 锁；
- UI 状态和 SPEAKING 文本由 shell/UI 任务异步同步；
- 异步同步使用 state generation 复核，不会把旧状态写回逻辑状态；
- WebSocket 文本回调不再同步执行 emotion UI 更新，原 session command 队列仍负责最终应用；
- START 收包日志移到 speaker enqueue 之后；
- 每轮 START 新增一条 speaker start latency 日志，记录 handler、enqueue、首次 I2S write 的时间；
- START 同时受 PCM I/O、END completion、空闲输出维护、cancel pending、output stop owner 和 runtime reset 六类门控；
- START 提交和队列 reset 在同一 speaker mutex 临界区完成，两个并发 START 不会互相清除新代次；
- cancel 先推进代次并阻断新写入，等待在途 action 结束后，由唯一 stop owner 清空 I2S DMA；
- START 回调、SPEAKING 更新、软件参考复位和 PCM 写入均在同一代次的 I/O claim 内执行；
- END 只有在 submitted/active generation 一致且未取消时才能取得 completion owner，旧 END 不能触发新会话的完成回调；
- 即时、异步和同步淡出均绑定请求时的 submitted generation，旧淡出不能取消新播放；
- PLAYBACK_BEGIN 元数据不再提前清除 cancel drop，只有通过全部门控的真实音频 START 才能恢复播放；
- prepare/release/deinit 使用 maintenance owner；音量更新与反初始化统一采用 speaker mutex -> output lock 锁序；
- 唤醒检测的麦克风单次读取等待按 feed chunk 计算并限制在 20 至 100 ms，缩短 TTS 接管麦克风时的停止盲区。

播放 END 的 DMA 尾帧等待不在本轮范围内，仍需单独验证是否存在 20 至 90 ms 尾音截断风险。

### 3.4 实时采集循环

采集路径每个检查点最多处理一条 session command，避免一次性清空最多 32 条命令。该措施降低突发积压风险，但单条 UI/网络命令仍可能阻塞；后续若实机 p99 不达标，应把 command、UI 和 ACK 完整迁移到独立 control worker。

## 5. OTA 清单身份

仅当设备已经完整安装同一双槽分区布局和 rollback bootloader 的 7.0.12 基线时，才可以直接执行本次 app-only OTA。若未建立该基线，必须先串口完整烧录五项。

已发布并独立回读校验的不可变对象：

~~~text
https://s3.nuwax.com:9443/nuwax-packages/firmware/nuwax-ai-partner/7.0.13/v2-713-c9a69e6f/NuwaxAIPartner.bin
~~~

2026-07-30 发布后使用独立 HTTP 客户端完整下载验证：直接返回 `200`、无重定向、
`Content-Length=3465200`、`Accept-Ranges=bytes`，远端 SHA-256 与本地最终镜像一致。
该次独立回读只证明发布物可用；后续实机 OTA 结果见第 8 节。

本机仍没有正式云端 OTA 管理接口或管理凭据。发布物校验完成时，本地测试网关
`devices=[]`，不能把连接到正式 WebSocket 的设备跨网关下发；设备 `device_secret`
也不能代替正式云端管理凭据。经用户明确授权后，实际采用 BLE Security 2 把设备
切回测试网关并完成 OTA，过程和最终状态见第 8 节。

从 7.0.12 / 7000012 升级时，清单必须严格匹配：

  "url": "https://s3.nuwax.com:9443/nuwax-packages/firmware/nuwax-ai-partner/7.0.13/v2-713-c9a69e6f/NuwaxAIPartner.bin",
  "version": "7.0.13",
  "project_name": "NuwaxAIPartner",
  "target_board": "miaopan_v2_0_n32r8",
  "target_chip": "esp32s3",
  "partition_schema": 1,
  "build_flavor": "product",
  "release_sequence": 7000013,
  "size_bytes": 3465200,
  "image_sha256": "c9a69e6f12d4556ef3fb85c7de5d0d9812735b9d637ff45b4c7575e6014cb90a",
  "force": false
}
~~~

`request_id` 与 `update_id` 必须是同一个全新 ID：长度 1 至 63 字节，首字符为
字母或数字，其余字符只允许字母、数字、下划线、点、加号和减号。两者不相等时，
设备会以 `bad_request` 拒绝 OTA envelope。

必须使用原始 app 文件 SHA-256 c9a6...b90a，不能误用镜像 footer validation hash 或 ELF SHA。

OTA 只下载 NuwaxAIPartner.bin，不能把 bootloader、partition table、ota_data_initial.bin 或 srmodels.bin 当作 OTA app 镜像。HTTPS 服务必须返回 200、禁止重定向，并提供与 size_bytes 完全一致的 Content-Length。

## 6. OTA 前置条件

- hello 必须确认设备当前运行 7.0.12、ota_state 为 valid/idle；
- Wi-Fi 和云端已有 positive activity；
- 电量计可信时电量不低于 30%；不可信时电池电压不低于 4000 mV；
- 会议、监控、关机流程均未占用设备；
- request_id 和 update_id 必须全新且完全相等；
- 设备上报 terminal result 后，云端必须回发字段匹配且 `persisted=true` 的
  `ota_result_ack`，设备才会进入重启闭环。

## 7. 实机验收步骤

1. 经用户确认后托管 app 镜像并下发一次 ota_update。
2. 验证 accepted、progress、staged、terminal ACK 和 reboot。
3. 重启后 120 秒内验证本地健康门、正式云端 positive activity、pending_verify 到 committed。
4. 验证新 hello 报告 7.0.13 / 7000013、ota_state=valid、rolled_back=false。
5. 在正式云端执行至少 20 轮正常问答，包含短句、连续问答、长 TTS 和一次播放中讲话。
6. 串口收集每轮 speaker start latency 和 conversation metrics。
7. 同时验证 Wi-Fi/云端图标、触摸、SW3、音量、BLE 配网入口、会议模式和监控模式可正常进入/退出。

建议通过线：

~~~text
first speech sample -> first uplink send p95 <= 60 ms
downlink handler entry -> first I2S write begin p95 <= 40 ms
DSP p95 < 12 ms, p99 < 18 ms
RT capture drops/gaps = 0
uplink sequence gaps/duplicates/out-of-order = 0
speaker gap frames = 0
formal cloud auth/listen/audio/TTS behavior unchanged
~~~

任一以下情况应停止继续推广并保留 7.0.12 回退条件：

- OTA 健康检查失败或发生 rollback；
- 正式云端拒绝 hello/listen/audio；
- sequence 缺口、重复、乱序；
- capture drop 或 speaker gap 增加；
- START 首帧延迟高于原基线；
- 会议/监控模式协议或完整录音行为变化。
