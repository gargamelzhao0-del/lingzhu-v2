## 2. R1：问候超时后失去自动恢复——确认存在，P1

### 真实触发过程

1. 休眠设备被唤醒，问候请求发送成功；为保持既定音画时序，在首 PCM 到来前保留 SLEEPING 逻辑状态。
2. awake session 已 active/paused，唤醒检测已停止。连接和心跳正常，但本次业务没有返回问候文本，或进入 TTS 等待后没有音频；本轮确认的两种复现均尚未绑定播放器 generation。
3. 超时清理回合后调用恢复函数；恢复函数因 SLEEPING 提前返回。
4. 空闲恢复只从 IDLE 重新收音，唤醒监督又因为 awake session 仍 active 而不重启唤醒。实际内部等待循环继续运行，外层补救没有获得执行机会。

证据位置：`main/nuwax_ai_partner_main.c` 的 `wait_for_mic_start_action`、`recover_normal_conversation_after_playback_abort`、`maybe_enter_idle_sleep`、唤醒监督、问候发送函数；对应关键行 9112、9541、11880、18933、19136、29687、34851。`main/app_shell.c:554` 还会在真正 SLEEPING 映射下强制显示 sleep，仅发布 LISTENING dialog 不会修复核心状态。

### 必须避免的修法

- **不能直接删除所有 SLEEPING 保护。** 主动休眠、关机和隐私停录会被意外重新收音。
- **不能只 start_prelisten 或设 IDLE。** 新收音启动后，同连接的迟到问候可能通过现有 cloud-output bootstrap 附着到新回合；仅清旧 guard 没有完成旧消息隔离。
- **不能只调用普通 request_close。** `main/ws_transport.c:2989` 和 `main/ws_close_policy.h` 对心跳健康时的普通业务关闭请求有抑制，故障恰好可以发生在心跳健康时。

### 推荐实施方案

采用只针对“已确认未完成问候”的恢复分支，先保证故障收敛，再考虑需要云端配合的同连接恢复。

1. 在清理 guard 前记录 `request_id + ws_epoch + awake_generation + turn_epoch + failure_reason`，确认仍是当前 wake greeting、没有首 PCM 且尚未绑定播放器 generation。已授权 START、但首 PCM 未到的另一分支沿用现有 terminal barrier 与物理停止确认，并单独回归；不能因“未见首 PCM”就统一抢占播放器所有权。
2. 由主 owner 执行恢复，重新核对身份与当前关机、主动休眠、配网、通知、会议/监控和 OTA 所有权。旧失败记录不得关闭新连接、抢占新回合或启动未授权收音。
3. 增加专门的、受上述检查保护的问候未完成关闭原因，允许在健康心跳下退休该连接 epoch。保留普通业务关闭策略；不要伪装为传输损坏来绕过策略。
4. 使用现有断开清理及 awake-session 重连恢复。新连接完成认证且资源允许后再开始新收音；菜单仍打开时等待菜单关闭。
5. 重连在现有宽限期内不能成功时，释放该 awake owner，回到允许本地唤醒的休眠路径。连接失败不应再次留下 active/paused 僵持状态。
6. 对已被其他 owner 替代的失败记录终止处理；OTA 等暂时阻塞采用有界的 owner 交接策略，不能留下永远 pending 的恢复票据。补齐实际任务队列与 transport-close 集成回归。

隔离候选 `WG-EPOCH-RECOVERY-v1` 已调用原有保留/重连恢复函数验证状态可收敛，但当前只验证 WAIT_TEXT/WAIT_TTS 且 `speaker_generation=0` 的情况。交叉检查发现，实际 START 授权在首 PCM 之前即可绑定非零 generation（主文件 10853、10911）。这一分支走 11834 起的 terminal barrier，正常释放时 `finalize_playback_terminal_if_ready` 在 9881 起先把可用 awake owner 转到 LISTENING，再于 9927 起调用恢复，避开了本次 R1 的 SLEEPING 早退。**这条已有恢复路径不能误报为同一缺陷，也不应被新重连策略无条件接管。** 候选不覆盖非零 generation，需对其取消、超时与物理停止单独回归。测试注入的“1 秒重连成功”仅为驱动测试，不是设备延迟预测。当前候选没有替换生产传输实现，不能直接当补丁发布。

### 影响与关闭标准

正常问候仍等待首 PCM 再切换既定表情、播放完成后进入收音，方案不增加正常流程固定等待。异常时由当前“可能一直不听”变成“超时后重连恢复，或回到可再次唤醒”。真实恢复耗时包含超时和网络重连，不能承诺无感。

普通唤醒等待可以与正式 SD 补传同跑。退休连接会中断补传，产生重试或重复提交成本。现有取消仅在成功 commit ACK 后才删除 `.ready`；取消、分片 ACK 或断线不会自行删除它。服务端已保存但 ACK 丢失时，需幂等接收后续重试。

现有断开路径等待补传 owner 退出最多 6 秒，逾期会受控重启。因此方案不能宣称“所有异常均无重启”；必须实测问候超时与 begin/chunk/commit 各阶段并发，确保正常取消能在界限内完成。服务器 ACK 是否确实代表持久保存，需要正式云端证明。

关闭条件：真实设备故障注入无文本、无 TTS、无首 PCM、迟到/重复输出，分别叠加菜单、主动休眠、停止、OTA、补传。每条路径最终可继续操作或再次唤醒；旧回复不进入新回合；正常唤醒延迟与准确率不退化。

## 3. R2：没有有效保存路径却仍显示运行中——确认存在，P1

这是状态真实性问题。当前真实重试存在，短暂交接也可能是正常的；故障在于持续保存失败没有改变用户可见的模式结果。

实际路径是：已授权在线会议/监控断网 → SD 初始化失败 → 保留自动恢复 lease → 持续重试仍失败 → UI 根据 lease 发布 ACTIVE。`s_offline_mode_capture_failed` 没有参与该状态判定。会议菜单 `main/nuwax_ui_v28/nuwax_drawer.c:1401` 把 ACTIVE 显示为“运行中”。网络恢复表情可能同时出现，因此不能说所有屏幕元素都显示正常。

关键位置：`main/nuwax_ai_partner_main.c:4372`、`:12795`、`:12824`、`:34333`、`:34975`；`main/offline_audio_spool.c:1581`。离线时诊断上报服务不会立即发往云端，日志也不是用户告知。

### 推荐实施方案

由模式 owner 汇总以下独立事实，再决定 UI 和恢复：

| 事实 | 最小必要内容 |
| --- | --- |
| 用户意图 | 会议/监控/OFF、停止代际、授权与绑定范围 |
| 采集健康 | MIC owner、启动/交接/运行/停止/故障、采集进展 |
| 保存路径 | 在线路径是否有效；离线写入准入、暂存余量、writer 结果、持久化水位 |
| 会话覆盖 | 正常、有已知缺口、边界无法确认；累计量与时间区间不能随重试清零 |

具体行为：

1. 健康交接采用现有启动/恢复状态，并保留有界缓冲；不能把短暂 `capture=false` 一律判失败。
2. 离线且没有可用保存路径，使用已有模式 ERROR，配合简短提示“录音已中断，当前内容无法保存”。不新增 SD 管理面板。停止控件仍可用，不能因 ERROR 禁止用户停止。
3. 写失败或满卡先按保存水位判断：内容仍完整留在有界缓冲且随后全部落盘，只记录等待/故障，不宣称丢失；确认未采集或已丢帧才记录已知缺口，结果无法确认则标记未知。发生真实缺口后恢复时，按仍有效的意图继续，并告知“录音已恢复，期间有内容未保存”。恢复不得把有缺口的会话重新标为全程完整。
4. 以 owner 快照和异步事件汇报，不在 UI/MIC 回调中执行目录扫描、同步写盘、NVS 压缩或等待 ACK。
5. 本地记录 `admitted/written/durable` 水位，区分已知帧丢失和根本没有采集的时间段。未采集区间不能凭时间猜造“准确缺失帧数”；重启前后使用 boot identity 区分时间基准。
6. 用独立、有限大小的持久记录保存故障摘要和覆盖状态；写不下时标记结果未知。现有有界诊断队列只作通知，不能承担唯一证据。新增元数据不改原音频 header/CRC。
7. 停止、到期、换绑和关机的代际检查优先于自动恢复；旧 ACK 或插卡不能重新打开用户刚关闭的录音。

需要保留的正常行为：有健康云端接收路径时，缺少可选 SD 备份不应停止在线会议；监控没有检测到人声时不写文件是正常的；“暂停云端上传”也不等于“隐私停录”。不能按几秒没有写字节就误报故障。

前后体验：原来用户可能在几分钟后仍看到“运行中”，实际没有录到这段；修复后当场知道中断，介质恢复后可续录，并能区分完整与缺失。已丢失的声音不会被修复代码补回来。

设备错误状态可先落地。若要 APP 历史记录展示缺口、恢复原因和保存完成结果，需要 APP/云端接入相应状态；现有 APP 是否已支持尚未验证，不能说只改设备就能完整实现。

关闭条件：无卡、满卡、慢卡、拔卡、写失败分别超过缓冲容量实测，核对当时 UI、MIC 数量、持久帧数和缺口记录；覆盖正常静音、在线无卡、插卡恢复、用户停止与恢复竞争。

## 4. R3：旧录音没有绑定归属隔离——本地缺口确认，P1

条件是旧账号留下未补传文件，设备进入另一账号的认证连接。当前归档没有原账号/绑定代际，补传扫描同一目录；`offline_audio_spool.c:3684` 的 begin ACK 门槛仍有效。**未证明云端实际接收并展示给新账号，但设备本身缺少这层防护。**

### 推荐实施方案

1. 用经可信认证的稳定 `recording_owner_scope` 和 `ownership_epoch` 表示录音归属；密钥轮换、Wi-Fi 配置和 WebSocket epoch 分开保存。不能用密钥哈希当账号身份，也不能把每次重连当换绑。
2. 在归档可补传前，原子保存 owner 侧车元数据/索引。保留音频原始字节、旧 header、segment_id 和 CRC，不为新增归属信息重写历史音频。
3. 换绑时封住旧代际新采集/补传准入，取消在途上传、停止旧采集并等待旧消费者退出，再提交新代际。begin、发送、commit ACK、本地删除均校验相同归属与 epoch，防止旧 ACK 越过换绑边界。
4. 同一用户换 Wi-Fi、正常换密钥或迁移 WSS，验证归属相同后继续补传。不同用户只访问新范围。
5. 旧版没有归属的文件先隔离保留。不能自动认领给当前用户，也不能为清理问题直接删除。只有取得原归属的独立证明，或通过经验证的原权利人授权恢复流程后才迁移；新绑定用户点击确认、持有设备或当前密钥本身均不足以授权旧数据迁移。
6. 云端协商 owner-aware 能力，身份不明时不自动补传。设备只能对它知道的变化隔离；云端在密钥不变时静默换账号，纯设备代码无法识别。

可以先做设备侧保守隔离，覆盖明确解绑、重新认领等本地可见事件；完整、少误伤的最终方案需要 APP/云端提供可信绑定身份。单纯保留 `audio_session_id` 只解决拼接，不解决所有权。

前后体验：同用户重配网仍保留待上传录音；转赠后新用户不会自动接收旧用户积压。历史来源不明的录音可能需要授权恢复，这是保护数据必须承担的迁移成本。该方案本身不加密可拆下的 SD 卡；物理读卡隐私是另一个需明确的产品边界。

关闭条件：A 录音→解绑→B；A 换 Wi-Fi/密钥/WSS；换绑时延迟旧 commit ACK；元数据提交各阶段断电；旧无归属文件迁移。验证无跨账号展示、误删、错认领或重复拼接。

## 5. R4/R5/R6：量产安全与迁移要一起解决

这组问题有真实配置和代码依据，但不能描述成“任何人随时远程接管”。当前 Security 2、UID 校验、随机盐、会话证明、WSS 证书校验以及 OTA HTTPS/摘要/启动回滚保护均有实现。

| 问题与前提 | 推荐方案 | 用户体验与代价 |
| --- | --- | --- |
| R4：生产候选包含共享开发 PoP；对方需遇到配网窗口并取得目标 UID/共享值 | 逐台 PoP/工厂 verifier；APP 通过正确标签或受控认领取得持有证明；量产配置拒绝 DEV_MODE，明确 USB 工厂入口策略 | 正常配网流程仍安全会话后联网；首次认领需扫描逐台凭据，防止别人的通用开发凭据认领设备 |
| R5：编译允许 `ws://`，若实际设备使用则凭据和控制可被网络中间人观察/伪造 | 正式 WSS 和可信 endpoint；验证服务端证书及设备绑定；现存设备先完成可回滚迁移，再切严格版本 | 正常交互流程不变；现存设备不能因直接开关导致被迫重配网。TLS 内存与性能成本必须真机测 |
| R5：控制消息给出的 URL+摘要不能独立证明固件发布者 | 独立签名和受控发布密钥；规划 Secure Boot、存储与调试保护的量产制程及恢复策略 | 用户不新增步骤，异常来源固件被拒绝；售后/返修需要匹配签名与工厂镜像 |
| R6：非 DEV 工厂身份存在默认 NVS，启动特定初始化失败会整区擦除 | 工厂身份独立持久区和专属 API；可恢复用户配置与不可重建身份分离；定义升级/回滚/重置策略 | 正常使用无变化，故障恢复后仍可配网；现有分区设备需要单独迁移路线，不能只改 namespace |

R4 的进一步反证：随机盐和 SRP 会话不是无效；盐不是保密口令，不能抵消共享 PoP 被掌握。APP owner 校验限制 BLE 会话内的所有者，并不等于云端账号归属。当前本地 cloud config 接受语法正确的任意 WSS 地址，且配网提交随 GOT_IP 完成；正式云端拒绝错误密钥不等于所有配置都只能指向该正式云端。

R5 的具体迁移顺序：

1. 清点已有 ws/wss 配置和服务端 TLS 能力，确定受信的新地址；不能机械替换 scheme 并假定原端口支持 TLS。
2. 通过可信渠道取得迁移参数，保留 active，把新配置作为 candidate。
3. 校验证书、设备身份、绑定归属和必要云端能力，成功后原子切换；失败保留可恢复状态。迁移身份不能仅由尚未可信的旧明文连接自行声明。
4. 迁移完成后轮换可能已在明文路径暴露的密钥，并禁止静默降级回明文；保留旧记录不等于继续向不可信路径发送敏感数据。迁移完成的设备才进入严格禁用明文版本；未迁移设备走受控 APP 恢复或工厂流程，而不是先删配置。
5. 单独验证 HTTPS OTA 与 WSS 并发的 TLS/内部内存峰值。内容缓冲配置不等于总 TLS 用量；当前离线补传速度不能直接代表 WSS 正式场景速度。

R6 的准确边界：`nvs_flash_init` 返回 `NO_FREE_PAGES`/`NEW_VERSION_FOUND` 才触发当前整区恢复逻辑，不是普通每次写满都会擦除。默认 NVS 中两个 namespace 仍属同一分区。独立工厂区需要分区表和对应读写 API；普通应用 OTA 不会自动替换分区表。已有设备与新生产设备必须分别规划，不能在线盲改分区，更不能把 eFuse 当可回滚配置试烧。

关闭顺序是先实现身份持久化和迁移，再注入逐台身份并关闭开发模式；WSS 迁移先于强制禁明文；签名信任链需结合工厂制程。三个开关同时直接改动不是可靠方案。

第一份迁移/签名桥接固件也必须经可信渠道交付，不能靠尚不可信的旧明文 OTA 来证明自己的可信性。若考虑软件验签先行，需要正确签名的初始镜像、后续连续两次升级及错签拒绝验证；回滚到旧无签名镜像的边界必须明确。普通应用 OTA 路径不会自动建立 bootloader/eFuse 硬件信任根。

关闭条件：旧设备 WSS/WS 升级、TLS 失败回退、错误账号/UID、工厂区缺失或损坏、NVS 初始化恢复、签名拒绝、升级回滚及售后恢复分别验证。不要以本地主机配置测试代替完整 BLE、手机和正式云端测试。

## 6. 问候触摸取消与电源边界

**屏幕按住动作有状态差异，但撤回其默认 P2 产品缺陷定性。** 首 PCM 后问候逻辑状态为 LISTENING，`app_shell.c:1656` 的屏幕取消只接受 THINKING/SPEAKING；touch wake 关闭时，LISTENING 返回 NONE。这是已确认的代码行为，只有产品要求问候也可按住取消时才构成功能缺失；当前不得把扩展该交互作为必修。

仅在另行决定保留并扩展该交互时，候选设计才是按有效播放器 owner、generation 和当前可取消业务决定取消。动作携带连接、awake、turn 和 speaker 身份，主 owner 消费时再次匹配，避免旧动作取消新回合；物理播放停止后才允许重新收音。若产品要求取消所有屏幕按住会话动作，应处理屏幕残留入口，保留头部触摸、正常点击及上下拉菜单。两种方向不能混作同一个修复，本轮均未实施。

**低电优雅停录与温度保护属于尚未闭合的产品边界，不能据此认定硬件充电不安全。**

- 当前 battery listener 主要更新 LED、UI；未发现电池耗尽会自动进入正常“停采集→等待保存→关机”链路。
- 正常长按关机已有存储准入屏障与收尾等待。强制关机由板级按键任务在持有到强制阈值、去抖释放后执行，绕过 app owner 收尾；仍依赖 FreeRTOS 任务运行，不能据此宣称 MCU/调度器完全卡死时也有独立硬件兜底。
- 归档断电恢复能保留完整记录前缀，但 RAM 与未稳定写入介质的尾部可能丢失。不能从同步周期推导绝对“两秒以内”保证。
- `battery_insights` 有温度分级计算，但未找到生产调用。不能把其中的通用温度值直接用作电芯充电截止阈值；需确认温度来源、充电芯片控制能力、电芯和保护板规格。

建议实施：由电源 owner 消费新鲜可信电压/电量与持续性条件，在经硬件实测确定的余量下禁止新高耗电操作、发出简短提示、停录并有界完成归档。复用现有关机收尾，不在电池回调里同步写盘。低电与 OTA 写入/切槽竞争需独立设计和断电验证；不能简单在任意瞬间强关，也不能无限等待。

前后体验预期：普通电池逐渐耗尽时，用户先收到提示，已保存范围可解释，再关机；突发硬断电依旧可能损失尾部。是否能达到该效果需量产板实测，不应改一个电压常量就宣布实现。USB 插入、净电流为正、接近充满和已满应分别验收，避免用“插线就闪电”掩盖没有净充电的情况。

## 8. 实施顺序与用户体验验收

| 顺序 | 工作 | 修复前的真实风险 | 修复后必须看到的结果 |

| 2 | R2 状态与覆盖记录 | 显示运行中却没有保存；恢复后缺失不明确 | 失败当场可知、可停止；恢复有说明；不把静音误报故障 |
| 3 | R3 绑定归属与存量迁移 | 旧录音可能被提议上传到新绑定连接 | 同用户保留，跨用户隔离；历史未知文件不误删、不默默认领 |
| 4 | R6 工厂身份、R4 逐台配网、R5 安全迁移 | 开发身份进生产；直接关开关可能让旧机失联 | 逐台认领；旧机有受控升级路线；异常恢复不丢不可重建身份 |

设备端可以先完成 R1、R2 本地状态和保守隔离；固定 PoP 保持，屏幕按住交互不默认恢复。完整绑定归属、APP 录音缺口展示、正式补传和可信端点迁移需要跨端协作。电源门槛及另外规划的工厂身份、启动信任链需要硬件/量产支持。

仍需沿用第一次评估中的多机 72 小时、八小时录音对账及故障注入矩阵，特别增加以下组合：问候超时×补传 commit；SD 故障×用户停止；换绑×旧 ACK；WSS 迁移×存量归档；低电×收尾/OTA。补传性能按“唯一有效音频字节/直到持久化完成的整场耗时”统计，区分空闲和交互并发。500 KiB/s 是性能目标，不能以牺牲录音可信度或交互恢复换取，也没有证据证明修复这些问题自然会达到该速度。

**上架条件仍未满足。** 已确认的缺陷需要修复，条件性安全风险需要按真实生产部署关闭，未知项需要拿到同一候选的实测和跨端证据。修复后是否稳定，应由这些结果决定，不能由报告篇幅或测试 PASS 数量决定。

## 9. 固定 PoP、保持现有正常流程前提下的实施清单

| 当前不混入功能修复 | 固定 PoP 保持；WSS、签名、逐台工厂身份属于不同部署/制程事项 | 不擅自改云端地址、配网数据、分区表或 eFuse | 固定 PoP 不是本轮已证实的通信故障根因；条件性安全风险仍按真实部署另行评估 |

新增兼容性检查：`nuwax_cloud_config_init` 在 `main/nuwax_provision_new/nuwax_cloud_config.c:128` 比较已存记录长度与当前 `sizeof(s_config)`，不匹配时可走 136 起的擦除路径。因此为了保存归属而直接给 `nuwax_cloud_config_t` 增加字段，也可能使正常旧设备丢配置。归属/覆盖状态应独立持久保存，或实施能读旧版本的事务迁移；不能只改 C 结构体。此项是修复实施风险，不是当前未改结构体时新增的线上故障。

第一批应仅交付两个确定缺陷的修复。保持云端消息、音频格式、分片/提交 ACK、固定 PoP、现有配网和会议/监控会话规则。数据归属策略、屏幕残留入口和低电收尾分别作为后续可独立验证的变更，避免一个大改动混入多种产品行为。

正常流程不增加固定延迟或逐帧 NVS/同步写盘；新增故障记录必须有界、异步，不阻塞 MIC/UI。不能提前保证零回归：需要以正常问候/继续对话、菜单与头摸、在线会议监控、静音和暂停、断网恢复、8 小时上限、补传、OTA、配网及关机作为同一候选的对照，核对内存和用户可感知延迟。异常恢复重连与补传取消的 6 秒边界、旧回复/旧 ACK、用户停止/主动休眠竞争须单独故障注入。
