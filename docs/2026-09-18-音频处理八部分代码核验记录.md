## 4. 第 1 部分核验结论

### A1-01 时钟和采样格式

**等级：事实；物理效果待验证。**

代码凭证：
- [根配置](../sdkconfig)：1005–1008、1066、1069、1083、1201。
- [板级头文件](../main/board/vocat_audio_board.h)：9–13，未启用 vendor 24 kHz 分支时使用 16000 Hz。
- [板级驱动](../main/board/vocat_audio_board.c)：595–667，配置 RX/TX。
- 编译配置头：452–455、486、503、586；板型开关在 410。

当前关键设置：
- RX：四个有效 TDM 槽，每槽 16 位，数据 16 位。
- TX：双槽，每槽 32 位，有效数据 16 位。
- 两侧 MCLK multiple 都为 256。
- 业务采样率 16000 Hz，业务帧长 20 ms。
- 模拟增益配置 30 dB，软件增益 Q15=32768，即 1 倍。

由此推算两侧每采样周期均为 64 个位时钟：BCLK=1,024,000 Hz，MCLK=4,096,000 Hz。**TX 的 32 位时隙不表示业务 PCM 是 32 位。**

没有从这些设置发现直接的时钟倍数冲突，但没有检验引脚波形、板卡批次、模拟输入或芯片实际寄存器状态，不能宣布硬件百分之百正确。

### A1-02 通道提取与四槽配置

**等级：软件行为已确认；实体布线待实测。**

代码凭证：
- [板级驱动](../main/board/vocat_audio_board.c)：39–52、784–793。
- [单声道读取](../main/mic_input.c)：614–619。
- [ES7210 依赖驱动](../managed_components/espressif__esp_codec_dev/device/es7210/es7210.c)：16、177–185、229–233。

单声道路径读取 `tdm[f * 4]`，即 slot0。它是通道提取，不是双麦平均。slot1/slot2/slot3 的物理角色是工程声明，不能仅凭声明重新证明实际布线。

依赖驱动按选中麦克风数量决定 TDM，阈值为 3。当前选中四路。直接改成选中一、两路会改变驱动工作分支；“减少槽数即可省资源”不能作为无条件优化结论。

slot2 是候选参考，根配置 1023 及 SD 测试配置 1121 均未启用该参考开关。此项不证明硬件参考实际可用，也不要求现在启用。

### A1-03 DMA 未读尾部被跳过的检测盲区

**等级：条件风险，路径已由源码确认；尚未实机复现。核验优先级高。**

证据链：
1. 板级 RX 注册 `on_recv_q_ovf`（板级驱动 720–723），回调在 276–284 增加计数。
2. `mic_input.c:272–335` 用读取前后的该计数判断不连续。
3. 本地 SDK `components/esp_driver_i2s/i2s_common.c:329` 创建长度为 `desc_num - 1` 的消息队列，当前为 7。
4. 同文件 634–640 的 GDMA RX 回调，在队列**已满**时丢弃队首并触发溢出回调。
5. 同文件 1403–1408 的同步读取，在队列剩余空间不超过 1 时也会切换当前缓冲，但此分支没有调用溢出回调。

关键源码摘录：

```c
if (handle->dma.rw_pos == handle->dma.buf_size ||
    handle->dma.curr_ptr == NULL ||
    uxQueueSpacesAvailable(handle->msg_queue) <= 1) {
    if (xQueueReceive(handle->msg_queue, &(handle->dma.curr_ptr),
                      pdMS_TO_TICKS(timeout_ms)) == pdFALSE) {
        ret = ESP_ERR_TIMEOUT;
        break;
    }
    handle->dma.rw_pos = 0;
}
```

明确的条件推演（不是硬件复现）：
- DMA 块长 240 个采样点；会议帧长由 `meeting_mode.c:59–60` 的公式和配置得到 320 点。
- 从块边界开始的一次正常 320 点读取会取 A 块 240 点、B 块 80 点，B 还剩 160 点。
- 若下一次读取时消息队列有 6 项，长度为 7，剩余空间为 1；队列尚未满。
- 上述第三个条件成立，接收下一块地址并把位置置零，B 的 160 点未被交付。
- 若推演期间没有其他实际队列溢出，设备端溢出计数可以保持不变。

因此，“溢出计数为零”不能单独证明采样无缺口。320/240 不整除**本身并不是错误**，在队列未接近满时 SDK 会正常保留并继续读取尾部。160 点（10 ms）只属于该例，不是每次固定损失，也不是已测出的损失量。

当前唤醒采集块为 240 点（`wake_word_detector.c:150`），与 DMA 块长相同；这减小该例中的尾部情形，但不能据此保证唤醒采集永不丢样。

候选措施，暂不实施：
- 评估按 DMA 粒度获取数据、在软件层保存余量后拼接业务帧。
- 评估为实际跳过的样本建立准确计数／断点通知，或采用具备明确连续性契约的采集接口。
- 验证队列接近满但未溢出、真正溢出、部分读取、切换和停止时的样本序列。
- 不直接删除 SDK 防失效缓冲保护，也不把驱动指针长期保存在业务层。

该问题涉及 SDK 的缓冲有效期保护，需测量调度压力后再选方案。不能把它直接解释为历史上传缺片、历史重启或当前音频损坏的根因。

### A1-04 DMA 容量

**等级：计算事实；是否足够待验证。**

当前 RX 每块大小为 240 × 4 × 2 = 1,920 字节；8 块为 15,360 字节，即 15 KiB，等价 120 ms 采样量。

依据：
- `vocat_audio_board.c:597–599`；
- SDK `i2s_tdm.c:138–145` 根据有效槽数计算；
- SDK `i2s_common.c:445–457` 根据采样宽度、有效槽数和帧数求大小。

这只计算 RX 数据缓冲，不包括描述符、消息队列、TX、任务栈及软件队列。也不是启动时固定增加 120 ms 延迟，更不是允许采集任务阻塞 120 ms 的保证。

上轮“容量合理”证据不足，改为“没有仅凭容量数值调整的依据”。需要测量最坏服务间隔、积压和内存余量，才能判断应否改变容量。

### A1-05 部分读取和显式溢出

**等级：已检查路径事实；不代表全部错误恢复均已验证。**

代码凭证：
- `mic_input.c:192–194`：接受 TIMEOUT 且已读取非零字节的结果。
- `mic_input.c:595–658`：在连续性检查通过后交付可用采样。
- `mic_input.c:296–324`：读取发生断点时不交付该批；启动阶段有限重同步，之后返回 INVALID_RESPONSE。
- [会议调用方](../main/audio_modes/meeting/meeting_mode.c)：933–1005，累积部分帧，明确断点时清空已累积部分并重置会议处理器。

这些保护存在，应保留。丢弃受断点影响的一批数据属于保守恢复，不等于恢复了物理上已失去的采样；也不能覆盖 A1-03 的未通知跳过路径。

### A1-06 去直流依赖读取分块

**等级：处理性质已确认；声学影响待验证。**

`mic_input.c:617–632` 先按本次返回的采样计算整数均值，再减去均值并饱和到 int16。配置当前开启该处理。

可直接证明它不具备分块不变性。例如输入 [100,100,200,200]，整块处理得到 [-50,-50,50,50]；分成两块分别处理得到 [0,0,0,0]。该例是算法演示，不是实机音频。

因此改变读取粒度、处理部分读取会改变输出；但是否有可听见失真或识别率变化，需要连续语音和测试信号评估。

连续状态 DC 滤波器或调整处理位置仅是候选，必须等第 2 部分核验 Cleaner 和会议处理器后，避免重复处理或产生新的状态切换问题。

### A1-07 重复初始化会清除原对象

**等级：误用条件下的缺口，未发现已确认业务触发证据。**

`mic_input.c:408–415`：

```c
memset(mic, 0, sizeof(*mic));
esp_err_t owner_err = acquire_owner(mic, owner);
if (owner_err != ESP_OK) {
    return owner_err;
}
```

`acquire_owner():140–147` 在已有 owner 时返回 INVALID_STATE。对仍持有资源的同一个对象再次调用 init，会先清掉其指针和租约，再因 owner 忙而返回。假定没有其他合法保管这些资源的对象，原实例将无法再通过该对象正常清理。

不能将此结论扩大为正常业务必然泄漏：
- 会议局部对象为零初始化（792），正常初始化调用在 909。
- 离线对象为零初始化（2363）；重试循环在 2399 调用，2400 成功立即退出。
- 唤醒局部对象为零初始化（1032），初始化在 1040。
- 这些读取到的路径没有证明“对成功且未释放的同一实例再次 init”。

接口头文件未明确重复初始化契约。后续宜补齐生命周期约定和防御；不能未经统一对象初始化约定，就读取任意对象的未初始化字段当作安全检查。

### A1-08 资源隔离与退出约定

**等级：机制已确认；全系统并发安全尚未证明。**

- [板级管理](../main/board/audio_board.c)：233–239 比较 generation/token/channels；369–401 校验租约并拒绝不匹配释放。
- 同文件 195–204 在最后一个引用仍有租约时拒绝销毁，避免直接拆掉仍在使用的通道。
- `mic_input.c:127–177` 还有全局 owner 类型互斥。
- `mic_input.c:1093–1154` 释放租约、板级引用及软件缓冲；租约异常时存在受控重启兜底。

板级租约不等于对象级 read/deinit 并发保护。麦克风对象读取和释放仍要求调用方正确停止、回收采集任务。本轮未证明存在实际并发释放，也没有完成所有调用方的退出时序验证，此项需第 8 部分继续。

### A1-09 原始统计混合了处理阶段

**等级：确定的可观测性语义问题，不是数据损坏证明。**

`mic_input.c:641–651`：
- first/last 来自原始 TDM；
- mean 来自软件增益处理后、去直流前；
- 当前 DC 开启时，min/max 来自去直流并饱和之后。

软件增益目前为 1，不消除去直流前后统计口径差异。后续宜明确 raw/processed 字段语义，并检查消费者再改名或调整行为。它可能误导诊断，但不能直接推断识别或录音已经异常。

### A1-10 ES7210 增益顺序和注释

**等级：顺序有源码依据；注释中的部分解释需修正。**

- 板级驱动 806–818 在 enable 后设置增益；841–852 在时钟就绪后的重启后再次设置。
- 依赖驱动 `es7210.c:306` 的 start 调用 mic_select；199–223 的选通分支写增益位，值来自 `codec->gain`。
- 依赖驱动 495–505 的 set_gain 检查 is_open，之后写通道增益。
- 依赖驱动 379–402 的 enable 也要求 is_open；它控制 enabled 状态，不是把 is_open 从 false 改为 true 的入口。

因此，板级注释“enable 前 is_open 为 false，故不能设置增益”不能作为当前驱动的普遍解释。正确保留理由是**启动会重写增益寄存器，需要按当前驱动行为恢复目标值**。当前顺序无需据此修改；注释准确性可在统一优化阶段处理。

## 5. 统一优化前的验证清单

本轮未执行以下测试，仅记录后续验收条件：

1. 用可识别采样序列验证 240/320 点拼接，覆盖队列剩余空间 2、1、0 和真实溢出；同时核对输出样本与溢出计数，不能只检查返回码。

5. 同一输入采用不同读取分块，对比波形、低频和语音效果；待第 2 部分统一处理方案。

第一部分不支持“提高采样率、减槽、加增益、扩大 DMA 即能提高补传速度”的结论。优化应在八部分的约束和证据汇总后实施。
