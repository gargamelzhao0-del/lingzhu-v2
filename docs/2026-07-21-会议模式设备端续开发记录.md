# 会议模式设备端续开发记录

更新时间：2026-07-21

适用工程：`Nuwax AI Partner 7.0/NuwaxAIPartner`

## 1. 本轮边界

本轮只继续正式 7.0 工程的会议模式设备端开发，没有把以下新版硬件测试工程的代码合并回来：

- `NuwaxAIPartner测试工程`
- `NuwaxAIPartner_test_ascii`
- `NuwaxAIPartner_test_build`

正式设备仍为 COM8；新版硬件验证设备仍为 COM5。本轮只构建，没有烧录任何端口。

## 2. 当前会议模式目标

1. UI 或云端均可请求开启、关闭会议模式。
2. 进入会议模式前，对正在播放的普通对话执行约 200 ms 淡出并取消后续旧音频。
3. 会议期间独占麦克风，连续上传每一个有效音频帧；VAD 只提供元数据，不删除静音或弱声帧。
4. 音频只做保守处理：去直流、能量分类和有界弱人声增益，不做普通对话链路中的强抑制。
5. 连续 30 分钟确认环境安静且无人声后，设备自动退出会议模式。
6. 断网、启动失败和关闭完成后，设备必须回到可再次开启的干净状态。

## 3. 本轮修复

### 3.1 控制消息不再被静默丢弃

此前 UI 开启批准消息和云端主动命令共用深度为 8 的队列。队列满时，WebSocket 回调仍返回“消息已消费”，但命令实际上没有进入状态机，云端也收不到 ACK。

现在控制面分为两条路径：

- `audio_mode_request_ack` 使用独立的单槽覆盖邮箱。设备同时只允许一个 UI 开启请求在途，因此最新批准消息不会被普通命令队列挤掉。
- `device_command/set_audio_mode` 仍进入有序命令队列。队列饱和时，设备立即返回 `ok:false`、`message:"control_queue_full"`，不会假装已接受命令。

WebSocket 接收回调只在异常过载路径直接发送失败 ACK；正常命令仍由应用任务按顺序处理。

### 3.2 会话瞬态状态统一清理

新增统一清理逻辑，覆盖以下路径：

- 云端拒绝 UI 开启请求。
- UI 开启请求发送失败。
- UI 开启等待超时。
- 麦克风、上行或 listen 启动失败。
- 正常关闭或 30 分钟安静超时。
- WebSocket 断开。

清理内容包括云端授权、待回 ACK、待关闭请求、打断标志、启动截止时间、音频会话 ID、停止原因、静音计时、采集/上传/丢帧计数、连续读超时和会议处理器内部历史。请求序号、回调、队列句柄和初始化状态不会被破坏。

### 3.3 开启/关闭 ACK 与真实状态一致

云端主动开启只有在以下条件全部满足后才回复 `ok:true + state:enabled`：

1. 旧播放完成淡出或等待结束。
2. `listen start` 已发送。
3. 会议专属麦克风初始化成功。
4. 上行队列初始化成功。
5. 状态机已经进入 `ACTIVE`。

如果开启尚未进入 `ACTIVE` 就被 UI 或云端关闭，设备不再错误回复“开启成功”，而是回复 `ok:false` 和 `start_cancelled` 或 `superseded_by_disable`。云端关闭命令只有在剩余音频完成入队、上行结束和麦克风释放后才回复关闭成功。

### 3.4 断线恢复完整化

断线处理现在同时清空命令队列和 UI 批准邮箱，并复位所有会议会话字段及处理器历史。重新连接后不会继承上一场会议的静音时间、请求 ID、停止原因、增益或噪声底估计。

## 4. 协议保持不变

本轮没有新增 `revision`、`base_revision`、`audio_mode_state` 或新的 listen ACK 契约。仍使用已约定的简单消息：

- 设备请求：`audio_mode_request`
- 云端批准：`audio_mode_request_ack`
- 云端命令：`device_command + set_audio_mode`
- 设备命令结果：`device_command_ack`

因此云端工程师现有的四类开启/关闭 JSON 不需要因为本轮代码修复而改字段。

## 5. 音频链路当前真实能力

会议模式当前链路为：

`I2S 麦克风 slot0 -> DC 去除 -> 能量/人声分类 -> 有界弱声增益 -> PCM16 上行`

当前配置为 16 kHz、单声道、16 ms/帧、PCM16。处理器不会因为低能量、静音或 VAD=false 删除帧。最后一帧由单帧延迟缓冲补上 END 标志，关闭时不会故意遗漏尾帧。

当前处理不是独立会议 AEC，也不是频带降噪。它满足“全量、保守上传”的框架要求，但会议环境中的风噪、稳态噪声、混响和设备播报残留质量仍需真机数据验证后再决定是否加入独立的轻量降噪模块。

## 7. 长时间上行失败及修复

### 7.1 首次 30 分钟测试失败证据

首次测试于 2026-07-21 16:51:49 由云端命令开启。设备没有等到 30 分钟静音退出，而是在 541.312 秒时提前结束：

- 已接收 33,832 帧，序号为 `0..33831`，聚合序号连续。
- 会话关闭原因是 `uplink_finish_failed`，不是 `quiet_timeout`。
- 最后一帧没有 END 标志，`end_frame_received=false`。
- WebSocket 设备会话前后未切换，普通 ping/pong 仍正常。
- ASR 增量为 0，说明会议音频隔离逻辑没有失效。

代码级根因是 PCM 上行队列只能缓冲约 2.048 秒：32 个槽，每槽 4 帧，每帧 16 ms。一次持续时间超过该裕量的发送背压会让生产端在 80 ms 等待后直接返回失败。旧实现还存在两个放大问题：

1. PCM 队列按每帧 960 个样本的理论上限分配，但当前实际帧只有 256 个样本，大量 PSRAM 容量没有转化为缓冲时长。
2. 入队失败后批次仍在本地缓冲，收尾路径却不能先重放该批次再追加真正的 END 帧；最终空槽只等待 180 ms，并且后续 `finish_failed` 会覆盖最早的入队失败原因。

### 7.2 修复内容

- PCM 构建按当前固定格式计算真实容量：每帧 `22 + 256 * 2 = 534` bytes，每个四帧批次 2,136 bytes。
- PCM 队列由 32 槽扩展为 128 槽，缓冲时长由 2.048 秒提升为 8.192 秒。
- 新 PCM 池为 273,408 bytes；旧池为 248,576 bytes，PSRAM 只增加约 24.3 KiB。
- Opus 仍保持 32 槽，避免在低码率路径无必要占用约 1 MiB PSRAM。
- 队列失败时保留尚未发送的批次；最终调用可先重放该批次，再构建携带 END 的真实末帧。
- 最终空槽等待由 180 ms 提升为 5,000 ms。
- 会议结束日志新增 queued、sent、dropped、queue_full、max_ready、ready 和 finish 结果。
- 收尾阶段不再用二次失败覆盖最早的根因。

## 10. 2026-07-22 连续静默退出边界修复

本节以当前生产代码和本轮测试结果为准；第 8、9 节中的“监控模式尚未开发”等历史状态已经过时。

### 10.1 问题与修复

旧逻辑要求人声连续 640 ms 或环境声连续 2000 ms 后才清零不活动计时。因此，人声或环境声恰好在 30 分钟阈值前出现时，`inactive_ms` 仍可能先到阈值并错误触发 `quiet_timeout`。

当前逻辑改为：

- 只有有效且判定为安静的帧才增加连续安静时间。
- 当前帧一旦判定为人声或非安静环境声，立即把连续安静时间清零。
- 麦克风采集无效帧既不增加也不清零连续安静时间。
- 人声和非安静环境声仍只作为分类元数据；所有成功读取的 PCM 帧继续上传，不丢弃、不置零。

该策略是保守自动退出策略：持续有环境声的房间不会自动退出，符合“无人声且周围无声音连续 30 分钟才退出”的需求。

### 10.2 当前音频处理能力边界

- 人声判别已进入实际采集路径，使用自适应噪声底、平均绝对幅值、峰值和 8 帧保持进行能量分类；它不是神经网络 VAD，不能保证把所有环境声与真人语音精确区分。
- 弱人声增益已实际写回待上传 PCM。默认目标为 `34816 / 32768 = 1.0625`，约 `+0.54 dB`；代码硬上限约 `+1.58 dB`，但当前默认目标不会达到该上限。
- 当前简单过滤只消除直流偏置和极低频漂移，不具备风扇、空调、混响或宽带稳态噪声抑制能力。
- 未直接复用正常对话的 `audio_cleaner`，因为该模块还包含静音衰减、脉冲抑制和播放回声策略，直接复用可能改变会议模式应完整保留的音频。

### 11.3 人声判别与弱声增益判断

网关当前只保存最终 PCM，没有把每帧 VAD 标志累计进元数据。因此无法从该 WAV 精确恢复设备处理前的判别结果。使用相同能量阈值在处理后 PCM 上近似重跑得到：

- 估算人声帧 8,486，占 18.174%。
- 估算人声活动被分为 561 段，最长连续段约 1.44 秒。
- 估算安静帧占 67.575%。
- 估算人声帧 RMS 中位数约 `-39.63 dBFS`。

这证明录音中存在大量可被当前能量判别捕获的活动，但也显示分类较碎片化。当前判别器是平均幅值、峰值、自适应噪声底和 8 帧保持，不是真人语音模型；不能仅凭本轮数据宣称人声识别准确率已经验收。弱声增益代码和合成信号测试均已证明生效，但因为没有同时保存处理前 PCM，本轮 WAV 无法直接测出真人语音的实际增益差值。

### 11.4 环境过滤判断

- 全文件样本均值仅 0.162；每秒直流均值绝对值最大约 3.682，证明直流偏置去除有效。
- 安静 1 秒窗口最低约 `-55.279 dBFS`，环境底噪没有被置零或大幅衰减。
- 安静区 20–200 Hz 能量约占 38%，主要窄带峰值包括约 20、37、50、86 和 100 Hz；低频环境噪声仍明显保留。
- 当前会议处理器不是宽带降噪器，对风扇、空调、房间混响等环境音没有完成产品级过滤。

因此，本轮结论为：持续采集、手动启停、全帧上行、文件保存和无断音已经通过真人长时测试；人声判别与弱声增益链路已工作但尚未完成真实准确率/听感验收；环境噪声过滤仅完成直流与极低频处理，宽带环境降噪尚未完成。
