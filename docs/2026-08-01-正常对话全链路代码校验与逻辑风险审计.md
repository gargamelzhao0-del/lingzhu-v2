## 3. 当前配置事实

| 项目 | 当前值 | 直接含义 |
|---|---:|---|
| 音频格式 | PCM16、16 kHz、单声道 | 每 20 ms 为 320 samples、640 B PCM |
| 实时采集队列深度 | 16 | 采集缓冲名义约 320 ms；打断控制器最大决策年龄仍为 100 ms |
| 实时上行队列 | 12 个 packet slot | 低压通常每 slot 1 帧，压力下自适应为 2/4 帧；不能等同“固定 12 帧/240 ms” |
| 上行最大实时年龄 | 120 ms | 超龄帧不能继续作为实时音频发送 |
| 扬声器队列深度 | 128 | 请求量约 249,940 B；按常用 320 samples 为 2.56 s，按允许上限 960 samples 可达 7.68 s |
| 扬声器背压超时 | 80 ms | RX 回调对每个内嵌音频 packet 最多等待该预算；一个 WebSocket batch 会累计 |
| 单次 I2S 写超时 | 1000 ms | 输出故障时物理停播响应上界会受其影响 |
| Vocat shared-TX DMA | 6 × 240 stereo frames | 16 kHz 下总容量约 90 ms；当前 stop 仅 preload/等待各 20 ms |
| 软件 reference | 启用，2000 ms | 默认产品对话的实际 AEC 参考来源 |
| 固定 reference delay | 840 samples | 52.5 ms；未启用 shadow delay |
| AEC 后端 | AFE、VC、LOW_COST | `afe_aec_create("MR", ...)`，双通道输入为 mic+reference |
| 自适应 reference | 关闭 | 不会自动随现场路径改变 reference 延迟/幅度模型 |
| Human rescue | 开启 | 基础 rescue 路径存在，但 FIR rescue 关闭 |
| 硬件 MIC3 reference | 配置允许但受健康门控制 | 普通产品启动默认不通过该门，实际回退软件 reference |
| 本地 VAD | 开启 | 最短语音 180 ms、尾静音 450 ms、无语音 1200 ms |
| awake 空闲超时 | 120000 ms | 只应统计等待用户讲话的时间 |
| auto-followup 窗口 | 60000 ms | 单次窗口，不等于 awake 的 120 秒总预算 |
| turn 超时 | text 30 s / TTS 15 s / playback 45 s / drain 10 s | 用于失效云端轮次和缺失的播放结束 |

补充边界：上行 120 ms 从首帧进入 `audio_uplink` staging 时开始计算，不覆盖 MIC 采集和前级 DSP；实时采集的 16 slot 是 320 ms 突发容量，100 ms 才是入 DSP 前年龄门。当前 Kconfig 把 12 个 packet slot 描述成 12 帧，正文已按实现纠正。

配置证据：`sdkconfig:1045-1050, 1060-1143, 1193-1250, 1327-1333, 1401-1416`，`main/conversation/audio_uplink.h:15-45, 195-220`，`main/conversation/audio_uplink.c:396-406, 712-715`。

## 4. 正常对话状态模型

当前状态不是单一枚举，而是三层共同约束：

1. `conversation_state`：UI/产品状态 `SLEEPING/IDLE/LISTENING/PROCESSING/SPEAKING`。
2. `awake_session_state`：持续对话 generation、是否等待用户、120 秒剩余预算。
3. `turn_guard`：单轮请求 epoch、request/turn/playback ID、speaker generation 和阶段 deadline。

正常时序如下：

```text
唤醒
  -> awake session 激活并暂停空闲计时
  -> listen start + 持续 PCM 上行
  -> 本地检测到人声，保持持续上行并暂停空闲计时
  -> 云端 ASR result，turn_guard 进入 WAIT_TEXT
  -> TEXT response / TTS metadata
  -> 二进制 START 等待 metadata 授权
  -> speaker generation 获准，进入 PLAYING
  -> TTS 二进制 PCM 写入 I2S
  -> END + playback_end，进入 DRAINING
  -> 扬声器实际完成，清理 turn_guard
  -> 重新开始完整 120 秒等待预算并继续监听
```

核心代码：

- `main/conversation/conversation_state.c:3-45`
- `main/conversation/awake_session_state.c:14-115`
- `main/conversation/turn_guard.c:55-194`
- `main/nuwax_ai_partner_main.c:930-1277, 12361-12635`

## 5. 功能逐项校验

### 5.1 唤醒、持续对话和两分钟休眠

状态：`代码闭环，待实机`。

- `awake_session_state` 只有在 `active && waiting` 时才判定超时；暂停、恢复、剩余时间和 32 位 tick 回绕比较正确。
- 用户语音被确认后暂停 120 秒计时；识别、思考、TTS、播放期间不应消耗等待预算。
- 自然播放完成后重新给予完整 120 秒，而不是沿用播报前已经消耗的剩余时间。
- 普通持续模式的本地 VAD 句尾只重置本地检测状态，不结束长连接上行；下一句话可以继续进入同一醒着会话。
- 当前源码在 WebSocket 断线时调用 `preserve_awake_session_for_ws_reconnect()`，设置 30 秒宽限；重连后按剩余预算恢复，过期才休眠，见 `main/nuwax_ai_partner_main.c:1171-1202, 14723-14730, 14832-14858, 14929-14939`。

旧日志中的 `clear reason=ws_disconnect -> boot_ready sleep` 对应旧固件，不能再作为当前源码漏洞结论。当前仍必须通过实机验证断线发生在 LISTENING、WAIT_TEXT、PLAYING 三个阶段时是否均能恢复到正确状态。

### 5.2 麦克风采集、VAD 和实时上行

状态：`正常路径代码闭环，异常路径未完全闭环`。

- 采集任务与上行任务分离；采集队列深度 16，上行 pool/队列为 12 个 packet slot。低延迟模式首包/稳态通常一帧，压力下单 packet 会聚合 2/4 帧。
- 每帧 20 ms；采集元数据保留 capture sequence、时间戳、reference generation、播放快照和音频可信度。
- 普通持续监听中，本地 VAD 用于确认讲话、暂停空闲计时及标记句界，不直接截断持续上行。
- 正常结束顺序为：停止采集任务 -> `audio_uplink_finish()` 发送 END -> 等发送任务退出 -> 发送 JSON `listen stop`。
- 实时上行普通路径能识别 `ESP_ERR_NOT_FINISHED` 为有界背压边界，停止接收新帧并通过 `finish()` 排空 retained batch。

异常漏洞：连续 30 次 MIC timeout 后代码直接 `break`，未将返回值设置为 `ESP_ERR_TIMEOUT`。若此前已有音频，整轮可能按成功结束并进入 THINKING；物理停播的 2 秒确认也只在收到新 capture frame 时推进，因此 MIC 卡住可拖到约 15 秒。证据：`main/nuwax_ai_partner_main.c:8660-8675`。

### 5.3 预监听与首音节缓存

状态：`设计存在，完整性未闭环`。

- 预录环共 256 帧，约 5.12 秒；每帧保存 mic、AEC 输出、reference、human rescue source 和控制元数据。
- 打断目标窗口要求 onset 到 confirmed 连续，并要求 onset 未被静音，方向上能避免把完全不可信的音频提交云端。
- 96 ms post-stop guard 按 20 ms 帧向上覆盖 5 帧；guard 内会 repair/sanitize，失败时用等时静音保持时间轴。

但当前存在三条破坏完整性的路径：

1. TTS 从持续采集切换到 during-playback 采集时，先丢弃当前帧、停旧 capture、finish 上行并执行同步 cleanup，直到 cleanup 末尾才启动新采集。代码结构形成采集盲区，见 `main/nuwax_ai_partner_main.c:2344, 11553-11563, 11642-11668, 12179-12180`。旧固件日志中 handoff 约在 91274 ms、TTS 已于 91354 ms 到达，而新 during-playback capture 到 92114 ms 才启动，实测旧路径约 840 ms；当前源码仍保留相同的先停后启顺序，所以结构风险仍成立，但 0.6-0.9 秒的具体数值必须在当前新固件重测。
2. confirmed 之后若 capture sequence 出现缺口，targeted window 只保留缺口前缀；随后实时帧用新的连续 wire sequence 上传，云端无法知道中间丢音，见 `main/conversation/preroll_window.c:54-65` 及 `main/nuwax_ai_partner_main.c:7417-7607`。
3. 发送预录音遇到 `ESP_ERR_NOT_FINISHED` 会提前退出，主循环再通过 `finish()` 把最终结果恢复为 `ESP_OK`；retained batch 会发出，但剩余预录和用户后续讲话被截断，见 `main/nuwax_ai_partner_main.c:7587-7599, 11373-11390` 与 `main/conversation/audio_uplink.h:150-192`。

所以当前不能宣称“从第一个音节开始完整保留用户话语”。

### 5.4 软件 reference 与实时 AEC

状态：`软件 AEC 已实现，声学效果待实机；硬件参考默认未启用`。

实际处理链为：

```text
speaker PCM
  -> 2 秒 software-reference ring
  -> 按固定 840 samples 延迟读取
  -> 与 mic1/mic2 对齐
  -> afe_aec_create("MR", filter=4, type=VC, mode=LOW_COST)
  -> residual / near-end preserve / dual restore / human rescue
  -> cleaner / VAD / barge controller / uplink
```

代码证据：

- 后端和创建：`main/conversation/live_aec.c:300-324, 2432-2503, 3038-3073`。
- 软件 reference 读取：`main/nuwax_ai_partner_main.c:6283-6297`。
- 软件 reference 不是未经音量处理的原始 TTS：`speaker_output` 先按当前音量缩放 PCM，I2S 返回后只把实际写出的完整物理 stereo frame 写入 reference 环；短写也按真实 `bytes_written` 记录，见 `main/speaker_output.c:279-374`。因此 0%-100% 软件音量变化在参考幅度上已被覆盖。
- 当前配置：`sdkconfig:1062-1143`。

硬件 MIC3 参考只有同时满足 `CONFIG_NUWAX_VOCAT_SLOT2_AEC_REF_ENABLE`、`s_hw_ref_health_passed` 和实时电平门时才采用。普通产品启动不会运行 P2 smoke health check；P3 prototype 也关闭，因此 `s_hw_ref_health_passed` 默认保持 false，见 `main/nuwax_ai_partner_main.c:6276-6289, 14398-14531`。当前产品正常对话实际应为软件参考回退，不能写成“硬件 AEC 已生效”。即使未来 MIC3 健康门通过，它提供的也是硬件线路取得的播放参考，真正执行消除的仍是 ESP-SR 软件 `afe_aec`，不是独立硬件 AEC 运算器。

配置限制：shadow delay、自适应 reference、software/hardware A/B 和 human-rescue FIR 均关闭。固定 52.5 ms 延迟是否覆盖不同音量、DMA 排队、腔体和不同设备个体，只能通过相关性、ERLE、双讲保真和全音量实机矩阵证明。

另一个异常门控缺口是：software-reference 初始化失败目前只记录 warning，`speaker_output_init()` 仍返回成功并使上层打印 speaker ready。后续播放可以继续，但 AEC reference 会缺失，打断控制只能降级/fail-closed。不能用“扬声器 ready”推断“实时 AEC reference ready”。证据：`main/speaker_output.c:54-61, 93-130`。

### 5.5 播报期间人声判定和动态音量

状态：`控制逻辑闭环，识别效果待实机`。

`barge_in_controller` 并非只看能量阈值：

- 音量分为 0-5、6-30、31-75、76-100 四档。
- 音量 generation 变化会取消旧候选并重新武装；降低音量要经过 10 帧滞回。
- 最少 guard 4 帧、reference lock 3 帧；候选通常要求连续 2 或 3 帧。
- 76-100% 强制 strict policy；0-5% 只有可信的 silent-reference 才走低音量特殊路径。
- 模糊候选可触发 4 帧、15 dB probe duck，再根据音量变化前后的证据判断。
- AEC/reference 健康不满足时控制器 fail-closed，本地 level-only VAD 不能直接停播。

证据：`main/conversation/barge_in_controller.c:32-92, 281-340, 524-537`。

这说明代码考虑了动态音量，但不能由静态代码推出“0%-100% 音量绝不自打断，同时所有真人声音均可打断”。该结论必须用纯播放、轻声、正常声、远场、双讲及音量动态变化实测。

### 5.6 安全打断与重叠段处理

状态：`协议骨架闭环，音频完整性未闭环`。

理想路径为：

```text
人声候选
  -> 人声确认
  -> generation-bound 物理停播
  -> 校验 onset..confirmed 连续且可信
  -> candidate / confirmed / listen start 原子语义提交
  -> 96 ms 重叠段 repair + sanitize
  -> 上传预录音并继续实时采集
```

已有保护：

- 未通过 AEC/reference 健康门时不会仅凭音量停播。
- candidate -> confirmed -> listen start 提交成功后才启动新的音频 uplink。
- generation-bound stop、失败和超时均参与软件事务判断。
- onset 到 confirmed 必须连续且 onset 不可被静音。
- capture/uplink 任务无法安全停止时会重启，避免释放仍被任务访问的内存。

未闭环点：

- 当前 Vocat 使用 shared-TX，`speaker_output_stop()` 不控制独立 PA，而是 disable TX、只 preload 20 ms 静音、重新 enable 后等待 20 ms即返回。实际 DMA 为 6 × 240 stereo frames，即 90 ms；IDF disable 只复位指针/队列，不清除 descriptor 内容，preload 只覆盖传入的 320 frames。第一圈约 20 ms 静音之后，剩余约 70 ms descriptor 仍可能重放旧 PCM；`auto_clear_after_cb` 只会在 descriptor 播放完成后清零。板级 `flush_tx_with_silence()` 自己使用 6 × 320 sample 零帧并等待 120 ms 来覆盖同一 DMA，反向证明当前 20 ms stop 不足。`completed_stop_timestamp` 在 stop 返回后立即登记，所以软件会把尚未真正静音的时刻当作物理停播完成。更严重的是，software reference 只写入 20 ms preload 静音，不包含可能重放的旧 PCM 尾巴，AEC 会看到“参考为静音、空气中仍有设备声”。证据：`main/speaker_output.c:31-32, 397-507`、`main/conversation/speaker_playback.c:1719-1748`、`main/board/vocat_audio_board.c:332-337, 1064-1082`、ESP-IDF `components/esp_driver_i2s/i2s_common.c:654-685, 1240-1328`。残留声音强度需实机测量，但“代码不能保证 stop 返回时已静音”是确定结论。
- `speaker_output_write_pcm16()` 在整个 I2S write 期间持有 output mutex；单个 960-sample 包可跨 4 个 240-frame descriptor，而 IDF 对每次 descriptor queue wait 都使用 1000 ms timeout。stop 只等 output mutex 250 ms，所以 TX 异常时可能数秒拿不到 stop 所有权；shared-TX 又没有 PA mute 兜底。静音分配/preload 失败时函数仍会重新 enable TX，虽向上返回错误，但不能保证设备已经静音。该路径与上一项共同归入 R-06。
- 96 ms guard 结束后，如果 barge dispatcher 仍在 pending/listen-sending，后续帧仅写入预录环，绕过 `repair_auto_followup_human_preroll()` 和 `sanitize_barge_overlap_preroll()`；最终验证也不逐帧检查 confirmed 后的 `audio_trust`。AEC hangover 为 700 ms，因此这些帧仍可能包含播放残声。证据：`main/nuwax_ai_partner_main.c:170-174, 10781-10879, 11245-11275, 7417-7507`。
- dispatcher 的提交 deadline 为 1 秒，但单次 WebSocket 文本发送允许等待生命周期锁最多 5 秒，取得锁后 I/O 预算又可达 4 秒。candidate 和 confirmed 在 deadline 检查前发送；随后失败可能没有匹配的 listen start，主循环对 `FAILED` 也没有完整补偿。证据：`main/conversation/barge_in_dispatcher.c:19, 140-180`、`main/ws_transport.c:42-47, 693-754` 与 `main/nuwax_ai_partner_main.c:11288-11297`。

因此当前“能检测并尝试停播”不等于“可靠打断并完整上传”。

### 5.7 下行音频准入、播放与完成

状态：`正常路径代码闭环，协议异常防御不完整`。

已有闭环：

- WebSocket 二进制帧只有在 normal downlink admission 打开且 epoch 未变化时才能进入扬声器。
- 支持一个 WebSocket batch 内多帧；逐帧校验 codec、PCM16、16 kHz、单声道和最大 sample count。
- 二进制 START 先建立 submitted generation，再等待 JSON turn/playback metadata 授权；2 秒未获授权会拒绝播放并使连接失效。
- 扬声器队列满时最多等待 80 ms；超时使 owner 标记状态不确定并关闭连接。
- I2S 写入失败会产生 playback fault、按 generation 停止播放并关闭不确定的云端轮次。
- END 后产生 playback done；云端 playback_end 后最多 drain 10 秒，整个播放最多 45 秒，缺失结束不会永久卡住。

证据：`main/nuwax_ai_partner_main.c:3654-3817, 2907-3267, 12515-12635`，`main/conversation/speaker_playback.c:1078-1231, 2654-2729, 2732-3140`。

仍有以下防御缺口：

1. WebSocket 只有一个 RX task，且每个入站 frame 都 `malloc(payload_size + 1)`；binary callback 在该任务内同步执行，`on_ws_binary()` 再逐份同步入 speaker queue。当前 WebSocket 上限 16 KB，按 22 B header + 640 B 的 20 ms PCM 帧可容纳约 24 帧，即约 480 ms 音频。队满时每份最多等待 80 ms，所以一个批次可累计阻塞数百毫秒，其间同一连接上的 JSON、stop、ping 和 pong 均不能处理。单份 80 ms 是上界，但整个 binary batch 没有统一回调总预算。证据：`main/ws_transport.c:42-49, 943-987`、`main/nuwax_ai_partner_main.c:3700-3801`、`main/conversation/speaker_playback.c:1108-1231`。
2. speaker 路径没有维护 expected sequence，重复、跳号和乱序 PCM 会按到达顺序播放；`playback_begin` 给出的 expected frames/bytes 也没有参与 END 完整性校验。WebSocket 本身有序，但云端封包错误或上层丢帧不会被设备识别。
3. active playback 队列暂时空时，speaker task 会按上一帧长度持续写静音；若 END 丢失，会一直写到 45 秒/10 秒阶段超时再取消并重连。这是有界恢复，不是永久死锁，但用户会看到过长静默和连接重建。
4. PLAYING 的 45 秒 deadline 不随收到有效 PCM 刷新，合法的长 TTS 也会在 45 秒被取消；DRAINING 固定 10 秒同样不感知真实播放进度。
5. `last_frame_samples` 只在 START 设置。若后续帧长度变化，队列暂空时的等待节奏和 gap silence 长度仍沿用首帧。
6. 不支持 codec 或错误格式的 START 只被跳过/返回，未立即使 turn 失败，通常要等待 15/45 秒阶段 timeout。

### 5.8 上下行响应时间

状态：`结构上已异步化，当前不能给出真实延迟结论`。

上行关键阶段：

```text
I2S DMA read -> capture task -> 16 槽 ready queue
-> AEC/cleaner/VAD -> 12 槽 uplink queue
-> audio uplink task -> WebSocket binary send
```

下行关键阶段：

```text
WebSocket RX -> frame parse/copy -> 128 槽 speaker queue
-> metadata start gate -> speaker task -> I2S write
```

有利点：采集、上行和播放均有独立任务；下行首帧已有 handler-to-enqueue、enqueue-to-I2S 和 I2S write 耗时日志。

限制：

- WebSocket RX 在 speaker 背压时每份音频可同步等待最多 80 ms；多帧 binary batch 会累计该等待并同时延迟该连接上的其他事件处理。
- 20 ms capture 帧经过 AEC/cleaner/VAD 后才能入上行；必须实测 DSP p95/p99 是否低于实时预算。
- 旧日志曾出现 DSP p95 约 22.5 ms 和 capture gap，但旧固件队列为 12，不能据此判断当前深度 16 已通过或仍失败。
- TTS handoff 的 0.6-0.9 秒盲区是当前结构问题，不属于网络延迟。

### 5.9 云端事件、断线和阶段超时

状态：`多数闭环，仍有两个确定的错误契约`。

- turn_guard 会绑定 awake generation、request/turn/playback ID 和 speaker generation，过时事件不能直接接管新轮次。
- WAIT_TEXT、WAIT_TTS、PLAYING、DRAINING 分别有 30 s、15 s、45 s、10 s 上限；超时会取消播放/采集并重连，使不确定事务失效。
- 短时 WebSocket 重连会保留 awake 剩余预算，当前源码已修复旧行为。

问题一：采集循环另有 15 秒 cloud-progress watchdog，而 WAIT_TEXT 允许 30 秒。watchdog 只由 ASR partial/final/result 更新；ASR result 后若文本响应耗时 15-30 秒，设备可能先关闭 WebSocket。本地再次确认语音又会重置 watchdog，反而可能延迟发现真正的云端停滞。证据：`main/nuwax_ai_partner_main.c:133-138, 8073, 8165-8187, 10636-10649, 12361-12387`。

问题二：persistent listen 已发送 `listen start` 后，若 AEC alignment 或 capture 初始化失败，cleanup 先发 `listen stop`，随后 destroy uplink 才隐式 finish 二进制 END，形成 `listen stop -> binary END` 逆序。证据：`main/nuwax_ai_partner_main.c:8075-8127, 12086-12131` 与 `main/conversation/audio_uplink.c:946`。

### 5.10 并发、内存和任务栈

状态：`存在确定的逐轮泄漏；峰值可承受性待实机`。

通过当前 build 对象 DWARF 核实的 ESP32-S3 ABI 大块如下：

| 项目 | 已知请求量 | 生命周期 |
|---|---:|---|
| 256 帧预录环 | 709,632 B | 常驻 PSRAM，约 5.12 秒 |
| Software reference | 64,000 B | 常驻 PSRAM |
| Speaker queue | 249,940 B | 常驻 PSRAM |
| Speaker task stack | 6,144 B | 常驻 PSRAM |
| Barge dispatcher queue+stack | 8,276 B | 常驻 PSRAM |
| Live AEC 显式 PSRAM-first buffer | 7,680 B | 常驻池；另有 4,096 B internal-first |
| 每轮 capture | 64,104 B | 会话期 PSRAM |
| 每轮 AEC alignment | 13,664 B | 会话期 PSRAM |
| 每轮 uplink | 42,580 B | 会话期 PSRAM |
| 每轮 mic raw TDM | 7,680 B | 会话期 PSRAM |

已知常驻 PSRAM-first 请求约 1,046,204 B；一个正常对话活跃阶段再增加 128,028 B，合计约 1,174,232 B（1.120 MiB）。该值未包含 allocator header、碎片、AFE 闭源库、I2S DMA、TLS、LVGL、Wi-Fi 和其他任务，因此不能把 1.12 MiB 当成最终峰值。

任务栈：main 16,384 B，当前 `stream_microphone_audio()` 编译栈帧约 4,704 B；speaker 6,144 B（顶层栈帧约 2,144 B）；capture 6,144 B；uplink 10,240 B；barge dispatcher 6,144 B；WebSocket RX 12,288 B。代码没有记录运行时 high-water mark，静态尺寸不能证明深层调用下没有栈风险。

确定泄漏：capture 与 uplink 使用 `xQueueCreateWithCaps()` 创建队列，却用普通 `vQueueDelete()` 清理。ESP-IDF v6 的 `xQueueCreateWithCaps()` 分别分配 `StaticQueue_t` 和 storage，必须由 `vQueueDeleteWithCaps()` 释放。当前每个完整生命周期泄漏：

```text
capture 两队列：232 B + 4 个 heap block 开销
uplink 两队列：564 B + 4 个 heap block 开销
合计：796 B + 8 个 heap block 开销/轮
```

证据：`main/nuwax_ai_partner_main.c:872-889, 6165-6170, 6595-6600`，`main/conversation/audio_uplink.c:396-477, 974-978`，ESP-IDF `components/freertos/esp_additions/idf_additions.c:197-260`。

不能简单把所有 delete 无条件替换为 `vQueueDeleteWithCaps()`：创建辅助函数存在普通 `xQueueCreate()` fallback，修复时必须记录每个队列的实际创建类型，并调用匹配的删除 API。

Speaker queue 是应用全生命周期常驻，不产生逐轮泄漏；但它通过 `xQueueCreateWithCaps()` 创建后，如果随后 mutex 创建失败，当前异常清理使用普通 `vQueueDelete()`。该启动失败路径会遗漏约 249,940 B 的外部分配及堆块开销，见 `main/conversation/speaker_playback.c:1234-1272`。这与 R-05 的逐轮泄漏不同，列为 R-19。

## 7. 异常时序推演

### 7.1 自然完成

```text
持续上行 -> ASR -> TEXT/TTS -> START gate -> PCM playback
-> binary END -> playback_end -> DRAINING
-> speaker playback done -> turn clear -> auto-followup
-> 重新开始 120 秒 waiting
```

结论：正常路径闭环。

### 7.2 用户在播报刚开始时讲话

```text
TTS 到达 -> 请求 handoff
-> 旧 capture 当前帧被丢弃并退出
-> stop capture -> finish uplink -> cleanup/log/deinit
-> TTS 已可能开始 I2S 播放
-> cleanup 末尾才启动 during-playback capture
```

结论：R-01 使用户在该窗口内的讲话无法完整保留，甚至无法形成候选。

### 7.3 用户成功触发候选与确认

```text
candidate -> confirmed -> 请求物理停播
-> 校验 onset..confirmed -> dispatcher 提交
-> 96 ms post-stop guard -> 预录上传 -> 实时上传
```

结论：骨架成立，但 R-02/R-03/R-04/R-06/R-11 可分别造成截断、静默缺段、旧 DMA 残声、清理绕过或协议半提交。

### 7.4 WebSocket 短时断线

```text
断线 -> 清理旧 transport/turn/audio session
-> preserve awake remaining + 30 s grace
-> 重连并 hello 成功
-> grace 内恢复 waiting；过期才 sleep
```

结论：当前源码已闭环，必须实机覆盖断线发生在不同阶段的 race。

### 7.5 MIC 卡死

```text
连续 500 ms read timeout × 30
-> 约 15 s 后 break
-> result 仍可能为 ESP_OK
-> finish/stop/THINKING 或等待云端恢复
```

结论：R-10，错误语义不闭环。

### 7.6 下行丢 END

```text
START/PCM 已播放 -> speaker queue 空
-> 周期性写 gap silence
-> 等待 playback 45 s 或 drain 10 s deadline
-> cancel generation + reconnect
```

结论：最终可恢复，但异常静默时间过长且下行序号不可诊断。

| 上行弱网 | 人为制造队列背压和 120 ms 超龄 | 无静默截断；协议明确失败或完整 finish，不得“成功但少音频” |
| 下行异常 | 多帧 burst、重复、跳号、乱序、缺 END、错误格式、>45 s 合法流 | RX callback 有总预算；设备拒绝或明确使轮次失效；长流按进度续期 |
| 硬件故障 | MIC timeout、I2S write timeout、内存分配失败 | 返回正确错误、END/stop 顺序正确、状态可恢复或明确重启 |
| 长稳 | 至少 1000 次 capture/uplink 生命周期 | free/largest PSRAM 无线性下降，heap block 数不持续增加 |
| 栈 | 所有音频任务压力测试 | 记录并审查 stack high-water，不发生 overflow 或极小余量 |

延迟需要拆分记录，而不是只记录“整轮感觉”：

1. capture DMA 完成 -> DSP 完成。
2. DSP 完成 -> uplink enqueue -> WebSocket send 完成。
3. binary callback 进入 -> speaker enqueue -> 首次 I2S begin/done。
4. 用户 onset -> confirmed -> stop requested -> physical stop completed。
5. onset -> 新 listen start -> 首个用户 PCM 实际发出。

## 9. 修复优先级建议

1. 先修 R-05 队列创建/删除所有权，建立 1000 轮内存基线。
2. 修 R-06 物理停播：shared-TX 必须在报告完成前可靠静音 PA/codec，或覆盖完整 DMA 环并等待最后旧 sample 离开；software reference 和完成时间戳必须对应真实输出。
3. 消除 R-01 handoff 盲区：播报期采集必须在旧持续采集释放前已有连续接管，或使用始终运行的原始采集环。
4. 统一 R-02/R-03/R-04 的预录完整性语义：保留 raw sequence，背压时不得返回伪成功，confirmed 后逐帧可信和连续性必须可证明。
5. 使 R-11 barge 协议事务的 deadline 与 WebSocket send 上界一致，并为半提交增加明确补偿/断线语义。
6. 修正 R-10 MIC timeout 和 R-08 listen stop/END 的错误顺序。
7. 拆开 R-07 WebSocket RX 解析与可阻塞 speaker enqueue，给整个 binary batch 建立总预算。
8. 增加 R-13 下行 expected sequence/expected totals、R-14 缺 END 的进度 watchdog，并修正 R-16/R-17/R-18。
9. 最后做 software-reference 健康门、延迟校准、MIC3 硬件参考 A/B 和全音量声学矩阵；声学优化不能掩盖前面的确定逻辑错误。

## 10. 最终审计结论

当前版本不是“所有功能已经正常”，也不是“正常对话完全不可用”。准确结论是：

- 普通对话 happy path、两分钟 waiting 计时、云端 turn 绑定、正常上下行和自然播放完成，在当前源码中基本闭环。
- 当前断线保留 awake session 的源码已经存在，旧日志所示问题不能继续当作当前根因。
- 软件实时 AEC 确实进入产品链路；MIC3 硬件参考在普通产品启动中默认没有通过健康门，不能宣称硬件 AEC 生效。
- 动态音量和 fail-closed 打断控制已实现，但当前存在采集盲区、shared-TX 假性停播完成、预录截断、confirmed 后静默缺段、post-stop 残声绕过等关键漏洞，因此“设备不自打断、用户可立即打断、完整保留首音节并消除重叠设备声”的最终目标尚未完成。
- 每轮至少 796 B 的 PSRAM 队列泄漏是确定问题；未修复前不能声明长期稳定。
- 本轮按用户约束没有构建和实机验证，所以所有“代码闭环”项仍需修复后通过编译、日志和声学矩阵转为“已验证”。

### 11.2 原文存在的纰漏或易误读点

1. “上行队列 12 帧/240 ms”不精确。实现是 12 个 packet slot；低延迟模式每个 packet 自适应承载 1/2/4 帧。120 ms 又是从 batch 进入 staging 开始计算的年龄，不是 MIC 到云端的端到端预算。
2. “采集 16 帧/100 ms”也必须拆开理解：16 slot 是 320 ms 突发容量，100 ms 是入 DSP 前年龄门，不是 16 帧等于 100 ms。
3. “可靠队列最多陈旧 10.24 s”不精确。10.24 s 是当前 PCM 配置可容纳的音频内容量；可靠 profile 没有年龄门，因此最旧 packet 的墙钟年龄并没有 10.24 s 上限。
4. 触摸 reset 的 5 ms 确实会折算成 0 tick，但当前 `CONFIG_NUWAX_TOUCH_PIN_RST=-1`，该 reset 分支未运行。当前运行期真正受影响的触摸路径是 `touch_input.c:324` 的 5 ms I2C retry backoff。
5. ES7210 stop/start 的显式 5 ms 同样退化为 0 tick且当前会执行，但本地 ES7210 简版资料没有规定这一最小间隔；只能证明“代码意图的等待失效”，不能冒充“已证明违反芯片 5 ms 规格”。
6. UI 底层对象无锁是架构风险，但现有调用点多数遵守 LVGL 外部锁，不能写成“已观测到并发数据竞争”。可以确定的是锁获取失败后没有重试，Wi-Fi、云、app state、电池更新会永久丢失。
7. 当前名为 `cloud_authenticated` 的布尔量实际混合 transport、service liveness 与身份认证；pong 或合法 device command 都能把它置真。不能把变量名当成认证证据。
8. BLE 生产 Security 2 salt/verifier 的读取分支已经存在；阻塞点是当前仍启用固定开发 PoP、仓内没有产线注入工具及 release profile，而不是“完全没有生产代码”。
9. “speaker queue 约 2.56 s”只对常用 320-sample packet 成立；协议当前允许单 packet 最多 960 samples，所以物理内存固定约 249,940 B，但可缓存的音频时长随帧长在约 2.56～7.68 s 之间变化。

## 12. 跨模块补充问题真实性

### C-01 会议模式停播失败后 fail-open

结论：`P1，确定问题`。

`meeting_mode.c:570-590` 最多等待 500 ms；超时后只告警，随后 `:593-603` 创建/使用 session 并发送 `listen start`，`:667-680` 还能进入 ACTIVE 并返回成功 ACK。监控在 `monitoring_mode.c:762-786` 已正确调用 `fail_capture_start(..., "playback_stop_failed")`。因此会议模式可能在 TTS 仍 pending 时宣告成功并录入设备声；若停播一直失败，污染不只限于首帧。

修复边界：必须在 `make_audio_session_id()`、`listen start`、MIC 和 uplink 初始化之前 fail-closed；负 ACK 应保留 `playback_stop_failed`，不能压缩为泛化的 `capture_failed`。但仅复制监控分支仍不够，`is_playback_active=false` 必须建立在 R-06 的真实物理静音语义上。

### C-02 唤醒 worker 的静态 TCB/栈生命周期与 init 回滚

结论：`任务退出竞态 P1；初始化回滚缺失 P2，均为确定问题`。

`wake_word_detector.c:342-351` 在 worker 仍使用旧栈、尚未 `vTaskDelete(NULL)` 时先写 `running=false/task=NULL`。`start():478-518` 可立即复用静态 TCB/栈，`deinit():560-582` 可立即释放。自删除任务还要等待 Idle task 做 kernel/TLS 清理，所以即使调用了 `vTaskDelete(NULL)`，静态存储也不能立即复用。`init():355-459` 的多处早退没有逆序释放 lock、models、MultiNet/WakeNet data 和 command 资源；再次 `memset` 会永久丢失指针。

正确所有权应为：

```text
STOPPED -> STARTING -> RUNNING -> STOP_REQUESTED -> EXITING
worker 清 MIC/样本 -> 发布 EXITED -> 自挂起
owner 确认任务已挂起 -> vTaskDelete(handle) -> 清 handle -> STOPPED
```

worker 不得清 task handle或自删除；`start()` 只接受 STOPPED；`deinit()` 只在 owner 完成 delete 后释放静态存储。init 全部错误统一进入一个 `goto fail` 逆序回滚路径。

### C-03 5 ms 延时退化为 0 tick

结论：`零 tick 事实确定；运行影响分路径，P2/潜在硬件时序项`。

当前 `CONFIG_FREERTOS_HZ=100`，`pdMS_TO_TICKS(5)==0`：

- `touch_input.c:164`：触摸 reset 低脉宽，但当前 RST=-1，未进入产品运行路径。
- `touch_input.c:324`：触摸 I2C 读失败后的 retry backoff，当前会运行，退化成立。
- `vocat_audio_board.c:545`：ES7210 stop/start 间隔，产品初始化会调用，等待退化成立；器件所需最小值缺少本地正式规格证据。

硬件脉宽或 codec 时序应在取得正式 datasheet/programming guide 后用 `esp_rom_delay_us()` 表达冻结值；普通 task retry 应使用向上取整且至少 1 tick 的 delay，避免 busy-wait。当前商家 CST816S 的 200/200 ms 实现只能作为参考先例，不能冒充本板 CST816T/CST816-family 的规格。

### C-04 会议/监控可靠队列的音频年龄与恢复语义

结论：`容量事实确定；模式策略是未冻结的产品/协议阻塞项`。

当前 PCM 可靠 profile 为 128 packet × 4 frame × 20 ms，即可容纳 10.24 s 音频内容；`nuwax_audio_uplink_send_budget_ms()` 对 reliable 返回无限年龄预算。会议和监控均使用 reliable profile。队列最终饱和时，两种模式都会显式失败/停流，并非在同一 session 静默丢帧；缺口在于“多旧必须终止”和“终止后如何恢复”没有契约。

- 监控若冻结为 latest-data：超过 oldest-audio age 后应中止旧 substream，报告 interrupted 原因，并以新 session 回到 ARMED；由于 END 也排在旧音频之后，必要时必须关闭旧 WebSocket，而不是企图在同一 FIFO 中插队。
- 会议若要求完整录音：必须二选一。其一，限制 1～2 s 后显式关闭/分段，以 timestamp/gap 元数据重新开流；其二，本地持久化并按时间戳可恢复上传。没有本地持久化时，不可能在任意长断网下同时保证“RAM 有界”和“会议音频完整”。

监控当前在 `monitoring_mode.c:962-968` 遇 enqueue 失败会 STOPPING，不会自动回到 ARMED；该恢复需增加 desired-state、重连和新 `audio_session_id` 语义。会议策略必须先由产品冻结，不能由设备端静默选择。

### C-05 UI 状态发布不完整

结论：`P2，确定丢更新；潜在线程安全契约风险`。

`app_shell.c:76-131, 271-315` 的 mailbox 只覆盖 dialog、meeting、monitoring、volume。云、Wi-Fi、app state 和电池仍直接抢 LVGL 锁，失败即 return，见 `app_shell.c:429-495` 和 `nuwax_ai_partner_main.c:578-596`。`nuwax_device_state.c:6-97` 是无锁全局并同步通知 listener，正确性依赖每个外部调用者都持 LVGL 锁。

应建立唯一 canonical state：生产者只提交字段 delta；在同一 mutex 内 merge、递增 revision，并用 `{revision, full_snapshot}` 覆盖单槽 latest-value mailbox。只有 UI task 能调用 `nuwax_device_state_set()`、listener 和 LVGL。不能由生产者先读旧快照再整包回写，否则会把其他任务的新字段覆盖掉。

### C-06 transport/service/auth 混用及 OTA 授权顺序

结论：`UI 状态 P2；身份/OTA 边界为 P1 条件安全问题`。

WebSocket 成功后，`nuwax_ai_partner_main.c:14827-14829` 未等业务响应就把云图标设为 connected。另一方面，`note_positive_cloud_activity():3281-3340` 把 hello OK、pong、device command 都视为 authenticated。更关键的是 `on_ws_text():3549-3567` 先用当前 device command 把认证置真，再把同一消息交给 OTA handler，因此 OTA 内部的 `auth_required` 不能独立证明这条命令此前已通过认证。

WebSocket 握手确实发送 `X-Bridge-Token`。如果正式云书面保证“只有校验设备 token/身份后才返回 101”，可以把 101 作为 transport-auth 证据；如果没有这个保证，当前就是实际授权缺口。无论哪种情况都必须拆为：

1. `transport_connected`：TCP/TLS/WebSocket 已建立。
2. `service_ready`：收到关联当前连接的有效业务响应。
3. `auth_state=unknown/verified/rejected`：仅由显式认证 ACK，或已冻结的 101 鉴权契约建立。

pong 只能建立 service-ready，不能自行提升身份；OTA/敏感控制必须检查处理当前命令之前已经成立的 verified 状态。UI 在 transport 后保持 CONNECTING，service-ready/auth 达标后才 CONNECTED，明确拒绝显示 AUTHFAIL。

### C-07 MCP 固定公布无效能力

结论：`P2，确定问题`。

`mcp_server.c:113-150` 固定公布 status、emotion、servo；主工程 `mcp_servo_head_shake():12307-12310` 恒返回 false，却仍注册 callback。结果只返回纯文本 true/error，也没有最终状态 revision。会议/监控还旁路普通 command dispatcher，当前不存在统一 command bus。

`tools/list` 应从真实 capability registry 和非空可用 callback 动态生成；立即移除 servo。云、MCP、UI 统一提交 typed command（source、request_id/idempotency key、command、args），由单 owner 串行处理音量、会议/监控互斥及状态提交。meeting/monitoring 应提供 typed internal request API，不能由 MCP 拼 JSON。异步模式切换返回 accepted + command_id，并提供最终 state/revision 回读，不能阻塞 WS RX。

### C-08 正常对话延迟预算漂移

结论：`确定的配置/测试契约缺陷；当前是否造成可见故障待实机`。

当前产品为：

- capture：16 个 20 ms slot（320 ms 容量），入 DSP 前最大年龄 100 ms；
- barge controller：处理后 frame age 上限也为 100 ms；
- uplink：12 个 packet slot，packet staging/send age 120 ms。

入 DSP 前允许接近 100 ms，而 controller 处理后总年龄也只允许 100 ms，给 AEC/DSP 留出的确定性预算为 0。`run-conversation-host-checks.ps1:311-321` 和 `run-v2-product-host-checks.ps1:195-202` 仍强制 capture 12/60；当前 defaults 为 16/100，静态推演会失败。上行 host check 又通过 stub/fallback 测 12/120，不读取真实产品生成配置，存在“host 通过、产品 contract 未测”的假象。

推荐先冻结候选基线：20 ms frame、capture 12 slot、pre-DSP age 60 ms、barge end-to-end age 100 ms、uplink 12 packet slot/120 ms。`60 ms + 40 ms DSP/调度预算 <= 100 ms` 才自洽；若实机频繁超限，应优化调度/DSP，而不是直接放宽到零余量。所有参数由一个 conversation latency contract 生成，Kconfig、defaults、产品 overlay、host stub 和 CI 不得各自复制。

### S-01 量产安全配置

结论：`量产 release blocker，不是当前会议/监控/对话功能故障`。

- `sdkconfig:803,805`：Secure Boot 和 Flash Encryption 未启用。
- `sdkconfig:4193`：NVS Encryption 未启用。
- `sdkconfig:1017-1019`：Security 2 dev mode 开启，固定 PoP 为 `Nuwax7-Dev-PoP`，开发 QR 还会包含它。
- `sdkconfig:1022-1023`：仍允许测试 `ws://`，且开启本地 USB provisioning control。
- 关闭 dev mode 后读取 `nuwax_factory/sec2_salt/sec2_verifier` 的生产分支已存在，但仓内没有产线写入/唯一性登记工具。

量产方案必须包含 per-device 至少 128-bit 随机 PoP、设备只保存 salt/verifier、受控标签或凭据服务交付 PoP、release artifact 扫描、WSS-only、USB integration control 关闭、NVS Encryption、Secure Boot V2、Flash Encryption release mode、签名 OTA、anti-rollback 和 eFuse 产线记录。不可在当前唯一样机上未经专门批准直接执行不可逆 eFuse 操作。

## 13. 全部问题、解决方案与验收矩阵

### 13.1 原正常对话 R-01～R-20

| ID | 代码级解决方案 | 最小验收 |

### 15.4 后续复核新增并修复的竞态

同一个 `nuwax_ws_client_t` 在 `app_main` 重连循环中长期复用，因此裸指针相等不能证明异步操作仍属于原连接。当前已落实的静态隔离如下：

- transport 在每次 connect attempt 推进单调 `connection_epoch`，文本、二进制发送和 close 均提供 `_if_epoch` 入口。
- `audio_uplink` 启动时冻结来源 epoch；worker 发送、失败关闭、finish 和 destroy 均按该 epoch 执行。
- barge item 同时冻结 binding generation 与 WebSocket epoch。dispatcher 在锁内比较并使旧 binding 失效，释放锁后调用 `nuwax_ws_request_close_if_epoch()`；并非“比较、解绑、关闭全在同一把锁内”。candidate、confirmed、listen start 和失败关闭均受原 epoch 约束。
- session protocol 已提供 listen、barge、cancel-turn、command ACK 的 epoch 版本。session command、P3/P5 异步请求在入队时保存 epoch，消费时拒绝旧代次；P5 的 listen、uplink、cancel 和 ACK 绑定同一来源连接。
- speaker packet 在 WebSocket RX 回调入口固化 `connection_epoch`；START 同时绑定 generation/epoch，后续 PCM、授权等待、I/O claim、progress、END、done、fault、state 和 cancel recovery 都使用该二元组。协议故障 pending、停播成功/失败、取消前旧 generation 也保存原 epoch。
- speaker owner event 不再在入队时读取 `active_ws_epoch_snapshot()` 补值；非 volume 事件缺少 epoch 会作为不变量错误被丢弃。停播 fault 的 stats 补发和 deferred START 失败同样携带原 epoch，旧回调只能关闭自己的连接代次。
- END physical stop 与 cancel 竞争时只发布一个终态；cancel 在 generation 自增前冻结旧 epoch，synthetic cancel generation 不继承任何活动连接。

普通 `nuwax_ws_request_close(ws)` 目前剩余调用均位于 `app_main` 同步 owner 调用链，当前不会越过重连边界；未来新增异步路径必须在事务入口冻结 epoch 并使用 `_if_epoch`。上述契约已加入 `run-conversation-host-checks.ps1`。

边界必须明确：epoch 只能拒绝陈旧操作，不证明消息送达、事务幂等、断线恢复或无缝重连。本轮也没有执行“旧 worker/旧 speaker callback 在新连接建立后到达”的确定性竞态注入；这些仍需实机或可控调度测试。
