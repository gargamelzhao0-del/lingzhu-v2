## 1. 根因结论（代码证据摘要）

| 问题 | 根因 | 关键证据 |
|---|---|---|
| 过渡期 25–31fps | 策略函数硬编码目标帧索引（`emotion_component_bridge_policy.h:132` SLEEPING=12/TOUCH=5/其它=0），与资产包内嵌 handoff 记录索引错位 → `decode_v4_handoff_frame`（player :2651）`ESP_ERR_NOT_FOUND` → :2687 `for` 循环逐帧重放 1..N（每帧 ~3ms）→ 24–36ms | 实测 `target_decode_us=24-36ms` vs idle 单帧 3.3ms（10 倍=重放帧数）；包 API `pack_v4_segment()->handoff_frame_index` 存在但未被查询 |
| flush 尖刺 7–10ms / 96ms 长尾 | NVS 写期间双核 cache 禁用，flash 执行任务全停；诊断 NVS 满 → `nvs_erase_all`+commit 压实（多页擦除 30–100ms）| `device_error_report.c:625-647` 压实路径；日志 `compacted after no-space` 多次出现（227s/823s）；快照持久化节流 5s |
| internal_min=51B | 固定内部驻留超订阅（WiFi ~42KB + LVGL 栈/缓冲 38KB + 显示 DMA 15KB + 音频）+ 碎片化（free 21KB 但 largest 7.7KB）+ ≤256B 小对象内部优先蚕食 | `sdkconfig:2263 SPIRAM_MALLOC_ALWAYSINTERNAL=256`；LVGL 栈实测峰值仅 ~4.9KB（`stack_hw=15552`/20480）——20KB 分配明显过大 |

## 2. 改动记录

### 改动 C1：过渡目标帧改用包内 handoff 索引

- **文件**：`main/nuwax_ui_v28/face/emotion_animation_player.c`（bridge 目标建立函数，原 :1488-1491）
- **改动前**：
  ```c
  nuwax_emotion_asset_v4_frame_t target_frame;
  const uint16_t target_frame_index =
      nuwax_emotion_component_handoff_frame(target_asset);
  const nuwax_emotion_asset_segment_t *segment =
      nuwax_emotion_asset_pack_segment(target_segment);
  ```
- **改动后**：先取 segment，再以 `nuwax_emotion_asset_pack_v4_segment(target_segment)->handoff_frame_index`（有效且 < frame_count 时）覆盖策略值；策略值保留为无 handoff 包的回退。快路径（:2651 的 handoff 记录查找）由此必然命中。
- **依据**：快路径命中条件 = 请求索引 == 包内记录索引；包内索引运行时可得（`emotion_asset_pack.c:397` 暴露）。
- **预期**：过渡 decode 24–36ms → 10–15ms（单绝对帧解码），过渡 fps 25–31 → 35+。

### 改动 A1：诊断 NVS 压实次数按启动封顶

- **文件**：`main/device_error_report.c`（:34 常量、:129 静态变量、:625-647 压实分支）
- **改动前**：每次 6KB blob 写撞 `ESP_ERR_NVS_NOT_ENOUGH_SPACE` 都执行 `nvs_erase_all`+`commit`+重试——压实频率随错误量无上界，每次 30–100ms 停摆。
- **改动后**：新增 `ERROR_REPORT_COMPACTION_MAX_PER_BOOT 2U` 与 `s_persist_compactions` 计数；达到上限后跳过压实、以 `ESP_ERR_NVS_NOT_ENOUGH_SPACE` 走既有退避/`storage_blocked` 机制（RAM 队列与云上报不受影响）。每次启动的压实停摆次数被硬性封顶。
- **依据**：压实 = 多页擦除 = 30–100ms 双核停摆；诊断快照是"可替换缓存"（原注释自证），丢弃持久化不损业务。

### 改动 B1：LVGL 任务栈 20KB → 12KB

- **文件**：`main/nuwax_lvgl_port.c:61`、`tools/run-v2-product-host-checks.ps1:765`
- **改动前**：`#define LVGL_TASK_STACK_SIZE (20 * 1024)`
- **改动后**：`#define LVGL_TASK_STACK_SIZE (12 * 1024)`
- **依据**：perf 遥测 `stack_hw=15552`（24 分钟含菜单/表情/keepalive）→ 峰值实际使用 ~4.9KB，12KB 仍留 2.5× 余量；512B 底部金丝雀 + 每 2s 校验 + <4KB 告警三重防护不变。**立省 8KB 内部 RAM**，为第二缓冲常驻恢复创造 largest≥14.4KB 条件。
- **风险注记**：历史遥测曾在旧 10KB 栈时代出现 40B 余量（代码注释 :1363-1366），当时的调用深度与现栈不可比；上机后需观察 `stack_hw` 与 lvgl_stack_low 告警，异常即回 16KB（中间档）。

### 3.1 设备实测第一轮（2026-09-17 17:44 日志，t=43.6s–1522s，含控制中心开合压测）

| 改动 | 状态 | 证据 |
|---|---|---|
| B1 栈 12KB | ✅ 生效且安全 | internal free 28,491→**35,723**（+7.2KB 兑现）；internal_min 51→**931**；`stack_hw=4976` → 栈峰值 **7.3KB**（无 lvgl_stack_low 告警） |
| C1 过渡快车道 | ⚠️ 未覆盖 | 全程无 `component bridge perf` 行——菜单开合期间表情 `paused=1`，无资产切换；需"唤醒→对话"专项测试 |
| A1 压实封顶 | ℹ️ 未触发 | 全程无 no-space/compaction 事件 |

**B1 重要修正**：栈峰值 7.3KB（含菜单/抽屉路径）高于 idle-only 遥测的 4.9KB——12KB 仍安全（余量 1.7×）但比预估薄；**守则：任何一次 `lvgl_stack_low` 告警即升档 16KB**。

**新发现（既有问题，非本轮回归）——控制中心 reveal 动画帧率不足**：
菜单压测（此前无 perf 基线）暴露 reveal 路径真实成本：backdrop 每帧合成 70–83K px，而 LVGL 软渲染吞吐 ≈0.3M px/s（idle 实测 9.5ms/2871px）→ 单帧 ≈230ms，对 40fps 目标 9 倍超支 → reveal 掉到 10–18fps（`fps=10.8 skipped_steps=26`）、handler 119–196ms 长尾。三项改动均不触及 drawer/compositor，flush 侧在风暴中按像素量线性扩展（avg 1.0–1.2ms、hz 116）无异常——**渲染像素量是物理瓶颈**。风暴后完全恢复（idle 39.4fps、无泄漏）。reveal 优化列为新专题：a) reveal 目标 fps 降至 24–30；b) backdrop 分带增量合成；c) reveal 帧预渲染序列缓存。

连带观察：菜单风暴期间 decode_max 被抢占膨胀至 107ms（解码 worker prio 4 被 190ms handler 饿），idle 恢复后 decode_avg 3.5ms/fps 39.1 正常；风暴期 flush avg 1.0–1.2µs/px 线性、hz 116 无回归。
