# 7.0.111 唤醒专注反馈修复

## 问题与修复

7.0.110 测试中，两次唤醒的反馈请求分别在检测后 65 ms、48 ms 发出，但使用了 THINKING 状态，因此先显示思考，再在问候首帧时显示专注。该思考不是云端正在推理，而是设备错误选择了反馈状态。

7.0.111 在建立问候请求的所有权、校验连接 epoch 后，直接异步发布既有 LISTENING 状态对应的专注表情。问候首帧沿用同一状态，减少一次表情切换。不增加新表情资源或任务。

LISTENING 在既有问候播放阶段本就表示专注的交互状态，并不等于麦克风已启动。提前显示时仍没有设置 prelisten、没有启动录音；问候发送成功后留在等待循环，正常播放完成事件再启动收音。问候发送失败继续原有收音回退，断线、超时和旧播放事件继续由已有所有权检查处理。

仅将休眠 → 专注的动画阶段预算设为 30 + 30 + 90 = 150 ms。进入休眠、配网等其他强状态仍采用原有时间。保留异步解码就绪检查、帧推进和最终画面刷新机制；150 ms 是动画预算，不是保证检测后 150 ms 全屏已更新，实际还包含任务调度与资源准备。

## 保留的行为

- 唤醒词 → 云端问候 → 播放完成 → 收音 → 正常对话。
- 用户音频上传后等待云端回答时，仍允许正常的思考/问号表情。
- 7.0.110 的背景估计改进和 0.09 模型阈值。
- 新近窗防杂音判定仅输出 shadow 日志，不拦截。上一轮两次成功候选均为 recent_voice_short，尚不能安全启用该条件。

本次不修改云端协议、问候文本、采音门限或弱语音起录规则。末尾 no_speech 不足以区分轻声、背景声和未说话，需要带人工标注的新测试，不能据此直接提高门限。

## 验证与真机验收

执行真实问候函数的主机测试，覆盖所有权申请失败、epoch 失效、立即响应和发送失败；执行会话及产品回归。动画策略验证唤醒方向为 150 ms，反向休眠与配网方向保持原时间。正式配置构建后核验镜像版本、哈希、栈预算和集成检查。

真机应看到：休眠直接转专注，无问候前思考插入；问候继续完整播放，随后才开始收音。观察 `wake feedback requested revision=wake-focused-v2`、`capture_started=0`、首帧与 `rt capture started` 的时间关系。分别测试连续唤醒、弱声唤醒、背景讨论，以及问候期间断网后恢复。量化唤醒率和误唤醒率仍需足够样本；本次不宣称准确率已有实测提升。

本地 OTA 构建和回归结果保存在版本包 verification 目录，真机结果待补充。
