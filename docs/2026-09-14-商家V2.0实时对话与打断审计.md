## 结论

商家代码具有实时对话及人声打断的实际实现，不是仅有配置项或宣传文字。
但这份交付代码不能据此认定为“默认启用、在 V2.0 上已稳定实现自然全双工打断”：

1. 首次启动默认关闭运行时 AEC，默认进入 auto 对话，而非 realtime。
2. 正常对话选取通道 0/1，却按 MR（麦克风/播放参考）处理；V2.0 原理图的电气参考实际接 MIC3。存在高优先级的参考通道错配风险。
3. 本地打断使用 VAD 状态变化事件，叠加 500 ms 忽略窗口，会漏掉从窗口内持续到窗口外的说话。
4. abort 清空待处理队列，但未完整取消在途解码和输出，存在尾音、旧音频重新入队以及解码器并发重置风险。
5. 底座模式主动关闭 AEC；服务器也必须支持 realtime/abort 的语义。源代码不能证明商家已部署云端的实际行为。

准确评价是：**有硬件基础和功能路径，但交付版本存在需要核实和修正的关键问题；稳定效果尚未获得实机证据。**

## 一、硬件链路

《SCH_主板二_2026-05-09.pdf》第 3 页 codec 与《SCH_麦克风_2026-05-09.pdf》第 1 页显示：

| 输入/输出 | 实际连接 | 含义 |
|---|---|---|
| ES7210 MIC1 | 麦克风板 U2，经 FPC | 真实环境拾音 |
| ES7210 MIC2 | 麦克风板 U1，经 FPC | 第二颗真实麦克风 |
| ES7210 MIC3 | ES8311 OUTP/OUTN，经 AEC 区 RC 网络 | 电气播放参考 |
| ES7210 MIC4 | 图中没有连接到麦克风或播放输出 | 不应作为有效参考 |
| ES8311 OUTP/OUTN | 同时送 NS4150B 输入及 AEC RC 网络 | DAC 模拟输出 |
| NS4150B VOP/VON | 扬声器连接器 CN4 | 功放后的扬声器驱动 |

AEC 取样点在功放之前，不能称为“直接采集扬声器功放输出”。它提供电气参考基础，实际回声抑制仍取决于采集路由、幅度、同步及整机声学条件。

《SCH_主板二》第 1 页 MCU 与 `main/boards/CyberVoc-Board-V2_0/config.h` 音频引脚对应：MCLK=42、BCLK=40、WS=39、DIN=38、DOUT=41、PA=4、I2C SCL=1/SDA=2。
《SCH_主板一》主要为供电、SD、底座等连接，没有另一颗替代设备端 AEC 的专用语音处理器。

## 三、问题与影响

### P1：正常对话参考通道与 V2.0 原理图不一致

- `main/audio/codecs/box_audio_codec.cc:19` 固定 `input_reference_=true`、两路输入。
- 同文件 77 行开启 MIC1–MIC4，使用四槽 TDM；204 行普通模式只选择 channel 0、1。
- 同文件 385 行普通模式直接读取，没有把 MIC3/slot2 换到第二路的代码；DOA 分支的四槽能量选择仅在 DOA 模式执行。
- `main/audio/audio_service.cc:143` 的输入重采样继续把偶数样本当麦克风、奇数样本当参考，没有纠正上述顺序。
- `main/audio/processors/afe_audio_processor.cc:55` 根据两路输入及 reference=true 生成 MR。

按标准四槽顺序，这相当于 M=MIC1、R=MIC2，而原理图要求参考来自 MIC3。第二颗环境麦克风包含用户人声，不能因为变量名叫 reference 就变成干净的播放参考。可能出现回声抑制不佳、用户人声受损、误打断或漏打断。

**确定项**：原理图 MIC3 参考连接、源码 0/1 选择及 MR 标记。
**待实测项**：实际固件依赖/寄存器是否另有槽位重排、实板焊接与 ADC 输出顺序。交付目录未提供 dependencies.lock 或已解析的 esp_codec_dev 源码，`main/idf_component.yml` 仅声明 `~1.5`；不能把静态推断写成已测得的 PCM 事实。

乐鑫 AFE 文档明确 M 是麦克风、R 是播放参考，数据必须按标记交织输入：
https://docs.espressif.com/projects/esp-sr/en/latest/esp32/audio_front_end/README.html

### P1：编译打开 AEC，不等于运行时默认打开

`main/application.cc:85` 从 NVS 读取 audio/aec_mode；没有设置时写入 AEC Off。
进入对话时以 `aec_mode_ == kAecOff ? AutoStop : Realtime` 选择模式；非实时 Speaking 分支停止音频处理。
`main/mcp_server.cc:271` 可通过云端工具调用开启并保存偏好，但新设备不能仅凭 sdkconfig 的 AEC=y 判定为开箱实时打断。

### P1：500 ms 保护窗与边沿 VAD 组合导致漏打断

`main/application.cc:798` 播放状态进入后的 500 ms 内忽略 VAD 打断。
`main/audio/processors/afe_audio_processor.cc:321` 只在静音→人声、人声→静音时产生回调。

可由控制流直接推导的场景：进入 Speaking 后 200 ms 用户开始讲话，VAD=true 事件被忽略；用户持续讲到 1.5 秒，VAD 没有再次变化，因此即使超过 500 ms 也不会重新判断本地打断。用户在进入 Speaking 前已经被判为人声时，同样可能缺少新的 true 边沿。
该结论针对设备本地路径；服务器若独立识别人声仍可能打断，但不能借此证明本地实现完备。

### P1：清队列不覆盖在途任务

`main/audio/audio_service.cc:808` ResetDecoder 只重置解码器并清队列。
同文件 390 行解码在队列锁之外执行，400 行完成后重新入播放队列，未检查取消代次。
同文件 293 行输出任务取出 PCM 后解锁，再 OutputData；清队列无法撤回已取出的 PCM 和已提交 DMA 的数据。

可能时序：解码任务取出旧包→abort 清队列→旧包解码完成再次入队→继续播放短尾音。
此外 ResetState 与解码并发调用同一解码器，应核实线程安全；当前队列锁没有覆盖解码本身。
`application.cc:622` 任何 tts/start 都清 aborted，缺少轮次标识时迟到的旧 start 也存在重新开放旧音频的风险，实际是否发生依赖服务器时序。

### P2：底座模式与实时 AEC 互斥

`main/boards/CyberVoc-Board-V2_0/base_control.cc:188` 检测底座连接后主动 SetAecMode(Off)，再切换 DOA。
该操作会写入 NVS；底座心跳丢失不会自动重新打开 AEC（同文件 240 行注释及实现）。
因此“支持声源追踪”和“同时支持实时 AEC 打断”不能在这个实现中直接画等号。

### 云端边界

该包提供设备端实时上传及 `abort` 消息；`abort` 的发送不等于服务器已完成取消。
服务器需要在 TTS 期间持续接收识别人声，取消原回答，并正确驱动后续 TTS 状态。
未获取商家部署服务器实现与联调日志，本轮不能确认语音识别、回答时延及打断后语句完整性。

## 五、向商家核验的最小证据

1. 提供和实板匹配的固件版本、依赖锁定文件、AEC 开启方法及启动日志，确认实际进入 realtime。
2. 导出四槽原始 PCM：静音、仅播放、仅用户讲话、双讲；核对哪一槽是电气参考，以及开启 AEC 后用户人声是否保留。不要仅凭 AEC enabled 日志验收。
3. 在播放开始后 100/300/600 ms、以及播放中段分别插话；测量首次人声到最后旧 TTS 输出的时间，检查是否漏打断、是否丢句首、是否重新冒出旧语音。
4. 追加无人讲话连续播放、不同音量、底座插拔和联网恢复测试，分别统计误打断、漏打断和打断后识别成功情况。

只有这些实机与云端证据通过，才能把“代码有支持路径”提升为“交付产品稳定支持”。
