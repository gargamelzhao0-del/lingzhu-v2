# 补传空闲调度与麦克风交接修复

## 对应测试与根因

本次修复针对会议 `meeting_20260914_76f279a7_270148` 和 `meeting_20260914_76f279a7_270270` 的设备日志。后一轮离线采集 39494 帧（789.88 秒），三个阶段合计 39847 帧。设备报告 SD 收尾成功，但网关没有收到这两轮归档。

根因是补传检查仅在外层连接调度和 `run_audio_source()` 入口执行。进入 `wait_for_mic_start_action()` 后，SD 才完成收尾，内部等待循环没有重新处理补传条件。已有重试标志无法让主任务离开这个循环。

## 本次修改

1. 将补传调度独立为 `service_offline_audio_replay()`，在空闲等待心跳服务中持续调用。按照待上传文件、存储忙闲及重试期限调度，不要求必须先收到某次失败产生的重试标志。保留网络退避，避免反复启动空任务。
2. 会议或监控有待处理控制、离线恢复租约、正常音频发送者、配网、通知或 OTA 活动时，禁止新建补传连接。修复新会议命令到达后先启动旧补传、随即因录音优先退出的无效连接。
3. 恢复申请和在线发送资源准备期间继续离线采集。会议、监控在在线 listen start 提交成功后，通过 `acquire_mic` 回调接管离线读者的原麦克风对象。交接发生在完整 PCM 帧边界，保留共享 RX、DMA 缓存、板级租约及下一帧序号；不执行交接时的麦克风反初始化、重新初始化和启动清空。
4. 麦克风交接使用独立请求票号防止超时重试的旧发布被误认。交接等待上限 1000 毫秒；超时发布的对象由明确的一方释放，避免双重释放和悬空栈指针。
5. SD 正常归档末尾已经位于最后完整记录边界时，不再重复执行 ftruncate。降级或位置异常时保留截断恢复路径。增加 `SD latency step=free_space/header_sync/footer_sync/periodic_sync/rename` 分阶段耗时记录，保留原有刷新频率与持久化确认规则。

协议保持原有格式：恢复请求使用新 request_id，设备沿用原 audio_session_id；补传仍为原来的 archive_only 协议。SD 用户状态界面未新增。

## 烧录与实测验收

在工程根目录运行，串口按实际连接修改：

```powershell
powershell -ExecutionPolicy Bypass -File tools/flash-sd-replay-test.ps1 -Port COM7
```

1. 录制后停止会议，保持联网且不唤醒、不再次开启会议，确认 SD 收尾后出现补传任务及 acknowledged and deleted 日志。
2. 网关核验实际文件的 sessionId、CRC、跨分段序号和帧时间戳；两轮旧积压与新测试分别统计，不能把旧分段当成新会议成功。
3. 离线恢复时确认 `offline MIC transferred without DMA reset`，确认 audio_session_id 保持一致，并从归档时间戳验证交接间隔。
4. 补传中开启会议应及时让出；会议结束后应自行继续。恢复等待时关闭会议或断开网络，也必须结束或保留正确的录音意图。
5. 根据 SD 分阶段耗时定位实卡长延迟。软件测试不证明实卡长时间写入性能；尚未完成硬件 8 小时录制，也未声称这两轮积压已经补传完成。
