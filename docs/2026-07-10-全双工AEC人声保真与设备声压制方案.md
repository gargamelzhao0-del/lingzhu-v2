## 第一部分:问题本质

### 1.1 问题的数学本质

设备 mic 收到的信号是**线性叠加**:

```
y(t) = α·x_human(t) + β·x_echo(t) + n(t)
```

其中 α、β 未知,x_echo 来自 ref(理论上已知),n 是环境噪声。算法的目标是**在不知道人声 x_human 的情况下分离这两个成分**——这是经典的盲源分离问题。

### 1.2 当前 7.0 系统在"两端都做不到极致"的具体表现

**端 1:人声清晰度受损**
- 起音阶段被 echo veto attenuation 误压(交接文档 §18.3)
- 交接文档 §18.2 数据:低能人声帧 `seq=2..30` 显示 `echo_veto_atten=1 speech_protect=1 protected_gain=0 continuity_gain=0`

**端 2:设备声压制不足**
- 交接文档 §4.1 真人反馈:"设备声仍大,人声仍小"
- ref 与 mic 对齐不够,抵消不彻底

### 1.3 四大根因(基于代码事实)

#### 根因 1:`playback_echo_veto` 单帧 boolean 误判

**代码位置**:`main.c:3623`
```c
playback_echo_veto = playback_ref_echo_veto || playback_spatial_echo_veto;
```

**问题**: 单帧决策,起音 100-300ms 期间 `spatial_echo_veto` 因双麦差分能量尚未累积而误判为设备声。

#### 根因 2:`playback_human_seed_active` 受 echo veto 限制

**代码位置**:`main.c:3661-3665`
```c
playback_human_seed_active =
    playback_active &&
    playback_human_seed_seen &&
    playback_human_seed_hangover_remaining > 0 &&
    !playback_echo_veto;  // ← 关键限制
```

**问题**: 即便起音期间 `playback_human_seed_seen` 已被设置,只要 echo veto 翻转为 true,seed_active 立即失效,cleaner 看不到任何保护信号。

#### 根因 3:`playback_human_seed` 触发条件依赖 echo veto

**代码位置**:`main.c:3651`
```c
if (playback_active && spatial_human_first) {  // spatial_human_first = !echo_veto && ...
    playback_human_seed_seen = true;
}
```

**问题**: `spatial_human_first` 内含 `!playback_echo_veto` 条件,起音期间无法触发 seed 设置。

#### 根因 4:adaptive ref 路径已开启但候选未形成

**代码事实**:`sdkconfig:1025` 显示 `CONFIG_NUWAX_LIVE_AEC_ADAPTIVE_REF_ENABLE=y`,并非默认关闭。

**代码位置**:`live_aec.c:904-978` (`read_adaptive_software_ref`)

**实际算法**(代码 927):
```c

    compute_residual_metrics(aec->pending_mic, out, sample_count, 32768);
```

使用的是 `aec->pending_mic`(原始 mic 缓存)与候选 ref,**并非 AEC output**。原文档关于"用 out/ref 相关性被污染"的描述不准确。

**实际问题**(从验收日志推断):
- `adaptive_candidates=0` —— 候选数始终为 0
- 原因很可能是 `ref_level_active()` 筛选过严(`live_aec.c:947`),把候选全部剔除
- 或 `ADAPTIVE_REF_MIN_CORR_Q15=1500` 门槛过高

**修订**:此根因真实存在但描述需修正,且不是当前起音问题的第一修复点,降级为"可选优化"。

## 第二部分:架构设计

### 2.1 四层架构概览

```
┌────────────────────────────────────────────────────────────────┐
│ Layer 1: 数据生成                                                │
│   - I2S 4-slot TDM 采集 (mic1+mic2+ref+nc)                       │
│   - DAC 同步生成 software ref                                    │
│   - 在 rt_capture 层加 mic1/ref 直接延迟扫描                     │
├────────────────────────────────────────────────────────────────┤
│ Layer 2: 证据(尽量标量)                                            │
│   - 时间相关: mic1/ref、mic2/ref(不同 lag)                         │
│   - 空间证据: 差分能量、平衡                                       │
│   - 信号证据: RMS、ZCR、voice_like 滑动窗                         │
│   - 上下文: playback_active、speaker_pending                      │
├────────────────────────────────────────────────────────────────┤
│ Layer 3: 决策(boolean + hangover 框架,只修 hook)                  │
│   - 新增 speech_onset_detected (不依赖 veto)                      │
│   - 解耦 playback_human_seed 与 echo veto                       │
│   - playback_echo_atten_guard 包含 onset                        │
├────────────────────────────────────────────────────────────────┤
│ Layer 4: 执行(平滑 boolean 应用,内部已部分平滑)                   │
│   - apply_playback_echo_veto_attenuation (streak+smooth)        │
│   - apply_playback_protected_gain (AGC+smooth)                   │
│   - 样本级衰减必须比上传门控更保守,优先保护人声                  │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 架构校准(基于代码事实)

#### 校准 1:"Layer 2 不做决策" 不成立

**代码事实**(`dual_mic.voice_like`):ZCR + 频谱特征综合为 boolean,这就是隐式决策。

**修订**: Layer 2 输出标量/向量,如 `voice_like_score_q15`(0.0~1.0),而非 boolean。

#### 校准 2:"三连续增益" 与代码"多 boolean" 不等价

**代码事实**: 现有架构是 15+ boolean 控制流,不是三连续增益加权。

**修订**: 务实选择是修 boolean 架构的 hook 顺序(改动小),而非重构为三连续增益(改动大)。

#### 校准 3:"状态机 enum" 与代码"boolean + hangover" 等价

**代码事实**: 7 状态在功能上已被 boolean + hangover 实现覆盖:
- SILENT ↔ `!playback_active`
- DEVICE_ONLY ↔ `playback_active && echo_veto && !seed`
- HUMAN_ONSET ↔ `spatial_human_first`(当前实现,但受 veto 限制)
- HUMAN_SUSTAIN ↔ `playback_human_seed_active`
- HUMAN_TAIL ↔ `seed_hangover_remaining--`
- DOUBLE_TALK ↔ `dual_mic_cleaner_hint_active`
- NEAREND_ONLY ↔ `playback_raw_human_hint_active`

**修订**: 不需要新框架,只修 hook 顺序。

### 2.3 不应纳入当前 MVP 的部分

| 架构项 | 原因 |
|--------|------|
| 频域 mask | 7.0 无实现、ESP32-S3 FFT 耗 CPU、当前瓶颈不在频域 |
| 重写为三连续增益 | 改动大,boolean 架构已经足够,只修 hook 即可 |
| 完全重构为 enum 状态机 | boolean + hangover 已覆盖功能需求,重构无收益 |
| 状态机内部转移表 | boolean 等效实现,无需重新设计 |
| rt_capture 层加 mic1/ref 延迟扫描 | 看似 ~15 行实际涉及 lag correlation 函数、CPU 预算、线程安全、抖动保护;不是当前起音问题的第一修复点 |

### 2.4 核心架构原则:门控 vs 样本级衰减分离

**这是当前问题的核心**(原文档遗漏):

```
门控逻辑(gate) — 用于决定音频是否上行
  → 可以严格,宁可漏人声也别上送设备声
  → 影响:VAD 决策、playback_gate_candidate、上传开关

样本级衰减(sample attenuation) — 用于决定 PCM 字节处理
  → 必须保守,宁可让设备声残留也别压没人声
  → 影响:playback_echo_veto_attenuation、playback_protected_gain

两者绝不能用同一个 boolean 决策!
```

**当前代码事实**:`audio_cleaner.c:631` 实现的 `apply_playback_echo_veto_attenuation` 已经区分这两层:
- 入口 1 `playback_echo_veto` boolean → 控制是否能衰减(粗决策)
- 入口 2 streak guard(`MIN_STREAK_FRAMES`) → 时间维度证据
- 入口 3 `speech_protect_hint || speech_gain_hint || speech_protected || playback_echo_atten_guard` → 保护信号(细决策)
- 入口 4 `smooth_playback_echo_atten_q15` → 实际衰减量平滑(连续量)

**架构意义**:任何修复 F1-F5 都必须保持**门控严格、衰减保守**的不对称原则。

### 3.2 条件性修复 F1:detect_speech_onset_no_veto

**触发条件**:只有在最新 `playback_echo_atten_guard` 版本测试后仍出现“人声起音被压没”,才实现本补丁。

**第一阶段用途**:只用于保护 cleaner 的样本级 echo attenuation,不要直接放开上传 gate。

**位置**:`main.c` helper 区域(放在 `compute_dual_mic_features` 之前或之后)

```c
// 新增函数:不依赖 echo veto 的起音检测
static bool detect_speech_onset_no_veto(const int16_t *mic1,
                                         const int16_t *mic2,
                                         const int16_t *ref,
                                         size_t n,
                                         const nuwax_mic_level_t raw_level,
                                         const nuwax_mic_level_t ref_level) {
    if (!mic1 || !mic2 || !ref || n == 0) {
        return false;
    }
    const nuwax_mic_level_t mic2_level = nuwax_mic_level_measure(mic2, n);
    
    // 三个独立证据:
    // 1. mic1 显著活跃(人声能量)
    const bool mic1_active = raw_level.avg_abs > 200 && raw_level.peak > 800;
    
    // 2. ref 处于低能量(没有设备声,或设备声已结束)
    const bool ref_silent = ref_level.avg_abs < 50 && ref_level.peak < 200;
    
    // 3. mic2 也有能量(避免单 mic 误判)
    const bool mic2_active = mic2_level.avg_abs > 30 && mic2_level.peak > 150;
    
    return mic1_active && ref_silent && mic2_active;
}
```

### 3.4 修复 F3:**删除**(高风险,不实施)

**原建议**:"移除 `playback_human_seed_active` 的 `!playback_echo_veto` 限制"

**风险警告**(经工程师核对):

`playback_human_seed_active` 的用途**不止 cleaner 的 protected_gain**,还参与多个关键路径:

| 代码位置 | 用途 | 影响范围 |
|---------|------|---------|
| `main.c:3851` | VAD 决策:`playback_human_seed_active && playback_weak_continuity_hint_active` | VAD 触发 |
| `main.c:3931, 3942` | `playback_gate_dual_candidate` | 上传门控 |
| `main.c:3968` | `playback_vad_gate_candidate` | VAD gate |
| `main.c:4025` | 日志输出 | 诊断 |

如果移除 `!playback_echo_veto` 限制,这些门控路径都会把"已经被判为设备声的帧"重新当人声,可能:
- 设备声被错误上传到 ASR
- 云端 ASR 误识别为用户说话
- VAD endpoint 错误触发,提早结束录音

**结论**:**F3 不实施**。当前 cleaner 的保护机制已经够用(`playback_human_context_guard` + `playback_echo_atten_guard` + `speech_protected` 多重 guard),工程师已按保守方向(保留 seed_active 对 gate 的严格性,用 guard 保护 cleaner)实现。

**替代方案**:F3 的精神(人声起音保护优先)通过 F1+F2+F4 实现:
- F1: 新增 onset 检测
- F2: 用 onset 触发 seed
- F4: 用 seed/onset 保护 cleaner 的 echo attenuation
- **不**改变 seed_active 对 gate 的影响(门控严格、衰减保守原则)

### 3.6 修复 F5:cleaner 已有 streak + guard,只需调参

**原建议**:"在 `apply_playback_echo_veto_attenuation` 中添加 `external_ref` 参数做二次确认"

**工程师核对发现的问题**:
1. 当前函数没有 ref 参数,添加需改函数签名,影响所有调用点
2. 硬件 ref(`s_audio_ref_samples`)已长期 inactive(`hw_ref_inactive=1219`),不能用作 active 判断依据
3. 软件 ref 的活跃度已在 `playback_ref_active` 中计算并传入(`main.c:3557-3559`),但不是直接传入 cleaner

**当前已实现的保护层级**(`audio_cleaner.c:631-682`):
1. 入口 1:`!playback_active` → 立即 reset state
2. 入口 2:`!playback_echo_veto` → 立即 reset state
3. 入口 3:任何 guard 信号(`speech_protect_hint || speech_gain_hint || speech_protected || playback_echo_atten_guard`)→ 立即 reset state 并 `*guarded=true`
4. 入口 4:`streak < MIN_STREAK_FRAMES` → `*guarded=true`,不衰减
5. 实际衰减:`smooth_playback_echo_atten_q15` 平滑后 apply

**结论**:**F5 不需要新增 ref 二次确认**,因为:

- 硬件 ref 不可靠(`hw_ref_inactive` 长期 1219),不能用 `external_ref active` 做门
- 软件 ref 的活跃度已通过 `playback_ref_active` 间接传递
- 已有 5 层 guard,足够保守
- 真正需要的是**调整已有参数**,不是新增代码

**替代方案**:把 F5 的工作量合并到 F7 的参数调整:
- `MIN_STREAK_FRAMES`: 3 → 5-8(100-160ms)
- `ATTENUATE_Q15`: 12288(0.375x) → 16384(0.5x)

这两个改动等效于"更保守的二次确认"。

### 3.7 修复 F6:**降级为可选优化**(不在 MVP)

**原建议**:"在 `rt_capture_read_frame` 加 mic1/ref 延迟扫描,约 15 行"

**工程师核对发现的问题**:

1. **实际工作量被低估**:
   - 需要新增 `correlate_with_lag` 函数(归一化互相关)
   - 需要 CPU 预算分析(每个 chunk 多 32 次相关计算)
   - 需要线程安全更新(原 `software_ref_delay_samples` 在 capture task 写,rt_capture_receive 读)
   - 需要 playback 状态同步(`rt_capture` 没有 `playback_pending` 语义,需要从 `speaker_playback_has_pending()` 拉取)
   - 需要抖动保护(每次扫描都更新 delay,可能导致 1-2 样本跳变)

2. **不是当前第一修复点**:
   - 当前起音问题(`playback_echo_veto` 误判)的根因不在 delay 不准
   - delay 偏差已被 `live_aec_process_internal` 的 adaptive 路径部分补偿(`ADAPTIVE_REF_ENABLE=y`)
   - 验收日志中 `adaptive_candidates=0` 说明问题在 `ref_level_active()` 筛选或 `MIN_CORR` 门槛,而非 scan 算法本身

3. **真实 adaptive ref 问题诊断**(优先级低于起音):

#### 4.2.4 标注入声起音窗口

**修订说明**(工程师反馈):全局 `min_rms >100` 不严谨,因为真人停顿、播放尾部、自然静音都可能低于 100。

**正确指标**:**标注的人声起音窗口内 RMS 不被压没**。

具体做法:
1. 测试人员按下"开始说话"按钮,日志记录时间戳 T0
2. 以 T0 为锚,分析 `[T0-100ms, T0+300ms]` 窗口的 RMS 曲线
3. 在该窗口内:RMS 应单调上升至峰值,然后稳定(不突然下降)
4. 若 RMS 在窗口内有突降 > 50%,即"起音被压没",记为失败

- ✓ 人声开头完整(无截断、无突变)

## 第五部分:技术细节补充

### 5.1 修复后的完整决策流

```
[单帧数据 + 历史状态]
   ↓
playback_ref_echo_veto, spatial_echo_veto  ← 单帧证据
playback_echo_veto = OR
   ↓
speech_onset_detected  ← 新增:不依赖 veto
   ↓
当前 MVP:
  speech_onset_detected 先只作为 echo_atten_guard 的输入
  不直接改变上传 gate
   ↓
playback_human_seed_active:
  if (seed_seen && hangover > 0 && playback_active && !echo_veto) {
    seed_active = true;
  }
   ↓
playback_echo_atten_guard:
  if (seed_context || dual_onset_guard || speech_onset_detected || ...) {  ← 新增 onset
    echo_atten_guard = true;
  }
   ↓
cleaner 决策:
  if (echo_veto && streak>=3 && !speech_protected && !echo_atten_guard) {
    attenuation();
  }
```

### 5.2 风险评估

#### 风险 1:误把起音检测接入上传 gate
**风险**: `speech_onset_detected` 如果直接触发 `playback_human_seed_active` 或上传 gate,可能把设备声误当用户语音上传。

**缓解**:第一阶段只把 onset 接入 `playback_echo_atten_guard`,只保护样本级衰减,不改变上传 gate。

#### 风险 2:guard 过宽导致设备声压制下降
**风险**: `playback_echo_atten_guard` 过于保守时,人声会保住,但设备声可能回升。

**缓解**:必须跑无人基线；如果无人基线设备声过大,再调 `MIN_STREAK_FRAMES` 和 `ATTENUATE_Q15`,不要牺牲人声起音。

#### 风险 3:参数调整可能打破现有平衡
**风险**: 7.0 系统经过多轮调优,部分参数值可能是经验最优。

**缓解**: 每次只调整 1-2 个参数,跑 3 轮真人 + 1 轮无人基线对比。

### 5.3 与交接文档 §18.4 的对照

交接文档给出的修复方向:

> "1. echo veto attenuation 必须要求连续 echo veto streak(2-3 帧)后才开始衰减。"

**对应**: streak guard 已实现(MIN_STREAK_FRAMES=3),但需要延长至 5-8 帧(F7)。

> "2. 如果最近 200-300ms 出现过 human_seed_active、raw_human_hint_active 等,则 echo attenuation 应该降级或关闭。"

**对应**: 当前已实现 `playback_human_context_guard`、`playback_dual_onset_guard`、`playback_echo_atten_guard`。不移除 `playback_human_seed_active` 的 `!veto`。

> "3. 对 speech_protected=1 但当前 hint 不足的帧,不应直接 0.5x 衰减。应区分 human onset / human tail / echo-only hangover。"

**对应**: F1 新增 onset 检测 + F4 echo_atten_guard 包含 onset + F7 调整衰减系数。

> "4. spatial echo veto 不应单独决定样本级衰减。"

**对应**: 当前样本级衰减需要 echo veto + streak + 无 `speech_protected` + 无 `playback_echo_atten_guard`。后续如果仍误伤,再补 `speech_onset_detected`。

> "5. 可以保留 echo veto 对上传门控的阻断,但样本级 attenuation 要比门控更保守。"

**对应**: F7 attenuation 0.375→0.5x 变温和,gate 仍严格。

> "6. 下一轮测试指标:playback_echo_veto_attenuated 应下降,playback_continuity_gain 应继续覆盖低能人声,人声开头应完整。"

**对应**: §4.2 验收指标已对齐。

## 第六部分:架构评价与设计哲学

### 6.1 架构"基本正确"的 3 个支撑点

1. **多证据融合** — 7.0 系统已经在做(compute_dual_mic_features、playback_mic_ref_corr)
2. **多增益维度** — 功能上等价于三独立增益(echo veto + protected gain + continuity gain + echo veto attenuation)
3. **时序证据** — hangover 机制已经实现

### 6.2 架构"需要校准"的 4 个点

1. **"Layer 2 不做决策" 不成立** — 证据函数内部有 boolean 决策
2. **"三连续增益" 与代码"多 boolean" 不等价** — 务实选择修 boolean 而非重构
3. **"状态机 enum" 与代码"boolean + hangover" 等价** — 不需要新框架
4. **adaptive ref 问题不在开关** — 当前 `sdkconfig` 已开启,但 `adaptive_candidates=0`,应单独排查候选形成与阈值

### 6.3 设计哲学

#### 哲学 1:不重写整个系统

**理由**: 7.0 是生产级固件,经过 7 个月迭代,任何大规模重构都风险高。

**实践**: 当前 MVP 只修样本级衰减保护和必要 hook,不引入完整状态机。

#### 哲学 2:修复 hook 顺序而非算法本身

**理由**: 算法本身(dual_restore、residual_cancel、protected_gain)已经成熟,问题在于 boolean 间的耦合。

**实践**: 先测试已实现的 guard 版本；必要时只补 F1/F4,不改 gate。

#### 哲学 3:基于代码事实,不基于理论最优

**理由**: 工程现实是"能用且稳定",理论最优是"更优雅但改动大"。

**实践**: 接受 boolean + hangover 架构,只修关键耦合点。

#### 哲学 4:多轮验证驱动

**理由**: DSP 算法调优无法纯理论推导,必须真人说话 + 无人基线多轮对比。

**实践**: Week 2 专门做验证,Week 3 做稳定性。
