# 对话开播等待与本地休眠修复

## 1. 触发条件与证据

最近一轮固件为 `shake-gap-v1`。测试中，设备在 215.434 秒进入等待回复，217.054 秒收到音频 START，但该轮累计只有 18 帧、11,520 字节（16 kHz、单声道 PCM16，约 360 ms），没有达到当时的 800 ms 开播水位，也没有收到完整结束信息。实际 I2S 播放尚未开始，因此一直显示疑惑表情。

原有 60 秒超时按“最后收到 PCM”计算；零星音频会延长它。310.424 秒发生 WebSocket 接收空闲超时，随后取消并重连，324.194 秒恢复聆听。此次疑惑状态持续约 109 秒。摇晃发生在重连已经启动之后，不能把此次恢复归因于摇晃。

另一次日志显示，只有 `playback_begin` 元数据、没有实际 START 的会话仍被计为 pending；电源键取消选中了历史 generation，连续得到 REJECTED，迟迟不能进入休眠事务。该现象与上述启动缓冲不足属于不同分支。

以上能够确认设备异常收敛不足；不能仅凭设备日志断言最初音频下行停顿来自云端、无线链路或 TCP 的哪一层。

## 2. 本次实现

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 收到播放元数据，完全没有音频 START | 等待原有 60 秒回合超时；重复元数据可能推迟回合期限 | 从首次相同播放的 `playback_begin` 计时，15 秒后原子检查并清理纯元数据会话；重复元数据不延长此计时 |
| 已有首段 PCM，却一直凑不够开播缓冲 | 每次 PCM 到达重置空闲时间，可能长时间保持疑惑 | 从首段 PCM 起累计 5 秒，仍未达标则声明该 generation 超时，通过原有物理停止和终止屏障恢复 |
| 截止时刻刚好有足够 PCM，或短回复已收到 END | 依赖正常缓冲判定 | 同一把 speaker 锁内先判定可播放，可播放优先；不会先做超时判断再误取消刚达标的响应 |
| 电源键遇到纯元数据会话和历史 generation | 反复请求取消历史 generation，REJECTED 后继续循环 | 先关闭普通下行准入，按当前 turn/playback ID 清理纯元数据，再判断是否需要物理取消 |
| 电源键与 START 同时发生 | 需要正确区分元数据与真实播放 | START 已取得所有权则纯元数据清理拒绝执行，继续原有 generation 取消及物理停止恢复流程 |

核心文件：

- `main/conversation/speaker_playback.c`：开播水位和超时在同一临界区决策；锁外发布故障事件；纯元数据清理增加 stream、I/O、维护、停止故障、淡出和运行时重置保护。
- `main/conversation/speaker_jitter_policy.h`：独立 5 秒开播等待预算，不依赖最后一帧到达时间。
- `main/nuwax_ai_partner_main.c`：15 秒纯元数据检查、本地电源休眠清理，复用既有取消和恢复入口。
- `main/conversation/speaker_playback.h`：增加可原子检查到期时间的纯元数据清理 API；speaker 禁用构建保留对应空实现。

故障发布先在锁内绑定连接 epoch 和 generation、阻止该流继续入队，然后在锁外投递主线程事件。物理停止完成与恢复聆听仍由原有终止屏障协调；不直接修改表情伪装恢复，也不绕过 OTA、会议/监控、配网或本地休眠的所有权。

新增开播期限只作用于普通对话 owner，通知和音乐保留原有策略。正常自适应开播水位 480～1600 ms（默认 800 ms）、播放中重缓冲 15 秒无进展保护、60 秒下行空闲上限、协议字段及 `no_speech` 行为均保留。没有新任务、定时器、永久音频缓冲或动态内存分配。

## 3. 验证方式

`tools/test-playback-startup.py` 抽取生产 C 函数编译执行，以可控时钟、RX、锁和 I/O 边界注入以下情况：

1. 日志同型 18 帧/360 ms、无后续数据，以及零星 PCM 持续到达：累计 5 秒触发故障，不能无限续期。
2. END 或水位在截止时刻到达、完整短回复、正常 800 ms 缓冲：正常放行，不误取消。
3. 新 generation、新连接 epoch、已有取消、已声明流故障、毫秒计数回绕：旧等待不影响新所有者。
4. START 授权前已耗时：首 PCM 总预算仍有效；播放中的既有重缓冲预算不被改成 5 秒。
5. 同 generation 多次故障声明只通知一次；通知后换代，旧物理取消拒绝触碰新 generation。
6. 首 PCM 等待 14,999/15,000 ms 边界、重复 `playback_begin`、错误 IDs、各类实际 I/O/停止占用：只清理匹配且确实没有实际音频工作的到期会话。
7. 执行生产 `remember_local_power_sleep_request`：历史 generation 元数据场景直接清理，不发送无效取消；START 抢先时只发一次真实取消，保留恢复观察直到物理完成。

另外编译 7 个故意破坏超时、达标优先、START 保护、ID 校验、迟到 RX 隔离、非对话 owner 隔离和休眠元数据清理的负例，确认测试能够拒绝这些错误。硬件输出和 RTOS 调度由桩模拟，不能代替实机测试。

产品综合检查、对话/WS 检查、正式全量构建和镜像验证的原始证据保存在 `docs/audits/2026-09-23-playback-startup-v1/`。新增测试已接入 `run-v2-product-host-checks.ps1`；新增构建核对已接入 `build-sd-replay-formal.ps1`。

烧录后优先测试：连续短句与长句对话；等待回复时短按电源键；回复期间断开热点再恢复；疑惑阶段重复摇晃；播放结束附近切换休眠/唤醒。每项需要确认：下一轮录音和回复正常、旧音频不串入新轮、无重复取消风暴、无异常重启、音频任务栈及内部内存无持续下降。

5 秒和 15 秒是启动等待的决策预算，并不承诺在此时刻已经恢复聆听。物理停止、主线程调度和终止屏障仍有独立收尾时间。网络持续中断时也无法保证云端回答恢复；本次修复的是设备不应无限停留在无法开播的旧轮。

风险与取舍：极慢链路可能在 5 秒后仍无法凑齐正常开播缓冲，本次会取消该轮，而不是继续无上限等待。正常音频无需降低缓冲水位；异常恢复后需要用户重新表达未完成的问题。主机检查和构建通过只证明覆盖范围内正确，真实弱网及连续运行仍需实机日志验收。
