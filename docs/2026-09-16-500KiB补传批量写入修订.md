# 500 KiB/s 补传：有界批量写入

## 实测基线与本轮改动

上一轮会话 `meeting_20260916_76f279a7_311937` 已核对 7 个归档：补传 5,378,180 字节，网关首个 begin 到最后 commit 为 14.379 秒，端到端平均 **365.264 KiB/s**。窗口内局部平均约 401.079 KiB/s，不能代替端到端速度。相同数据量要达到 500 KiB/s，需在 10.504 秒内完成。

上一轮完整约 1 MiB 归档平均 `send_ms=1627`、`write_ms=1082.5`、`encode_ms=281.5`，预读等待已接近零。耗时包含被调度出去的时间，不能全部归因于 TCP 或 SD 硬件。此轮针对每个约 8 KiB 帧都执行一次 socket 写入的固定开销，不再提高任务优先级。

| 项目 | 本轮实现 |
| --- | --- |
| 明文测试网关发送 | 最多 4 个完整 WebSocket 帧编码至 PSRAM，一次 TCP 写入；短写从尚未发送的字节继续 |
| 每帧内容 | 原 NWXCH1 头、offset、request_id、音频字节和独立随机掩码；只有窗口最后一帧设置结束标记 |
| 帧大小与窗口 | 每帧音频仍最多 8064 字节；窗口仍最多 128 KiB；每窗口持久化后 ACK |
| 缓冲 | 最多 32,568 字节线性发送缓冲，4 个 64 字节协议头；较原分配增加 24,618 字节 PSRAM |
| 低内存退路 | 保留 1 MiB PSRAM 预算；总量不足或批量缓冲分配失败时退回单帧，优先保留原窗口容量 |
| TLS | 保留原单帧分块写入方式和重试缓冲约束，不套用明文批量写入；共享有界超时 |

无短写、无重试时，一个 128 KiB 窗口的 17 个帧只需 5 次 TCP 写入；约 1 MiB 归档从 136 次降至约 40 次。**调用次数降低不等于吞吐提高同等比例，本轮尚未实机测得 500 KiB/s。**

## 稳定性边界

- 保留读任务优先级 6、发送优先级 5、内部 DMA 16 KiB 空闲余量，以及采音积压 >=60 ms 暂停、<=30 ms 恢复的保护。
- 每批最多 32,256 字节归档数据；预读只需发布当前批次前缀，不等整个窗口读完。读取仍按原有小片进行。
- 公平调度仍按实际发送字节数和编码工作时间计费；录音/取消检查在批次边界执行。相比单帧，单次发送持有 I/O 锁的工作量增大，须实测心跳和采音保护等待，不能把这一影响忽略。
- 批次共享最多 1500 ms 的发送期限。部分发送失败后关闭当前连接；禁止在同一字节流中重发半个批次。未发生发送进度的超时按既有连接/epoch 条件重试。
- 窗口保留到持久化 ACK；丢 ACK 使用原请求和原始字节重发。最终 commit ACK 前不删除 SD 归档。取消后先 join 读任务再释放内存。
- 不更改在线协议、离线协议、归档格式、会话关联、SD 时钟、Wi-Fi 缓冲或断网测试开关行为。测试网关无需更新协议。

## 已完成验证

1. 直接编译生产发送路径：192 组批量编码组合，以及 320 组控制帧竞争调度；覆盖独立掩码、长度边界、源数据不变、短写、背压、TLS、epoch、参数/重叠拒绝、部分批次失败断开和重连。
2. 生产补传循环：探针启用/关闭两种配置，覆盖 16,896 处头部变异、CRC、任意偏移续传、丢失/错误 ACK、录音抢占、连接变化、预读发布、低内存退回单帧与读任务退出。
3. 独立本地 TCP 网关：4 帧合并写入、拆分帧头/内容、中途断开、重复持久化窗口、commit；500 帧最终归档逐字节一致。测试使用临时目录与随机端口，没有修改运行中的测试网关或测试录音。
4. 完整诊断版和性能版构建；检查最终 ELF 的单帧和批量掩码路径、两个 RNNT 修复调用点，以及 BIN 内嵌 ELF SHA。

反汇编检查额外修复了一处工具误报：Xtensa 跳转后的 2 字节填充会使线性反汇编错位，产生不存在的 call。检查现按可达分支和真实指令边界解码，保留普通 memcpy 的负向对照，不放行实际掩码函数调用。

主机回归能验证协议与失败处理，不能模拟 ESP32 的实际 CPU、PSRAM、Wi-Fi 时序，也不能证明此前 Cache/MMU 重启根因已经消除。

## 烧录与实机验收

建议先用保留 UART 崩溃转储的诊断快照；串口按实际设备修改：

```powershell
powershell -ExecutionPolicy Bypass -File tools/flash-sd-replay-test.ps1 -Port COM11 -BuildDir C:\tmp\nuwax-replay-batch500-diagnostic-20260916
powershell -ExecutionPolicy Bypass -File tools/monitor-sd-replay-test.ps1 -Port COM11 -BuildDir C:\tmp\nuwax-replay-batch500-diagnostic-20260916
```

性能快照为 `C:\tmp\nuwax-replay-batch500-speed-20260916`；默认构建目录 `C:\tmp\nuwax-sd-test-20260911` 同步更新。性能和诊断配置需各自比较，不能把移除诊断缓冲带来的内存变化当成代码优化收益。每份快照的 `build-result.json` 记录完整 SHA、源码、验证结果和 6 个烧录镜像。

下一轮先进行约 5 分钟离线会议，恢复网络后退出会议，保存从启动到补传后至少 30 分钟的串口日志。重点检查：

- 启动 SHA 匹配快照；`reader_priority=6 sender_priority=5 lane_probe=0 tx_batch_frames=4`。内存不足时 `tx_batch_frames=1` 是预期退路。
- 完整约 1 MiB 归档通常 `batch_max=4`、`batch_calls≈32`、`batch_frames≈128`；其余尾帧走单帧接口。`calls` 统计实际 socket 调用，短写和 EAGAIN 会使其高于约 40 次。
- 对比 `write_ms`、`writable_wait_ms`、`encode_ms`、`data_wait_ms`、采音保护等待、帧丢失、堆检查和 UI 响应。若背压或保护等待明显上升，应先缩小批次，不放宽保护阈值。
- 用网关完整会话的首个 begin 到最后 commit 测量 >=500 KiB/s；同时校验真实文件 CRC、连续序号、帧数及无重复。日志局部峰值不算达标。
