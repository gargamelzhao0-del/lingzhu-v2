# 7.0.213 会议与监控稳定性修复

针对 2026-11-02 17:32 的 7.0.212 测试：本地和 App 开启均进入 STARTING，首批数据独立读回及内部 DMA 直接复读都与 SDK 写入参数不符；另有诊断导出干扰启动、界面等待约六秒才清除的问题。

## 写入端验证与一次恢复

启用 `NUWAX_SD_WRITE_VERIFY_ENABLE`，位于原 SDK 读写适配器内，有卡会议、监控以及目录/清单写入均经过此路径。

1. 保持原 SDK 写入范围和调用者的源数据，记录源 CRC。
2. 原 SDK 写入成功后，使用独立内部 DMA 缓冲直接读回全部请求扇区，逐字节比较，再检查源数据未变化。
3. 仅在“写成功、读成功、内容不符”时，最多重写一次相同范围、相同原数据，并重新完整验证。
4. 持续不符返回 CRC 错误；SDK 原始错误、无法验证、源数据变化和内存不足都不能当作成功。不通过跳过 CRC 或设置完整标记来恢复功能。

验证在现有 FatFs 卷锁和原同步 SDK 调用的所有权内完成；只重写原请求扇区，不执行任意地址修复、原始扇区擦除或格式化。SDK 内部原有状态错误传播补丁保持不变。新的额外读回发生在项目适配层。

临时 DMA 缓冲为 512～4096 B，调用结束即释放，保留 16 KiB 内部内存底线。SDK 多扇区写入仍保留，验证读取按缓冲容量分组。最多两次写入，后续读写边界检查 1.5 秒软件预算；单次 SDK 调用仍使用其正常超时，因此不是严格的整次调用 1.5 秒墙钟上限。

这能恢复已在宿主机故障注入中复现的静默丢写，不代表已经证实原卡的物理故障原因或修复永久介质故障。

## 诊断保存退出开启关键路径

诊断导出从 `recover_if_idle()` 中移除，只允许后台存储主管在恢复完成后尝试。用户的开启意图先以带期限的原有预留发布，再尝试获取存储锁，导出者因此可以看到等待中的会议或监控请求。

导出按 4 KiB 数据边界检查新开启意图、存储占用和 750 ms 软件预算。发现需让路就停止新增写入，正常完成 FILE 关闭，保留 RAM 快照及已有 `.part`；不再用会在脏 FILE 仍存活时到期的 SDK 硬截止作用于导出。750 ms 是协作让路预算，不是文件系统调用的硬墙钟上限。

命名冲突、权限、空间和策略让路不会把整个 SD 标为不可用；真正 I/O 错误或不确定的关闭仍要求有序恢复。导出日志增加 `stage`、`errno`、`elapsed_ms`、`yielded`。四个槽和每份最多四次尝试保持不变，现有证据不覆盖、不自动上传。

## 会议失败的界面结果

控制器进入 ERROR 时，通过现有线程安全的动作失败邮箱锁存结果。单一状态发布者继续发布最新状态，LVGL 在处理新触摸前消费失败结果并清除等待。即使 `ERROR -> DISABLED` 在同一轮完成，也无需等待瞬间 ERROR 被屏幕看到；不会把旧 DISABLED 快照直接当成新请求失败。

没有新增 UI 控件、修改表情资源或调整云端/App 协议。
