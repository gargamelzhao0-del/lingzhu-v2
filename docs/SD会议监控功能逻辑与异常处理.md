# SD 会议／监控：功能、数据链路与异常处理

当前核对版本为设备 7.0.202 正式云端配置（2026-10-29）。以下保留此前版本的功能演进记录；当前 SD 上传复用配网后的正式云端 WebSocket，PC 网关和局域网发现默认关闭。完整字段和字节布局见 [SD 会议监控场次上传协议](SD会议监控场次上传协议.md)。

7.0.202 保留满文件封口上传与严格顺序，将预读准入改为可唤醒交接：写任务清除 busy 后发布已有事件组的独立进展位，预读先清位、再登记等待、再检查条件；释放发生在登记前由状态检查发现，发生在检查后由保留事件唤醒。仅锁被占用时，改为有界 mutex 等待。等待仍每 tick 检查取消、连接代次和存储状态；阻塞拿到锁后重新核对，失败即释放。原 SD DMA 互斥、队列 8/2、TX 64/32、内部内存水位、文件 ACK 持久化及删除规则不变。短事件唤醒不能清除全部公平性预算，防止加速后挤占低优先级任务。

正式上传任务按启动时是否正在采集选择核心：采集期间 Core1，采集停止后 Core0，保持优先级 5，低于读取／写入和 UI。若采集状态变化，只在上个文件／场次操作完成、帧和读取任务退出后释放原 worker，再按新核心启动，不在 TLS 帧中途迁移或关闭健康连接。同步调用和独立测试链路不使用该 worker 调度。唤醒与采集优先级不变。

新增 `SD formal reader admission revision=202`，输出预读总准入等待及 writer、queue、wake、mutex 分项、通知／超时次数；原 pipeline 的 pressure_ms 仍为发送端压力，不能代替此指标。`SD replay worker routing` 和 `SD replay core handoff` 用于核对核心策略。主机竞态与构建验证不代表已达到 500 KiB/s；需分别验收录制中上传和退出后的积压上传。

Core0 回放在完整 WebSocket 帧之间响应现有表情解码租约，单次仍受原 tick／租约期限约束，不持有传输或存储锁等待，也不把界面进展当作 IDLE 进展。帧发送前重新检查取消、连接和前台状态。`SD formal UI handoff revision=202` 单独输出次数和耗时，供核对速度与显示效果。

7.0.201 将有卡会议接入与监控共用的封口文件 FIFO：文件写满后同步、关闭并发布索引，在线即安排上传，采集继续写下一个文件；离线继续保存，恢复后从最早未确认文件接续。两个模式分别维护队列，跨场次按物理文件产生顺序处理，同场按 segment_index 递增。前序未封口文件不能被越过；前场 session_end 尚未确认，也不能先发后场文件。会议的 type、场次 ID、文件字段和 ACK 均沿用原协议，不使用监控实时／历史标签。

尾文件在停止时封口。只有录制结束、所有文件均有持久化 ACK 或真实缺失记录后，才发送 session_end；确认后再次核对收尾快照再保存 done，不能把尚在录制的空队列当作会议结束。无卡会议／监控、8 小时会议上限、120 秒监控静音监听和原前台优先级不变。SD 读取仍经过写任务让路和 8／2 队列门槛，TX 保留原压力门槛；录制故障、媒体恢复、关机、OTA 或新的开启准入仍暂停补传。

同时修正空队列调度：只剩未封口尾文件时不反复创建上传任务；文件封口或场次结束重新发布待传标记。失败队头由监督任务退避，新文件的元数据修订可唤起另一条可用队列，不丢失录制期间的封口事件。

已结束场次若留下未封口的预留索引，先检查 ready、part、隔离文件与原确认副本。存在任何源文件就保留等待；只有确认源文件全部不存在，且无法恢复原确认记录时，才将该编号记为真实缺失并将场次标记为不完整，不能伪造上传确认。尚在录制的预留尾文件始终保留。

TCP socket API 改用 ESP-IDF/lwIP 的 TCP 核心互斥锁路径，减少每次发送向 TCP/IP 任务投递消息及等待返回的开销；接收输入仍经原 TCP/IP 任务。沿用 SDK 的互斥锁及阻塞等待时解锁机制，TCP 缓冲区、Wi-Fi 参数和任务优先级不变。这会影响普通 socket 调用路径，需与正常云端通信、重连和资源切换一起进行实机回归。

正式 TLS 的数据 GHASH 增加可选 8 位查表实现，使用原生 32 位移位和约 4 KiB PSRAM 密钥表，减少原 SDK 的 4 位／64 位逐块运算。AES-CTR、IV／AAD、最终长度认证和标签仍使用 ESP-IDF。每把密钥先与原 SDK 的 GHASH 结果比对，再进行三组有界短测；只有结果一致且最短耗时至少降低 15% 才选用，分配不足、比对或测时不满足均保留 SDK。每种记录路径首次真实加密继续与软件实现比较，中途失败保留原明文并回退，密钥变化与任务结束清理密钥表。预读缓冲在可选加密资源分配后才按原保留水位选择大小，内部 DMA 水位不降低。

新日志 `GHASH calibration` 给出设备当场选择及两种实现的短测；`SD formal GCM` 区分 CTR、GHASH 与 SDK 更新路径的墙钟耗时，均包含调度抢占，不能作为纯 CPU 占用率。改动不增加请求、确认或上传字段。是否达到 500 KiB/s 必须由实机整场数据确认耗时验收，不能以主机密码学比对或调整会议上传时机代替积压数据吞吐测速。

7.0.200 调整正式 TLS 上传的资源使用及两条异常路径，保持云端／App 字段、Binary 格式、落卡格式及文件确认规则不变：

- 同一上传任务跨文件保留 GCM 上下文和工作区，任务退出前释放。密钥相同则复用 H 与乘法表；实际密钥或长度变化时清理旧状态、重新建表，并与软件结果逐字节比较。每条记录仍独立重置 IV、计数器、AAD、长度和 GHASH 累积状态。
- 内部 DMA 工作区能容纳 8 KiB 时沿用直接加密。只能分配原 4 KiB 工作区时，可增加一块约 8 KiB 的 PSRAM 密文暂存区，按 4,096 字节对齐块处理完整的 8 KiB TLS 记录，最后一块允许不足 16 字节。GHASH 和 CTR 的工作数据仍在内部 RAM；整条记录成功前不修改调用方明文，分块中途失败也能安全回退软件 TLS。新增 PSRAM 分配失败时继续使用原 4 KiB 记录；内部 24 KiB 准入水位、12 KiB 运行水位及录音／唤醒让路策略不变。
- 云端已经确认文件，而新录音先占用了 SD，或 ACK 本地保存失败时，保留一个有界的 RAM 待保存项。下次空闲先核对实体卡、绑定、场次和文件的大小／CRC／路径／时间，再重写 ACK，随后沿用原清理流程。任何身份不符均放弃该内存提示、保留原件并走正常对账；断电后沿用原幂等恢复，不承诺跨掉电保留这条 RAM 提示。可见但同步失败的 ACK 必须再次写槽、同步及保存旁路备份，不能仅凭读到 ACK 就删除音频。
- 有效 CRC 的索引若与同路径归档的大小／CRC 不符，先独立复核整个音频文件，再核对同卡、绑定及场次，用现有旁路元数据恢复该文件索引。其他所有者、已确认记录及冲突旁路元数据不能覆盖；文件本体损坏仍保留并按原异常流程处理。修复不将完整性标记升为完整。

验证包括生产适配器与未修改的 ESP-IDF GCM 实现组合，覆盖 8／4 KiB DMA 工作区、768 次密文及标签比对、密钥变化、分块中途失败回退，以及真实目录／索引的待保存 ACK 和修复故障注入。主机验证不代表设备已达到 500 KiB/s；仍需实机按完整场次确认字节与总时间验收。新日志 `scoped AES ready` 区分逻辑容量与 DMA 窗口；`SD formal AES key_cache` 给出建表、复用及分块暂存次数，供确认新路径是否实际生效。

7.0.199 增加元数据准入自检和失败诊断。每个挂载周期首次初始化／恢复时，使用独占临时文件执行实际清单的双槽初始化、读后交替更新、同步、关闭、改名后回读及跨扇区稀疏索引校验；通过后复用结果，重新挂载或清单回读失败时作废。临时文件使用专用名称，检查与清理只针对本次独占创建的文件。正常音频读写、任务优先级和上传协议保持不变。

清单回读失败时，日志区分 creating、published 和 repairing，记录首次是否选出有效记录、预期／实际代数、CRC 及差异偏移。`sample=original` 记录首次读取的两槽状态；`sample=retry` 另读两槽，给出文件长度、读取长度、magic、CRC 和有效性，成功也不改变首次失败判定；`diff_offset=4294967295` 表示没有可比较的首次有效记录或没有字节差异。日志不输出绑定密钥或完整 owner。7.0.198 实机在原卡格式化／清空前六次开启会议／监控失败、处理原卡后成功开启会议，说明故障与当时存储状态有关；本版用于更早识别并准确定位该类异常，不将主机回归当作实卡故障已根治的证明。

7.0.198 补齐活跃场次清单损坏时的恢复：存储任务退出文件读写后，先核对同一张 SD 卡、绑定归属和采集代次，再用当前录制的内存身份修复清单，随后恢复音频及文件索引。修复临时文件保留双槽 CRC，改名前后均重新打开校验；修复中掉电时，下次启动可完成已验证的改名。有效的其他身份、已结束场次或确认记录不能被覆盖。恢复沿用原场次 ID、麦克风和 8 小时计时，不重复写已确认落卡的尾帧；发生过存储故障的场次继续标记不完整。

新场次在清单发布及首文件预留后分别回读校验；首个完整音频帧同步成功后，才确认录制就绪。仅进入 RAM 队列不能作为开启成功的依据。40 MHz 自检失败后，20 MHz 也必须通过同样的读写校验；仍失败时拒绝使用该卡，不把已检测到的坏卡当成无卡设备。系统错误不再使用摇晃素材；会议／监控退出后，即使应用正在等待唤醒，也会继续处理延后的状态恢复。正常摇晃、云端表情、无卡链路和上传协议不变。本轮保留既有上传优化，没有实机速度或长时稳定性验收结论。

7.0.196 修复本地存储异常的三条路径：开机恢复先核对实际保留的归档，再修复损坏／缺失索引和错误完成游标；目录读取失败返回错误，不能当作空目录；录制中发生 SD I/O 故障时，暂停存储和补传，在所有文件句柄退出后尝试恢复同一张卡。原采集任务、场次 ID、麦克风代次和有界 RAM 缓存保持不变，不重置会议 8 小时计时。恢复窗口为 10 秒，按 250／500／1,000／2,000 ms 退避；耗尽、换卡、关机或低电保护时停止录制并保留已存文件，不能迟到重启采集。该窗口是恢复流程的判定期限，底层卡命令和必要的文件检查可能使一次调用越过期限；越期后仍按失败收尾，不宣称无缺口。存储监督任务使用 8 KiB PSRAM 栈，大函数从目录遍历中分离，为文件系统调用留出栈余量；SD DMA、TLS 内部内存预留和任务优先级不变。

新封存归档旁增加 `.ready.meta` 本地副本，含绑定归属、场次身份、文件索引、录制来源及双槽 CRC；文件确认也先持久化到索引和副本，再删除音频。副本不上传，不增加云端确认次数，不改变 `.ready` 格式。恢复只找回有效且归属明确的源数据，不把损坏索引、保留音频或发送成功当作上传成功。若写失败时无法确认尾帧是否已落卡，重挂载后先校验该尾帧：相同内容不重写，未保存则重试，内容冲突保留现场并停止恢复。

旧固件已经损坏的监控索引可能没有录制来源副本。这种情况下能找回的音频保守归入 history，保持 `recording_complete=false`；正常索引和新副本仍保留原 realtime／history 属性。物理坏卡、断电前未落盘的数据和旧固件实际删除的音频无法凭空恢复。7.0.195 的读写调度、TLS 记录限长、队列保护和文件确认规则继续保留；是否达到 500 KiB/s 仍需同一硬件及网络实测。

7.0.194 将监控 FIFO 与上传优化统一构建。监控按场次及文件顺序处理，旧场的结束确认与本地完成状态持久化成功后再处理下一场；失败保留队头并退避，会议仍独立调度。空间复查已恢复时同步清除空间不足标志，不能返回成功却继续阻止录音。通信字段、无卡链路、SD 格式及内存／队列压力下的降档规则不变。

7.0.195 将 SD 读取 DMA 的申请、读取、校验、复制和释放放入写入任务使用的同一存储锁内，避免临时 DMA 缓冲重叠。读取在写入队列达到 8 帧时先让路，回落至 2 帧后继续；等待可取消，不持锁等待网络。写入任务优先级改为 6，与读取相同，仍低于 LVGL 7 和屏幕刷新 8；发送任务保持 5。发送侧原有 64／32 帧保护不变，大分片恢复门槛由 16 帧改为与发送恢复一致的 32 帧。内部堆和唤醒积压保护继续有效。

WebSocket 音频分片和 TLS 记录分开限长：最大音频分片仍为 8064 字节，4 KiB 加密工作区通过多条 TLS 记录完成同一 WebSocket 帧。WANT_READ／WANT_WRITE 重试固定原输入地址与长度，保留完整帧锁、发送期限和部分失败重连。加密算法、密钥、自检和内部内存预留不变。geometry 日志增加 tls_limit、record_splits；这些属于设备内部实现，不增加协议字段。

当前处理规则：

- 有卡会议／监控开启时，先暂停后台补传，等待读取、发送任务退出，再申请采集资源。等待期间保留开启期限；取消或超时后不迟到启动。采集真正就绪后才确认开启成功。会议／监控开启后均允许已封存文件边录边传。
- 补传的正常暂停不作为断网。尚未发送的 Binary 帧可直接暂停；TLS 已接收的帧在原有有界期限内发完，再交出连接。真实断线、连接代次变化或发送期限耗尽仍走原异常流程，不把部分发送当作文件确认。
- 重启恢复历史目录时，检查被完成标记／游标跳过的保留文件，不能只凭首尾文件已确认就跳过中间文件。有确切未确认归档证据才恢复待传；不改文件 ACK、绑定归属和音频内容，不把不确定场次改为完整。检查遇到实际 I/O 错误时停止该场恢复，保留源数据，不能据此清理索引。
- 有卡会议按实际可用容量及预留空间判断，不再受旧总计 1.5 GiB 配额限制。两场离线长会议可同时保留，前提是卡上空间足够。会议和监控均保留未确认音频；监控只清理已持久化确认的文件，仍不足则停止新增保存并报告录制不完整。
- 监控按旧场次先、新场次后，同场按文件编号递增上传。当前文件未确认时不能越过；旧场 session_end 确认并持久化后才能传新监控场次。新场可继续录制，会议调度及前台资源让路规则不变。
- 中断文件的校验进度在内存中保留最近四个文件，减少多个场次轮换时的重复读取。缓存绑定卡代次和文件身份；内存不足时回退重新校验，CRC 错误、换卡或媒体恢复后不能沿用旧进度。上传成功仍以云端确认并持久化本地状态为准。

本轮不改变协议、文件布局和无卡实时链路。主机回归与构建验证不能代替实机长时间测试，也不能据此认定达到 500 KiB/s。

7.0.193 原实时抢占查询不再用于监控排序，本次改为监控 FIFO 队头和分段扫描。连续上传复用旧场队头；单次最多处理 16 条场次元数据／文件索引记录，释放锁后继续，不跨网络等待持有存储锁。在线文件也不会抢占前面的离线文件。身份、文件头和 CRC 检查保留。

SD 上传专用 AES-GCM 工作区改用有界内部 DMA 内存。优先容纳 8 KiB TLS 记录，空间不足缩至 4 KiB，分配后保留至少 24 KiB 内部堆；无法分配则使用原软件 TLS。先复制到私有工作区再原地加密，硬件部分失败不会改坏软件回退所用的明文。保留已知答案自检和首条真实记录与软件结果逐字节比较；不改密钥、算法、认证和协议。

监控期间以完整 Binary 帧为边界调整分片：队列、内部堆和唤醒积压均有余量时最多 8,064 字节；压力达到门槛后回到原小分片，压力回落后再提速。内部工作区较小时同步限制单帧大小。录音与前台请求仍优先，不提高上传任务优先级。日志新增 `SD formal arbitration` 和 `SD formal geometry`，分别记录实时检查／前台让路／读取任务回收耗时，以及工作区容量和大小帧数量。

当前常规云端 `hello` 携带顶层布尔字段 `has_sd_card`，每条连接只在建立时发送，会议／监控开启不重复发送。重连时重新读取 SD 检测状态；该字段不代表当前可写性或剩余容量。此规则不涉及 SD 上传能力协商，不改变电脑 SD 测试网关的 begin／Binary／commit 数据链路。

7.0.178 的正式连接上传使用两块最多 64 KiB 的预读缓冲，逐块读取、校验和发送，完整文件校验成功才允许 commit。内存不足时缩小缓冲，仍不足则回退至可取消的原小缓冲路径。读取任务结束并回收后才能关闭文件或释放缓冲；取消、抢占、断线或 CRC 错误均不构成上传成功，保留原文件。监控实时／历史属性沿用文件保存的在线／离线录制标记，上传等待、重连或重启不改类。

以下为历史轮转方案，7.0.201 的有卡会议／监控均已改为严格 FIFO，旧场失败不跳过。7.0.179 修正失败场次轮转：单轮跳过表仍为 16 项；表满时保存轮转位置，下一轮从后续场次继续并最终回绕。先完成场次元数据的顺序选择，再检查候选文件，不能只比较目录前 16 个文件而漏掉后面的场次。冷扫描每次最多读取 16 份场次元数据，文件索引另有 16 条预算；用尽后释放存储锁并继续扫描。正常连续上传复用已选场次，不逐文件重扫目录。录音封存、场次变化或身份变化会作废旧扫描结果。

上传场次缓存仍为 32 槽。暂时失败而延后的场次释放缓存；缓存满时回收最近最少使用的场次，避免长连接因槽位耗尽无法继续上传。曾发送过的文件保留 SD 尝试标记，再次上传先按现有 begin／resume 查询云端持久化位置，不能把内存中的已发送字节数当成成功确认。正常未回收的场次仍只 begin 一次。轮转和缓存回收不删除未确认文件、不修改场次 ID、文件编号或云端错误处理规则。

当前日志 `SD formal pipeline revision=195` 分别记录读取、校验、发送和等待耗时；`SD file confirmed` 的 `attempt_bytes_per_sec` 按本次实际发送字节数除以本次文件处理总耗时计算，包含本次 begin／commit 及本地清理。它不包含前次失败和退避时间；整场吞吐量需另按全部有效字节和首发至最后确认的总时间计算。500 KiB/s 是实机验收目标，不能由主机回归或编译通过推定。

7.0.159 没有改变网络协议、录音格式、监控封存大小或音频模型。7.0.162 的封存调整见下一节。以前已经生成的 `.blocked` 不自动清除：其中可能是真实冲突，应先检查设备归档与网关对象，再恢复。

## 2. 开启、录制和结束

| 场景 | 实际行为 |
| --- | --- |
| 无 SD 卡、在线 | 保留原会议／监控实时音频链路 |
| 无 SD 卡、离线 | 无法保存离线音频，停止原实时采集；不产生 SD 补传文件 |
| 有可用卡、会议 | 在线与离线都先录入 SD；满文件封存后按序上传，结束后封存并上传尾文件 |
| 有可用卡、监控 | 保存已录入的音频；封存后按场次创建顺序及文件编号上传，离线保存、恢复后继续队头文件 |
| 检测到卡但卡暂未准备好 | 云端命令的身份预检受 20 秒执行期限约束，本地启动沿用原等待期限；失败不虚报已录制，不悄悄切成无卡模式 |

7.0.208 起，App／云端的 set_audio_mode 按目标状态执行。开启、关闭请求均可不带 audio_session_id；缺少或不适配 SD 的控制 ID 由设备生成录音 ID，历史已用 ID 也改用新 ID，不覆盖旧文件。成功开启 ACK 返回实际 ID。已有同模式录音时，再次开启保留原录音并回复 already_active；关闭请求直接关闭该模式的当前录音，不因 ID 不匹配拒绝，也不等待重连同步五秒。

录音 ID 仍贯穿场次、文件和上传消息。同次录制的在线／离线切换、监控静音暂停与恢复不换 ID；多场离线录音分别存档。7.0.209 起，云端按约定不再下发初始化开关状态命令。每次连接就绪后设备完整上报两种模式：运行模式为 enabled 并携带原场次 ID，未运行模式为 disabled；普通对话时两者均上报 disabled。首次发送失败会退避补发，回执失败、丢失或超时不直接启停录音，也不抢占对话；用户明确的开关和模式切换仍按原流程执行。近期请求去重、连接代际、局部停止代际和命令期限继续保留；不提供跨重启的无限历史请求去重。

跨模式开启先异步校验实际新录音身份、存储和资源，再停止原模式，封存后启动目标模式。队列满、真实存储故障或校验期间断线不会因为该命令提前停止原录音。包含转义 NUL 等畸形控制消息仍拒绝；报文构造失败不发送残缺 JSON。详见协议第 3.4 节及设备模式控制兼容说明。

7.0.170 起，云端模式命令从设备收到时开始计时，包含排队时间：执行期限 20 秒，ACK 发送截止 25 秒，对应云端 30 秒超时。正常情况下新模式实际开始采集即回复成功。超时返回已有 `ok=false / mode_handoff_failed`，取消目标模式的待启动工作；目标采集已经申请但尚未就绪时，通过其原有停止流程释放资源，原录音尾数据继续安全封存。同一超时请求的近期重复副本不会重新触发启动。

必要收尾只包括本地采集资源和数据保存，不等待音频上传及上传 ACK。旧模式 `STOPPING` 期间也检查新模式命令期限；慢 SD 校验结果和迟到的麦克风就绪不能让过期命令重新生效。ACK 采用原连接约束及统一截止时间，最多 5 次，每次最长 250 ms；真实成功的采集不因 ACK 丢失被撤销。该改动不增加消息类型、字段或错误码，不改场次 ID 和 SD 文件上传格式。25 秒是设备发送截止，不保证断网时送达云端。

7.0.171 修复三处控制边界（2026-10-23）：SD 启动和结束收尾在同一把锁内交接归属，收尾取得锁后再次核对状态，避免清除下一场录音；进入停止或实际采集结束后作废旧开启成功 ACK，本地停止独立发送关闭状态；所有模式控制发送使用最长 250 ms 的发送期限，命令拒绝沿用原接收时间，并在处理队列事件之间检查命令超时。关闭状态发送失败在同一连接内最多重试 5 次、总计不超过 5 秒，重连或下一场开始时取消，避免误关新场次。录音数据仍按原流程封存、上传并在确认后删除。

有卡模式不启动原实时 NA 上传任务，也不把该任务的旧 `listen start/stop` 作为音频上传入口。App 的模式控制及状态同步仍使用现有控制消息。音频接收侧必须允许第一次收到场次 begin 时创建记录，不能要求此前一定有 listen 或在线业务记录；控制请求 ID 不是文件去重键。

会议开始后连续保存。监控开始时也保存，持续约 120 秒没有确认人声后暂停落盘；麦克风继续检测，连续约 10 帧／200 ms 确认人声后恢复，带最多 500 ms 前导音频。暂停不结束监控场次。

有卡会议保持单场总时长 8 小时上限，在线、离线时间都计入，重连不重置计时。7.0.172 起，有卡监控取消该时长限制，断网、静音暂停和恢复在线都不自动结束场次；联网后仍在原场次内录制和上传，收到云端关闭后封存尾文件。本地关闭、关机、掉电及硬件故障仍按原逻辑处理，不保证跨断电继续同一录制。无卡路径不变。

有卡监控按实际容量保存，不再受固定 1.5 GiB 配额限制。预留 SD 文件系统容量的 1%，下限 16 MiB、上限 128 MiB；每次开新文件还保留一文件容量及 64 KiB 元数据余量。后台在四文件余量处提前清理已确认文件，减轻新文件创建时的等待。

7.0.193 的空间清理仅针对当前绑定身份下已封存并已确认的监控文件；会议、无关文件、隔离场次、未确认、正在写入和上传的文件受保护。删除前必须有持久化的确认依据，确认写入或同步失败就保留源文件。目录／文件索引检查按预算分批进行，跨调用保留游标，避免一次遍历长期占有 SD 锁。新监控场次使用每页 128 个文件的本地索引，处理完的整页可删除，避免索引随场次时长不断增长；旧目录仍可读取。

旧固件的循环覆盖记录仍按 7.0.173 的顺序恢复：场次新副本校验失败、回退旧副本时，已保存的文件缺失／待回收记录仍有效。每次完成旧待回收删除前，重新写入并同步场次不完整标记；同步失败就保留源文件。跳过缺失编号或清理索引页前，也必须保留该不完整状态，避免覆盖过的场次被误报完整。新固件不再创建未确认文件的回收记录。

旧固件被覆盖的历史无法恢复，仍保留原编号范围，最终上报 `recording_complete=false`。恢复联网后继续上传当前文件和保留下来的历史，文件编号不复用、场次 ID 不变。若剩余空间均被受保护数据占用，按存储不足处理，不靠删除未确认音频或未知文件维持录制。

升级能读取旧目录；新监控索引不支持直接降级回不识别分页索引的旧固件。降级前应结束监控并完成上传，或另行备份整张卡。现有协议的每场 1,000,000 文件边界仍有效，到界安全停止，不生成超范围编号。

### 文件何时封存

- 会议：通常录满文件上限；结束、录制属性切换或异常可提前封存。
- 在线、离线监控：均持续写入，剩余空间不足下一条完整记录时立即封存；在线安排上传并继续录制下一个文件，离线留存后补传。
- 停止监控、静音暂停和在线／离线采集属性切换仍提前封存尾文件。
- 最大归档为 4 MiB；完整记录不能拆开，因此满文件实际为 4,193,930 字节、6,297 帧、125.94 秒。

**7.0.162 起，监控采用“文件写满后上传”。** 连续保存时约 125.94 秒产生一个满文件，云端处理还需等待上传和提交。连续 120 秒没有确认人声仍会暂停保存，因此安静环境可能先封存不足上限的尾文件。此前版本已保存的小文件保持原内容，不合并、不改编号，仍可正常补传。

## 3. 实际通信

正常情况下每场只有一次 begin，每个文件一次 commit，整场结束一次 session_end。每条 JSON 请求均等待对应 ACK。

```text
开始录制 → 创建本地场次 → 采集、入队、写 SD → 封存文件
  会议：等场次结束
  监控：已封存文件可进入上传

场次 begin → begin_ack
文件 0 Binary 分片 → commit(0) → commit_ack(0)
文件 1 Binary 分片 → commit(1) → commit_ack(1)
……
录制已结束、所有可上传文件已确认 → session_end → session_end_ack
```

| 操作 | 会议 type | 监控 type |
| --- | --- | --- |
| 场次建立／恢复 | `meeting_audio_begin` | `monitoring_audio_begin` |
| 文件提交 | `meeting_audio_commit` | `monitoring_audio_realtime_commit` 或 `monitoring_audio_history_commit` |
| 场次结束 | `meeting_audio_session_end` | `monitoring_audio_session_end` |

ACK 名称在请求后加 `_ack`。例如：

```json
{"type":"meeting_audio_begin","request_id":"begin_01","audio_session_id":"meeting_example"}
{"type":"meeting_audio_begin_ack","request_id":"begin_01","audio_session_id":"meeting_example","ok":true}

{"type":"meeting_audio_commit","request_id":"commit_02","audio_session_id":"meeting_example","segment_index":0,"total_bytes":4193930,"crc32":2156111519}
{"type":"meeting_audio_commit_ack","request_id":"commit_02","audio_session_id":"meeting_example","segment_index":0,"ok":true}

{"type":"meeting_audio_session_end","request_id":"end_03","audio_session_id":"meeting_example","segment_count":1,"recording_complete":true}
{"type":"meeting_audio_session_end_ack","request_id":"end_03","audio_session_id":"meeting_example","ok":true}
```

上述 CRC 仅为格式示例。实际值必须由该文件的全部 NA 帧计算。

- `request_id` 匹配本次请求和 ACK，重试可换新值。
- `audio_session_id` 固定标识本场。
- `segment_index` 固定标识本场的文件，从 0 递增。
- 文件唯一键为已认证设备身份 + 场次 ID + 文件编号，不包括 realtime/history。
- 新场次协议不传 JSON `segment_id`；设备与网关内部文件名仍可有此名称。
- 不发送 SD 能力 hello，不协商 replay_version/replay_revision，不发送 window_bytes，不逐片确认。

正常 4 个满文件加一个尾文件：一次 begin、五次 commit、一次 session_end。监控正在录制时不会因为当前积压传完就结束场次，后续封存的文件继续沿用原场次。

### 实时与历史如何判断

只检查文件保存的录制来源：在线录制用 realtime，离线录制用 history。按序等待、断线、重启及录制结束都不把在线文件改成历史文件。已有的在线／离线切换封存规则保持不变，实时分类不代表上传延迟保证。

已经确认的文件不改内容或首次提交的处理类型。Binary 没有实时／历史类型，云端以 commit 前缀确定业务处理；文件去重键仍是设备身份、audio_session_id 与 segment_index。

## 4. 数据保存和完整性

音频为 16 kHz、单声道、PCM16，每帧 20 ms。归档由 96 字节头、若干 `4 字节长度 + 662 字节 NA 帧`、32 字节尾组成；每帧含 640 字节 PCM。

传输时，每条 Binary 是 64 字节 `NWXCH1` 传输头加 1～8,064 字节归档原文。头中包含场次 ID、文件编号、offset、长度及末片标记；分片可以跨归档记录。传输头布局值固定为 3，SD 归档内部格式值仍固定为 1；它们不是可选协议或版本协商。

网关按 offset 保存连续前缀；文件 commit 时检查长度、末片、结构、场次／模式／编号、音频参数和 CRC。CRC 范围是完整 NA 帧，不含每条记录前的 4 字节长度及归档头尾。

```text
网关：音频可靠保存 + 文件索引和去重状态保存 → commit_ack.ok=true
设备：收到匹配 ACK → SD 目录持久化确认 → 删除对应音频文件
场次：所有可上传文件完成 + 录制结束 → 场次清单确认 → 本地标记 done
```

设备仅调用发送接口成功不算上传成功。确认收到但 SD 确认记录写失败时仍保留源文件；下一轮查询、幂等提交，不因重复请求生成重复音频。上述删除流程是上传成功后的清理；7.0.193 的容量清理也遵守确认先持久化、后删除的顺序，不再清理未确认的旧文件。

新设备音频位于 `/sdcard/offline2/<分桶>/`，旧归档仍可位于 `/sdcard/offline_audio/`；场次及文件目录记录位于 `/sdcard/audio_sessions/`。新监控场次另含 `.paged` 标记和 `.index.<页号>` 本地索引，这不改变上传文件格式。本机网关存储位置：

```text
runtime-logs/sd-session-test-20261013/archives/
  <设备>__<内部文件ID>.complete       校验后的归档原文件
  <设备>__<内部文件ID>.complete.json  文件元数据
  sessions/<设备>__<场次ID>/          场次身份、文件索引、session.json
  session-refresh/                  迟到文件触发的待更新任务
  playback/                         网页请求播放后生成的缓存
```

以上目录相对工程根目录。`.part` 是未提交接收文件；不能仅看目录中有文件就认定传输完成。

拼接时先按文件唯一键去重，再按采集时间排列 PCM。帧时间戳低 32 位回绕通过文件头的 64 位开机时间展开。监控合法静音间隔不等于丢包，不应把上传到达时间用作采集时间。

从 7.0.164 起，场次 begin 和 session_end 另带 session_time：started_at_ms 是场次开始的 UTC Unix 毫秒，duration_ms 是从开启到采集结束的总持续毫秒，含静音暂停、不含后续写盘收尾及上传耗时。仍在录制或无法确定的值为 null；实际保存音频时长仍按帧数计算。

设备用正式云端应用心跳 pong.server_ms 建立真实时间与本次开机 64 位计时的对应关系。离线期间继续据此推算；同次开机先录制后校时，也可在后续 begin／session_end 中回填。时间一旦确定即另行保存，上传重试保持一致。心跳回调仅更新内存；存储任务异步保存时间基准，持续在线时最多每分钟更新一次，避免占用音频收发路径。

从 7.0.167 起，每个文件在原 96 字节头的偏移 84 写入 uint64 file_started_at_ms（首帧 UTC 毫秒），偏移 92 写入 uint32 file_duration_ms（首帧开始到末帧结束的跨度）。均为小端，0 表示未知。两项共用原 12 字节保留区，文件大小、NA 帧、CRC、64 字节上传头及场次清单布局不变。时长包含文件内部的采集间隔，与有效音频的帧数时长分开；每个文件均独立标记时间，不靠前面文件的有效音频累加推算。

文件日期沿用已保存的场次时间映射，离线继续计算，已封存文件不因重传或后续校时被改写。掉电恢复未封存文件时，按保留的完整帧恢复时间跨度；旧开机的日期只用旧开机已保存的依据。无可信日期时保留 0，仍上传音频。旧文件保留区全 0 继续兼容。PC 网关保存文件日期和跨度，网页分别展示采集时间、跨度与有效音频时长；播放仍只拼接已保存的 PCM。

重启恢复旧场次时，只用该场次已保存的时间或相同开机身份的时间基准。设备不知道完全断电经过多久，因此不能用上次开机的基准为新开机场次冒充真实日期；无可用基准时保留 null。时间信息缺失或损坏不影响已有音频上传。字段和例外规则见《SD会议监控场次上传协议》4.2.1。

## 5. 断线与突发情况

| 情况 | 设备与接收端处理 |
| --- | --- |
| 录制时断网 | 有卡继续保存同场次；恢复后会议仍等结束，监控按原编号从最早未确认文件继续 |
| PC 网关断开，但普通云端仍在线 | 文件保留、后台重试；网关可达与普通云端在线是两个状态 |
| 某个文件只传了一部分 | 重发场次 begin，resume 列出编号、长度、CRC；按返回的可靠连续偏移续传，不默认重传全部 4 MiB |
| 新监控文件已封存，但旧文件仍在上传 | 新文件在队列中等待；先完成旧文件确认，再传下一个编号，不因分类插队 |
| commit ACK 丢失 | 查到 offset 等于文件长度时只重发 commit，不重发 Binary；网关幂等确认 |
| session_end ACK 丢失 | 同连接重发 end；重连先 begin 再 end，网关使用已有结果，避免重扫全场 |
| busy、storage_unavailable、未知错误或 ACK 超时 | 后台退避重试，不因重试次数耗尽或容量不足删除未确认文件 |
| 参数非法／身份或内容冲突 | 返回 invalid_argument／conflict；设备持久化 `.blocked` 并保留数据。监控队头不越过，后续监控等待处理；会议仍按原规则调度 |
| 未提交数据 CRC 错误 | 网关清除错误临时接收数据；设备复核本地归档，再从 0 重传；不覆盖已提交对象 |
| 本地文件确实丢失或损坏 | 标记缺失／不完整，不把它当上传成功；损坏文件保留用于排查 |
| 网关进程重启 | 从持久化前缀、文件索引和提交结果恢复；待更新场次清单任务自动继续 |
| 设备突然断电／重启 | 恢复能校验的已写入完整记录，旧场次标记不完整，继续上传未确认文件；新录制用新场次 ID |
| 有卡监控容量不足，有已确认但未删除的文件 | 分批清理已持久化确认的合规监控文件；未确认及上传中的文件保留 |
| SD 拔出、写入失败或空间不足且无可回收文件 | 不虚报完整录制，采集进入失败／结束处理；保留已有可恢复数据，介质恢复后再扫描处理 |
| 新会议录制、OTA 或关闭设备 | 上传在读取、发送、等待 ACK 的检查点退出／让路，未确认数据保留；恢复条件满足后继续 |
| 解绑／更换绑定密钥 | 旧场次所有者摘要与当前身份不符时不上传给新绑定，旧数据保留 |

resume 单次最多 16 项，超过时分批查询。偏移 0 表示从头传，文件中间表示续传，等于文件长度表示直接 commit；非法偏移不能推动发送。

begin/commit ACK 上限 6 秒，session_end ACK 上限 60 秒，等待期间持续检查连接和取消状态。临时失败按 1、2、4、8、16、30 秒退避，成功后重置；调度压力也可能使实际启动更晚。

`recording_complete=false` 的成功 end ACK 只表示不完整结果已保存，不表示音频没有缺失。其编号范围内的迟到文件可以补入，后台刷新清单，但不把场次自动改成完整。突然断电前仍在 RAM、尚未写到 SD 的声音不能凭软件恢复。

## 6. 本次固件的传输链路

```text
麦克风 → 采集／监控人声策略 → 写入队列 → SD 归档、场次目录
                                              ↓
                                  文件选择、身份检查、断点恢复
                                              ↓
                      SD 读取／预读 → WebSocket Binary → PC 网关
                                              ↓
                           校验、持久化 → ACK → 设备清理已确认文件

App／模式控制及普通设备通信 ↔ 原正式云端连接
```

本次构建启用 `NUWAX_SD_SESSION_ENABLE`、PC 测试路由、配对局域网发现，关闭正式 SD 上传路由和设备开发测试栏。普通云端连接恢复后才会触发后台 SD 测试上传；只保证 PC 可达而普通云端未连接，并不等于当前调度已允许上传。

网页：<http://127.0.0.1:8810/>。设备通过已配对的网关发现机制取得电脑当前局域网地址，再连接 `ws://<电脑地址>:8810/api/device/ws`；电脑 IP 可能变化，不能把某次测试的地址当作固定配置。设备和电脑需网络可互通；电脑不能关机或休眠。

已结束场次、当前未开启监控时，独立 PC 连接允许大块预读、连续发送，每个文件仅等一次 commit ACK。监控运行中沿用有界发送路径及动态分片，保证采集和前台功能先得到资源，不再为后续实时文件抢占当前监控文件。内存不足时退回小缓冲路径，不透支录音及网络预留。

当前正式共享 WebSocket 路径与 PC 独立连接不同：共享路径每次最多 4 KiB，并受实时业务资源准入影响。**PC 路径的速度不能直接作为正式云端路径的速度。** 工程根 sdkconfig 也不是本次测试配置；使用 `tools/build-sd-session-test.ps1` 才是这里验收的配置。

## 7. 验证结果与速度结论

### 7.0.173 代码与文档复核

本次复核先用真实 C 目录逻辑复现了“待回收删除失败后，场次最新 CRC 副本损坏，回退旧副本并重试删除时误保留完整标记”的问题，再修复删除前的持久化顺序。同时覆盖缺失记录跨 128 文件索引页清理、连续同步失败和重启恢复，防止缺失证据随页清理丢失。

本轮整机构建、17 个回归入口及 2 项构建身份／资源校验通过；两份主文档的 22 个 JSON 示例可解析，相关 15 份文档中的 42 个本地链接均有效。验证结果与固件见 `artifacts/firmware/7.0.173-monitor-retention-review-20261023/`。长期满卡、实际 Wi-Fi 速度和真实掉电仍需实机验证，不能由主机模拟推出“无 bug”或“达到 500 KiB/s”。

### 7.1 7.0.172 循环存储验证

ESP-IDF v6.0 整机构建通过，应用分区余量约 5%。共 18 个回归入口通过，另通过 OTA 身份与 JSON 资源构建校验。覆盖真实 C 写入器、目录、回收、模式控制、旧补传路径及电脑网关协议，主要新增用例：

- 模拟 8／32／64 GiB 文件系统容量和超过原固定配额的已有数据，验证自适应预留、按旧到新回收及剩余文件 PCM／CRC／时间逐项一致。

### 7.2 早期速度基线与验收口径

以下为 7.0.159 的历史验证结果：设备真实 C 状态机、ACK 解析、上传器、目录／采集控制主机回归，以及网关场次协议、故障注入、旧协议兼容、网页播放、连接生命周期、发现协议等测试通过。ESP-IDF v6.0 工程构建成功，应用分区余量约 6%。

| 长场次模拟：30,000 索引、约 8 小时监控元数据 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 一个 32,096 字节迟到文件的同步提交 | 32,467 ms | 99.6 ms |
| 提交时在主线程重读索引数 | 30,000 | 0 |
| 事件循环最大计时间隔 | 约 32,467 ms | 100.2 ms |
| 后台清单更新 | 在提交内同步完成 | 约 36.3 秒，期间可处理网络请求 |

这验证的是长场次异常路径响应改善，**不是实际录了 8 小时，也不是 Wi-Fi 上传测速**。正常多文件用例另验证 4 个满文件和一个尾文件，共 28,336 帧、566.72 秒，按字节和时长核对通过。

不能据此宣布达到 500.0 KiB/s。当前代码具备减少逐片等待的快路径，但真实速度仍取决于 SD、Wi-Fi、内存余量、网关落盘、是否同时监控和重试。端到端速度应按“本轮新增确认的归档字节 ÷ 从首个 begin 到最后 session_end ACK 的时间 ÷ 1024”计算；另列纯传输阶段速度。网页瞬时接收速度含重传，不能替代完成速度。

500.0 KiB/s 对应 512,000 字节／秒，一个满文件纯传输约 8.19 秒。8 小时连续会议的归档约 915 MiB，该速度纯传输约 31 分 13 秒，实际还需计入建立连接、场次收尾和让路时间。监控静音暂停会减少实际数据量。

本次没有烧录或推送 OTA，也没有新增设备运行日志。稳定性结论限于已执行的构建、主机回归和故障模拟。下一轮实机应同时记录：完成速度、文件数／CRC／时长、session_end 完整性、重连次数、最小内部堆、麦克风丢帧、看门狗和重启。至少覆盖长会议上传、监控实时与历史并发、断网、上传中断电后恢复。
