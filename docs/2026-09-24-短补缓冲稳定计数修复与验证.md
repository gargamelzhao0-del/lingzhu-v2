# 短补缓冲稳定计数修复与验证

日期：2026-09-24。总计划 W05。仅处理已由日志和代码确认的自适应开播水位问题；Wi-Fi 接入专项继续暂缓，AU03～AU05 另轮验证，不同时修改。

## 风险真实性

附件 `3939cf4b-98b1-4b5d-8484-16a0fe30c798` 中，长回复 generation=8 完成时记录：

```text
startup_target_ms=800 next_startup_target_ms=480
rebuffer_events=2 rebuffer_wait_ms=1228 rebuffer_max_wait_ms=684
write_failures=0 queue_drops=0
```

生产 `speaker_wait_for_jitter_watermark()` 只有在进入等待后又收到新 PCM，才增加 `jitter_rebuffer_events`。只有 END 到达而没有新 PCM 的尾部等待单独计数，因此这两次不是正常播放尾部等待。

播放完成提交路径在锁内调用 `nuwax_speaker_jitter_adapt_startup_ms()`，传入真实中途补缓冲次数是否大于零及最大等待时间。旧策略把最大等待达到 800 ms 视作需要升档的不稳定播放，但最大等待不足 800 ms 时直接进入“稳定播放计数”分支。因此发生真实断粮的回合也能触发下一轮水位下降。

执行实际生产头文件的最小复现：四次稳定完成后，输入一次 `playback_rebuffered=true, max_wait=684`：

| 阶段 | 开播目标 | 稳定计数 |
| --- | ---: | ---: |
| 补缓冲之前 | 800 ms | 4 |
| 修复前处理补缓冲后 | 480 ms | 0 |
| 修复后处理同一输入后 | 800 ms | 0 |

该最小序列用于证明触发条件，不声称重放了原日志的完整音频或所有内部状态。

## 最小修复

在原有大幅抖动升档分支之后、稳定计数累加之前，增加短补缓冲分支：如果本轮确实发生过中途补缓冲，则清零稳定计数并返回当前水位。

| 播放结果 | 修复后行为 |
| --- | --- |
| 实际补缓冲，最大等待小于 800 ms | 保持当前水位，中断稳定计数 |
| 实际补缓冲，最大等待至少 800 ms | 保留原有升档/上限规则 |
| 无实际补缓冲的稳定完成 | 保留原有稳定计数及降档规则 |
| 仅等待 END 的正常尾部 | 不作为中途补缓冲处罚 |

既有 3 回合明显抖动历史位仍按原规则更新。短补缓冲不会被改成强制升档。新分支只影响本轮完成后供下一轮使用的策略状态；没有增加缓冲、任务、锁、分配或每帧计算，没有改动当前播放发送、接收、停止、取消和 generation/epoch 校验。

普通开播 5 秒、通知开播 10 秒、元数据等待 15 秒、恢复水位 640/800/960 ms、强制恢复预算和模型阈值均不修改。没有改变协议或要求 APP/云端配套更新。

这项修复防止错误地降低后续缓冲，不保证消除网络供给不足造成的长音频停顿。当前水位已是 480 ms 时发生短补缓冲仍保持 480 ms，这是本轮保留的低延迟策略，并非自动提高所有回复延迟。

## 验证

## 实机验收

使用正常短回复及数分钟长回复，重点检查 `speaker playback complete` 中 `startup_target_ms`、`next_startup_target_ms`、`rebuffer_events` 和 `rebuffer_max_wait_ms`：

- 当水位 800 ms、实际补缓冲且最大等待不足 800 ms 时，下一轮保持 800 ms。
- 不应出现因本轮短补缓冲而降至 480 ms。
- 后续连续稳定播放仍能恢复低延迟档，不应永久固定在高水位。
- 对话结束恢复聆听、触摸/摇晃打断、通知结束恢复及普通唤醒继续正常。
