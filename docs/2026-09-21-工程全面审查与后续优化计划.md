## 1. 结论与使用方式

当前工程已具备完整的主要业务链路，也有较多针对历史故障增加的状态隔离和回归检查，但还不能据此认定已经达到量产发布标准。下一阶段应从“增加功能”转向“发布安全、边界可靠性、可测量性能和可维护性”。

优先处理以下问题：

1. **正式云端配置与量产安全配置尚未分离。** 当前有效配置仍启用开发配网凭据模式、USB 配网控制，并允许 `ws://`。这些开关不会因为关闭 SD 测试网关而自动关闭。
2. **回归门禁存在真实漏检。** 长稳脚本对包含丢帧和唤醒异常的模拟日志仍返回 PASS；配网检查则存在旧源码匹配规则失效，造成整套检查失败。
3. **对话主线程仍承担过多职责。** 单文件约 3.5 万行；上轮修复了诊断写 NVS 阻塞播放收尾的路径，但并不等于所有慢操作、锁等待和生命周期竞争都已排除。
4. **正式 SD 补传与测试网关不是同一性能路径。** 正式链路仍采用 4 KiB 逐片确认，窗口上传只用于独立测试连接；不能沿用测试网关结果承诺正式云端 500 KiB/s。
5. **隐私和输入资源限制仍需收紧。** SD 归档直接保存音频，INFO 日志输出对话文本片段，JSON 解析深度仍为 1000，存在应当优先验证的资源耗尽风险。

## 4. 发现的问题与风险

### F01：正式配置仍包含开发安全开关——P1 / B

**依据：** 有效配置 `sdkconfig.h:427/439/440` 分别启用了 `NUWAX_PROVISION_SEC2_DEV_MODE`、`NUWAX_CLOUD_CONFIG_ALLOW_INSECURE_WS`、`NUWAX_PROVISION_USB_CONTROL_ENABLE`。

`nuwax_provision_main.c:1408` 在开发模式下使用编译期 PoP 构造 Security 2 参数，`build_qr_payload():252` 也使用开发 PoP。`nuwax_cloud_config.c:39` 在开关开启时接受 `ws://`；主程序 `:34207/:34288` 将设备密钥用于连接认证及 hello。USB 控制代码 `nuwax_provision_usb_control.c:14/61` 支持通过串口命令申请进入配网。

**影响与边界：** Security 2 并未关闭，设备也不是任意时候都开放 BLE。问题是共享开发凭据、允许未加密传输和调试入口不适合作为默认量产配置。若实际配置为 `wss://`，现有连接仍走 TLS；不能据“允许 ws”断言当前流量已泄露。USB 风险要求本地接入，不能描述为远程绕过绑定。

**计划：** 分为开发、工厂、量产三个构建配置；量产强制 WSS、每台设备独立 PoP/salt/verifier、关闭普通 USB 配网指令；工厂模式提供受控恢复流程。已有设备迁移前先验证工厂凭据存在，不能直接关闭开发模式导致无法配网。

**验收：** 量产配置加载 `ws://` 必须失败；缺少独立出厂凭据不能被错误标为可发布；错误 PoP/重复安全会话/USB 指令不能进入未授权绑定流程；APP 配网成功路径回归通过。

### F02：设备密钥和固件缺少量产级本地保护——P1 / B

**依据：** `tmp/sdkconfig.sd-replay-formal:801/803/4221/5328` 显示独立签名应用校验、安全启动、NVS 加密和 Flash 加密未启用。`nuwax_cloud_config.c:187` 使用 NVS blob 保存包含 `device_secret` 的配置。

OTA 已有 HTTPS、SHA256、大小、项目名和版本校验，见 `nuwax_ota_transport.c:310/653/674/689`；但 manifest 的允许字段只有 `type/command/update_id/url/version/size_bytes/image_sha256`，见 `nuwax_ota_manifest.c:153`，没有独立发布签名字段。SHA256 证明内容与声明相符，不独立证明发布者身份。

**边界：** 这是构建及应用层保护缺口；本轮没有读取实物 eFuse，不能仅由配置断言所有设备硬件安全状态。现有 OTA 也不能描述为完全没有验证。

**计划：** 先设计生产密钥、签名、轮换和恢复策略，再选择签名应用校验、安全启动和 Flash/NVS 加密路线。硬件 eFuse 配置必须作为单独工厂变更审批和试产项目，不能夹带在普通性能优化中启用。

**验收：** 未受信发布者签名的镜像被拒绝；受支持版本正常升级/回滚；掉电后仍可恢复；设备密钥不以明文方式出现在可读取的生产 Flash 中。

### F03：日志和 SD 归档存在隐私暴露面——P1 / B

**依据：** `session_protocol.c:760` 的 `log_text_preview()` 在 INFO 级输出最多 96 字节文本预览，被 ASR、用户文本和助手回复调用。有效配置日志级为 INFO。主程序 `:263` 的密钥诊断输出前三位、后三位和指纹，未输出完整密钥，但仍暴露部分凭据信息。`offline_audio_spool.c:1152` 直接 `fwrite()` 保存帧长度和音频数据，所审阅归档路径没有加密步骤。

**影响：** 可读取串口日志或取出 SD 的人可能获得对话片段或录音。CRC 能检测损坏，不能提供保密性；Flash 加密也不自动保护可拆卸 SD 卡。

**计划：** 量产日志默认禁止正文、密钥片段和完整 URL 查询参数；保留长度、错误码和去标识化关联信息。单独确定 SD 录音保留期限、解绑后处理规则和加密需求；若加密归档，设计格式版本、nonce、认证标签、断点续传及密钥撤销兼容，不能只在 `fwrite` 前加一道变换。

**验收：** 扫描真实量产日志没有对话正文和凭据片段；解绑/换绑后的旧归档处置有明确测试；加密版能在重启、损坏、部分写入和补传重试中保持可恢复性。

### F04：JSON 深度预算偏大且存在重复解析——P1 / B+C

**依据：** 有效 `CONFIG_CJSON_NESTING_LIMIT=1000`；WS 单帧上限 16 KiB（`ws_transport.c:109`）。cJSON 的 `parse_array/parse_object` 为递归解析（依赖源码 `cJSON.c:1497/1662`）。OTA 分发 `nuwax_ota_device.c:1305` 先完整解析，再判定是否 OTA；普通消息随后还进入 `session_protocol.c:718` 校验和其他模块解析。

**影响：** 16 KiB 长度限制不等于低递归深度；大量嵌套的小 JSON 可以在长度限制内消耗栈、堆和 RX 时间。认证检查发生在部分解析之后。本轮确认资源预算过宽，没有在设备上复现栈溢出，不能写成已确认崩溃漏洞。

**计划：** 统计现有协议实际深度，先评估 16～32 层限制；增加节点数/字符串总量/解析耗时预算；统一一次解析后的类型分发，保持各模块对必填字段、重复字段、数值范围的语义校验。不能用简单子串命中替代安全解析。

**验收：** 对所有入口执行深嵌套、截断、重复键、超大数、非法 UTF-8、尾随数据及分片边界测试；设备能拒绝异常输入并继续处理心跳，栈余量和最大解析耗时满足预算。

### F05：长稳验收脚本可将异常测试判定为成功——P1 / A

**2026-09-22 状态：** 下述旧反例现已判为 FAIL。新版按启动周期、模块/诊断流、任务代次及可用会话标识计算计数增量，增加时长/缺失证据检查和 JSON 报告。超时/部分读取缺少生命周期解释时判为 INCOMPLETE，不以一次健康记录豁免。实现及测试见 W01 记录；下文为原问题依据。

**依据：** `tools/check-device-longrun-gate.ps1:10` 的丢帧正则检查 `dropped=`，没有覆盖实际的 `dropped_frames=`、`queue_drops=`。唤醒检查只要求全文曾出现一条 `partial_reads=0...timeouts=0...input_gaps=0`，后续变坏不会因此失败。

### F06：配网回归脚本与显示缓冲实现脱节——P1 / A+B

**依据：** 本轮 `run-provisioning-host-checks.ps1` 的配网策略可执行测试通过，但脚本在 `:176` 的综合源码契约失败。其中 `:174` 仍要求 `heap_caps_free(previous1)`；当前 `nuwax_lvgl_port.c:1765` 调用 `release_draw_buffer(previous1)`，以兼容驱动缓冲借用归还。

### F07：对话协调器过大，长操作仍可能影响事件及时性——P1 / B+C

**依据：** `nuwax_ai_partner_main.c` 34,969 行；`drain_session_commands_limited()` 既消费命令，也运行通知、触摸/摇晃、超时、音量上报和诊断服务。文件中仍有长等待、资源重建及部分 `portMAX_DELAY` 锁获取，需要逐个区分任务空闲等待与业务阻塞，不能直接把所有 `portMAX_DELAY` 判成 bug。

**计划：** 建立所有 owner 服务调用的耗时清单和锁顺序表；先给慢操作增加 begin/end 指标，再将必要的 Flash/资源重建工作移交串行作业服务，使用请求 token、取消和完成事件回到唯一业务 owner。是否增加常驻任务必须先评估内部堆及栈成本，不能为了异步化增加无法承受的固定占用。

**验收：** NVS 近满/GC、摇晃开始、播放结束、配网取消交错时，业务事件不被低优先级维护长时间阻塞；旧 token 的完成不改变新状态；每个慢任务有明确超时和恢复路径。

### F08：正式补传无法直接复用测试版速度结论——P1（性能交付）/ B

**依据：** `offline_audio_spool.c:99` 正式分片为 4096 字节；`:3580/:3607` 只在 `independent_transport` 下提出并使用窗口协商；正式路径逐片进入 `replay_exchange_chunk()` 等待确认。正式补传与实时音频共享连接并实施避让。

达到 500 KiB/s 时，每个 4 KiB 分片的**全部串行成本**必须不超过 8 ms，且还没有计入控制消息和归档扫描。ACK RTT、服务端持久化、SD 读取、TLS 和调度任一成本增大都会降低速度。这个推导是协议路径约束，不是本轮正式云端实测速率。

另一个细节：代码使用 `vTaskDelay(pdMS_TO_TICKS(1))`，实际 tick 为 100 Hz，转换结果为 0；其效果不是等待 1 ms。不能机械改成 1 tick：10 ms 等待反而会降低吞吐，应按公平性目标重新设计。

**计划：** 单独建立正式 WSS 基准，先拆分 SD/read、校验、TX 锁、TLS write、ACK、云端落盘和业务避让耗时。若串行 ACK 已成为瓶颈，设计正式云端能力协商与有界窗口/信用机制，保留 v1 回退，并明确需要云端配合。不能绕过 ACK 或提前删除文件换速度。

**验收：** 使用落盘确认的唯一有效字节计算端到端速度；分别报告纯补传与交互并发结果。500 KiB/s 是待验证目标；网络/云端达不到时报告瓶颈，不把测试网关结果当作交付达标。

### F09：SD 持久化、提交与幂等仍需要真实故障矩阵——P1 / B+C

**已有保护：** `.part` 恢复、记录校验、CRC、`fflush/fsync`、重命名、最终 commit ACK 后删除、错误保留和 SD 回退均已有代码与主机测试。不能笼统说“补传不可靠”或“没有掉电保护”。

**待关闭边界：** `offline_audio_spool.c:81/1172` 每 100 帧同步一次，20 ms 帧条件下存在约 2 秒数据的正常同步窗口，另有队列和介质行为。它不是任意断电场景的最大丢失承诺。还需验证 commit ACK 丢失、云端先 ACK 后实际落盘、ACK 后设备删除前掉电、卡满/拔卡/坏扇区、会话停止和重连同时发生。

归档幂等标识使用 basename 的 CRC32 加 segment index（`:3542/:3558`），这不是无碰撞证明；需检查云端是否同时绑定设备、会话、长度和内容校验值。不要随意更改已存在归档的幂等标识算法。

**计划：** 建立 SD 文件与云端持久化清单对账；增加确定性的失败注入点；归档完整、降级、可恢复、不完整状态分别验收。若调整标识算法，必须版本化并兼容已上传一部分的旧文件。

**验收：** 正常 8 小时采集完整对账；失败路径不误删未确认数据、不把不完整归档标为完整；同片重复提交不重复入库；明确突然断电的可恢复范围。

### F10：观测数据还不能准确区分音频时长与状态延迟——P2 / B

**依据：** `metrics_mark_playback_done()` 在 owner 消费完成事件时更新指标（主程序 `:3513/:11056`）。前轮日志中约 3.5 秒 PCM 内容对应 `tts_playback_ms=14465`，该指标包含缓冲/等待/消费延迟，不能直接用它计算语音内容时长或网络速度。

### F11：WS/协议能力和云端兼容边界需显式声明——P2 / B+C

### 5.1 主程序拆分顺序

先测量和固定不变量，再抽取模块。建议从边界最清楚的部分开始：

1. 诊断和后台维护协调：保留业务 owner 对执行时机的决定权，后台只返回结果。
2. 联网与配网协调：封装 Wi-Fi/BLE/云连接的切换和回滚，不将硬件停止散落到 UI 回调。
3. 对话事件循环：统一 envelope，包含来源、epoch、generation、入队时间；按生命周期事件和普通设置分类调度。
4. 普通对话与交互回合：将触摸、摇晃、唤醒问候的差异封装为策略，保持统一播放收尾屏障。
5. 会议/监控协调：将恢复请求、模式租约、UI 状态发布从主程序移入明确接口。
6. 最后整理捕获/AEC 热路径；先保持结构和内存布局不变，再讨论算法和性能。

主程序的第一阶段目标是显著减少职责与跨模块静态变量；不以单纯拆成多个 `.c` 文件或达到某个行数作为完成标准。不得让两个任务同时成为状态所有者，也不得用大量 getter/setter 掩盖原有全局耦合。

### 5.2 性能优化实施原则

- 每次改动必须说明减少的是 SD 读取、解析、锁等待、绘制、网络 RTT 还是持久化耗时。
- 内部堆、最大连续块、PSRAM、任务栈分别预算，不能只看总剩余内存。
- 固定缓冲或常驻任务的收益必须扣除其长期内存成本；减少一次 malloc 不等于整体更稳定。
- 先确定受保护业务：采集和播放正确性优先，其次控制响应，再争取后台补传吞吐。
- 不默认提高任务优先级或缩短所有轮询周期；先测调度延迟与 CPU 占用。
- 不把 UI 流畅、Wi-Fi 恢复或数据完整性作为吞吐提升的代价。

| 解绑重绑 | 密钥失效但 Wi-Fi 仍连接 | 自动/手动进入正确重绑流程，旧云命令失效 |
| 配网失败 | BLE 断开、凭据写入失败、模型恢复失败 | 回滚或保持隔离，不能半恢复并继续云端音频 |
| JSON | 过深、过长、重复键、异常数值、畸形编码 | 有界拒绝，线程继续运行，内存回收 |
| WS | 半帧、短写、慢读、断线、旧 epoch ACK | 无跨帧损坏，错误导致明确重连或安全重试 |
| 会议/监控 | 开启→离线→恢复→继续→停止 | 同一 audio_session_id，新恢复 request_id；旧恢复不覆盖用户停止 |
| 8 小时离线 | 正常卡/慢卡/语音稀疏/持续语音 | 根据模式记录完整性，字节/帧/时间轴与云端清单一致 |
| 归档故障 | 写入/同步/改名/commit/删除附近断电 | 不误删，重复补传幂等，损坏片不伪装完整 |
| 正式补传 | RTT、带宽、云端落盘延迟、实时交互并发 | 报告唯一字节吞吐和避让时间，能暂停/恢复 |
| 菜单/显示 | 连续下拉、横向切页、二级页、OTA 覆盖 | 页面正确，反馈及时，无 DMA 缓冲竞争和花屏 |
| Flash/NVS | 近满、GC、音量/配置频繁变化 | 核心事件及时处理，关键凭据优先，诊断可降级 |
| OTA | 下载中断、写入掉电、SHA 错、同版本、资源不兼容 | 拒绝或回滚；失败后 UI/音频恢复；成功可确认 |
| 电源 | 低电、充电变化、按键关机、突然断电 | 不接受不适宜升级，关机保存顺序可解释，可恢复 |
| 长稳 | 正式版本 72 小时混合负载 | 无未知重启/死锁/持续内存下降，日志覆盖完整 |

建议初始时延验收线：关键 owner 事件排队 P95 ≤50 ms、P99 ≤100 ms，超过 250 ms 有明确原因；本地播放完成且云端结束已到达后，恢复聆听目标 ≤200 ms；正常网络下菜单首反馈目标 ≤80 ms。上述是后续测量与优化目标，不是当前实测保证；云端尚未给出结束确认时应单独记账。

内存阈值应由每条关键分配的峰值与安全余量确定。现有长稳脚本统一要求 `internal_min >=16384`，不能代替按阶段和连续块的分析，也不能为了通过检查简单降低阈值。
