# SD 会议监控功能与协议完整说明

基础说明版本：7.0.125 SD 本机网关测试版；有卡监控录音策略已更新至 7.0.150（2026-10-16）。本文为历史版本说明，场次 ID、监控封存及后续协议章节包含旧逻辑；当前接入以 [SD会议监控场次上传协议](SD会议监控场次上传协议.md) 为准，当前运行逻辑见 [功能逻辑与异常处理](SD会议监控功能逻辑与异常处理.md)。

本说明覆盖会议和监控的启停、录音、SD 保存、实时及历史上传、断线恢复、网关接收和网页播放，并列出该功能使用的控制消息、上传 JSON 和二进制布局。配网、普通对话、设备认证及 OTA 的完整协议不在本文范围，继续沿用工程既有实现。

有卡会议先完整录到 SD，结束后上传；有卡监控开启即连续录音，连续 120 秒无有效人声后暂停保存，检测到人声后恢复。在线时上传刚封存的短文件，离线时留存，恢复后区分当前音频和历史音频。无可用 SD 时沿用原在线流程，断网停止采集，不提供离线录音保证。

测试版的有卡音频统一送到本机网关。App 控制、普通云端连接和无卡音频仍连接原云端。没有 SD 专用 `hello`，也没有必须回复的 SD 能力消息。当前精简协议只要求开始文件、提交文件及整场结束的确认，不要求逐块 ACK。

## 1 运行条件与业务规则

### 1.1 选择录音路径

| 启动条件 | 会议 | 监控 |
| --- | --- | --- |
| SD 已挂载、存储服务可用、有空间 | 连续保存全部音频，结束后上传 | 连续录音，120 秒无人声后暂停，有人声后恢复；封存文件后上传 |
| 无卡、卡未就绪或存储不可用，云端在线 | 原实时上行流程 | 原实时上行及云端暂停恢复流程 |
| 无可用 SD，云端离线 | 不启动离线录音 | 不启动离线录音 |
| 有卡录音期间网络断开 | 本场继续采集和保存 | 本场继续按 120 秒静音暂停策略保存 |
| 有卡录音期间拔卡或持续写失败 | 停止本场，保留可恢复内容 | 停止本场，保留可恢复内容 |

“有卡”指当前可用的存储能力，不只是物理插卡。开始本场时决定数据路径；采集中不因插拔卡自动切换到另一套上传流程。有卡启动失败会报错退出，不将失败录音伪装成正常实时录音。

会议和监控互斥，与普通对话争用麦克风时由原音频所有者流程协调。开启时停止普通播报；真正获得麦克风、录音与存储就绪后才进入 ACTIVE。停止时先终止采集、排空缓存并封存；不会等待整场上传完成才关闭模式开关。后台上传不重新打开会议或监控。

设备本地在有卡时可以离线开启、关闭，仍需要已保存的绑定配置来确定录音归属，不要求现场联网认证。App 的远程指令仍需普通云端连接。已有会话断网重连保持本场 ID；停止后再开启生成新 ID。过期的开启回复受本地停止代次检查约束，不能用于恢复已经停止的场次。

### 1.2 场次和身份

| 标识 | 当前含义 |
| --- | --- |
| `device_id` | 接收连接关联的设备身份；正式环境来自现有认证，不能信任音频内容自报身份 |
| `audio_session_id` | 一次开启到停止的场次 ID；有卡时设备生成 `meeting_` 或 `monitor_` 加 16 位随机十六进制文本 |
| `segment_index` | 本场从 0 开始的文件编号，封存、续传、实时转历史时保持不变 |
| `segment_id` | 新场次为 `sd_<audio_session_id>_<segment_index 的八位十六进制>`，同一文件始终不变 |
| `request_id` | 单次控制或上传请求的关联 ID，不是会议 ID；重新 begin、commit 或整场结束可生成新值 |
| 连接 epoch | 设备内部的连接代次，不是线上 JSON 字段；旧连接 ACK 不可确认新连接的请求 |

例如场次 `meeting_81326b4afea7bbbf` 的第 20 个文件，`segment_index=19`，对应 `segment_id=sd_meeting_81326b4afea7bbbf_00000013`。设备文件名中的全局存储序号不一定等于场次编号，接收端以 begin 和归档头为准。

设备按设备 ID 与绑定密钥的摘要核对本地数据归属。解绑、换绑或换卡后，归属不匹配的旧录音不自动上传到新归属；也不自动删除。

### 1.3 在线、时长与容量

有卡业务的在线状态来自普通云端业务连接就绪，不能只看 Wi-Fi 图标。7.0.136 起关闭设备端测试页及模拟断网开关，离线测试使用真实网络断开；此前启用测试页的版本还受 UI 模拟断网开关控制。测试网关可达性是另一条件：云端在线而电脑网关不可达时仍录音、保留文件并重试；不会改投正式云端。

当前会议、监控的离线预算均为每场累计 8 小时，在线时间不消耗该离线预算。监控静音期间虽然不持续写文件，离线时长仍累计。恢复网络不清零已经用掉的预算；达到上限后结束采集，不因网络回来自动续开原场。

16 kHz、单声道 PCM16、20 ms 一帧时，8 小时连续录音为 1,440,000 帧。每帧 640 字节 PCM、22 字节 NA 头、4 字节记录长度，合计约 959 MB，另有文件头尾和索引。当前归档配额下限 1536 MiB，并保留 16 MiB 文件系统空闲余量；已有积压也占配额。八小时支持以实际可用空间和正常供电为条件，不自动格式化，不删除未确认数据腾空间。

## 2 会议流程

```text
本地开启或接收 App 指令
  → 确定有卡路径，建立场次清单
  → 麦克风采集全部 PCM，连续 sequence 和采集时间
  → 缓存 → SD writer → 分段 .ready 文件
  → 期间网络变化只影响在线状态，不触发本场上传
  → 用户停止、到达时长上限或异常结束
  → 排空缓存、封存尾段、记录 ended 和 complete
  → 在线时按文件上传；离线时保留待传
  → 每个文件 commit 成功并保存确认记录后删除本地文件
  → meeting_audio_session_end → 对应 ACK → 本场上传完成
```

当前本机网关测试版文件上限配置为 4 MiB。会议按完整记录切分，满段实际为 4,193,930 字节、6297 帧、125.94 秒；尾段按实际帧数保存。已有 1 MiB 文件继续正常上传，不在设备上重新合并。监控仍受实时 48 帧（960 ms）、历史 1500 帧（30 s）和在线边界限制。增大文件不增加录音缓冲，原有每 100 帧同步文件的策略保持。“完整一场”由一组有序文件和场次记录组成，不要求设备生成一个巨大的文件。

多场会议独立保存。调度按保存的结束时间选择同类场次，会议与历史监控轮换；失败场次在本轮暂缓，其他场次可继续。结束时间是开机时间，跨重启的严格自然时间先后不是当前协议保证，不能据此生成伪造的 UTC 会议日期。

## 3 监控流程

### 3.1 人声与文件切分

从 7.0.150 起，有卡监控开启即连续保存全部采集音频，包括静音和环境声。连续 120 秒未确认有效人声后封存尾段、暂停保存新音频，监控模式和麦克风监听保持开启；已有文件继续上传。连续约 200 ms 有效人声会重置无声计时，短促候选噪声不重置计时。暂停后再次连续检测到约 200 ms 有效人声便本地恢复，并保存最多约 500 ms 前置音频，无需等待云端暂停或恢复 ACK。在线、离线策略相同，网络切换不重置计时或场次 ID。

暂停不是结束场次；只有用户关闭、时长限制或采集故障等真正结束条件才生成场次结束记录。麦克风不连续会标记采集不完整，清掉旧前置缓存后保持原录音/暂停意图。检测器不是说话人识别，环境声是否误判仍需实机验证。无卡监控的云端暂停/恢复流程不变。

7.0.151 将写卡积压与上传取消分开：写入队列达到 64 帧时暂停下一次读取，回落至 32 帧以内继续；等待期间保留连接并正常接收 ACK。下线、OTA、关机、介质故障或连接代次变化仍会中止本次上传。目录锁暂时被写卡占用时让出调度，不因此重新建连。失败场次只按其 ID 暂缓，本轮仍尝试其他场次，下一轮重试未完成项。

异步尾段按产生顺序取得写入权，避免后来的尾段先分配文件编号。测试网关对旧固件留下的监控尾段编号乱序，先核对原编号清单，再按归档内采集时间排序拼接；不修改 ID、不删除音频、不补造成功确认，真正的时间重叠仍拒绝场次完成。会议顺序校验不变。

| 当前状态 | 封存规则 | 上传类型 |
| --- | --- | --- |
| 在线录音期间的音频 | 最多 48 帧，约 960 ms；暂停或结束时封存尾段 | 满足新鲜度条件时为实时 |
| 离线录音期间的音频 | 最多 1500 帧，约 30 秒；暂停或结束时封存尾段 | 历史 |
| 在线离线属性发生切换 | 先封存上一类尾段，再写新段 | 分段分别分类 |

前置缓存保留原序号和时间。网络刚恢复时，前置缓存里较早的音频不会因为现在上传就被视作新实时音频。

### 3.2 实时与历史判定

同时满足以下条件，才按 `monitoring_audio_realtime` 上传：本次开机产生、采集时在线、文件已经封存且未确认、采集起点不早于最近恢复在线的时间、begin 时距离文件最后一帧不超过 3000 ms。其余使用 `monitoring_audio_history`。

实时文件 begin 额外带 `capture_age_ms`。网关到 commit 时再次判断：`capture_age_ms + 本次事务耗时 > 3000 ms` 则保存为历史处理类别，仍回复原实时前缀 ACK。内容、文件 ID、场次和序号不变。

恢复后优先上传当前实时文件，空闲时补历史。监控仍活动时使用较短的 v1 事务保持可让位；停止后，剩余历史可使用 v2。实时优先不是硬性一秒到达保证，写卡、链路和接收端耗时都会影响延迟。

云端接入时应让实时文件进入当前监控处理，历史文件进入历史内容处理，不补发过时的即时告警。**本机测试网关只接收、分类、校验和提供播放，不实现云端识别、转写或告警业务。**

## 4 控制消息与无卡实时音频

以下沿用现有普通云端连接，与 SD 文件上传是两套不同的事务。不要用文件 `commit_ack` 控制模式开关，也不要把 `NWXCH1` 当成实时 NA 音频。

### 4.1 设备申请和云端控制

设备申请开关，`mode` 为 `meeting` 或 `monitoring`，`state` 为 `enabled` 或 `disabled`：

```json
{"type":"audio_mode_request","request_id":"device_open_001","mode":"meeting","state":"enabled","reason":"ui_open"}
```

```json
{"type":"audio_mode_request_ack","request_id":"device_open_001","mode":"meeting","state":"enabled","ok":true}
```

App 经云端下发：

```json
{"type":"device_command","command":"set_audio_mode","request_id":"cloud_open_001","mode":"meeting","state":"enabled"}
```

设备实际启动后回复，失败时 `ok:false`，`message` 说明结果；主程序在冲突等场景还可能附加 `error_code`、`active_mode`：

```json
{"type":"device_command_ack","command":"set_audio_mode","request_id":"cloud_open_001","mode":"meeting","state":"enabled","ok":true,"message":""}
```

控制字段约束：`request_id` 为 1～47 个字母、数字、点、下划线或短横线；`mode/state` 按上述枚举。`reason` 可选；控制解析器中的 `audio_session_id` 可选、最长 47 字节。会议兼容 `interrupt_current_turn:true` 和 ACK 中的 `current_turn_cancelled:true`，用于取消旧对话。监控开启沿用原停止普通对话语义。

有卡本地开启可直接启动 SD 场次，不把云端 `audio_mode_request_ack` 当作录音前置条件。有卡场次 ID由设备本地创建，文件 begin 是接收端关联该场次的依据；不要假设现有控制 ACK 都携带场次 ID。关闭控制的 ACK 表示模式关闭，不表示后台文件已经全部上传。

### 4.1.1 有卡录音的重连控制（7.0.149）

本地启动的有卡录音进入 ACTIVE 后，在线时使用已有的 `audio_mode_request` 同步状态；正在录音时重连也同步一次。每次连接使用新的 `request_id`，保持本地 `audio_session_id`。同一次同步失败重试沿用请求 ID，间隔 1 秒，最多发送 3 次。App 指令已在当前连接启动的场次不重复申请；收到匹配的成功 ACK 后完成同步，不重新启动录音、不切文件、不重置帧序号。

```json
{"type":"audio_mode_request","request_id":"meeting_sync_1_12345678","mode":"meeting","state":"enabled","reason":"offline_audio_recovered","audio_session_id":"meeting_0123456789abcdef"}
```

这属于原有云端模式控制，不是 SD 能力协商。没有新增 `hello`，没有增加 SD 文件字段或数据阶段 ACK；同步失败、拒绝或超时均不停止本地录音。

重连同步期间，设备拒绝未指定场次的关闭指令，回复现有 `device_command_ack`，`ok=false`、`state=enabled`、`message=sd_state_sync_pending`。设备记录接收顺序，先收到的关闭不会因为 ACK 队列先被处理而错误生效。成功 ACK 之后收到的新关闭指令正常执行；不回应时，保护最多持续 5 秒，之后允许新请求关闭。设备本地停止始终有效；带当前场次 ID，或此前匹配控制事务关联的云端场次 ID 的关闭立即执行。其他场次的关闭回复 `audio_session_mismatch`。

每场保留最近 4 个被重连保护拒绝的请求 ID，相同请求重发仍拒绝，避免旧关闭在保护期后重试成功。结束当前场次后清除这些临时记录。云端返回的控制场次 ID 只作控制别名，不改写 SD 归档 ID。

兼容边界：原协议中不带场次的关闭没有“同步状态/用户操作”的可靠来源标识，设备不能无条件区分两者。用户恰好在上述保护期间通过 App 停止，可能收到拒绝，需要同步完成后重新操作；设备本地停止不受影响。超过保护期才首次到达的无场次旧关闭，也不能仅凭当前字段可靠辨认。因此仍需实机复测重连与 App 控制，不能把有界保护宣称为任意时序下都能判定用户意图。

### 4.2 无卡在线数据

无卡仍经原 `listen` 建立实时流，随后发送 NA 二进制帧；停止时收尾并发送 `listen` stop。典型字段如下，实际 request/session 值由当前控制流程生成：

```json
{"type":"listen","state":"start","mode":"meeting","audio_session_id":"meeting_stream_001","request_id":"cloud_open_001"}
```

```json
{"type":"listen","state":"stop","mode":"meeting","audio_session_id":"meeting_stream_001"}
```

现有监控实时流程使用暂停和恢复控制，例如：

```json
{"type":"monitoring_capture_control","request_id":"monitor_pause_001","mode":"monitoring","state":"pause","audio_session_id":"monitor_stream_001","reason":"silence","silence_ms":1000}
```

```json
{"type":"monitoring_capture_control_ack","request_id":"monitor_pause_001","mode":"monitoring","state":"pause","audio_session_id":"monitor_stream_001","ok":true}
```

恢复时 `state:"resume"`，省略 `silence_ms`。有卡 SD 监控使用本地录音和文件通路，不依赖这条 ACK 来保存人声。原 `listen` 不增加新的 `listen_ack` 启动门禁；测试网关兼容回复不代表正式设备新增该要求。

旧离线恢复控制保留 `audio_mode_request` 携带旧 `audio_session_id`、新 `request_id`、`reason:"offline_audio_recovered"` 的能力；有卡新流程在断线期间本就持续录音，不需要通过重新申请来开启第二场。无卡断网期间没有可恢复的本地音频，不能用会话 ID 补回未录制内容。

## 5 SD 上传消息总表

WebSocket Text 使用 UTF-8 JSON 对象；Binary 使用第 7 节格式。上传一条连接同一时刻绑定一个文件事务。数值字段使用 JSON number 的整数值，布尔值必须使用 `true/false`。

| 用途 | begin / begin_ack | chunk_ack | commit / commit_ack |
| --- | --- | --- | --- |
| 有卡会议 | `meeting_audio_begin` / `meeting_audio_begin_ack` | `meeting_audio_chunk_ack` | `meeting_audio_commit` / `meeting_audio_commit_ack` |
| 监控实时 | `monitoring_audio_realtime_begin` / `monitoring_audio_realtime_begin_ack` | `monitoring_audio_realtime_chunk_ack` | `monitoring_audio_realtime_commit` / `monitoring_audio_realtime_commit_ack` |
| 监控历史 | `monitoring_audio_history_begin` / `monitoring_audio_history_begin_ack` | `monitoring_audio_history_chunk_ack` | `monitoring_audio_history_commit` / `monitoring_audio_history_commit_ack` |
| 旧归档兼容 | `offline_audio_begin` / `offline_audio_begin_ack` | `offline_audio_chunk_ack` | `offline_audio_commit` / `offline_audio_commit_ack` |

整场结束另有：

- `meeting_audio_session_end` / `meeting_audio_session_end_ack`。
- `monitoring_audio_session_end` / `monitoring_audio_session_end_ack`，实时和历史共用这一场结束消息。

旧 `offline_audio_*` 携带 `mode:"archive_only"`，仅归档，不重复驱动在线业务。三个新前缀不携带该 mode，类型本身决定业务用途。没有名为 `meeting_audio_chunk` 的 JSON 数据消息，实际数据走二进制。

## 6 JSON 格式与确认条件

下面用一个 48 帧、960 ms、32,096 字节的小会议文件示例说明格式。CRC `3074630480` 对应工程测试 fixture 的该样本，实际上传必须计算自己文件的 CRC，不能照抄。

### 6.1 开始文件 begin

```json
{
  "type": "meeting_audio_begin",
  "request_id": "offline_begin_12345678",
  "segment_id": "sd_meeting_demo_01_00000000",
  "audio_session_id": "meeting_demo_01",
  "segment_index": 0,
  "capture_start_ms": 0,
  "capture_end_ms": 960,
  "total_bytes": 32096,
  "crc32": 3074630480,
  "window_bytes": 524288
}
```

| 字段 | 类型和约束 | 说明 |
| --- | --- | --- |
| `type` | string，见消息表 | 必填 |
| `request_id` | string | 本次 begin 关联 ID；当前设备生成约 22 字节的 ID |
| `segment_id` | string | 文件唯一键，当前新类型为 1～47 个字母、数字、下划线或短横线 |
| `audio_session_id` | string，1～47 字节 | 新类型必填，归档头中必须一致；设备生成值更短，便于组成 segment_id |
| `segment_index` | uint32 | 新类型必填；本机网关接受 0～999999，与归档头一致 |
| `capture_start_ms` | 非负整数 | 新类型必填，相对本场开始的采集起点，毫秒 |
| `capture_end_ms` | 大于 start 的整数 | 新类型必填，最后一帧结束时间，左闭右开 |
| `capture_age_ms` | 非负整数 | 仅实时监控必填，begin 时距最后一帧结束的时间，重试时重新计算 |
| `total_bytes` | uint32 | 完整归档文件大小，包含头、记录长度和尾；本机接收范围 128～4,194,304，当前测试设备段上限配置 4 MiB |
| `crc32` | uint32 | Footer 中的音频记录 CRC，不是整文件逐字节 CRC |
| `replay_version` | 旧格式可选，值 2 | 7.0.125 配对网关的大窗口请求省略；正式云端及旧归档保持原规则 |
| `replay_revision` | 旧格式可选，值 2 | 旧格式仍须 version=2 且 revision=2；revision=1 不开放窗口，避免旧固件对齐问题 |
| `window_bytes` | 可选，8064～524288 | 申请的最大窗口归档字节数，不含 NWXCH1 头 |

时间在设备端由 64 位毫秒值计算；JSON 使用可精确表示的非负整数，本机网关要求不超过 `Number.MAX_SAFE_INTEGER`。相对时间不受 SNTP 校时影响，也不代表 UTC。

实时监控用同一组字段，将 `type` 换为 `monitoring_audio_realtime_begin`，增加 `capture_age_ms`；当前活动监控不申请 v2。历史监控换为 `monitoring_audio_history_begin`，省略 age。旧归档 begin 只需 `type/mode/request_id/segment_id/total_bytes/crc32`，场次和采集格式从归档头解析。

成功回复：

```json
{
  "type": "meeting_audio_begin_ack",
  "request_id": "offline_begin_12345678",
  "segment_id": "sd_meeting_demo_01_00000000",
  "ok": true,
  "next_offset": 0,
  "window_bytes": 524288
}
```

7.0.125 配对测试网关使用精简格式：typed begin 同时省略 `replay_version` 和 `replay_revision`，以合法 `window_bytes` 申请窗口；ACK 只回 `window_bytes`。仅省略其中一个字段不表示精简格式。显式旧版本必须保留原有双字段门槛。`offline_audio_*` 旧归档不隐式启用新格式。活动监控仍不申请大窗口。

`next_offset` 为已可靠保存的连续字节数，范围 0～total_bytes。全新文件为 0，断点可以是任意字节，不必对齐 NA 或 NWXCH1。已提交文件返回 total_bytes，设备可直接重做 commit。不返回有效窗口同意时，设备按 v1 发送，并保留 commit 的完整长度和 CRC 字段；这仍是普通 begin ACK，不是新的 hello。

### 6.2 数据确认 chunk_ack

v1 例如持久化 offset=0、长度 8064 的分片后：

```json
{"type":"meeting_audio_chunk_ack","request_id":"offline_chunk_12345679","segment_id":"sd_meeting_demo_01_00000000","ok":true,"next_offset":8064}
```

v2 示例将全部 32096 字节作为一个窗口分成多个二进制帧，最后一帧标记窗口结束；窗口所有字节可靠保存后只回复一次：

```json
{"type":"meeting_audio_chunk_ack","request_id":"offline_window_12345679","segment_id":"sd_meeting_demo_01_00000000","ok":true,"next_offset":32096}
```

ACK 中 request_id 必须等于二进制头中本片或本窗口的 ID。v1 只在确认有效推进后继续；v2 要求 next_offset 精确等于窗口尾端，不接受中间偏移作为整窗口成功。不能在仅进入内存缓冲时回复成功。

### 6.3 提交文件 commit

收到最后一个数据 ACK 后：

```json
{"type":"meeting_audio_commit","request_id":"offline_commit_12345680","segment_id":"sd_meeting_demo_01_00000000"}
```

```json
{"type":"meeting_audio_commit_ack","request_id":"offline_commit_12345680","segment_id":"sd_meeting_demo_01_00000000","ok":true}
```

以上为精简事务的 commit：长度和 CRC 已在匹配的 begin 中保存，因此不重复发送。只有成功收到精简窗口确认后才能省略；接收端仍按 begin 中的值做完整校验。若显式携带长度或 CRC，必须与 begin 一致。旧格式、未协商窗口、活动监控及正式云端继续携带 `total_bytes`、`crc32`。窗口协商后因内存不足切换 v1 小包，仍属于原精简事务，可以省略重复字段。重连后先重新 begin，再续传或 commit。

commit 不重复携带场次元数据。接收端必须校验长度、NWXOFF1/NWXEND1、记录边界、NA 格式、帧数、payload_bytes 和 CRC，并核对 begin 中场次、编号、模式。新有卡格式还校验 16 kHz、单声道 PCM16、20 ms、每帧 640 字节 PCM。

归档原子发布为完成对象、索引可靠保存后，才回复成功。设备收到匹配的成功 ACK 后，先保存本地分段确认状态，再删除文件。删除失败会在之后清理，不能将该文件重复视为未提交音频。

### 6.4 整场结束 session_end

```json
{"type":"meeting_audio_session_end","request_id":"sd_end_12345681","audio_session_id":"meeting_demo_01","segment_count":1,"recording_complete":true}
```

```json
{"type":"meeting_audio_session_end_ack","request_id":"sd_end_12345681","audio_session_id":"meeting_demo_01","ok":true}
```

监控换为 `monitoring_audio_session_end` 和对应 ACK。`segment_count` 是应有分段总数，当前网关接受 0～1000000。零音频监控允许 count=0；`recording_complete` 为采集完整性布尔值，不是“网关已有文件可播放”。

当前设备实际发送的字段只有上述五项，**没有发送 `missing_segments` 或 `gap_ranges`**。异常结束使用 `recording_complete:false`；网关根据应有数量和已提交索引推导缺段，结合帧时间和序号分析缺口。不要将旧方案中拟增加的缺口字段当成现有协议必填项。

完整场次只有 0～count−1 全部提交、分段完整标记满足要求、采集区间不重叠，网关才确认完整。异常场次可确认收到全部可恢复内容并记录为部分录音。整场 ACK 成功后设备将清单标记 done；当前代码保留场次元数据，没有自动清理全部已完成清单的策略。

整场结束幂等。同一场次重试不得改变 mode、count、recording_complete；相同进行中的请求共用整理任务，已完成场次直接回复持久化结果。确认后不接受该场新增文件。

### 6.5 错误回复和匹配

```json
{"type":"meeting_audio_begin_ack","request_id":"offline_begin_12345678","segment_id":"sd_meeting_demo_01_00000000","ok":false,"next_offset":0}
```

文件错误使用对应步骤 ACK；整场错误使用对应 session_end_ack 并回传 audio_session_id。`error_code`、`message` 可用于诊断，但设备不依赖其具体枚举。当前本机网关 begin/commit/session_end 校验失败返回负 ACK；严重二进制格式或偏移错误可能直接断开连接，设备按续传流程恢复，不能假定所有错误都会有负 ACK。

新类型 ACK 必须匹配 type、request_id、segment_id；整场 ACK 匹配 audio_session_id。begin/chunk 还要求合法整数 next_offset。设备内部同时检查连接 epoch。旧 offline_audio ACK 兼容缺省 segment_id，但新实现应始终回传，不沿用该兼容放宽。

## 7 二进制分片 NWXCH1

每个 WebSocket Binary 消息为 `64 字节头 + N 字节归档内容`。本节多字节整数均为 little-endian；WebSocket 自身的长度和掩码规则仍按 WebSocket 标准。

| 偏移 | 字节数 | v1 | v2 |
| ---: | ---: | --- | --- |
| 0 | 6 | ASCII `NWXCH1` | 相同 |
| 6 | 2 | 0，保留 | 相同 |
| 8 | 4 | version=1 | version=2 |
| 12 | 4 | 当前 payload 在完整归档中的 offset | 相同 |
| 16 | 4 | payload 长度 N，1～8064 | 相同 |
| 20 | 40 | 本片 request_id，ASCII、NUL 填充，最多 39 字节 | 本窗口 request_id，窗口内所有帧相同 |
| 60 | 4 | 0，保留 | flags：bit0=1 表示窗口最后一帧；其余位为 0 |
| 64 | N | 原始归档字节 | 原始归档字节 |

二进制头没有 segment_id、audio_session_id 或 type，由已成功 begin 的事务确定。不能把文件 ID 截断塞入 40 字节 request_id 字段。

v1 每片持久化 ACK 后发送下一片。当前设备独立测试连接和正式共享连接的单片 payload 上限都为 **8064 字节**；接收端兼容所有 1～8064 长度，不假设固定长度或固定增量。

v2 在 begin ACK 同意后使用。一个窗口内 offset 连续、ID 相同，接收端收齐带结束标记的窗口后持久化并回复累计偏移。下一窗口必须等上一窗口 ACK；ACK 等待期间设备可以预读下一窗口。接收端对相同窗口重发应核对已保存字节一致，不追加重复内容。7.0.124 的 SD 支撑大窗口若丢 ACK、收到错误偏移或中途取消，会结束当前独立上传连接并保留 SD 文件；下一次 begin 以网关 next_offset 为准恢复，不从已经复用的 RAM 重发。原单槽保留路径继续支持同连接窗口重试。

设备使用两块最大 128 KiB 预读缓冲，一次最多合并四个独立 WebSocket 帧写入 TCP。合并不改变单帧格式，每帧仍有自己的掩码。7.0.124 将内存槽和确认窗口分离：正常预读模式把最多四个槽合为一个确认窗口，受 begin ACK 的上限约束，最大实际窗口 512 KiB。槽内数据在同步发送完成后可被下一次预读复用；未确认数据始终保留在不可变 SD 文件中。跨槽的短帧仍是合法的 1～8064 字节 payload，只有协议窗口末帧设置 flags=1。资源不足时可缩小缓冲；串行降级和读取诊断模式保留单槽确认。

当 begin 已同意 v2 但设备尚未发送任何数据且无法分配安全缓冲时，允许同一文件改发 v1。网关必须接受这条兼容路径。窗口已开始后发生错误不能擅自切换格式，需退出并重新 begin 续传。

## 8 SD 归档格式

```text
96 字节 NWXOFF1 Header
重复 frame_count 次：uint32 record_length + record_length 字节完整 NA 帧
32 字节 NWXEND1 Footer
```

所有整数 little-endian，字符串为定长 ASCII/NUL 填充。没有 WAV 头，也没有 MP3/Opus 压缩；不能把整个 .complete 文件直接当 PCM 播放。

### 8.1 NWXOFF1 Header

| 偏移 | 字节数 | 字段及当前值 |
| ---: | ---: | --- |
| 0 | 8 | `NWXOFF1` 加 NUL |
| 8 | 2 | version=1 |
| 10 | 2 | header_bytes=96 |
| 12 | 1 | mode：0 会议，1 监控 |
| 13 | 1 | channels=1 |
| 14 | 2 | codec=1，PCM16 |
| 16 | 4 | sample_rate=16000 |
| 20 | 2 | frame_duration_ms=20 |
| 22 | 2 | source_flags：新场次为 2；旧归档可能为 0 或镜像值 1 |
| 24 | 4 | segment_index；新场次与 begin 一致 |
| 28 | 8 | start_uptime_ms；新场次为本文件第一帧采集开机时间 |
| 36 | 48 | session_id；新场次与 begin.audio_session_id 一致 |
| 84 | 12 | 保留，0 |

### 8.2 每条记录和 NA 帧

记录长度前缀为 uint32，不计入 NA 帧自身。当前新有卡录音 record_length=662，每条记录共 666 字节。

| NA 内偏移 | 字节数 | 字段及当前值 |
| ---: | ---: | --- |
| 0 | 2 | ASCII `NA` |
| 2 | 1 | version=1 |
| 3 | 1 | codec=1，PCM16 |
| 4 | 1 | flags，位含义见下文 |
| 5 | 1 | channels=1 |
| 6 | 2 | sample_rate=16000 |
| 8 | 2 | frame_duration_ms=20 |
| 10 | 4 | sequence，采集帧序号 |
| 14 | 4 | timestamp_ms，开机采集毫秒值低 32 位 |
| 18 | 2 | payload_bytes=640 |
| 20 | 2 | 保留，0 |
| 22 | 640 | 320 个有符号 int16 PCM 样本，little-endian |

flags 的已定义位：`0x01 START`、`0x02 END`、`0x04 VAD_SPEECH`。会议归档通常为 0，监控按本地 speech 标记；不能要求每个 SD 文件都具有 START/END。无卡实时流可使用 START/END 和结束控制，不能套用“归档每条必须 640 字节”的限制去拒绝旧实时流合法尾帧。

新有卡会议序号在整个场次连续，不因文件切分重置。监控序号随实际采集推进，静音未保存造成的跳号属于预期筛选，不能直接判作传输丢帧。采集完整性还要结合设备 dropped/discontinuity、时间区间和完整标记判断。

### 8.3 NWXEND1 Footer

| 偏移 | 字节数 | 字段及当前值 |
| ---: | ---: | --- |
| 0 | 8 | `NWXEND1` 加 NUL |
| 8 | 2 | version=1 |
| 10 | 2 | footer_bytes=32 |
| 12 | 4 | frame_count |
| 16 | 8 | payload_bytes：全部完整 NA 帧的长度之和，包含各自 22 字节头 |
| 24 | 4 | crc32 |
| 28 | 1 | complete：1 正常封存，0 异常或降级边界 |
| 29 | 3 | 保留，0 |

长度必须满足 `total_bytes = 96 + frame_count×4 + payload_bytes + 32`。当前 PCM 场次还满足 `payload_bytes=frame_count×662`。Footer.complete 不是“整场结束”或“已经上传”的标志；正常容量分段也会是 1。complete=0 的有效文件仍可提交保存，但不能伪装成完整场次。

### 8.4 CRC

CRC-32/ISO-HDLC：反射多项式 `0xEDB88320`，初始寄存器 `0xFFFFFFFF`，结果异或 `0xFFFFFFFF`，标准向量 `123456789 → 0xCBF43926`。

输入仅为文件顺序中每条完整 NA 帧的拼接，包括 NA 头和 PCM。不包含记录长度前缀、NWXOFF1、NWXEND1、NWXCH1 或 WebSocket 头。可以对 NA 帧连续累计，等价于对拼接后的数据一次计算。

commit 必须满足 `计算值 == Footer.crc32 == begin.crc32`；携带 `commit.crc32` 时还必须与其相同。JSON CRC 用十进制 uint32，Footer 用 little-endian uint32。CRC 检查传输内容完整性，不替代连接身份认证。

## 9 断点恢复与异常处理

| 情况 | 当前处理 |
| --- | --- |
| 断网或 TCP 失败 | 保留设备文件和网关可靠前缀；重连使用同 segment_id，新 begin 获取 next_offset |
| ACK 丢失 | v1 和单槽 v2 最多 3 次交换尝试；SD 支撑的跨槽 v2 窗口结束连接，下一次 begin 读取已落盘偏移后续传，避免重发已复用的 RAM |
| begin/chunk/commit ACK 超时 | 每次等待 2500 ms；不能用无效 ACK 推进或删除 |
| 整场结束 ACK 慢 | 最长 60000 ms，期间约每 100 ms 检查取消、连接和录音压力 |
| 重复 begin/commit/session_end | 同身份和内容幂等处理；不重复转写、入库或触发告警 |
| 同 ID 不同内容、模式或场次 | 拒绝，不覆盖已经接收的对象 |
| 切换到实时文件或开始新录音 | 调度在安全边界让位；失败/取消保留可靠前缀，之后重新 begin |
| 正在发送的帧中断 | 交由传输层处理完整性或重连，不能把半帧继续当成另一个文件 |
| 正常停止 | 排空暂存、封存，停止开关不等待网络 |
| 低电量或正常关机 | 尝试在关闭预算内停止并封存；未完成内容按异常恢复处理 |
| 突然掉电 | 恢复完整记录前缀，舍弃不完整尾记录，标记异常结束；不自动重新开麦 |
| SD 暂时读写失败 | 有限重试与介质恢复；临时 I/O 错误不直接当成坏音频删除 |
| 文件确认损坏或缺失 | 场次标为部分录音；保留损坏原文件，继续处理其他有效场次 |
| 清单损坏 | 单独隔离，正常清单继续；无法恢复的内容不能宣称完整 |
| 卡满或积压超过配额 | 停止并报告，不自动清理未确认录音 |
| 已确认文件删除失败 | 已保存的 ACK 状态用于之后清理，避免重复业务处理 |

切换文件 A→B→A 时，接收端可丢弃 A 未确认的内存窗口，但必须保留其可靠文件前缀和固定元数据。新 begin 接管同设备事务后，旧连接不能继续写入新事务。

当前网关按 `device_id + segment_id` 去重，场次按 `device_id + audio_session_id` 分组。仅有成功 chunk ACK 不等于文件可用；仅有 commit 不等于整场完成。

测试连接每个任务最多尝试 3 次，任务间有退避；暂时失败后文件仍保留，监督器可再次调度。会议采集中暂停后台读取；监控实时优先，SD 写入和采集压力升高时上传主动让位。存储锁不跨网络 ACK 等待持有。

开机先在本地盘点 SD。只有确有待上传文件、尚未确认的场次结束信息，或盘点发现需要复查的历史 `.ready.bad` 文件时，才启动上传任务。单纯的“开机需要复查”标记不会连接网关；已完成场次不会因重启重新上传。目录读取失败时保留上一份待办状态并触发存储恢复，不视为空目录。

7.0.123 调整 OTA 与后台上传的交接：正在会议/监控录音、场次启停、配网、关机或存在未释放的异常传输资源时，仍拒绝升级。只有普通后台补传时，OTA 可按原协议进入队列；队列预留立即阻止新的补传，并让已有补传在文件读取、完整网络帧及 ACK 等待边界退出。OTA 控制器最多等待 5 秒，确认上传、预读及测试连接释放后才进入升级流程；超时则本次升级失败，不强制删除任务或释放仍被使用的缓冲。未取得提交确认的 SD 文件保留，OTA 失败释放预留或升级重启后按原断点协议继续。主云连接不因正常补传让位而主动关闭，OTA 和 SD 上传消息格式保持不变。

## 10 整场组织与播放

接收端按设备、场次、segment_index 组织，不能按到达先后连接数据。逐个解析归档，去掉文件头尾、记录长度和 NA 头，得到 PCM16。会议完整场次按帧序号和时间核对连续性，发现真实缺口要显示异常，不能悄悄压缩后宣称完整。

监控只保存语音区间及前后缓冲，保存音频长度可能明显短于场次经过时间。若云端需要还原时间线，应按 capture_start/end 和帧时间放置音频、给静音区间补静音；如做紧凑回听，应说明省略静音。

NA timestamp 为 32 位开机时间，跨回绕要按场次展开；begin 时间为相对场次的 64 位毫秒值。不同开机的原始 uptime 不能直接比较。没有可靠绝对时钟映射时保留相对时间，不把接收时间当作录音时间。

**本机网页采用紧凑回听**，按已提交文件顺序提取 PCM 后生成 WAV，不给静音或缺失区间填零。准备播放时使用文件快照，新文件到达后需重新准备。网页能播放，只证明有可用音频；必须看整场结束状态及完整性核查才能判断是否收齐。

## 12 本机测试网关发现与网页接口

### 12.1 连接方式

电脑网页：`http://127.0.0.1:8810/`。设备不能使用 127.0.0.1 连接电脑，而是通过配对 UDP 8811 发现电脑当前局域网 IP，再连接 `ws://<电脑IP>:8810/api/device/ws?device_id=<设备ID>`。设备与电脑需要局域网互通，热点客户端隔离会阻断连接。

配对配置保存在 `runtime-logs/sd-test-gateway/settings.json`，包含网关身份和发现密钥。构建和启动共用该文件，不能随意重新生成；本文不列出密钥。UDP 发现验证的是测试网关身份，当前 LAN WebSocket/网页不是生产账户认证或加密存储服务。

没有 SD hello。连接成功即发送文件 begin 或整场结束。普通云端的原认证、hello 和心跳保持；本机网关兼容旧客户端 hello 不代表新固件需要发送。

### 12.2 UDP 二进制格式

查询发往 UDP 8811，共 72 字节：

| 偏移 | 长度 | 内容 |
| ---: | ---: | --- |
| 0 | 8 | `NWXSDQ1` 加 NUL |
| 8 | 16 | 本次随机 nonce |
| 24 | 16 | 网关 ID，32 字符 hex 解码后的字节 |
| 40 | 32 | HMAC-SHA256，输入前 40 字节，使用配对密钥 |

回复共 76 字节，返回查询源端口：

| 偏移 | 长度 | 内容 |
| ---: | ---: | --- |
| 0 | 8 | `NWXSDR1` 加 NUL |
| 8 | 16 | 原 nonce |
| 24 | 16 | 原网关 ID |
| 40 | 2 | WebSocket 端口，**big-endian**，当前 8810 |
| 42 | 2 | 0 |
| 44 | 32 | HMAC-SHA256，输入回复前 44 字节 |

设备检查长度、标识、nonce、网关 ID、保留位和 HMAC 后，使用 UDP 报文来源 IP 作为 WebSocket 地址，不信任内容中的任意主机名。发现失败保留数据并重试，不切到正式云端。UDP 发现是测试设施，不要求正式云端实现。

### 12.3 网页 HTTP 接口

| 方法和路径 | 用途及主要结果 |
| --- | --- |
| `GET /api/status` | sessions、issues、endpoint/endpoints、discovery、devices、bytesPerSecond、receivedBytes、pending；7.0.122 网关增加只读 runtime 诊断 |
| `GET /api/sessions/<id>?offset=0` | 场次详情，records 每页最多 100 条；id 是网页场次 64 个十六进制字符的摘要，不是 audio_session_id |
| `POST /api/sessions/<id>/prepare` | 无必需请求体；生成播放快照，200 表示已准备、202 表示处理中，429 表示已有另一转换任务 |
| `GET /api/jobs/<id>` | 查询 state=preparing/ready/error、进度和 ready 后的 url |

## 13 性能策略和诊断

7.0.122 沿用全部线上字段和二进制格式，调整的是设备内存重试与诊断：

- 预读缓冲分配前重新读取当前 PSRAM 余量，分配后复查。复查失败也尝试更小批次，再缩小窗口；最多 20 个候选配置，不无限等待。
- 始终保留 768 KiB 录音 PSRAM 预算和 16 KiB 读任务余量，内部 DMA 保护线独立保留。确实没有合法 v2 配置时，在未发数据的前提下才回退 v1。
- 新日志区分预算不足、malloc 失败和分配后余量不足；记录最终窗口及批次数，便于确认是否消除不必要的整文件降级。
- TCP 增加等待次数、等待超时次数和单次最长等待，不改变发送顺序、超时、ACK 和断线策略。写入重试数不是无线 TCP 重传包数。
- 网关报告增加累计最大落盘耗时、事件循环最大间隔，以及最近 120 个有上传活动的采样区间。事件循环采样分辨率为 20 ms，约 20 ms 的观测值包含正常采样间隔，不代表额外阻塞了 20 ms。可将设备 writable_wait 与接收端忙碌程度和磁盘耗时对照；这些仅为测试诊断，不是设备上传协议字段。

500 KiB/s 的验收口径为：`本场归档文件总字节 / 1024 / (首个 begin 发出至整场结束 ACK 收到的秒数)`。应从零偏移开始、包含全部文件和结束确认。断点续传不能拿整文件大小除以只传尾部的耗时；网页短时速度、payload 峰值和分段平均都不能代替整场成绩。

目标适用于会议结束后或监控停止后的积压上传。活动监控优先实时延迟和录音完整性，不以占满带宽为目标。7.0.121 本轮 11 分 25.760 秒录音已核对 22 文件、34,288 帧、无缺口和 CRC 错误；整场约 214 KiB/s，未达 500。7.0.122 的实机速度和八小时运行需以新测试结果验收，不能从主机模拟成绩推定。

7.0.124 为每种模式缓存当前待传场次身份及无待办结果，绑定身份隔离；新场次、封存、结束、挂起、恢复等变化使缓存失效，索引 CRC 和确认落盘仍保留。修正 RX 竞争路径重复让出两个 tick，并在发送已发生足够长的 socket 等待后抵扣重复调度退让。当前仍需关注：长期大量已完成清单的首次目录扫描、存储清单自动清理策略、UI 菜单动画卡顿、无线及 TCP 发送等待、异常断电尾部损失。7.0.123 修复了空检查误启补传及正常后台补传阻挡 OTA 的交接问题；实机仍需验证上传中触发 OTA、升级失败后续传、断电及资源超时等场景。

## 15 7.0.125 优化与验证边界

本轮不扩大录音缓冲、不提高任务优先级、不改变 SD 时钟。保持两块最大 128 KiB 预读槽、最大 512 KiB ACK 窗口以及采集压力和内存余量保护。

- 独立明文网关的窗口发送采用有上限的进度容忍：无首字节进度时仍使用原发送期限（通常 1500 ms）；已有写入进度时，允许连续无进度最多 2000 ms，同时单次发送不超过原预算加 2000 ms（通常 3500 ms；调度延迟另计）。每次最多 10 ms 的 socket 等待后检查取消。部分帧最终失败仍关闭该连接，再按网关持久化偏移续传。普通云端、TLS 和实时语音的发送期限保持原规则。
- 同一上传任务保存最近八个完整验证状态，包含 CRC、帧边界和部分记录头。重连后从不超过网关偏移的最近检查点继续读取和校验。检查点绑定 segment_id、完整文件头尾、长度和介质代次；只在预读任务回收后发布，SD 恢复、任务重启或校验/读取错误后失效。没有检查点时从头校验，不能仅靠 seek 跳过校验。检查点不写入 SD/NVS，不跨重启信任旧状态。
- begin 和 commit 的精简只应用于本机配对网关的 typed 大窗口事务。二进制版本、窗口结束标志、ACK、CRC、文件提交和场次结束确认全部保留，不增加 hello。

7.0.124 最近一轮会议收到 22,796 帧、455.92 秒音频、15,182,648 字节归档；网关首个 begin 到整场结束约 33.676 秒，整场速度约 440.28 KiB/s。途中发生一次发送中断，恢复时重新读取已确认前缀约耗时 971 ms。本轮针对这些恢复开销，不把省掉的 JSON 字节算作显著提速。500 KiB/s 对同样数据要求不超过约 29.654 秒，仍需新固件实测。

验收应同时观察 `offline replay transport progress` 的恢复次数和停顿时间、`offline replay checkpoint` 的复用字节、整场 begin/session_end 时间、网关实际 CRC/帧序号、设备丢帧及任务资源回收。主机故障模拟能验证流程和边界，不能代替 ESP32 上的速度、供电、SD 兼容性和长时间稳定性测试。


## 16 7.0.126 接收调度与后台持久化修正

7.0.125 最近一轮会议为 `meeting_4f1e32503fa34bfd`，共 15,498 帧、309.96 秒音频、10,322,052 字节归档。网关首个 begin 到整场持久化结束耗时 27.559 秒，约 365.77 KiB/s；三份文件 CRC、帧序号和场次结束均完整。这轮没有重连，125 的断线检查点优化未被触发，不能用它解释速度收益。同样数据达到 500 KiB/s 需要总耗时不超过 20.160 秒。

已确认的代码问题：

1. 后台持久化门禁只检查界面和语音状态，没有排除正在上传的 SD 音频。设备处于休眠表情也会执行音量/诊断持久化服务。本轮三个可见调用耗时约 184、127、108 ms；这些是服务总耗时，包含锁和调度，不能全算作 Flash 写入时间。126 在补传期间延后这一闲时服务，上传释放后再处理待保存状态。主动关机保存和错误上报发送不受该门禁改变。
2. 独立明文上传连接沿用共享 I/O 锁和 RX 轮询。TX 持锁等待可写时，RX 因 tx_waiters 退让；空闲 RX 也每 10 ms 唤醒。126 仅在独立测试上传连接启用事件驱动接收，通过 select 等待可读，不再等待 TX 的 I/O 锁。SDK 必须启用 LWIP_NETCONN_FULLDUPLEX；握手、正式连接和 TLS 仍走原路径。每次空闲等待最多 100 ms，数据和 shutdown 可提前唤醒；关闭顺序仍是标记断开、通知退出、回收 RX、释放 socket。回收失败不释放被引用的连接。

诊断新增 `offline window ACK latency`：`wait_ms` 是发送完成后等待 ACK 的时长，`rx_to_owner_ms` 是 ACK 匹配回调至上传任务处理确认的时长，仅在成功的块确认等待至少 100 ms 时输出。回调在发送结束前发生时，后者也可能包含剩余发送时间，不能单独等同于纯调度延迟。RX 结束日志记录 read/select/空闲超时次数。都属于本地日志，不增加协议字段。

本轮设备 socket 可写等待累计约 9.04 秒，ACK 等待约 3.27 秒；预读 data_wait 为零，网关 20 次窗口持久化累计约 89.95 ms。因此继续提高 SD 时钟、扩大预读缓冲或缩减 JSON 不是这轮优先项。上述代码问题可以确定并修复，但现有日志无法把全部网络等待归因于它们，也不能确认无线重传次数。126 不承诺达到 500 KiB/s；仍按整场传输和完整性口径实测，必要时再结合 TCP 抓包定位剩余等待。

126 保持 125 的报文、二进制布局、ACK、CRC、文件提交与整场结束语义，继续使用本机配对网关。主机回归覆盖接收分片/空闲/错误/取消、旧接收路径、持久化门禁、发送时限与重连、窗口完整性、OTA 交接；不代替八小时实机稳定性验收。


## 17 7.0.127 调度优化与界面维护

## 18. 7.0.128：TCP 可写通知门槛修正

### 这轮为什么变慢

2026-10-14 的 `meeting_631b9003d8bafd9f`，设备采集 14,293 帧，网关收到相同数量的帧，三个文件共 9,519,522 字节，CRC、帧序号和每帧 20 ms 时间戳连续。第一条 begin 到整场持久化确认耗时 25.943 秒，平均 358.34 KiB/s。设备停止采集到收到整场确认约 30.54 秒。

对照此前 546.95 KiB/s 的短会议，本轮发送可写等待从约 2.62 秒增加到 12.27 秒；SD 读取没有断供，`data_wait_ms=0`，网关数据窗口持久化合计 68.61 ms。发送侧共 586 次可写等待，其中 516 次超时。重试次数不等于 TCP 丢包重传次数。

已核实的代码限制有两层：

1. ESP-IDF 6.0 的 lwIP 默认 `TCP_SNDLOWAT` 是发送缓冲的一半。测试配置发送缓冲为 46,080 字节，所以需要空闲空间大于 23,040 字节，且 pbuf 队列低于原门槛，才发送可写通知。扩大缓冲时，这个通知门槛也跟着变大。
2. 项目申请 10 ms 的 `select()` 等待，但 IDF 的 `sys_arch_sem_wait()` 会向上取整并多加一个 tick。在 100 Hz 下使用两个 tick；任务恢复执行还可能晚于超时。586 次等待累计 12.266 秒，比每次 10 ms 的总预算至少多出 6.406 秒。这部分包含 tick 取整、调度和调用开销，不能直接当作 Wi-Fi RTT。

这些机制会放大网络和 CPU 调度的波动。它们能解释为何反复等待造成明显损耗，但仅凭日志不能把本轮降速全部归因于某次固件修改，也不能证明无线链路没有影响。当前电脑与设备都连接同一手机热点的 2.4 GHz 网络。

### 本轮改动及边界

- 测试固件通过工程 CMake 设置 `TCP_SNDLOWAT=2*MSS+1=2881`。安装的 ESP-IDF 源文件不修改。TCP 发送缓冲仍为 46,080 字节，pbuf 队列门槛保持原值。
- 按整 MSS 释放空间计算，原策略要等 17 个 MSS，新策略等 3 个 MSS 即可发出可写通知。这个数字是通知边界，不是吞吐倍数。
- 设置只在 PC 网关测试构建启用，由 `CONFIG_NUWAX_SD_REPLAY_EARLY_TCP_WRITABLE` 控制。它是该构建的 lwIP 全局通知设置，也覆盖测试固件的正式云端 socket；TLS 发送、超时及失败处理代码保持。正式生产构建不开启该选项。
- 保持非阻塞发送和原来的 10 ms 有界探测；不改为阻塞发送。IDF 阻塞写超时依赖 TCP 回调及轮询，不能把短 `SO_SNDTIMEO` 当成严格返回上限。
- 启动日志新增 `snd_lowat`、`queue_lowat`，分段统计新增 `timeout_overrun_ms` 和 `timeout_overrun_max_us`，只统计 select 返回超时时超过请求截止点的墙钟时间。
- 不改变 begin/chunk/commit/session_end 格式、窗口大小、CRC、持久化 ACK、续传、文件删除规则、采集完整性和 OTA 交接。没有提高任务优先级或增加 Wi-Fi/上传缓冲。

### 验收

`tools/test-sd-tcp-writable.py` 直接提取本机 IDF 的 `sent_tcp()` 和 `sys_arch_sem_wait()`，核对新旧空间/队列边界、写入与关闭回调、tick 取整及诊断计数。这个测试不模拟实机带宽，不把模型结果当成 500 KiB/s 实测。

实机验收仍看网关第一条 begin 到整场持久化确认，包含所有段间等待、重试和结束确认。本轮同等 9,519,522 字节需要在 18.593 秒内完成才达到 500 KiB/s。同时必须满足设备采集帧数与落盘帧数一致、CRC 正确、序号和时间戳连续、无重启及采集丢帧。还需要长会议、上传中断网、唤醒与 OTA 交接回归。

7.0.128 构建和主机检查完成并不代表实机达标；尚未烧录时不得宣称速度问题已完全解决。对照复测应使用同一位置和热点状态，保留每轮完整启动、停止录音、上传统计与整场确认日志。

## 19. 7.0.129：减少掩码循环与网关校验开销

128 本轮会议 `meeting_32a64b4ca8caf627` 共 18,762 帧、375.24 秒音频，三份归档共 12,495,876 字节。网关第一条 begin 至整场持久化结束为 25.548 秒，整场速度 477.65 KiB/s。文件 CRC、连续帧号 0..18761、相邻 20 ms 时间戳均通过。设备记录拒收、丢帧和时间轴不连续均为零。

129 做两项局部优化：

1. 对齐的 WebSocket 掩码复制每轮处理 16 字节，减少指针更新和循环判断。4 字节尾部、未对齐字节路径及掩码相位保持。使用固定大小内建复制和强制内联，避免 ROM memcpy 和掩码辅助函数调用；不使用违反别名规则的指针强转，不越界读取，不修改源音频。

对同一份真实 4,193,930 字节归档逐帧计算 CRC，七次测量中位数：原逐位实现 104.516 ms、原生实现 1.771 ms、查表实现 7.726 ms。这是电脑 CRC 计算耗时，不是设备吞吐或整个 commit 的耗时。网关重启使用原音频目录和配对设置。

本轮不改变 begin/chunk/commit/session_end、音频布局、确认窗口、续传和删除规则；保留 128 的 TCP 可写通知门槛。没有增加音频缓冲、提高任务优先级、关闭采集或削减界面动画。正式云端与 App 无需修改。

下一轮应继续按首个 begin 至整场持久化结束计算速度，目标 >=500 KiB/s，同时核对采集帧数、接收帧数、CRC、帧号与时间戳连续性。关注 encode_ms、writable_wait_ms、commit_ms、界面长处理、采集队列及重启；保留完整设备日志和对应网关记录，不凭单段峰值判断达标。

## 20. 7.0.130：Wi-Fi 发送缓存与底层诊断

129 本轮会议 `meeting_9790c3c70127fa91` 录制 640.72 秒，共 32,036 帧、6 份文件、21,336,744 字节。网关整场耗时 57.476 秒，362.53 KiB/s；CRC、连续序号 0..32035、跨文件 20 ms 时间戳均通过。TCP 可写等待累计 24.342 秒，窗口 ACK 等待 4.200 秒，预读 data_wait 均为零。第一份文件存在两次超过一秒的发送停顿，但均在原有有界进度规则内恢复，没有重连或丢弃音频。

### 修改依据及范围

当前 TCP 发送空间为 46,080 字节，相当于 32 个 1,440 字节 MSS；Wi-Fi 静态 TX 缓冲为 6，缓存上限为 16。TCP 突发排队量与 Wi-Fi 缓存容量并不匹配。这是队列压力风险，不能单凭容量关系证明上轮已经发生溢出：实际占用还受拥塞窗口、驱动排空速度和其他连接影响。

本机 IDF 的 `wlanif.c` 将发送层 `ESP_ERR_NO_MEM` 转为 `ERR_MEM`。`lwip_netconn_do_writemore()` 对 tcp_output 的一般发送失败没有立刻退还已排入 TCP 的数据；恢复依赖后续发送/ACK/定时器。它解释了为什么需要检查底层发送失败，而不是继续把所有 select 超时当作丢包。

130 将测试构建的 `CONFIG_ESP_WIFI_CACHE_TX_BUFFER_NUM` 从 16 改为 32，保持静态 TX/RX 缓冲各 6、TX BA 窗口 6、TCP 发送空间 46,080 及可写门槛 2,881 不变。构建脚本明确覆盖复用 SDKCONFIG 中的旧值，并检查最终生成的配置。没有扩大静态 DMA 缓冲，也没有修改任务优先级。缓存上限增大仍可能增加运行时内存用量；IDF Wi-Fi 分配器优先 PSRAM，失败时仍有内部内存回退，不能宣称完全不增加内部内存压力。原有 768 KiB 上传 PSRAM 预留和采集优先退让保留。

### 如何确认生效及定位剩余等待

连接日志新增 `SD network profile revision=130 tx_static=6 tx_cache=32 tx_ba=6 probe=netif_tcp_output`。每段传输后新增 `net_tx_probe: cumulative ...`：

- `netif_calls/netif_nomem/netif_other`：本次启动以来观察到的网卡发送调用及错误，包含正式云端和 ARP 等流量，并非仅补传。
- `replay_output_calls/replay_output_errors`：目标端口 8810 的 TCP 输出调用及错误。
- `zero_window_samples/rto_samples`：观察到对端零窗口或 TCP 超时恢复标志的采样次数，不能当作重传包数。
- `nrtx_peak`：观察到的 PCB 重传计数峰值；`last_cwnd/last_peer_window/last_send_free/last_queue` 是最近一次样本，不能当作整段最小值。

诊断使用链接器包装跨目标文件调用；SDK 同一目标文件内部调用可能绕过包装，因此统计是已观察事件，不是全量抓包。包装函数保留参数、调用一次原 SDK 函数并原样返回，不重试、不丢包、不保留 PCB/pbuf/socket 指针，不在网络回调中分配内存或输出日志。统计通过原子标量读写。主机检查验证转发语义；最终 ELF 检查确认实际 SDK 调用进入包装函数，包装函数仍调用原实现。SDK 安装目录未修改，正式构建不启用包装。

### 验收状态

本轮属于针对队列压力的优化候选，是否消除秒级停顿及达到 500 KiB/s 必须用设备验证。不得把配置生效或主机回归通过等同于性能达标。同样 21,336,744 字节需在 41.673 秒内完成整场确认；保留完整性、断网恢复、唤醒采集、UI、启动内存和长时运行验收。若仍低于目标，结合上述底层统计与抓包继续定位，不以缩短统计区间或只报最快分段替代整场指标。

录音、SD 文件和线上协议均不变，App、正式云端和 PC 网关无需升级。本机网关继续使用现有配对身份、端口及音频目录。

## 21. 7.0.131：保留合并发送，恢复被拒绝的 TCP 输出

130 实测会议 `meeting_f769880e2618bfc0` 为 384.20 秒、19,210 帧，四份文件共 12,794,372 字节。首个 begin 到整场确认耗时 107.659 秒，116.06 KiB/s；四次失败重试后完整上传，CRC、帧号和 20 ms 时间戳连续性通过。TCP 可写等待累计 53.170 秒；观察到网卡层 31 次 ESP_ERR_NO_MEM、补传 TCP 输出 30 次错误。错误计数并不能单独证明 PSRAM 耗尽，也不能把不同无线条件下的全部降速归因于缓存设置。

### 缓冲与窗口

130 在约 1.08 MB 空闲 PSRAM 时，先保留两块 128 KiB 读缓冲，再将合并发送从四帧缩减到一帧。131 优先尝试 128 KiB × 2 加四帧，不足时先尝试 64 KiB × 2 加四帧；更低内存下才继续减少发送帧数或读缓冲。仍检查分配前预算和分配后的真实剩余内存，保留 768 KiB PSRAM 安全余量与 16 KiB reader 余量，不挪用内部 DMA 内存。

读缓冲大小不再将协议确认窗口限制为最多四个 RAM 槽。重试来源已经是封存 SD 文件，因此在 64 KiB 读缓冲下仍可使用网关确认的 512 KiB 窗口；同时在 RAM 中保留的仍只有两个槽。非整倍数窗口向下取完整槽数，始终不超过网关限额。串行回退、取消、监控抢占、CRC、断点续传和提交后删除规则保留。

### 网络恢复

默认测试配置恢复 Wi-Fi 缓存上限 16，静态 TX 缓冲仍为 6。可用 `tools/build-sd-session-test.ps1 -WifiCacheTxBuffers 32` 单独构建同代码的对照版本；两个构建不能并行使用同一 SDKCONFIG。未改变 TCP 发送空间、任务优先级、发送超时或 ACK 超时。

仅测试构建、远端端口 8810 的 tcp_output 返回 ERR_MEM 时触发恢复提示。发送循环和 ACK 等待循环以非阻塞方式投递 TCP/IP 回调，最多一个回调排队。在回调执行时重新扫描当前有效连接，只处理 ESTABLISHED、存在未发送数据且带 TF_NAGLEMEMERR 的连接。这沿用本机 SDK tcp_txnow 的重试条件，但限制到测试网关端口。

每次提示最多四次输出尝试，间隔下限为 20、40、80、160 ms，实际调度可能更晚；不会在 TCP/IP 线程睡眠或忙循环。回调投递失败至少退让 100 ms，原 TCP 定时器仍可恢复。成功、非内存类错误、连接关闭或自然恢复后停止这一轮尝试。后续正常发送再次产生 ERR_MEM 可以触发新一轮，原有发送/ACK 截止时间始终有效。

不跨线程保存 PCB、socket 或 pbuf 指针，不再次调用 tcp_write 入队音频，不手工调整序号、拥塞窗口或 RTO。包装函数仍只调用一次原函数并原样返回结果；恢复通过单独回调执行。正式构建不启用此恢复。App、云端、测试网关和线上消息格式无需修改。

### 生效与验收

日志应出现 `SD network profile revision=131 ... tx_cache=16 ... recovery=bounded_core_retry`，以及 `SD bulk pipeline revision=sd-backed-window-v4 layout=batch_first`。内存受限时关注 `capacity=65536 tx_batch_frames=4 ack_capacity=524288`；内存充足时保留 128 KiB 四帧是正常行为，不能要求每一轮都固定为 64 KiB。

新增 `net_tx_probe: recovery ...` 区分 tcp_mem、tcp_route、tcp_other；retry_attempts 是额外输出尝试数，retry_recovered 只表示那次 tcp_output 返回成功，不代表对端已经持久化。retry_exhausted 表示该轮四次尝试耗尽；retry_stale 表示执行时无需恢复；retry_post_failures 表示回调未能排队。仍以网关整场确认作为完成依据。

回归覆盖上轮七个真实内存值、并发分配挤占、分配失败、任意断点、丢失 ACK、监控抢占和资源回收；低内存生产 C 路径导出的 4,193,930 字节包交给现有网关逐字节核对。网络故障注入覆盖四次重试上限、自然恢复、连接提前关闭、不同端口、投递失败及毫秒计时回绕。构建后再核对固件版本、配置、实际函数链接和资产哈希。

131 的构建与主机回归不代表实机达到 500 KiB/s。按 130 同样的数据量，首个 begin 至整场确认需要在 24.989 秒内完成才达标。还需实测长会议、断网续传、唤醒、UI 和无重启；本轮不改充电、表情及界面功能。

## 22. 7.0.132：发送队列、核心分工与独立恢复

### 历轮结果与结论

以下均采用网关首个零偏移 begin 至整场持久化完成的口径，包含分段切换和重试；不是网页瞬时峰值。这些是不同录音和不同时间的测试，不能当作严格的单变量对照。

500 KiB/s 不是已知硬件极限，126 曾在一次短会议达到目标。当前问题是不能稳定达到。131 的文件 CRC、帧号 0～8167、20 ms 时间戳均连续；其中 383 次内存类输出错误不是丢失 383 帧。TCP 可写等待累计 3.033 秒，发送方为唤醒采集等待 1.927 秒，预读断供仅 81 ms；网关分块持久化合计 43.48 ms。读写和采集等待会重叠，不能相加推算可节省时间，也不能把墙钟编码时间全当 CPU 开销。

### 代码核查

1. `sdkconfig.defaults` 的 TCP 发送缓冲为 46,080 字节、MSS 为 1,440，约容纳 32 个满长 TCP 报文；131 的 Wi-Fi 静态 TX 为 6、缓存为 16。SDK Wi-Fi Kconfig 明确说明静态 TX 不足时进入缓存队列，队列也有上限。满窗口突发具有压满此队列的条件，但现有计数不能区分每次拒绝是队列上限还是实际分配失败。130 使用缓存 32 的同时退化为单帧发送并发生重连，不能由该轮推断缓存 32 本身导致降速。
2. TCP/IP 任务优先级 18，之前没有固定核心；唤醒推理优先级 10、采集优先级 12，均在核心 1。网络任务能够抢占采集和推理，采集积压又使上传暂停。代码证实存在这种竞争条件，但旧日志没有逐核心运行时间，尚不能量化它造成了多少等待。
3. 131 的恢复只在发送和 ACK 循环主动轮询。上传任务在采集保护、预读或调度等待期间不会轮询，原 20/40/80/160 ms 只是最短等待，不能保证按时调用。SDK `sys_now()` 来自 FreeRTOS tick，当前分辨率 10 ms，也不适合新设计的 5 ms 首次恢复。
4. SD 已有双槽预读、按已验证前缀发布和后台校验。本轮读操作约 4.726 秒已大部分与发送重叠，继续扩大预读、提高 SD 时钟或缩减 begin JSON 不是主要改动方向。CRC、持久化 ACK 和录音采集保护仍必须保留。

### 本轮实现

- 仅本机 SD 测试构建将 TCP/IP 固定核心 0，与 Wi-Fi 同核；采集和唤醒仍在核心 1。网络和音频任务优先级不变。核心 0 仍有 SD 与 UI 工作，实际是否减少总争用需复测；新增 `scheduler core0/core1` 记录观察到的 TCP 输出调用位置。
- Wi-Fi 缓存上限从 16 改为 32，静态 TX/RX 仍各 6，不增加固定 DMA 缓冲。针对新增 16 个缓存槽，上传分配时额外预留 32 KiB PSRAM，保留原 768 KiB 录音余量和 16 KiB reader 余量。内存不足优先使用 64 KiB × 2 读槽与四帧发送，512 KiB ACK 窗口不随读槽缩小。分配前、分配后都检查余量。
- 创建一个全生命周期的单次定时器，只有观察到测试端口 TCP 输出 `ERR_MEM` 才启动。定时器只非阻塞投递 TCP/IP 回调，不读取或保留 PCB，不直接发送音频。回调重新扫描当前有效连接，仅重试 lwIP 原有待发链表；不重新入队数据，不改序号、拥塞窗口或 lwIP 重传时钟。
- 一轮最多四次尝试，最短间隔为 5/10/20/40 ms，以 `esp_timer_get_time()` 的单调时间计算。主机时序测试中、上传任务完全不轮询时，四次回调发生在 5/15/35/75 ms；实机调度仍可能延后。定时器与原轮询共用原子排队标志，不能重复排队；投递失败也消耗预算并退避 100 ms，持续失败后停表，避免空闲时永久唤醒。创建或启动失败仍保留原轮询和 TCP 自身恢复。
- 网络暂时不可用、取消或连接关闭仍按原期限退出，未确认的文件保留 SD。旧定时器最多额外唤醒一次并重新检查状态，没有连接指针越过关闭边界。没有错误时不产生周期定时器唤醒。

`tools/build-sd-session-test.ps1` 默认生成 7.0.132、缓存 32、TCP/IP 核心 0，并清除旧 SDKCONFIG 中相冲突的核心配置；构建后核对实际生效值。需要单变量对照时可使用 `-WifiCacheTxBuffers 16` 或 `-TcpipAffinity unbound`，不要并行运行共用 SDKCONFIG 的构建。默认版本的日志标志为 `SD network profile revision=132 ... tx_cache=32 ... tcpip_core=0 ... recovery=timer_bounded_retry` 和 `SD bulk memory network_headroom=32768 reader_headroom=16384`。

### 验证与交付边界

协议字段、WebSocket 帧、NWXCH1、归档格式、512 KiB 持久化确认、断点续传和确认后删除规则不变。云端和 App 无需修改，继续使用原配对电脑网关及音频目录。构建配置调整会影响测试固件中共用 TCP/IP 任务的所有连接，但不改变正式连接的报文或重试策略；需同时回归正式连接心跳和唤醒响应。

验证包括实际恢复代码的四次上限、上传暂停、时钟回绕、关闭连接、自然恢复、重复投递竞争、定时器分配/启动失败、持续回调队列失败；实际窗口代码的新增网络余量、130/131 内存现场、并发分配与取消；生产 C 输出送入现有接收器的 4,193,930 字节逐字节校验、CRC、8 次持久化 ACK；原发送路径短写、TLS、交错、重连检查。最终 ELF 检查调用链和实际配置，不能只查看 defaults 文件。

7.0.132 尚未经设备实测，不能写成已经达到 500 KiB/s 或八小时稳定性已通过。131 同量文件达到目标需在 10.625 秒内结束，相比 13.415 秒需减少约 2.79 秒。下一轮应至少核对：整场速度、CRC/序号/时间连续性、设备与网关帧数一致、重连与重启、采集丢帧、UI 长处理、主云心跳；再做长会议和上传中断网/唤醒/OTA 交接。`audit-offline-session.js` 的退出码 3 表示完整性通过但吞吐目标不通过，不能作为达标包交付。

## 23. 7.0.133：修复重试状态竞争

### 已复现的问题

132 的上传任务先检查剩余次数和截止时间，再用原子标志取得排队资格。两步之间，定时器与 TCP/IP 回调可能已经完成恢复、清零次数。旧调用继续投递失败后对零减一，次数变为 4,294,967,295。同一竞争也可能提前消耗下一次重试，破坏退避间隔。复现使用实际 C 源码和确定性的任务抢占顺序，不是设备重启原因的实测证明。

### 修复方式

剩余次数、截止时间和排队标志改为同一个短临界区内检查和更新。投递资格取得后，一直保留到投递失败处理完成或 TCP/IP 回调结束；新一轮不能在旧一轮更新到一半时插入。失败扣减同时限制在零以上。临界区仅操作标量状态，TCP 输出、PCB 扫描、消息投递、定时器调用、分配和日志均在锁外。

保留原四次预算和 5/10/20/40 ms 最短重试间隔，投递失败仍消耗一次预算并退避 100 ms。每轮结束后，后续新的自然发送失败可以开始新一轮。单次定时器是唤醒提示，实际是否到期由受保护的当前状态决定；无待重试任务时不周期唤醒。

定时器创建失败后不再永久关闭自动恢复。连接或上传轮询活动会在至少 1 秒冷却后重试创建，初始化同时只允许一个调用者执行；取得初始化资格后再次检查冷却截止时间，防止旧调用绕过另一轮失败刚设置的冷却。空闲时不增加后台分配任务，失败期间仍使用原轮询和 TCP 恢复。

### 验证与使用

回归包含两种已复现的抢占顺序、最后一次投递失败与新一轮交错、TCP/IP 回调先于投递函数返回、创建失败冷却竞争与自动恢复，以及原有四次上限、断连、自然恢复和时钟回绕。主机替身对锁内调用网络和定时器 API 会直接断言失败。最终 ELF 另核对实际调用链和构建配置。

生效标志：`SD network profile revision=133 ... recovery=locked_timer_retry`；诊断增加 `timer_init_attempts=...` 和 `state=locked`。默认构建脚本版本更新为 7.0.133。

本轮保持 132 的缓存 32、TCP/IP 核心 0、四帧发送、双槽预读和 512 KiB 确认窗口。协议、云端/App、配对网关及存储目录不变。窗口、生产报文接收和 WebSocket 回归用于验证数据与资源处理；主机模拟 300 秒音频不等于设备持续运行 300 秒，更不等于八小时稳定性测试。

133 修复的是已确认的并发缺陷，不标记为已实测达到 500 KiB/s。沿用第 22 节整场持久化口径进行实机验收。

## 28. 7.0.138：短时 TCP 停顿恢复与网关连接清理

### 137 实测结果与修复依据

场次 `meeting_5468d809389b130d` 录制 44,132 帧，共 882.64 秒；8 个文件合计 29,392,936 字节。从网关首次 begin 到整场持久化结束共 343.148 秒，整场速度 83.65 KiB/s。全部文件 CRC、序号 0..44131 和 20 ms 时间间隔通过检查，没有发现缺帧或时间缺口。

前两个文件连同切换耗时约 294.199 秒，占整场 85.7%。截取的四次发送失败中，等待 TCP 可写占发送时间约 84.9%，每次在约 2 秒无进展后断开，随后重新连接、begin 和读取校验已接收前缀。其余五个完整大文件连同切换平均约 438.86 KiB/s，说明排除重试后仍不能宣布达到 500 KiB/s。

网关另有明确缺陷：升级为 WebSocket 后没有处理 TCP FIN，部分连接停留在 CLOSE_WAIT，网页仍把它们计作在线。该问题已用独立端口的真实 socket 复现。旧连接回调也缺少同一设备连接代次限制。它们需要修复，但现有证据不足以认定它们就是首次无线 TCP 停顿的原因。

### 本轮处理

- 网关在 FIN、error、close 等出口统一释放连接，取消待发 ACK 定时器，保留已经落盘的数据。同一设备新连接取得所有权后，旧连接及其迟到消息不能重新占用上传事务；新连接仍通过原 begin 获取持久化断点。
- 独立明文批量发送改为最多 6 秒没有正向写入进展、单次整批最多 12 秒。队列在本次第一字节前已经满时，也允许进入这段有界恢复等待。成功可写即继续发送，没有新增固定等待；少量持续写入也不能绕过 12 秒绝对上限。
- 传输取消、连接代次和关闭检查仍在原短轮询内执行。TLS、普通控制报文和实时上行保留原发送时限。发送了半帧后仍必须完成或关闭连接，不能在同一字节流上跳过剩余内容。
- 独立历史窗口的 begin、窗口 ACK 和 commit 等待上限为 6 秒；串行实时路径仍为 2.5 秒，整场最终持久化 ACK 仍为 60 秒。等待中每 100 ms 检查退出条件，离线、OTA、录音占用及新开启的实时监控可中止历史上传。事件唤醒后再检查连接代次和取消状态。
- TCP 诊断记录观察到的 ACK 推进、实际重传计时、发送与未确认队列，并标明采样年龄。只在 TCP/IP 上下文读取 PCB，链表低频且有界扫描；不改变拥塞窗口、重传算法或重试次数。`observed_conn` 不是 WebSocket epoch，TCP 序号推进也不是音频持久化确认量。

协议字段、持久化 ACK、确认后删除、CRC、断点恢复、配对网关和音频目录保持原约定。没有增加任务或音频缓存。SD 调度 revision=137、解码 revision=135 和网络恢复 revision=133 继续表示相应策略；整机版本为 7.0.138。设备测试栏和模拟断网开关仍关闭。

### 验收口径

主机故障回归覆盖 5 秒短暂停顿后恢复、6 秒无进展退出、12 秒持续少量写入退出、取消和代次改变、ACK 延迟及与取消同时到达、TCP FIN 与旧连接抢占。它们验证代码边界，不代表设备吞吐或长时间运行已通过。

实机仍须在同一电脑网关按整场首次 begin 到 session_end 持久化完成计算速度，不能只取最快文件或发送阶段。至少三次重复测试同时满足整场 ≥500 KiB/s、动态表情平均 ≥35 FPS，并核对长帧间隔、菜单、唤醒、云端心跳及全部录音；之后再验证 30 分钟和八小时场次。若恢复后有效发送速度仍不足，结合新增 TCP 采样定位，不能靠继续放宽超时宣称提速成功。
