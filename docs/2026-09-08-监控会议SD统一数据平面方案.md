# 监控、会议与 SD 卡统一数据平面方案

日期：2026-09-08。范围：当前会议/监控模式、`offline_audio_spool`、SD 驱动、WebSocket 上行与重连流程。

## 结论

当前实现支持“无 SD 在线上传”和“断网后写 SD、重连补传”，但不是“有 SD 时所有在线数据先入 SD，再从 SD 实时上传”。在线时会议和监控直接使用 WebSocket reliable uplink；只有 WebSocket 断开后，外层才释放原模式并启动独立 SD-only capture。重连后又先停止 SD capture、等待历史 replay，再恢复模式。

这个方案能工作，但状态分散在会议/监控控制器、离线租约、I2S owner、SD writer、WebSocket epoch 和 replay worker 中，重连期间还存在不采集窗口。它已经比简单的“断线即丢音频”可靠，却仍然比优秀产品复杂。

## 当前实现核对

- 无 SD：启动时 `nuwax_offline_audio_init()` 挂载失败不会阻止在线业务；会议/监控继续走 WebSocket。
- 有 SD 在线：不会统一落盘，只保留在线 uplink。
- 断网：模式 cleanup 后由外层设置 `offline_resume_required`，启动 `offline_audio_start_capture()`，采集任务拥有新的麦克风 owner。
- 重连：停止 SD capture，关闭归档为 `.ready`，异步按 begin/chunk/commit、offset 和 CRC replay；replay 期间阻止在线模式重新获得音频 owner。
- SD spool：128 个 PSRAM slot、约 2 KiB 最大帧、1 MiB 分段、256 MiB 配额、每 100 帧 fsync、只有 commit ACK 后删除文件。
- 监控在线路径有 ARMED/STREAMING 和人声门控；离线 capture 主要是连续 PCM 归档，未完全复用在线监控的门控策略。

## 三种方案

| 方案 | 优点 | 问题 | 结论 |
|---|---|---|---|
| 全部先写 SD，再从 SD 实时上传 | 数据看似统一 | 每帧多一次文件系统路径；SD 延迟/拔卡/坏块会影响实时；读写争用；掉电仍可能丢缓存 | 不推荐 |
| 当前：在线直传，断网后切 SD-only | 改造少、在线延迟低 | 断线需要重新抢 I2S；重连补传期间可能停止采集；两套状态机 | 可作为过渡 |
| 单采集双下游：在线直传 + SD 异步镜像，离线只写 SD，重连按序补传 | 网络变化不改变采集 owner；低延迟且可恢复 | 需要统一 frame bus、游标和云端幂等 | **最优方案** |

## 推荐架构

### 单一 Capture Owner

会议和监控只允许一个 `audio_capture_owner` 持有 I2S。每个 20 ms PCM16 帧成为不可变对象，携带 `device/session/mode/sequence/timestamp/flags/payload`。采集任务不等待 SD 或 WebSocket，只写入有界 frame bus。

### 两个 Sink

`RealtimeSink` 在线时直接发 WebSocket，使用小队列和严格 age deadline，丢旧保新。`JournalSink` 在 SD 存在且用户允许归档时异步写日志；它不能阻塞采集，也不能让 SD 故障停止在线上传。

会议可默认保留连续归档；监控应只把经过本地人声门控的帧写入 journal，静音帧不应持续消耗 SD。SD writer 慢、拔出、满卡时要记录 `journal_gap`，在线 sink 继续工作。

### 网络状态只切换 Sink

```text
CAPTURE_ACTIVE
 ├─ online  -> RealtimeSink + optional JournalSink
 ├─ offline -> JournalSink only
 └─ stop    -> close journal, write footer, finish session
```

网络断开不应释放麦克风后再启动另一套离线采集任务；同一个 session 和 sequence 持续写入。这样可以移除大部分 `offline_resume_required` 和重连采集窗口。

### 重连不暂停新采集

维护三个游标：

```text
journal_write_seq   SD 已写入最高 sequence
cloud_acked_seq     云端已确认最高 sequence
realtime_sent_seq   当前实时发送最高 sequence
```

恢复在线后，新帧继续进入 journal，RealtimeSink 发送新帧，ReplaySink 从 `cloud_acked_seq + 1` 补传旧帧。云端用 `device_id + session_id + sequence` 幂等去重，追平后关闭 ReplaySink。现有 offset ACK、CRC 和 commit 机制可以继续使用。

## 目标行为

### 无 SD

会议和监控保持当前在线可靠上传。断网时继续采集没有持久化介质，则必须明确统计丢失帧；不能报告为已保存。网络恢复后继续新序列或带 gap 标记的同一 session。

### 有 SD

在线时实时直传并异步镜像。突然离线时不切换 I2S owner，只停止 RealtimeSink。恢复在线时不等待历史 replay 完成，新帧继续实时发送，旧数据后台补传。用户停止时先 flush、写 footer，再结束 session。

“在线数据从 SD 实时上传”可以作为审计或严格留存模式的可选策略，但不应作为默认路径。若强制所有数据先落 SD，需要接受更高延迟和 SD 故障影响面。

## 容量、寿命和隐私

16 kHz mono PCM16 约 32 KiB/s，即约 115 MiB/h；256 MiB 配额只能保存约 2.2 小时连续原始 PCM。应明确满卡策略（淘汰最旧、停止归档或只留事件片段）、最大保存时长、用户删除、恢复出厂和云端 commit 后删除规则。若要长时间监控，应使用 Opus/ADPCM 归档或只保存语音片段，不能只扩大配额。

当前归档是原始 PCM 文件，需明确 SD 明文是否可接受；若不接受，应做分段加密、完整性校验和密钥清理。在线监控/会议必须由用户显式授权本地归档，不能因为插入 SD 就默认改变隐私策略。

## 迁移顺序

1. 抽取统一 `audio_frame_bus`，不改会议/监控协议。
2. 将现有 audio uplink 与 offline spool 接成 RealtimeSink/JournalSink。
3. 先上线“在线直传 + SD 异步镜像”，保留当前断线 handoff 作为回退。
4. 增加 sequence、journal_write_seq、cloud_acked_seq、journal_gap 监控。
5. 验证网络拔插、SD 拔插、慢卡、满卡、掉电、重复 ACK、云端重连和长时间运行。
6. 稳定后移除独立 offline capture task 和重连前停止采集逻辑。

## 发布门禁

- 无 SD 在线会议/监控无回归；断网丢失计数准确。
- 有 SD 时 SD 写慢、拔出或满卡不影响实时上传。
- 断网和重连不产生第二个 I2S owner，session/sequence 连续。
- 重连期间新帧不等待旧文件补传；云端最终序列幂等且连续。
- 掉电最多损失约定的同步周期，`.part` 恢复不伪造完整文件。
- 满卡、坏卡、删除失败和隐私撤销均可解释、可恢复。

最终建议：采用“**单采集、在线直传、SD 异步镜像、断网持续写盘、重连按序补传**”。它比“全部先写 SD”更低延迟，比当前断网后重建采集更简单，也最能保证会议和监控在网络与存储故障下继续运行。

## 精简云端协议

设备继续使用现有 `offline_audio_begin/chunk/commit` 三步事务，仅增加一个字段：
`mode: "archive_only"`。`begin` 携带 `segment_id/total_bytes/crc32`，云端返回
`{type:"offline_audio_begin_ack",request_id,ok,next_offset}`；每个二进制 chunk
返回 `offline_audio_chunk_ack` 和 `next_offset`；完成后发送 `commit`，云端校验长度与
CRC，返回 `offline_audio_commit_ack`。云端以 `device_id + session_id + segment_id`
幂等，重复 begin 从已落盘偏移继续，重复 commit 直接成功。

`archive_only` 的语义是只归档到对象存储或归档库，不进入 ASR、监控事件、告警和计费
流水线；云端可以异步转码或索引，但不得重新触发业务事件。设备只有收到 commit ACK
才删除 `.ready` 文件，断线、超时或 ACK 不匹配均保留文件等待下次补传。旧云端不声明
该能力时，设备不发送镜像补传，避免误进入实时识别链路。
