# BLE 动态云配网开发阶段总结与续开发指南

更新时间：2026-07-25  
阶段状态：`FIRMWARE_LOCAL_E2E_VERIFIED`  
适用工程：ESP32-S3 桌搭固件、Android APP Provider、本地测试网关和配网模拟器

## 1. 文档目的

本文用于当前 BLE 配网开发阶段结束后的长期留档。后续重新进入此模块开发时，应先阅读本文恢复上下文，再按文中的权威文件和验证顺序操作，避免重新踩过已经纠正的问题。

本文回答以下问题：

- 当前到底完成了什么，哪些仍未完成。
- 设备、APP、模拟器和云端之间如何通信。
- 已冻结的 BLE/Wi-Fi/云配置协议是什么。
- 代码分别落在哪些文件中。
- 当前固件和交付包的可验证基线是什么。
- 下一次继续开发时，从哪里开始、先检查什么、如何避免破坏现有成果。

本文不保存 Wi-Fi 密码、生产 PoP、`deviceSecret`、APP Token、签名私钥或网关注册表。

## 2. 一分钟恢复记忆

当前实现不是单纯的“BLE 下发 Wi-Fi”。完整流程是：

```text
设备二维码/受控身份材料
  -> APP 精确锁定 BLE 设备
  -> protocomm Security 2
  -> device-info 二次核对设备 ID
  -> APP 向云端 claim 动态签名配置包
  -> BLE cloud-config 写入设备 pending
  -> 官方 prov-config 下发 Wi-Fi
  -> WIFI_READY
  -> 设备使用动态 cloudUrl/deviceSecret 连接云端
  -> pending 提升 active 并发送 cloud_config_committed
  -> 云端 status 返回同一 credential 的 DEVICE_ONLINE
  -> APP 显示 SUCCESS
```

最重要的结论：

1. 本期只支持 BLE，不支持 SoftAP fallback。
2. BLE 使用 NimBLE + protocomm Security 2，不使用 Security 0/1。
3. Android 系统 BLE pairing/bonding 不是协议前提；应用层安全由 Security 2 提供。
4. 业务设备 ID 是 `device-info.serialNumber`，不是 BLE 地址、广播名、PoP 或 `credentialId`。
5. `apiBaseUrl` 只供 APP 调用云 API，不下发设备。
6. `cloudUrl`、`credentialId`、`deviceSecret`、`bundleVersion` 和 `signature` 由云端动态签发，固件没有 URL/secret fallback。
7. `prov-config=connected` 只等于 `WIFI_READY`，不能作为完整成功。
8. 完整成功必须是同一次流程、同一 `deviceId + credentialId` 的 `WIFI_READY + DEVICE_ONLINE`。
9. 当前真机已完成一次本地三端 E2E，但 Android Provider 尚未真机验收，正式账户绑定也尚未实现。
10. 当前固件只发送一次 `cloud_config_committed`，提交消息丢失后的幂等补发仍是生产阻塞项。

## 4. 已完成范围与未完成范围

### 4.1 已完成

- 固件已经接入 ESP-IDF 6.0 的 `espressif/network_provisioning` 和 protocomm。
- 已实现 BLE Security 2，不允许降级到 Security 0/1。
- 已实现稳定硬件派生设备 UID、广播名和设备二维码。
- UI `Device` 详情页已有 `Device QR` 和 Meeting 下方 BLE 配网按钮。
- 首次未配网设备可自动进入 BLE 配网。
- 已配网设备可通过本地 UI 进入可回滚重配网流程。
- 已实现设备侧官方 `prov-scan` Wi-Fi 扫描。
- 模拟器在配网期间每 15 秒请求一次设备扫描；开始配网后停止后续扫描，并等待当前请求结束后串行进入配网。
- 已实现 `device-info` 自定义 endpoint。
- 已实现 `cloud-config` 自定义 endpoint。
- 已实现云配置 ECDSA P-256/SHA-256 验签、防回滚和 NVS `pending/active`。
- 已移除设备连接云端时的编译期 URL/共享密钥 fallback。
- 已实现动态 WebSocket URL 和逐设备 secret 的 101 前鉴权。
- 已实现测试网关 claim/status、pending/active、commit 和错误 secret 401。
- 已实现 Mock/Real 两种模式的网页模拟器及二维码定向设备选择。
- 已完成一次设备 + Real 模拟器 + 测试网关真实 E2E。
- 已形成可交付给 APP 工程师的冻结协议包。

### 4.2 尚未完成

- Android Provider 尚未与真实设备联合验收。
- Android 12+ 权限、不同手机 BLE 栈、前后台和进程恢复尚未实测。
- 正式用户账户所有权绑定、反抢绑、解绑、转移、吊销和审计尚未实现。
- 正式 claim API 的 `onboardingAttemptId`/Idempotency-Key 尚未实现。
- 当前测试网关每次 claim 都会生成新的 pending credential，不是生产幂等语义。
- `cloud_config_committed` 丢失后的设备端持久化/补发尚未实现。
- 逐设备生产 PoP、factory NVS 注入和凭据发放流程尚未完成。
- Android 参考库原始二维码/PoP `Log.d` 尚需 patched/forked 产物或经过验证的 R8 清除方案。
- NVS Encryption、Flash Encryption、Secure Boot 和生产签名公钥轮换尚未完成。
- 连续 20 次重配网、300 秒边界、断电/NVS 写失败和完整故障注入尚未完成。
- 纯 WPA3-only AP 不在当前首轮验收范围；当前只验证了 WPA2/WPA3 transition AP 的可靠 WPA2 路径。

## 5. 身份和凭据必须分清

| 数据 | 作用 | 是否永久身份 | 是否进入 BLE payload |
| --- | --- | --- | --- |
| `device-info.serialNumber` | 业务设备 ID | 是 | 设备返回给 APP |
| 二维码 `username` | Security 2 username，并与设备 ID 互验 | 对本设备稳定 | 是 |
| BLE address | 本次扫描连接定位 | 否，可能变化 | 否 |
| `PROV_xxxxxx` | 附近设备定位 | 否，只有 24-bit MAC 后缀 | 广播数据 |
| PoP | 证明有权配置近端设备 | 否 | 用于 Security 2 |
| APP 用户 Token | 证明用户有云端 claim 权限 | 否 | 不发给设备 |
| `apiBaseUrl` | APP 调用 claim/status 的 API 地址 | 否 | 不发给设备 |
| `cloudUrl` | 设备连接 WebSocket 的动态地址 | 否，可轮换 | 是 |
| `credentialId` | 标识一版设备云凭据 | 否，可轮换 | 是 |
| `deviceSecret` | 设备到云端逐设备鉴权 | 否，可轮换 | 是 |
| `bundleVersion` | 防回滚和配置排序 | 否，单调递增 | 是 |
| `signature` | 证明整个云配置包由可信云端签发 | 否 | 是 |

当前开发 PoP 的权威来源是机器契约 `security.developmentPoP` 或开发二维码 `pop`。正式 APP 不得把共享开发 PoP 作为 fallback。生产屏幕二维码是 identity-only 时不包含 PoP，APP 必须从逐设备产线标签或已鉴权凭据服务取得 PoP。

当前实测设备信息可以用于回忆测试记录，但不能写成通用常量：

```text
deviceId: NX-3927-2693-9288
BLE name: PROV_1467C4
```

## 6. 固件逻辑

### 6.1 初始化和进入配网

主要入口：

- `main/nuwax_provision_new/nuwax_provision_main.c`
- `main/nuwax_ai_partner_main.c`
- `main/nuwax_ui_v28/nuwax_focus_menu.c`

行为：

1. Wi-Fi 初始化完成后调用 `nuwax_provision_main_init()`。
2. ESP-IDF Wi-Fi provisioned marker 不存在时自动进入 BLE。
3. 已有 Wi-Fi，但 `pending/active` 云配置都缺失时，保存旧 STA 后自动进入可回滚 BLE cloud recovery。
4. 正常已配网且已有云配置时不广播 BLE。
5. 用户在 `Device` 菜单点击 BLE 按钮时，内部 RAM Flash 任务保存旧 STA 回滚记录，随后重启进入配网。
6. `nuwax_provision_main_run(300000)` 管理 300 秒 admission window。
7. 新 Wi-Fi 失败或超时，重配网流程恢复旧 Wi-Fi；旧 active 云配置保持。

设备二维码入口：

- `main/nuwax_ui_v28/menu/nuwax_device_qr_view.c`
- `main/nuwax_ui_v28/nuwax_focus_menu.c`
- `main/nuwax_provision_new/nuwax_device_uid.c`

开发二维码包含 Nuwax v1 的名称、传输、安全版本、username 和开发 PoP。生产 identity-only 屏幕二维码应省略明文 PoP。

### 6.2 BLE endpoint

官方 endpoint：

```text
proto-ver
prov-session
prov-config
prov-scan
prov-ctrl（仅保留受控 reset/reprovision 语义，不作为日常远程清除入口）
```

自定义 endpoint：

```text
device-info
cloud-config
```

两个自定义 endpoint 在 provisioning start 前 create，在 start 后 register。其 characteristic UUID 不是冻结常量；Android 必须通过 GATT characteristic 的 `0x2901 User Description` descriptor 建立 endpoint name -> UUID 映射。

`proto-ver` capability 来源必须分开：

```text
prov.cap  = wifi_prov, wifi_scan
nuwax.cap = wifi_prov, wifi_scan, cloud_prov
```

Espressif Android `ESPDevice.getDeviceCapabilities()`只解析 `prov.cap`，不能用它检查 `cloud_prov`。APP 必须解析 `ESPDevice.getVersionInfo()` 原始 JSON 中的 `nuwax.cap`。

### 6.3 device-info

请求是 Security 2 会话内的 UTF-8 JSON 对象：

```json
{}
```

响应至少包含：

```text
protocolVersion
serialNumber
productModel
hardwareVersion
firmwareVersion
capabilities
lastProvisioningOutcome
lastProvisioningReason
wifiDisconnectReason
wifiDisconnectReasonName
cloudConfigState
```

APP 必须验证：

```text
deviceInfo.serialNumber == QR username
```

不一致时立即断开，不 claim、不发送 cloud-config、不发送 Wi-Fi。

### 6.4 cloud-config

APP 从已登录云端领取签名 bundle，并在同一 Security 2 session 发送：

```json
{
  "op": "set",
  "bundle": {
    "version": 1,
    "deviceId": "<device-info.serialNumber>",
    "cloudUrl": "<dynamic-ws-or-wss-url>",
    "credentialId": "<dynamic-credential-id>",
    "deviceSecret": "<per-device-secret>",
    "bundleVersion": 1784954350746,
    "signature": "<base64-ecdsa-der>"
  }
}
```

七个 bundle 字段全部必填。`version` 必须是 JSON 整数 `1`；`bundleVersion` 必须是 `1..9007199254740991` 的 JSON 整数。APP 使用 Kotlin `Long`，不能经由 `Double`。

固件验证：

- `deviceId` 必须等于硬件派生 UID。
- `cloudUrl` 必须符合构建策略；生产仅允许有效证书验证的 `wss://`。
- credential、secret、signature 非空且不能含控制/空白字符。
- ECDSA P-256/SHA-256 签名有效。
- `bundleVersion` 不回滚；完全相同的同版本内容允许幂等重放，同版本不同内容拒绝。

成功响应：

```json
{
  "ok": true,
  "state": "pending",
  "credentialId": "<same-as-claim>",
  "bundleVersion": 1
}
```

APP 和模拟器必须核对 `state + credentialId + bundleVersion`，不能只判断 `ok=true`。

### 6.5 NVS pending/active

namespace：`nuwax_cloud`。主要槽位：`pending`、`active`。

- BLE 验签成功只写 `pending`。
- 设备启动云连接时优先使用 pending，没有 pending 才使用 active。
- WebSocket authenticated hello 的 credential 必须匹配当前配置。
- 内部 RAM Flash 任务执行 `pending -> active` NVS 提交。
- active 持久化后设备发送 `cloud_config_committed`。
- 明确 401，或有旧 active 且新 pending 连续失败三次时，丢弃 pending 并回退 active。
- 一个槽位损坏时独立隔离，不能拖垮另一个有效槽位。

当前限制：设备没有持久化服务端 `cloud_config_committed_ack`，也不会在重连后自动补发 active credential 的 commit。正常路径已跑通，但消息丢失时 status 可能停留在 `CLOUD_CONFIG_COMMIT_PENDING`。生产前必须实现幂等补发/状态收敛。

### 6.6 Wi-Fi 扫描和配网

- Wi-Fi 列表来自设备官方 `prov-scan`，不是电脑或手机网卡扫描。
- `prov-scan` 是 APP 请求/设备响应，不存在设备主动向 APP 推送私有 Wi-Fi 列表 endpoint。
- 模拟器默认首轮延迟 1.2 秒开始扫描，完成后每 15 秒刷新。
- 后端 BLE 操作使用一把串行锁，设备发现、Wi-Fi 扫描和 provisioning 不并发。
- 点击开始配网后取消未来扫描；已发出的扫描正常返回并释放连接，随后开始 provisioning。
- Wi-Fi 使用官方 `prov-config` SetConfig、ApplyConfig、GetStatus protobuf。
- 成功依据是 `IP_EVENT_STA_GOT_IP`，对应 `WIFI_READY`。
- 屏幕 Wi-Fi 图标更新时间不参与协议成功判断。

### 6.7 WebSocket 动态鉴权

设备从 `nuwax_cloud` NVS 读取动态配置，不使用编译期 URL/secret fallback。Upgrade 前发送：

```http
X-Device-ID: <deviceId>
X-Credential-ID: <credentialId>
Authorization: Bearer <deviceSecret>
```

网关在返回 HTTP 101 前校验三项。错误 secret 返回 401。服务端注册表只持久化 `deviceSecret` 的 SHA-256 摘要并使用常量时间比较。

## 7. APP Provider 应实现的固定顺序

推荐状态机：

```text
SCANNING_QR
SCANNING_BLE
CONNECTING_BLE
READING_PROTOCOL
ESTABLISHING_SECURITY_2
READING_DEVICE_INFO
DEVICE_VERIFIED
CLAIMING_CLOUD_CONFIG
CLOUD_CONFIG_CLAIMED
SENDING_CLOUD_CONFIG
CLOUD_CONFIG_STAGED
SCANNING_WIFI（可选/循环）
SENDING_WIFI_CONFIG
WAITING_WIFI_READY
WIFI_READY
WAITING_DEVICE_ONLINE
CLOUD_CONFIG_COMMIT_PENDING
SUCCESS / FAILED
```

实现顺序：

1. 严格解析 Nuwax v1 QR。
2. 同时匹配完整 `PROV_xxxxxx` 名称和固定 Service UUID，不能自动选择最强 RSSI 的其他设备。
3. 创建 `TRANSPORT_BLE + SECURITY_2` 的 `ESPDevice`。
4. 在任何惰性 session API 前设置 username 和 PoP。
5. 等待 BLE service/descriptor discovery 完成。
6. 读取原始 `getVersionInfo()`，检查 `prov.sec_ver=2`、`prov.cap` 和 `nuwax.cap`。
7. 显式 `initSession()`，便于把认证失败映射成 `SECURITY_AUTH_FAILED`。
8. 调用 `device-info` 并二次比对身份。
9. 使用 APP 用户登录态调用 claim。
10. 验证 HTTP 201、`ok=true`、`version=1`、deviceId 和全部字段。
11. 把 bundle 原样发送到 `cloud-config`，不得 trim/normalize/重签名。
12. 严格核对 cloud-config 回执。
13. 停止周期 Wi-Fi 扫描，等待当前 scan callback 完成。
14. 调用官方 `ESPDevice.provision(ssid, passphrase, listener)`。
15. `deviceProvisioningSuccess()`只进入 `WIFI_READY/WAITING_DEVICE_ONLINE`。
16. 释放 BLE，每约 1 秒查询 status，最多 90 秒。
17. 只接受同一 `deviceId + credentialId` 的 `DEVICE_ONLINE`。

重试规则：

- BLE 断开后废弃旧 Security 2 session，重新连接并建立新 session。
- cloud-config 响应丢失时重发同一个 bundle，不重新 claim。
- Activity/Fragment 重建不能重复 claim/provision，状态应由 ViewModel/用例层持有。
- 当前测试 claim 非幂等；进程死亡恢复需要正式云端 Idempotency-Key 方案。
- status 停留 pending 时不能显示成功；90 秒后返回 `CLOUD_CONNECT_TIMEOUT`。

Android 安全阻塞：参考库 `lib-2.4.4` 内部会 `Log.d` 原始二维码和 PoP。普通 wrapper 无法消除库内部日志。生产 APP 必须使用经审计的 patched/forked 依赖，或配置并验证 R8 从 release 产物移除这些调用。

## 8. 成功、错误码和 BLE 生命周期

### 8.1 成功标准

```text
Wi-Fi 成功: WIFI_READY
完整 onboarding 成功: WIFI_READY + matching DEVICE_ONLINE
```

`CLOUD_CONFIG_COMMIT_PENDING` 是等待态，不是成功态。

### 8.2 APP 结果码

| 场景 | APP 结果 |
| --- | --- |
| Security 2 username/PoP 错误 | `SECURITY_AUTH_FAILED` |
| QR username 与设备 ID 不一致 | `DEVICE_ID_MISMATCH` |
| 未发现精确设备 | `DEVICE_NOT_FOUND` |
| capability/endpoint/回执不符合契约 | `PROTOCOL_ERROR` |
| BLE 操作占用 | `BUSY` |
| cloud-config 字段/格式错误 | `CLOUD_CONFIG_INVALID` |
| 云配置签名错误 | `CLOUD_SIGNATURE_INVALID` |
| bundle 版本回滚或同版本冲突 | `CLOUD_CONFIG_ROLLBACK` |
| Wi-Fi 密码/认证失败 | `WIFI_AUTH_FAILED` |
| AP/SSID 不存在 | `NETWORK_NOT_FOUND` |
| Wi-Fi 或本地流程超时 | `TIMEOUT` |
| Wi-Fi 已连、云端凭据被拒绝 | `CLOUD_CREDENTIAL_REJECTED` |
| Wi-Fi 已连、90 秒未完成云上线 | `CLOUD_CONNECT_TIMEOUT` |
| 其他未映射错误 | `INTERNAL_ERROR` |

### 8.3 BLE 生命周期

- 首次未配网：自动广播。
- 正常已配网：不广播。
- 已配网切换 Wi-Fi：在设备 UI 点击 BLE，保存旧 STA，重启进入 300 秒窗口。
- 失败：窗口/active attempt 宽限内允许重建会话和重试。
- 成功：`GOT_IP` 后保留官方状态查询 15 秒，再停止 provisioning BLE。
- 300 秒结束：停止广播；已配网设备恢复旧 Wi-Fi，首次设备需要重新打开配网窗口。
- 不提供 SoftAP fallback，也不提供 APP 远程清空 Wi-Fi endpoint。

## 9. 模拟器和测试网关

### 9.1 活动模拟器

## 11. 已纠正的主要误区

1. 不能自建一套私有 BLE GATT 配网协议替代 `network_provisioning + protocomm`。
2. 不能把 BLE address 当永久设备 ID。
3. 不能只凭 `PROV_` 前缀或最强 RSSI 选设备。
4. 不能把系统 BLE pairing/bond 当成 Security 2。
5. 不能使用 Security 0/1 或删除 PoP；`deviceSecret` 不能替代 PoP。
6. 不能从 `getDeviceCapabilities()`查找 `cloud_prov`；它位于 `nuwax.cap`。
7. 不能硬编码 `device-info/cloud-config` characteristic UUID。
8. 不能把 `cloudUrl`、共享 Token 或逐设备 secret 写死进固件。
9. 不能让 APP 自己拼接、修改或签名云配置字段。
10. 不能只检查 cloud-config `ok=true`，还要核对 state/credential/version。
11. 不能并发执行 `prov-scan` 和 provisioning。
12. 不能把 `prov-config=connected` 或屏幕 Wi-Fi 图标当完整成功。
13. 不能在 BLE 重连时自动重新 claim 新 credential。
14. 不能把本地测试 credential 绑定误称为正式用户账户所有权绑定。
15. 不能认为普通 Android wrapper 会消除第三方库内部敏感日志。
16. 不能把一次 E2E 成功扩展解释为丢包、断电和量产安全已经通过。
