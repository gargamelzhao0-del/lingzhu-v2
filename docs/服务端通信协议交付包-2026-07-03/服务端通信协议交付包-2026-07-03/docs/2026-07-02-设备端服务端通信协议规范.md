# 设备端与服务端通信协议规范

> 版本: v2.1  
> v2.1 修订:删除 §4.10 `pc_status_request` / `status_app_request`(设备端未实现,不在当前版本交付)。
> 适用对象: 服务端、音频、ASR/TTS、设备接入、App 后端工程师  
> 交付目的: 服务端团队不依赖任何本地工程文件、不需要了解 ESP32S3 内部实现，也能实现一套可与当前设备端通信的服务。  
> 范围: 本文只定义设备端与服务端之间的 WebSocket 通信、JSON 控制消息、`NA` 二进制音频帧、ID 关联、字段限制、播放下发和基础验收。云端业务算法、模型编排和智能体路由不属于本文范围。

---

## 0. 结论

服务端必须提供一个设备 WebSocket 接入入口。设备连上 WiFi 后，会主动连接该入口，并在同一条 WebSocket 长连接内传输两类数据:

| 类型 | WebSocket opcode | 内容 |
|---|---:|---|
| JSON text message | `0x1` | 设备注册、心跳、听音状态、ASR/TTS 状态、播放上下文、设备命令、WiFi 状态、表情状态 |
| Binary message | `0x2` | 使用 Nuwax `NA` header 封装的音频帧，不是裸 PCM，也不是裸 Opus |

服务端第一版必须完成:

1. 接受设备 WebSocket 握手并完成鉴权。
2. 接收并解析设备 `hello`。
3. 处理设备 `ping`，返回 JSON `pong`。
4. 处理设备 `listen start/stop`，并能容忍未知或异常 listen 状态。
5. 解析设备上行 binary message 中的一个或多个 `NA` 音频帧。
6. 将上行音频送入服务端自己的 ASR/音频处理链路。
7. 向设备发送 `text_response`，用于文本、TTS 状态和语义表情同步。
8. 向设备发送 `playback_begin`、PCM16 mono `NA` 音频帧、`NA END`、`playback_end`，完成 TTS 播放。
9. 维护 `request_id`、`audio_session_id`、`turn_id`、`playback_id` 的生命周期。
10. 支持最小设备命令: `set_emotion`、`set_volume`、`stop_playback`、`set_state`、`sleep_conversation`、`show_status`、`wifi_scan`、`wifi_connect`。

本文中的“设备端”只作为音频和状态入口: 上传设备采集/处理后的音频，接收服务端下发的音频和状态命令。服务端不需要任何本地工程文件或开发测试工具。

## 1. 传输层

### 1.1 Endpoint

| 项 | 规则 |
|---|---|
| 协议 | 协议层支持 `ws://` 和 `wss://`；`wss://` 需要交付固件启用 TLS/证书包能力 |
| 生产建议 | 使用 `wss://`，但服务端上线前必须与设备交付方确认该批固件已启用 TLS |
| 默认路径 | 服务端可自定义，例如 `/v1/device/ws`；设备端配置的 URL 必须与服务端一致 |
| URL 配置 | 设备端配置的 URL 必须与服务端入口一致；URL 如何配置由设备交付方处理 |
| 鉴权头 | 当前设备支持 `X-Bridge-Token: <token>` |
| JSON 编码 | UTF-8，无 BOM |
| 音频 binary | Nuwax `NA` 帧封装 |

服务端只需要实现本文描述的协议入口，并让设备端配置的 URL 指向该入口。开发期可使用 `ws://`；生产期若只开放 `wss://`，必须先确认设备固件可完成 TLS 握手。

### 1.2 WebSocket 握手

设备发起标准 WebSocket Upgrade。若设备配置了 token，会携带:

```http
GET /v1/device/ws HTTP/1.1
Host: api.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: <random-base64>
Sec-WebSocket-Version: 13
X-Bridge-Token: <device-token>
```

服务端必须返回标准 `101 Switching Protocols`:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: <accept>
```

鉴权建议:

| 阶段 | 要求 |
|---|---|
| 当前兼容 | 接受并校验 `X-Bridge-Token` |
| 后续增强 | 如需更换鉴权方式，必须与设备端同步约定；本文第一版以 `X-Bridge-Token` 为准 |

### 1.3 Frame 规则

| 方向 | 规则 |
|---|---|
| 设备 -> 服务端 text | JSON message |
| 设备 -> 服务端 binary | 一个 binary message 可能包含一个或多个连续 `NA` 上行音频帧，服务端必须循环解析 |
| 服务端 -> 设备 text | JSON message |
| 服务端 -> 设备 binary | 每个 binary message **必须且只能包含一个 PCM16 mono `NA` 下行音频帧** |
| 服务端 -> 设备 frame 大小 | 任意单个下行 WebSocket payload，包括 JSON text 和 binary，均不得超过 16 KiB |
| 压缩 | 不启用 `permessage-deflate` 或其他 WebSocket payload 压缩 |
| 分片 | 不发送 fragmented message；当前设备端不重组 WebSocket continuation frame |
| ping/pong | 服务端应响应设备 WebSocket ping；也要处理设备 JSON `ping` |

关键硬约束:

1. 服务端下行 binary message 不能拼接多个 `NA` 播放帧。
2. 服务端下行音频当前必须是 PCM16 mono。
3. 服务端下行最后一个音频帧必须带 `NA END`；`playback_end` JSON 不能替代 `NA END`。
4. 服务端上行解析必须支持一个 binary message 中有多个 `NA` 帧。

## 2. 连接生命周期

### 2.1 正常对话流程

```text
Device  -> Server: WebSocket handshake
Device  -> Server: hello
Device  -> Server: ping
Server  -> Device: pong

Device  -> Server: listen start
Device  -> Server: binary NA mic frame(s)
Device  -> Server: listen stop

Server  -> Device: asr_partial / asr_final (optional)
Server  -> Device: asr_result
Server  -> Device: text_response
Server  -> Device: playback_begin
Server  -> Device: binary PCM16 mono NA playback frame START
Server  -> Device: binary PCM16 mono NA playback frame(s)
Server  -> Device: binary PCM16 mono NA playback frame END
Server  -> Device: playback_end
```

### 2.2 断线重连

服务端必须把 WebSocket 连接视为易断连接:

| 情况 | 服务端处理 |
|---|---|
| 断线后重连 | 创建新的连接上下文 |
| 旧连接仍在线但同一设备新连接到达 | 必须只保留最新连接为 active；旧连接应关闭或标记 inactive，禁止继续发送音频和命令 |
| listen 中断线 | 关闭该 audio session，不生成错误回答 |
| playback 中断线 | 停止该连接上的下行音频发送 |
| 重连后 | 重新等待 `hello`，不要复用旧连接内的音频流状态 |

## 3. ID 与上下文

服务端必须维护以下 ID:

| ID | 生成方 | 生命周期 | 用途 |
|---|---|---|---|
| `connection_id` | 服务端 | 一次 WebSocket 连接 | 服务端内部连接索引 |
| `device_id` | 设备端 `hello` | 设备生命周期 | 设备身份 |
| `request_id` | 发起方 | 一次请求/命令 | 请求、命令、ack 关联 |
| `audio_session_id` | 服务端或设备端 | 一段听音/上传音频 | 归属上行音频和 ASR |
| `turn_id` | 服务端 | 一轮对话 | 归属 ASR、智能体回复、TTS |
| `playback_id` | 服务端 | 一段 TTS 播放 | 归属下行音频和播放状态 |

约束:

1. `turn_id` 不在 `NA` 二进制帧头内，必须通过 JSON 上下文维护。
2. `playback_id` 不在 `NA` 二进制帧头内，必须通过 `playback_begin/playback_end` 维护。
3. 普通 `listen` 当前可能不携带 `audio_session_id`，服务端必须能为该连接生成隐式 audio session。
4. 同一设备连接上不要同时打开多个普通上行 audio session；当前 `NA` 帧头无法区分并发 audio session。
5. 某个 `turn_id/playback_id` 被取消或结束后，服务端必须停止发送旧音频。

### 3.1 字段长度限制

设备端使用固定长度缓冲区保存部分字段。服务端应遵守以下最大字符数，避免设备截断后造成日志和状态关联混乱。

| 字段 | 服务端建议最大字符数 |
|---|---:|
| `command` | 31 |
| `mode` | 23 |
| `request_id` | 39 |
| `audio_session_id` / `audioSessionId` | 47 |
| `turn_id` | 47 |
| `playback_id` | 47 |
| `playback_reason` / `reason` | 23 |
| `provider` | 23 |
| `ssid` | 32 |
| `password` | 64 |
| `state` | 23 |
| `emotion` / `assistant_emotion` / `assistantEmotion` | 23 |
| `title` | 39 |
| `lines[]` 单行 | 47 |
| `assistant_text` / `text` / command `text` | 511 |
| `user_text` | 255 |
| `error` | 127 |
| `mcp.payload` 序列化后 | 511 |

建议服务端生成短 ID，例如:

```text
req_20260703_000001
aud_20260703_000001
turn_20260703_000001
pb_20260703_000001
```

## 4. 设备 -> 服务端 JSON

所有 JSON message 都必须包含 `type` 字段。服务端应忽略未知字段，但不能因为未知字段断开连接。

### 4.1 `hello`

设备连接成功后发送一次。下面是 `hello` 字段形态示例；具体值会随固件构建、设备型号和启用能力变化。服务端不得硬编码示例值，必须以实际收到的 `hello.audio_params` 为准。特别是 `sample_rate`、`output_sample_rate`、`frame_duration_ms`、`codec` 可能随固件配置变化，示例中的 `16000/24000/20ms/pcm16` 不代表所有交付固件:

```json
{
  "type": "hello",
  "version": 1,
  "device_id": "esp32s3-demo",
  "transport": "websocket",
  "features": {
    "audio_upload": true,
    "audio_playback": true,
    "mcp": true
  },
  "audio_params": {
    "input_format": "pcm16",
    "codec": "pcm16",
    "opus": false,
    "output_format": "pcm16",
    "sample_rate": 16000,
    "output_sample_rate": 24000,
    "channels": 1,
    "mic_channels": 4,
    "frame_duration_ms": 20,
    "speaker": true,
    "wake_word": true,
    "vad": false,
    "full_duplex": true,
    "shared_i2s": true,
    "hardware_profile": "esp_vocat_v1_0",
    "aec": false,
    "aec_reference": "es7210_slot2",
    "has_ref": true,
    "ref_slot": 2,
    "afe_input_format": "MR"
  }
}
```

服务端必须:

1. 保存 `device_id` 与连接映射。
2. 保存 `audio_params`，用于解析上行音频和生成下行音频。
3. 按 `codec` / `opus` 判断上行音频可能是 PCM16 或 Opus。
4. 按 `output_sample_rate` 生成下行 PCM16 音频。不要硬编码 `16000` 或 `24000`；采样率以实际 `hello` 为准。
5. 不把 `aec`、`aec_reference`、`has_ref` 等硬件声明字段当作服务端业务决策依据；它们只描述设备端当前声明状态。

### 4.2 `ping`

```json
{
  "type": "ping",
  "now_ms": 123456789
}
```

服务端返回:

```json
{
  "type": "pong",
  "now_ms": 123456789,
  "server_ms": 123456790
}
```

`server_ms` 建议携带，设备当前不会强依赖。

### 4.3 `listen`

开始听音:

```json
{
  "type": "listen",
  "state": "start",
  "mode": "wake_word",
  "audio_session_id": "aud_001",
  "request_id": "req_001"
}
```

结束听音:

```json
{
  "type": "listen",
  "state": "stop",
  "mode": "wake_word",
  "audio_session_id": "aud_001",
  "request_id": "req_001"
}
```

字段:

| 字段 | 必填 | 说明 |
|---|---|---|
| `state` | 是 | 当前主线为 `start`、`stop`；其他值按异常状态处理 |
| `mode` | 是 | 触发来源，例如 `wake_word`、`touch_listen`、`auto_followup` |
| `audio_session_id` | 否 | 可能缺省；服务端必须能生成隐式 session |
| `request_id` | 否 | 可能缺省 |

服务端处理:

1. 收到 `start` 后创建 audio session。
2. `start` 后收到的上行 `NA` 音频归属当前 session。
3. 收到 `stop` 后关闭该连接上的当前 active audio session，flush ASR。
4. `stop` 可能缺省 `audio_session_id/request_id`，也不保证 `mode` 与 `start` 完全一致；服务端不能因为缺少 ID 或 mode 不匹配而保留旧 session。
5. 收到未知/异常 `state` 或连接断开后，关闭当前 session，不继续生成本轮回答。

### 4.4 `text_request`

非语音文本入口，可选兼容:

```json
{
  "type": "text_request",
  "request_id": "req_text_001",
  "text": "你好"
}
```

服务端可按普通用户输入创建 turn，并返回 `text_response` 和 TTS。

### 4.5 `cancel_turn`

设备请求取消某个 turn:

```json
{
  "type": "cancel_turn",
  "request_id": "req_cancel_001",
  "turn_id": "turn_001",
  "reason": "device_cancel"
}
```

服务端必须:

1. 将对应 `turn_id` 标记为 canceled。
2. 停止该 turn 的 LLM、TTS 和下行播放帧。
3. 丢弃该 turn 后续已排队但尚未发送的音频。
4. 返回 `cancel_turn_ack`。

响应:

```json
{
  "type": "cancel_turn_ack",
  "ok": true,
  "turn_id": "turn_001",
  "new_turn_id": "turn_002",
  "reason": "device_cancel"
}
```

`new_turn_id` 为可选字段。若服务端尚未创建下一轮 turn，可省略该字段。

### 4.6 `input_event`

设备触摸或本地输入事件:

```json
{
  "type": "input_event",
  "source": "touch",
  "action": "press",
  "touch": {
    "x": 120,
    "y": 80,
    "gesture": 1,
    "points": 1,
    "event": 0
  }
}
```

服务端可记录埋点。可选返回:

```json
{
  "type": "input_event_ack",
  "source": "touch",
  "action": "press",
  "events_received": 1
}
```

### 4.7 `wifi_scan_result`

设备执行 `wifi_scan` 后返回:

```json
{
  "type": "wifi_scan_result",
  "ok": true,
  "message": "ok",
  "count": 2,
  "networks": [
    {
      "ssid": "OfficeWiFi",
      "rssi": -45,
      "authmode": 3,
      "secure": true
    }
  ]
}
```

### 4.8 `wifi_status`

```json
{
  "type": "wifi_status",
  "phase": "connected",
  "ssid": "OfficeWiFi",
  "ip": "192.168.1.10",
  "ok": true,
  "message": "ok"
}
```

`phase` 常见值:

| phase | 说明 |
|---|---|
| `connecting` | 正在连接 |
| `connected` | 已连接 |
| `failed` | 连接失败 |
| `disconnected` | 已断开 |

### 4.9 `device_command_ack`

设备执行服务端命令后返回:

```json
{
  "type": "device_command_ack",
  "request_id": "cmd_001",
  "command": "set_emotion",
  "ok": true,
  "message": "happy"
}
```

服务端必须用 `request_id + command` 关联命令结果。命令重发必须具备幂等性。

## 5. 服务端 -> 设备 JSON

### 5.1 `pong`

见 4.2。

### 5.2 `device_command`

通用格式:

```json
{
  "type": "device_command",
  "request_id": "cmd_001",
  "command": "set_emotion"
}
```

设备会返回 `device_command_ack`。生产服务端只应使用本文列出的产品通信命令。

#### `set_emotion`

```json
{
  "type": "device_command",
  "request_id": "cmd_emotion_001",
  "command": "set_emotion",
  "emotion": "happy"
}
```

用于立即切换设备 UI 语义表情。更推荐在 `text_response.emotion` 中随回答下发。

#### `set_volume`

```json
{
  "type": "device_command",
  "request_id": "cmd_volume_001",
  "command": "set_volume",
  "volume_percent": 35,
  "persist": true
}
```

| 字段 | 说明 |
|---|---|
| `volume_percent` | 0..100，必填 |
| `persist` | 是否持久化，默认 false |

#### `stop_playback`

```json
{
  "type": "device_command",
  "request_id": "cmd_stop_001",
  "command": "stop_playback",
  "turn_id": "turn_001",
  "title": "VOICE",
  "text": "playback stopped"
}
```

用于要求设备停止当前播放。服务端同时必须停止继续发送旧 `playback_id` 的音频帧。

#### `set_state`

```json
{
  "type": "device_command",
  "request_id": "cmd_state_001",
  "command": "set_state",
  "state": "thinking"
}
```

支持状态:

| state | 说明 |
|---|---|
| `booting` | 启动 |
| `wifi_connecting` | WiFi 连接中 |
| `ws_connecting` | WebSocket 连接中 |
| `idle` | 空闲 |
| `sleeping` / `wake_only` | 休眠或仅唤醒 |
| `listening` | 听音 |
| `thinking` | 思考 |
| `speaking` | 播放中 |
| `error` | 错误 |

注意: `set_state` 是设备状态机控制，不等同于语义表情。语义表情使用 `text_response.emotion` 或 `set_emotion`。

#### `sleep_conversation`

```json
{
  "type": "device_command",
  "request_id": "cmd_sleep_001",
  "command": "sleep_conversation",
  "turn_id": "turn_001",
  "text": "进入休眠"
}
```

用于让设备退出当前对话态并进入休眠/待唤醒状态。

#### `show_status`

```json
{
  "type": "device_command",
  "request_id": "cmd_status_001",
  "command": "show_status",
  "title": "NETWORK",
  "lines": ["WiFi connected", "RSSI -45", "WS online"],
  "text": "status"
}
```

用于状态展示。`lines` 最多按设备端显示能力处理，建议不超过 6 行。

#### `wifi_scan`

```json
{
  "type": "device_command",
  "request_id": "cmd_wifi_scan_001",
  "command": "wifi_scan"
}
```

设备会先返回 `device_command_ack`，随后异步返回 `wifi_scan_result`。

#### `wifi_connect`

```json
{
  "type": "device_command",
  "request_id": "cmd_wifi_conn_001",
  "command": "wifi_connect",
  "ssid": "OfficeWiFi",
  "password": "password123"
}
```

该命令只适用于设备已经能连接服务端的场景。新设备首次没有 WiFi 时，不能依赖 WebSocket `wifi_connect`。

### 5.3 `asr_partial`

```json
{
  "type": "asr_partial",
  "provider": "asr-provider",
  "audio_session_id": "aud_001",
  "turn_id": "turn_001",
  "text": "今天天气",
  "definite": false,
  "sequence": 3,
  "at_ms": 640
}
```

用于设备日志和状态展示。服务端可按需发送。

### 5.4 `asr_final`

```json
{
  "type": "asr_final",
  "provider": "asr-provider",
  "audio_session_id": "aud_001",
  "turn_id": "turn_001",
  "text": "今天天气怎么样",
  "definite": true,
  "sequence": 8,
  "at_ms": 1600
}
```

### 5.5 `asr_result`

成功:

```json
{
  "type": "asr_result",
  "ok": true,
  "provider": "asr-provider",
  "audio_session_id": "aud_001",
  "turn_id": "turn_001",
  "text": "今天天气怎么样"
}
```

失败:

```json
{
  "type": "asr_result",
  "ok": false,
  "provider": "asr-provider",
  "audio_session_id": "aud_001",
  "turn_id": "turn_001",
  "text": "",
  "error": "no_speech"
}
```

### 5.6 `audio_session`

```json
{
  "type": "audio_session",
  "state": "closed",
  "audio_session_id": "aud_001",
  "frames": 80,
  "duration_ms": 1600,
  "rms": 1380
}
```

用于服务端向设备同步音频会话统计。设备当前主要用于日志和状态辅助。

### 5.7 `text_response`

```json
{
  "type": "text_response",
  "ok": true,
  "request_id": "req_001",
  "turn_id": "turn_001",
  "user_text": "今天天气怎么样",
  "assistant_text": "我来帮你看一下。",
  "emotion": "thinking",
  "tts_pending": true
}
```

字段:

| 字段 | 必填 | 说明 |
|---|---|---|
| `ok` | 是 | 是否成功 |
| `request_id` | 建议 | 对应请求 |
| `turn_id` | 是 | 本轮对话 ID |
| `user_text` | 否 | 用户文本 |
| `assistant_text` | 否 | 助手文本，设备用于日志/展示 |
| `emotion` | 建议 | 语义表情 |
| `tts_pending` | 是 | 后续是否会下发 TTS 音频 |
| `error` | 失败时 | 错误信息 |

若 `tts_pending=true`，服务端应随后发送 `playback_begin` 和下行音频。

### 5.8 `playback_begin`

```json
{
  "type": "playback_begin",
  "request_id": "req_001",
  "turn_id": "turn_001",
  "playback_id": "pb_001",
  "provider": "tts-provider",
  "sample_rate": 24000,
  "channels": 1,
  "frame_duration_ms": 20,
  "frames": 120,
  "bytes": 115200
}
```

必须先发送 `playback_begin`，再发送对应的 binary PCM16 mono `NA` 播放帧。

`sample_rate` 必须等于实际收到的 `hello.audio_params.output_sample_rate`。上面的 `24000` 只是示例值；如果设备 hello 声明 `16000`，服务端必须下发 16kHz PCM16 mono。

`frames` 和 `bytes` 建议填写总帧数和总字节数。若服务端采用流式 TTS，开始播放时暂时无法得知总量，可以填 `0` 或省略；最终统计可在 `playback_end` 中补齐。

### 5.9 `playback_end`

```json
{
  "type": "playback_end",
  "request_id": "req_001",
  "turn_id": "turn_001",
  "playback_id": "pb_001",
  "provider": "tts-provider",
  "sample_rate": 24000,
  "channels": 1,
  "frame_duration_ms": 20,
  "frames": 120,
  "bytes": 115200,
  "reason": "completed"
}
```

`playback_end` 只结束 JSON 播放上下文，不能替代最后一个音频 `NA END` 帧。

`playback_end.sample_rate`、`channels`、`frame_duration_ms` 应与对应 `playback_begin` 和实际下发的 `NA` 播放帧一致，不能使用示例值覆盖设备 hello 中的真实输出参数。

### 5.10 `tts_result`

TTS 失败时建议发送:

```json
{
  "type": "tts_result",
  "ok": false,
  "request_id": "req_001",
  "turn_id": "turn_001",
  "provider": "tts-provider",
  "playback_id": "pb_001",
  "frames": 0,
  "duration_ms": 0,
  "sample_rate": 24000,
  "channels": 1,
  "playback_start": false,
  "playback_end": false,
  "error": "tts_failed"
}
```

成功播放主链路以 `playback_begin`、binary `NA`、`playback_end` 为准。

`tts_result` 中的音频参数同样是统计字段；若携带，必须与设备 hello 和实际播放流一致。

### 5.11 `mcp`

可选兼容。第一版服务端可以不实现该链路；设备基础对话、表情和播放不依赖 MCP。

```json
{
  "type": "mcp",
  "payload": {
    "jsonrpc": "2.0",
    "id": "mcp_001",
    "method": "tools/call",
    "params": {
      "name": "self.ui.set_emotion",
      "arguments": {
        "emotion": "happy"
      }
    }
  }
}
```

服务端如需同步表情，优先使用 `text_response.emotion` 或 `device_command set_emotion`，不要把 MCP 作为基础对话必需链路。

## 6. `NA` 二进制音频帧

### 6.1 Header

每个音频帧由 22 字节 header 和 payload 组成:

```text
+----------------------+--------------------+
| 22-byte NA header    | audio payload      |
+----------------------+--------------------+
```

字段布局，所有多字节整数均为 little-endian:

| offset | size | 字段 | 类型 | 说明 |
|---:|---:|---|---|---|
| 0 | 2 | magic | bytes | 固定 ASCII `NA` |
| 2 | 1 | version | uint8 | 当前为 `1` |
| 3 | 1 | codec | uint8 | `1=pcm16`，`2=opus` |
| 4 | 1 | flags | uint8 | bit flags |
| 5 | 1 | channels | uint8 | 通道数 |
| 6 | 2 | sample_rate | uint16 | 采样率 |
| 8 | 2 | frame_duration_ms | uint16 | 帧时长 |
| 10 | 4 | sequence | uint32 | 音频帧序号 |
| 14 | 4 | timestamp_ms | uint32 | 流内相对时间 |
| 18 | 2 | payload_len | uint16 | payload 字节数 |
| 20 | 2 | reserved | uint16 | 当前为 `0`，服务端解析时忽略 |
| 22 | N | payload | bytes | PCM16 或 Opus packet |

### 6.2 codec

| codec | 名称 | payload |
|---:|---|---|
| 1 | `pcm16` | little-endian signed 16-bit PCM samples |
| 2 | `opus` | 单个 Opus packet |

`codec=2` 时 payload 是一帧 Opus packet，不是 Ogg、WebM、RTP，也不包含容器头。

### 6.3 flags

| bit | 值 | 名称 | 说明 |
|---:|---:|---|---|
| 0 | `0x01` | `START` | 流或片段开始 |
| 1 | `0x02` | `END` | 流或片段结束 |
| 2 | `0x04` | `VAD_SPEECH` | 设备侧认为该帧含语音 |

服务端必须忽略未知 bit。

### 6.4 上行音频规则

设备上行 binary message 可能包含多个连续 `NA` 帧:

```text
WS binary payload = NA frame 1 + NA frame 2 + NA frame 3 + ...
```

服务端解析伪代码:

```js
function parseNaBatch(buffer) {
  let offset = 0;
  const frames = [];
  while (offset < buffer.length) {
    if (buffer.length - offset < 22) throw new Error("short NA header");
    if (buffer[offset] !== 0x4e || buffer[offset + 1] !== 0x41) throw new Error("bad magic");

    const version = buffer.readUInt8(offset + 2);
    const codec = buffer.readUInt8(offset + 3);
    const flags = buffer.readUInt8(offset + 4);
    const channels = buffer.readUInt8(offset + 5);
    const sampleRate = buffer.readUInt16LE(offset + 6);
    const frameDurationMs = buffer.readUInt16LE(offset + 8);
    const sequence = buffer.readUInt32LE(offset + 10);
    const timestampMs = buffer.readUInt32LE(offset + 14);
    const payloadLen = buffer.readUInt16LE(offset + 18);
    if (version !== 1) throw new Error("unsupported NA version");
    if (codec !== 1 && codec !== 2) throw new Error("unsupported NA codec");

    const frameEnd = offset + 22 + payloadLen;
    if (frameEnd > buffer.length) throw new Error("truncated NA payload");
    if (codec === 1 && (payloadLen % 2) !== 0) throw new Error("bad PCM16 payload length");

    const payload = buffer.subarray(offset + 22, frameEnd);
    frames.push({ version, codec, flags, channels, sampleRate, frameDurationMs, sequence, timestampMs, payload });
    offset = frameEnd;
  }
  return frames;
}
```

服务端必须:

1. 校验 `magic=NA`。
2. 校验 `version=1`。
3. 按 `codec` 解析 PCM16 或 Opus。
4. 按 `payload_len` 循环解析直到 binary message 结束。
5. 记录 `sequence` 跳变，但不要因为单次跳变立即断开连接。
6. 禁止同一连接同时打开多个普通 audio session。

### 6.5 下行音频规则

服务端下发给设备播放的 binary message 当前必须满足:

| 项 | 硬要求 |
|---|---|
| WebSocket message | 一个 binary message 必须只包含一个 `NA` 帧 |
| codec | 必须为 `1`，即 PCM16 |
| channels | 必须为 `1`，即 mono |
| sample_rate | 必须匹配 `hello.audio_params.output_sample_rate` |
| frame_duration_ms | 建议与 `hello.audio_params.frame_duration_ms` 一致；常见为 20ms，但必须以实际 hello 为准 |
| payload | PCM16 little-endian mono samples |
| payload_len | 不超过 `uint16`，且整个 WebSocket payload 不超过 16 KiB |
| END | 最后一帧必须带 `flags & 0x02` |

以下是 20ms / 24kHz / mono PCM16 的计算示例；实际服务端必须使用 `hello.audio_params.output_sample_rate` 和 `hello.audio_params.frame_duration_ms`:

```text
sample_count = 24000 * 20 / 1000 * 1 = 480 samples
payload_len = 480 * 2 = 960 bytes
websocket_payload_len = 22 + 960 = 982 bytes
```

允许用 0 payload 的 `END` 控制帧结束播放队列:

```text
magic=NA, codec=pcm16, flags=END, channels=1, payload_len=0
```

该 `END` 控制帧仍必须单独占用一个 WebSocket binary message。

## 7. 音频上行流程

### 7.1 服务端处理顺序

```text
1. 收到 listen start
2. 创建 audio_session
3. 收到 binary NA 音频帧
4. 解码为 PCM
5. 送入服务端音频处理 / ASR
6. 收到 listen stop
7. flush ASR
8. 创建 turn
9. 返回 asr_result / text_response / TTS 播放
```

服务端不应等 `listen stop` 后才开始处理音频。建议边收边解码，边送流式 ASR 或音频前处理。

### 7.2 时间戳

`NA.timestamp_ms` 是音频流内相对时间，通常为:

```text
timestamp_ms = sequence * frame_duration_ms
```

它不是 Unix 时间，也不是设备绝对时钟。服务端若需要精确对齐，应同时记录:

1. WebSocket frame 到达服务端的 wall clock。
2. 当前 `audio_session_id` 的开始时间。
3. 每个 `NA.sequence` 的接收时间。

## 8. 音频下行播放流程

### 8.1 标准流程

```text
Server -> Device: text_response
Server -> Device: playback_begin
Server -> Device: binary PCM16 mono NA seq=0 START
Server -> Device: binary PCM16 mono NA seq=1
Server -> Device: binary PCM16 mono NA seq=2
Server -> Device: binary PCM16 mono NA seq=N END
Server -> Device: playback_end
```

播放顺序:

1. 推荐先发送 `text_response`，用于文本、TTS 状态和语义表情同步。
2. 必须先发送 `playback_begin`，绑定 `turn_id` 和 `playback_id`。
3. 再连续发送 PCM16 mono `NA` binary message，每个 binary message 只包含一个 `NA` 帧。
4. 最后一帧必须带 `END`。
5. 最后发送 `playback_end`。

### 8.2 TTS 切片

```text
samples_per_frame = output_sample_rate * frame_duration_ms / 1000 * channels
payload_bytes = samples_per_frame * 2
```

当前下行 `channels` 必须为 1。若 TTS 供应商输出 stereo，服务端必须先 downmix 为 mono，再重采样到 `output_sample_rate`，再切片。

### 8.3 旧帧处理

服务端必须保证:

1. 一个 `playback_id` 结束或取消后，不再发送该 `playback_id` 的音频帧。
2. TTS worker 中已排队的旧音频必须在服务端发送前过滤。
3. 新 `playback_begin` 前不得混入旧 `playback_id` 音频。
4. 重复 `playback_end` 必须幂等。

## 10. 错误处理

### 10.1 JSON 错误

服务端收到非法 JSON:

1. 记录错误。
2. 不要让服务进程崩溃。
3. 可以忽略该 message。
4. 连续非法消息可断开连接。

设备收到带 `error` 字段的 JSON 会记录日志，但不是统一错误事件协议。

### 10.2 音频帧错误

服务端收到非法 `NA`:

| 错误 | 处理 |
|---|---|
| magic 非 `NA` | 丢弃当前 binary message，记录错误 |
| header 不足 22 字节 | 丢弃当前 binary message |
| version 不支持 | 丢弃该帧 |
| codec 不支持 | 丢弃该帧并标记 session 错误 |
| payload_len 越界 | 丢弃当前 binary message |
| PCM16 payload 非偶数字节 | 丢弃该帧 |
| sequence 跳变 | 记录丢帧，不立即断开 |

### 10.3 幂等

服务端必须保证:

1. 重复 `listen stop` 不生成重复回答。
2. 重复 `cancel_turn` 不重复取消新 turn。
3. 重复 `stop_playback` 不造成设备状态异常。
4. 重复 `playback_end` 不造成播放状态错误。
5. 旧 `turn_id/playback_id` 的结果晚到时必须丢弃。

本文只规定设备通信入口的最小安全要求，完整账号体系、设备证书体系和 App 绑定方案由云端团队另行设计。

| 项 | 要求 |
|---|---|

| 旧连接 | 同一设备重复连接时关闭旧连接 |

## 12. 最小服务端伪代码

```js
function onDeviceConnection(ws, request) {
  verifyWebSocketUpgrade(request);
  verifyBridgeToken(request.headers["x-bridge-token"]);

  const ctx = {
    deviceId: null,
    audioParams: null,
    activeAudioSession: null,
    activeTurnId: null,
    activePlaybackId: null
  };

  ws.on("message", (data, isBinary) => {
    if (isBinary) {
      try {
        const frames = parseNaBatch(data);
        for (const frame of frames) {
          handleUplinkAudioFrame(ctx, frame);
        }
      } catch (err) {
        logBadAudioFrame(ctx, err);
      }
      return;
    }

    let msg;
    try {
      msg = JSON.parse(data.toString("utf8"));
    } catch (err) {
      logBadJson(ctx, err);
      return;
    }
    switch (msg.type) {
      case "hello":
        ctx.deviceId = msg.device_id;
        ctx.audioParams = msg.audio_params;
        registerDeviceConnection(ctx);
        break;
      case "ping":
        ws.send(JSON.stringify({ type: "pong", now_ms: msg.now_ms, server_ms: Date.now() }));
        break;
      case "listen":
        handleListen(ctx, msg);
        break;
      case "text_request":
        handleTextRequest(ctx, msg);
        break;
      case "cancel_turn":
        handleCancelTurn(ctx, msg);
        break;
      case "input_event":
        handleInputEvent(ctx, msg);
        break;
      case "wifi_scan_result":
      case "wifi_status":
      case "device_command_ack":
        handleDeviceStatus(ctx, msg);
        break;
      default:
        logUnknownMessage(ctx, msg);
    }
  });
}

function sendPlayback(ws, ctx, turnId, playbackId, pcm16MonoFrames) {
  ws.send(JSON.stringify({
    type: "playback_begin",
    turn_id: turnId,
    playback_id: playbackId,
    sample_rate: ctx.audioParams.output_sample_rate,
    channels: 1,
    frame_duration_ms: ctx.audioParams.frame_duration_ms,
    frames: pcm16MonoFrames.length,
    bytes: pcm16MonoFrames.reduce((n, f) => n + f.length, 0)
  }));

  for (let i = 0; i < pcm16MonoFrames.length; i++) {
    const flags = (i === 0 ? 0x01 : 0) | (i === pcm16MonoFrames.length - 1 ? 0x02 : 0);
    const na = buildNaFrame({
      codec: 1,
      flags,
      channels: 1,
      sampleRate: ctx.audioParams.output_sample_rate,
      frameDurationMs: ctx.audioParams.frame_duration_ms,
      sequence: i,
      timestampMs: i * ctx.audioParams.frame_duration_ms,
      payload: pcm16MonoFrames[i]
    });
    ws.send(na, { binary: true }); // 必须一条 WS binary message 只发一个 NA 帧
  }

  ws.send(JSON.stringify({
    type: "playback_end",
    turn_id: turnId,
    playback_id: playbackId,
    reason: "completed"
  }));
}
```

## 13. 验收清单

服务端与当前设备联调前，至少通过以下检查:

| 编号 | 必须通过 |
|---|---|
| S1 | 设备可建立 WebSocket，服务端收到 `hello` |
| S2 | 服务端能校验 `X-Bridge-Token` |
| S3 | 服务端能回复 JSON `pong` |
| S4 | 服务端能处理 `listen start/stop`，并能容忍未知 listen 状态 |
| S5 | 服务端能解析一个 binary message 中的多个上行 `NA` 帧 |
| S6 | 服务端能处理 PCM16 上行 |
| S7 | 若设备声明 Opus，服务端能按 Opus packet 解码 |
| S8 | 服务端能发送 `asr_result` 和 `text_response` |
| S9 | 服务端能通过 `text_response.emotion` 同步设备表情 |
| S10 | 服务端能发送 `playback_begin` |
| S11 | 服务端能发送 PCM16 mono 单 `NA` 帧下行 binary message |

## 14. 交付边界

本文不强制要求服务端团队拥有或运行完整本地工程。服务端只需要按本文协议实现设备 WebSocket 接入、音频上行解析、音频下行播放、JSON 状态/命令交互；若要做自动化一致性验收，可使用第 13 节列出的 schema、fixtures 和 fake-device 资产。

不属于本文交付范围:

1. 本地开发工具、测试脚本、开发期诊断命令。
2. 智能体内部编排和模型提示词。
3. 云端业务算法。
4. 首次开箱配网和 App 绑定产品方案。
5. 设备端固件实现细节。

若服务端只做第一版设备通信，按本文实现即可完成与当前设备端的基础收发闭环。
