## 1. 当前开发目标

设备端要实现可靠全双工语音链路：

- 设备播放 TTS 时，仍持续采集用户真人声音。
- 设备端做第一层 AEC/回声压制，尽可能消除设备自己扬声器播报的声音。
- 设备端保留完整、连续、足够响度的用户真实声音。
- 设备端把处理后的音频上传给云端 ASR。网关目前只是测试桥，后续会替换为云端工程师提供的 URL。
- 播放期间收到状态命令时，设备要立刻执行，例如切换表情、状态等。
- 非播放期间：
  - 休眠态：不上传音频，只监听唤醒词。
  - 唤醒/聆听态：正常采集、做基础噪声过滤、上传。
- 当前验收重点不是网关，而是设备端音频处理：可靠采集、可靠播放、第一层清洗、播放中采集并压低设备声。

验收音频保存目录：

```text
NuwaxAIPartner/acceptance/human-audio
```

验收 WAV 应是设备端处理后的上行音频，不是原始麦克风音频。它经过当前设备端 `live_aec` 和 `audio_cleaner` 后再上传到测试网关，由网关保存为 WAV。

## 3. 当前音频链路代码逻辑

### 3.1 播放参考写入

设备播放侧在 `main/speaker_output.c`：

- `nuwax_speaker_output_init()` 初始化软件参考环形缓冲。
- `nuwax_speaker_output_write_pcm16()` 把即将写入 I2S speaker 的 PCM 转为 stereo buffer。
- I2S 写成功后调用：

```c
nuwax_p3_software_ref_write_interleaved_lr(speaker->stereo_buffer, frames_written);
```

这就是软件参考，也就是 AEC 用来知道“设备自己正在播什么”的 reference。

当前硬件 slot2 AEC ref 在最近真实测试中始终无效：

```text
hw_ref_frames=0
hw_ref_inactive=1202/1219 左右
```

因此当前有效参考路径是 software ref，不是硬件 slot2。

### 3.2 软件参考读取

`main/p3_software_ref.c`：

- `nuwax_p3_software_ref_write_interleaved_lr()` 写入播放参考。
- `nuwax_p3_software_ref_read_delayed(out, sample_count, delay_samples)` 读取延迟后的参考快照。
- 读取函数会先把 `out` 清零，再把环形缓冲里能读到的样本复制进去。
- 当前验收默认 delay 是 360 samples，即 16 kHz 下约 22.5 ms。

验收脚本参数：

```powershell
-AcceptanceDelaySamples 360
```

如果参考和麦克风声学路径延迟不匹配，AEC 抵消能力会下降；后续可能需要做 capture-time adaptive delay 或系统性扫 delay。

### 3.3 采集入口和实时采集队列

核心入口是 `main/nuwax_ai_partner_main.c` 的 `stream_microphone_audio()`。

采集队列结构：

- `nuwax_rt_capture_ctx_t`
- `nuwax_rt_capture_frame_t`
- `rt_capture_task()`
- `rt_capture_read_frame()`
- `rt_capture_receive()`

设计目的：

- 独立任务持续从 I2S mic 读取 mic1/mic2/ref。
- 主线程从 ready queue 取采集帧，避免播放/网络/处理阻塞 I2S 读取。
- 最近真实日志显示采集链路本身是稳定的：

```text
sent=1202/1219
dropped=0
queue_full=0
rtcap_drop_no_slot=0
rtcap_ready_full=0
```

所以此前“断音/静音”主要不是采集丢帧，而是 DSP 输出被压没或 FIFO underrun。

### 3.4 播放期判定

`stream_microphone_audio()` 中根据 speaker 状态生成：

```c
playback_active = speaker_pending || aec_session_gap_active || aec_hangover_active;
```

相关含义：

- `speaker_pending`：speaker 当前有待播放/正在播放。
- `aec_session_gap_active`：同一播放 session 的短间隔。
- `aec_hangover_active`：播放结束后的短保护期。

acceptance capture 只在 `playback_active` 后开始上传，见：

```c
if (acceptance_capture_enabled && !upload_started && playback_active) {
    start_mic_cloud_upload(..., NUWAX_ACCEPTANCE_CAPTURE_MODE, ...);
}
```

播放结束后：

```c
if (acceptance_capture_enabled && upload_started && acceptance_capture_playback_seen && !playback_active) {
    stop_requested = true;
}
```

所以验收 WAV 的窗口是：播放 active 起点到播放结束/尾部 hangover，不是整段脚本运行时间。

### 3.5 Live AEC

核心文件：

### 3.7 双麦当前用途

当前两个 mic 都有用，但还不是完整 beamforming：

- mic1 是主上行音频。
- mic2 用于 `compute_dual_mic_features()`，计算：
  - `diff_avg_abs`
  - `diff_peak`
  - `diff_energy_ratio_q15`
  - `level_balance_q15`
  - `voice_like`
- 这些特征用于：
  - `dual_mic_aec_preserve_hint()`
  - `dual_mic_cleaner_preserve_hint()`
  - `dual_mic_playback_raw_human_hint()`
  - `dual_mic_playback_weak_continuity_hint()`

历史问题是：双麦 hint 主要看空间差异和能量，没有充分结合播放 ref 相关性，导致设备声也可能被误判为 human-first，从而被强保护。

## 5. 已确认的主要根因

### 5.1 `have_aec_ref` 语义错误

修改前 `rt_capture_read_frame()` 中：

```c
frame->software_ref_snapshot = soft_ref_active;
frame->have_aec_ref = soft_ref_active;
```

旧逻辑把“参考快照复制成功”和“参考能量超过阈值”混成一个概念。后果：

- TTS 间隙或低能量参考帧会让 `have_aec_ref=false`。
- 主流程会在 `nuwax_live_aec_process_with_ref_and_dual_mic()` 和 `nuwax_live_aec_process_with_dual_mic()` 之间切换。
- `live_aec_process_internal()` 看到 `pending_external_ref` 模式变化，会清 pending/FIFO。
- FIFO 不足时输出补 0，形成可听硬静音。

### 5.2 Live AEC external-ref 模式切换会清 FIFO

修改前：

```c
if (aec->pending_count > 0 &&
    (aec->pending_external_ref != use_external_ref ||
     aec->pending_dual_mic != use_dual_mic)) {
    aec->pending_count = 0;
    fifo_clear(aec);
}
```

随后：

```c
if (aec->output_count < release_threshold) {
    memset(samples, 0, sample_count * sizeof(int16_t));
    aec->output_underrun_frames++;
    return ESP_OK;
}
```

这解释了真实 WAV 中 4/7/11/15 秒硬静音。

### 5.3 nearend hint 过强，设备声被保护

当前双麦 hint 在无人播放基线也可能大量触发。hint 一旦触发：

- Live AEC 会 nearend blend，把 raw mic 混回。
- raw mic 包含用户声，也包含设备声。
- cleaner softref 原来会因 nearend hint 直接 return，导致同帧设备声也被保护。

这解释了“设备声大过人声”和“人声带回声”。

### 5.4 不能只靠 VAD 区分真人和设备声

VAD/能量门限只能判断“像不像语音/有没有能量”，不能可靠区分：

- 用户真人语音。
- 设备 TTS 经过扬声器/房间/麦克风回采后的语音。

因此必须结合：

- 播放参考 ref。
- mic/ref 相关性。
- 双麦空间差异。
- AEC residual。
- 平滑/hangover。

### 6.2 `live_aec.c`

强 hint raw mic 默认混入比例从 25% 降到约 9%：

```c
#define CONFIG_NUWAX_LIVE_AEC_HINT_STRONG_RAW_MIX_Q15 3072
```

nearend blend 只计算一次 dual evidence：

```c
const bool dual_evidence = nearend_blend_dual_evidence(aec, sample_count);
```

hint 强但当前双麦证据不足时，raw mix 降级：

```c
if (hinted_strong_nearend && !dual_evidence &&
    raw_mix > CONFIG_NUWAX_LIVE_AEC_STRONG_NEAREND_RAW_MIX_Q15) {
    raw_mix = CONFIG_NUWAX_LIVE_AEC_STRONG_NEAREND_RAW_MIX_Q15;
}
```

external-ref 模式变化不再清 FIFO：

```c
const bool external_ref_mode_changed = aec->pending_external_ref != use_external_ref;
const bool dual_mic_mode_changed = aec->pending_dual_mic != use_dual_mic;
if (aec->pending_count > 0 &&
    (external_ref_mode_changed || dual_mic_mode_changed)) {
    aec->pending_count = 0;
    if (dual_mic_mode_changed) {
        fifo_clear(aec);
    }
}
```

理论效果：

- 播放期 ref active/inactive 波动不会造成 FIFO 清空。
- `output_underrun_frames` 应显著下降到 0 或接近 0。
- raw mic 设备声回灌减少。

### 6.3 `audio_cleaner.c`

新增 nearend 下 softref 线性抵消阈值：

```c
#define CONFIG_NUWAX_AUDIO_CLEANER_SOFTREF_NEAREND_LINEAR_MIN_CORR_Q15 8192
#define CONFIG_NUWAX_AUDIO_CLEANER_SOFTREF_NEAREND_MAX_LINEAR_GAIN_Q15 8192
```

新增：

```c
static int32_t clamp_abs_i32(int32_t value, int32_t max_abs)
```

修改前 nearend hint 直接 return：

```c
if (nearend_hint || (speech_protected && pre_linear_nearend_guard && !high_corr_echo)) {
    return level;
}
```

修改后：

- nearend hint 下，如果 softref corr 达到 8192 以上，允许做受限线性抵消。
- 抵消增益最大 8192，即 0.25。
- 低相关帧仍保护，避免误伤人声。

核心逻辑：

```c
const bool nearend_guard_requested =
    nearend_hint || (speech_protected && pre_linear_nearend_guard);
const bool nearend_linear_echo =
    nearend_guard_requested &&
    metrics.corr_q15 >= CONFIG_NUWAX_AUDIO_CLEANER_SOFTREF_NEAREND_LINEAR_MIN_CORR_Q15 &&
    metrics.gain_q15 != 0;
```

理论效果：

- 双讲时不再无条件保护设备声。
- 高相关设备声会被有限削减。
- 人声不会被整帧强压。

## 14. 不建议直接采用的错误修复方向

不要直接做：

```text
REF_MISSING_ATTENUATE_Q15 2048 -> 24576
REF_INACTIVE_ATTENUATE_Q15 2048 -> 24576
直接移除 dual guard
单独把 ADAPTIVE_REF_MIN_CORR_Q15 6000 -> 1500 就期待解决
```

原因：

- 提高 ref_missing/ref_inactive attenuation 会让用户声变大，但设备声也会一起变大。
- 直接移除 dual guard 会增加 raw mic 回灌，可能加重设备声和人声回声。
- 当前主路径是 capture-time external ref，且 internal software ref 被关闭；单独调 adaptive internal ref 阈值不是第一优先级。

正确优先级：

1. 保证播放期 external ref 模式稳定。
2. 降低 `output_underrun_frames`。
3. 增加 ref-aware hint，避免设备声被 human-first 保护。
4. 控制 raw mic 混回。
5. 在保人声前提下做 softref/residual 设备声削减。
6. 最后再调参数。

## 15. 后续可能需要继续开发的方向

如果 2026-07-10 修复后设备声仍偏大，下一步建议：

### 15.1 延迟校准

当前 acceptance delay 是 360 samples。需要做 delay sweep：

```text
240, 300, 360, 420, 480, 560 samples
```

观察：

- `mic_ref_corr_q15`
- `residual_corr_q15`
- `softref_corr_q15`
- 主观设备声残留

最终应实现 capture-time adaptive delay，而不是只依赖固定 360。

### 15.2 更完整的 ref-aware 双麦分类

当前只加了 mic1/ref correlation veto。后续可增加：

- mic2/ref corr。
- mic1/ref gain。
- mic2/ref gain。
- output/ref corr。
- residual/ref corr。
- 双麦相位/延迟差。

目标分类：

```text
echo_confidence = ref active + mic/ref 高相关 + 双麦差分不强
nearend_confidence = 双麦近场差分强 + ref 相关低/中 + 语音能量稳定
doubletalk = ref active + nearend_confidence 同时成立
```

不同分类采用不同策略：

- echo-only：强压设备声。
- nearend-only：保人声。
- doubletalk：低增益 ref cancellation + 人声 floor/gain，不大比例 raw mix。

### 15.3 减少 raw mic 依赖

人声音量不要主要靠 raw mic 混回。raw mic 一定包含设备声。应更多依赖：

- AEC 输出后的 protected gain。
- nearend floor restore。
- 双麦增强。
- 平滑 gain envelope。

### 18.3 最新问题的代码级根因

本轮“设备声有些许压低”说明 `playback_echo_veto_attenuated=409` 生效；但“人声开头被压没”也能从代码和日志对应上。

关键代码路径：

```c

    dual_mic_aec_hint = false;
    dual_mic_cleaner_hint = false;

    playback_active &&
    !playback_echo_veto &&
    dual_mic_playback_raw_human_hint(...);

    !playback_echo_veto &&
    (dual_mic.voice_like || dual_mic_aec_hint || dual_mic_cleaner_hint || playback_raw_human_hint);
```

也就是说：一旦人声起音阶段被 `playback_spatial_echo_veto` 判成设备声，当前帧所有人声 hint 都会被关掉，`playback_human_seed_active` 也不会建立。

```c

```

以及：

```c

    reset_playback_echo_atten_state(cleaner);

```

这意味着：人声开头如果没有形成 `speech_gain_hint`，但又被 echo veto 命中，则不会被 continuity gain 拉起，反而会被 echo veto attenuation 压低。

### 18.4 下一步修复方向

优先级必须改为“人声起音保护 > 设备声衰减”。

建议下一步不要继续加大 echo attenuation，而是增加 human-onset guard：

1. echo veto attenuation 必须要求连续 echo veto streak，例如 2-3 帧后才开始衰减。
2. 如果最近 200-300ms 出现过 `playback_human_seed_active`、`playback_raw_human_hint_active`、`dual_mic_cleaner_hint_active` 或 `speech_gain_hint`，则 echo attenuation 应该降级或关闭。
3. 对 `speech_protected=1` 但当前 hint 不足的帧，不应直接 0.5x 衰减。应区分：
   - human onset / human tail：保护或轻微增益。
   - echo-only hangover：才允许衰减。
4. spatial echo veto 不应单独决定样本级衰减。样本级衰减至少需要：
   - echo veto 连续命中；
   - 无 human seed；
   - 无 raw onset；
   - 无 weak continuity；
   - 最好有 softref/ref 相关性或低双麦差分稳定证据。
5. 可以保留 echo veto 对上传门控的阻断，但样本级 attenuation 要比门控更保守。
6. 下一轮测试指标：

```text

playback_continuity_gain 应继续覆盖低能人声。
```

当前判断：

- `continuity gain` 方向正确，已经拉起不少低能人声。
- `echo veto sample attenuation` 方向也正确，但当前触发条件过早、过宽。
- 最新首要修复不是加大消回声，而是给 echo attenuation 增加人声起音保护和延迟确认。

#### 18.6.5 当前代码中的核心问题

当前问题不是单点 bug，而是策略层缺少“人声保真”和“设备残留抑制”的连续权衡。

问题 1：`speech_protected` 是二值保护，保护后几乎禁止多数 echo 抑制。

代码表现：

```text

-> echo attenuation bypass
-> unprotected gate bypass
-> softref nearend guard bypass
-> protected gain/limiter 仍可执行
```

结果：人声安全了，但设备声和伪影也被安全放行。

问题 2：`playback_echo_atten_guard` 过于宽，但这是为修复人声起音必须做的保守选择。

本轮 `playback_echo_veto_guarded=466` 证明 guard 有效。但 guard 当前没有细分：

```text
真人强证据 guard
真人弱证据 guard
历史 human seed guard
双麦疑似 onset guard
```

它们在样本级处理上都等价为“不衰减”。后续需要把它们改为连续置信度，而不是同一个 bool。

问题 3：softref gate 只在 `!speech_protected` 下工作，双讲时清设备声能力不足。

当前代码为了避免误伤人声，只有非保护帧才执行强 gate。双讲时应增加“温和 residual echo suppression”，例如：

```text
high ref confidence + weak/medium human confidence:
    低增益线性 ref cancel 或轻度频段抑制
strong human confidence:
    只做很小 residual cleanup，不做整帧 gate
echo-only confidence:
    才做强 attenuation
```

问题 4：live AEC 的 restore 路径可能把 echo 残留加回去。

`nearend_blend`、`dual_restore`、`floor_restore` 是保人声所需，但当前恢复内容不是纯人声。尤其 `dual_restore` 使用 `mic1 - k*mic2`，对真实近场人声有效，但对房间反射/扬声器泄漏也可能产生残留差分。

问题 5：保护增益/limiter 不是人声专用。

`playback_protected_gain=496`、`playback_continuity_gain=466` 说明本轮大量低能片段被增益。它解决了人声小的问题，但也会放大：

- 设备残留；
- AEC musical residual；
- 双麦 restore 差分伪影；
- TTS 高频辅音边缘。

问题 6：adaptive ref 没有实际工作。

虽然配置打开：

```text
CONFIG_NUWAX_LIVE_AEC_ADAPTIVE_REF_ENABLE=y
CONFIG_NUWAX_LIVE_AEC_ADAPTIVE_REF_SPAN_SAMPLES=1600
CONFIG_NUWAX_LIVE_AEC_ADAPTIVE_REF_STEP_SAMPLES=160
```

但日志：

```text
adaptive_ref=0
adaptive_candidates=0
```

说明当前 AEC 主要还是固定 delay。设备声大、回声残留和电音感都可能与 ref delay/声学路径不匹配有关。

#### 18.6.6 下一步修复方向

下一步不应回退 onset guard，也不应直接加大 `playback_echo_veto_attenuation`。否则很容易重新压坏人声开头。

建议修复顺序：

1. 保留当前 onset guard，确认人声不再强衰减。
2. 降低尖锐风险：
   - 将 `CONFIG_NUWAX_AUDIO_CLEANER_PLAYBACK_PROTECTED_LIMIT_PEAK` 从 12000 下调到 9000-10000 区间验证。
   - 将 `CONFIG_NUWAX_AUDIO_CLEANER_PLAYBACK_PROTECTED_GAIN_TARGET_AVG_ABS` 从 1200 下调到 900-1000 区间验证。
   - 给 protected/continuity gain 增加更慢的 envelope 或帧间 slew limit，避免 20ms 内增益突变造成电音边缘。
3. 收紧 live AEC restore：
   - 降低 `dual_restore` 和 `nearend_floor_restore` 的混入比例。
   - 在 `mic_ref_corr_q15` 较高且不是 very strong nearend 时，禁止或降低 dual restore。
   - 确保 dual restore 后 `apply_dual_restore_residual_guard()` 能实际触发；当前 `dual_post_residual=0` 需要重点查。
4. 增加双讲温和 residual suppression，而不是二值 gate：
   - `speech_protected=true` 时不做强整帧 attenuation；
   - 但当 `ref_active=true` 且 `softref_corr_q15` 达到中高阈值时，允许小增益线性抵消或轻度频段压制；
   - 强人声帧只做很轻 residual cleanup；
   - echo-only 帧才做强压制。
5. 查 adaptive ref 为什么没有候选：
   - 打印每次 scan 的 base_corr、best_corr、copied、ref_active；
   - 若候选一直不 active，降低 candidate active 条件或扩大/细化 delay sweep；
   - 目标是让 `adaptive_candidates>0`，并观察 `adaptive_ref` 是否能稳定选到更好 offset。
6. 增加诊断保存：
   - raw mic1；
   - mic2；
   - ref；
   - live AEC output；
   - cleaner output；
   - gate/hint CSV。

当前配置：

```text
CONFIG_NUWAX_LIVE_AEC_REF_INACTIVE_ATTENUATE_Q15=2048
```

即默认压到约 6.25%。本轮：

```text
external_ref_inactive=463
ref_inactive_attenuated=463
```

这意味着约三分之一 AEC chunk 在 ref 不活跃时走了强衰减路径。人声起音、小声段、或者被设备声覆盖导致 hint 不稳定的段，会直接被这条路径压低。

虽然 `append_ref_inactive_chunk()` 对 `nearend_preserve_hint` 和 `level_nearend` 做了保护，但当前人声 hint 很容易被 echo veto 清掉，且 level onset 早期不一定达到阈值。因此主观听感中“大部分人声被压低”有明确代码依据。

#### 18.8.4 echo veto 为什么会误伤人声保护

播放期 echo veto 在 `main/nuwax_ai_partner_main.c:3605`：

```c
const bool playback_ref_echo_veto =
    playback_active &&
    playback_ref_active &&
    playback_mic_ref_corr_q15 >= NUWAX_PLAYBACK_REF_ECHO_VETO_CORR_Q15 &&
    dual_mic.diff_energy_ratio_q15 < NUWAX_PLAYBACK_REF_ECHO_VETO_DIFF_ENERGY_Q15;
```

当前阈值：

```text
NUWAX_PLAYBACK_REF_ECHO_VETO_CORR_Q15=9830
NUWAX_PLAYBACK_REF_ECHO_VETO_DIFF_ENERGY_Q15=5243
```

`9830/32768` 约等于 0.30 相关性。播放声较大时，mic 中的混合信号 `human + echo + noise` 很容易与 ref 达到这个相关度。echo veto 一旦成立，会在 `main/nuwax_ai_partner_main.c:3624` 附近清掉：

```text
dual_mic_aec_hint
dual_mic_cleaner_hint
playback_raw_human_hint
spatial_human_first
```

随后在 `main/nuwax_ai_partner_main.c:3691` 附近清空多个 hangover：

```text
dual_mic_aec_hint_hangover_remaining = 0
dual_mic_cleaner_hint_hangover_remaining = 0
playback_raw_human_hint_hangover_remaining = 0
playback_weak_continuity_hint_hangover_remaining = 0
dual_mic_human_first_hint_hangover_remaining = 0
```

这就是当前逻辑与目标冲突的根本点：人声起音阶段最需要保护，但也是最容易被设备声相关性抢先判成 echo 的阶段。单帧 echo veto 不应拥有清空人声状态机的最高优先级。

#### 18.8.5 两个 mic 的利用现状

本轮日志：

```text
mic2_speech_like=733
dual_mic_voice_like=4
```

说明第二麦有被采集，也有相当多帧达到 speech-like 能量；但当前双麦强人声判据几乎不成立。

对应 `main/nuwax_ai_partner_main.c:2825` 的 `compute_dual_mic_features()`：

```c
features.voice_like = enough_mic_energy && enough_difference &&
                      (imbalanced_near_field || strong_difference);
```

当前强判据同时要求：

- mic1/mic2 能量足够。
- 双麦差分 `diff_avg_abs/diff_peak` 足够。
- level imbalance 或 diff energy 足够。

这对近距离强人声可能有用，但对实际验收场景不稳定。真人在 0.5-1m，双麦间距很小，两个 mic 收到的人声差异可能并不大。因此当前并不是“两个 mic 没用”，而是“采集到了两个 mic，但用法过硬，未形成稳定人声保护”。

下一步双麦应改成分级证据：

```text
mic2_speech_like + mic1 能量 + 弱差分 + 连续性 = possible_human
强差分/强失衡 = strong_spatial_human
```

不能只依赖 `dual_mic_voice_like` 这种强判据。

#### 18.8.6 设备声为什么仍大且部分尖锐

设备声仍大的原因不是单一的。

第一，主 AEC ref 不够可靠：

```text
hw_ref_frames=0
fixed software ref delay=360
adaptive_scans=0
```

固定 360 samples 不一定匹配实际声学路径。ref 对不齐时，AEC 只能去掉部分设备声。

第二，restore/保护路径会把残留重新加回来：

```text
nearend_blend=214
dual_restore=122
floor_restore=57
playback_protected_gain=310
playback_continuity_gain=296
```

这些路径是为了保人声，但输入不是纯人声，而是 `human + residual echo + room reflection`。当人声 hint 不稳或误触发时，设备残留也会一起被混回或放大。

第三，softref linear cancel 是二次固定 ref 抵消，可能产生金属/电音边缘：

```text
softref_linear=87
```

`audio_cleaner.c:771` 附近会在 corr 达标时执行：

```c
apply_softref_linear_cancel(cleaner, samples, ref_samples, sample_count, linear_gain_q15);
```

如果 ref 延迟不准，线性相减会形成梳状残留或高频边缘，听感上可能表现为尖锐、电音、字音刺耳。

第四，没有播放期最终总 limiter。当前 `audio_cleaner.c:592` 的 limiter 只在 `speech_protected` 时触发：

```c
if (!playback_active || !speech_protected || !samples || !level || sample_count == 0) {
    return false;
}
```

本轮：

```text
playback_protected_limited=0
WAV peak=12958
```

说明尖峰没有被最终统一限制。设备残留在未被 `speech_protected` 覆盖的帧里仍可能超过 10000，造成尖锐听感。

#### 18.8.7 当前系统是否合理

当前系统的采集/播放/上传框架是可用的：

```text
播放期可采集。
验收 WAV 是设备端处理后音频。
上传保存没有丢帧。
两个 mic 都被采集。
software ref ring 可读。
```

但当前播放期音频处理策略不合理，原因是：

```text
人声保护依赖不稳定 hint。
echo veto 是单帧硬决策，并且能清空人声状态。
ref inactive 被当成应衰减场景，导致人声被压低。
双麦强判据不适配当前物理场景。
固定 delay software ref 不能稳定消设备声。
restore/gain 会把设备残留一起放大。
缺少播放期最终 limiter 和分级 residual suppression。
```

因此下一步不是继续小幅调参，而是要改播放期决策结构。

#### 18.8.8 下一步必须修复的内容

优先级 P0：ref inactive 不能强压人声。


#### 18.8.9 下一轮修复后的预期指标

人声保真指标：

```text
主观：人声不能再“大部分被压低”。
主观：人声起音不能丢，整体音量应更连续。
ref_inactive_attenuated 不应继续代表强 2048 q15 压制。
playback_echo_veto 不应再清空 human hint/hangover。
dual_mic_voice_like 可以仍低，但 possible_human / human_state 应能稳定覆盖真人说话段。
```

设备声压制指标：

```text
设备声可以暂时仍有残留，但不应尖锐。
peak 应 <=10000 或接近 10000。
near_count >=11000 应降到 0 或极低。
softref_linear 不应在 human_state 强时大量触发。
adaptive_scans 应 >0，或者 capture 层应输出 equivalent adaptive delay 统计。
```

日志期望：

```text
hw_ref_frames 仍可能为 0，这是硬件现实。
soft_ref_active 仍会随 TTS 间隙变化。
adaptive_scans / adaptive_probe_attempts 必须能解释 ref delay 是否在工作。
ref_inactive_preserved 或 ref_inactive_human_preserved 应出现。
playback_gate_suppressed 可以高，但验收 WAV 人声不应因此被压低，因为验收保存的是处理后全帧音频。
```

阶段性判断：

```text
当前采集和保存链路可靠。
当前 AEC/cleaner 决策结构不满足“人声优先”的目标。
下一步需要中等规模重构播放期决策：先建立 human_state，再决定 AEC restore、ref inactive 策略、echo suppression 和最终 limiter。
不要再通过单纯加大 echo attenuation 解决设备声，否则会回到人声起音被压没的问题。
```
