# 摇晃唤醒采样容错修复

版本标记：`20260923-shake-gap-v1`。本次修改设备端检测逻辑，不改变云端协议、动作阈值或交互所有权。

## 原因与证据边界

日志证明 QMI 初始化完成，但没有 qualified shake，也没有门控拒绝记录，不能据此断言传感器硬件失效或实际发生了多少次 I²C 争用。

代码确认两处缺陷：QMI 为保护触摸总线，抢锁失败会直接跳过读样本；检测层却将任何读失败视为整段摇晃作废。采样任务迟到一个周期（50ms）也清空累计。原来的 300ms 容错只处理成功采样后的静止间隔，不处理这些中断。

## 修复

- 每次读尝试均按单调时钟更新判定；读失败不计入摇晃时长，短暂缺口保留已获取的证据。
- 最近一次有效运动证据距现在超过 300ms，丢弃累计，防止把不相关动作拼起来。长时间无采样后恢复也先检查过期。
- 每次有效运动样本最多贡献 50ms；快速连续调用只贡献实际经过的时间。任务晚调度不能凭空累计缺失时长。
- 读失败或调度严重迟到后，首个成功样本仅重新建立加速度差分基准，不算有效运动。
- 持续有效运动累计仍需 1500ms，加速度差值总和阈值仍为 700mg，角速度绝对值总和阈值仍为 150°/s，摇晃冷却仍为 4s。
- 保留 I²C 零等待抢锁、10ms 传输超时、任务优先级及现有通知/OTA/配网/独占录音保护。未增加忙等、重试循环或缓冲分配。
- 每 10 秒输出一次 `shake health`，包括尝试次数、读失败、调度迟到、当前/最大累计、超时重置次数、运动峰值、合格/抑制次数、最后读错误和任务栈余量。窗口计数每次输出后清零，累计状态不清零。诊断不写 NVS。
- 为新增诊断及 I²C 调用链保留余量，现有摇晃任务的 PSRAM 栈从 2048B 增至 3072B，仅增加 1KiB PSRAM，不新增任务或内部堆分配。

## 自动验证

`tools/test-shake-gap.py` 从生产 C 文件提取判定函数与任务采样循环，用 100Hz RTOS tick 模拟注入故障。

| 10 秒模拟场景 | 修复后结果 |
|---|---|
| 持续超阈值运动、采样正常 | 3 次触发，首次 1550ms |
| 每秒一次读失败 | 3 次触发，首次 1650ms |
| 每秒额外 50ms 调度延迟 | 3 次触发，首次 1650ms |
| 持续读失败 | 0 次 |
| 每 20 次采样中断 1 秒 | 0 次 |
| 静止、周期性短促动作 | 各 0 次 |
| 共享交互门控拒绝 | 0 次回调，有资格判定 |
| 前 5 秒读失败随后恢复 | 自动恢复触发，首次 6550ms |

同时验证阈值边界、毫秒计数回绕、同时间重复调用、缺失时间不补算、4 秒冷却。恢复“读失败清零”“迟到清零”、关闭过期和按丢失时间补算的四种错误变体均被测试拒绝。

产品回归入口已接入测试；正式构建入口新增 `verify-shake-gap-build.py`，验证实际 BIN 中的修订/诊断标记、源文件和目标文件新鲜度、BIN/ELF 一致性及任务静态栈帧。静态栈帧检查不代表实机调用链的最大栈占用，仍需看运行日志的余量。

## 实机验收

1. 启动日志确认修订标记；联网进入休眠后持续摇晃约 2 秒，检查 qualified shake 与后续 shake agent 请求。
2. 间隔至少 4 秒重复，多次测试，并在菜单操作后重试。
3. 静置、拿起放下、短促晃动不应误触发；通知、OTA 和独占录音仍遵守原来的准入保护。
4. 如未触发，保留至少两条 `shake health` 及摇晃时间：先看读失败/调度迟到，再看运动峰值和 peak_ms，最后检查 qualified/suppressed 与主循环的拒绝理由。

未刷入实机，不能把主机故障注入结果等同于实机问题已全部消除，也不据此降低传感器运动阈值。
