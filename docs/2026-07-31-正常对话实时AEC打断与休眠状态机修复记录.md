# 正常对话实时 AEC、打断与休眠状态机修复记录

日期：2026-07-31

## 1. 本轮目标

产品路径必须同时满足：

1. 设备播报期间持续采集，并对采集帧实时消除设备播报回声。
2. 播报音量高低变化时，设备自身声音不能触发打断。
3. 用户开口后，只有在本地证据和音频健康状态可信时才停止当前播报。
4. 打断上传保留用户第一个音节，并且不能把未消除的播报声重新混回上行。
5. 唤醒后的会话仅在稳定等待用户说话时累计 120 秒。ASR、云端处理、TTS 和播放时间不计入 120 秒；每轮自然播放完成后重新获得完整 120 秒。

## 3. 修复后的会话状态机

`awake_session_state` 现在保存 `active`、`waiting`、`remaining_ms` 和递增 `generation`，其产品语义如下：

```text
唤醒
  -> begin(active=true, waiting=false, remaining=120000)
  -> 问候/ASR/云处理/TTS/播放：计时暂停
  -> 稳定监听建立：waiting=true，开始消耗 remaining
  -> 本地确认用户语音：立即暂停计时
  -> ASR/云处理/TTS/播放：保持暂停
  -> 自然播放完成：remaining 重置为 120000，随后重新监听
  -> 只有 waiting=true 且 remaining=0：进入 sleeping
```

每个 ASR 事件同时绑定 awake `generation` 和 `audio_session_id`。旧 generation 或旧 audio session 的 partial/final/result 会被忽略，不能清除当前会话或改变当前状态。

正常监听内部仍可按 60 秒采集窗口分段，但分段不是会话休眠：第一个静默窗口结束后继续使用剩余预算，累计稳定静默达到约 120 秒才休眠。

`ESP_ERR_NOT_FINISHED` 表示实时上行瞬时背压；`ESP_ERR_NO_MEM`、`ESP_ERR_TIMEOUT` 和 `ESP_ERR_INVALID_SIZE` 在 awake session 仍有效时也先保留会话并重启监听。只有无法恢复且不属于有效 awake session 的错误才进入 `audio_source_error` 休眠。

## 4. 产品实时音频路径

```text
云端 PCM
  -> speaker queue (128 frames)
  -> 实际 I2S 写入边界镜像
  -> software-reference ring
  -> 固定 840-sample 声学延迟

ES7210 MIC1/MIC2 TDM
  -> 20 ms capture frame
  -> VC / LOW_COST / filter=4 AEC
  -> 标量 human rescue + 双麦差分 restore
  -> residual guard / conservative cleaner
  -> human evidence + barge controller
  -> onset preroll
  -> realtime uplink queue (96 frames)
  -> WebSocket
```

软件参考记录在实际扬声器 I2S 写入边界，不使用收到云端音频的时间作为参考。这样网络抖动和 speaker queue 深度不会改变参考时间基准。

产品构建关闭以下实验路径：

- shadow delay correlation scan；
- adaptive reference delay scan；
- dynamic FIR delay；
- 256-tap float human-rescue FIR。

这些路径在旧日志中和 45/60 ms 的 DSP p95/p99、capture stale/gap 同时出现。产品路径使用已校准的固定参考延迟，保留 ESP-SR LOW_COST AEC、轻量标量救援、双麦证据、残余保护和预卷。

`NEAREND_RAW_MIX_Q15` 与 `STRONG_NEAREND_RAW_MIX_Q15` 均为 0。确认人声后不直接把原始麦克风混回 AEC 输出，避免同时恢复设备播报声。

## 5. 安全打断顺序

播放期间只有 AEC、参考和 capture 时序健康时，控制器才允许从候选进入确认：

```text
AEC/ref healthy
  -> candidate started（记录 onset sequence）
  -> 多证据确认，必要时短时 probe duck
  -> generation-bound local fade/stop request
  -> 物理停止结果确认
  -> 验证并整理 onset preroll
  -> 开始新的 barge audio session 和上行
  -> 发送与当前 turn/playback 绑定的取消协议
```

AEC 未启用、参考丢失、帧过期、序号缺口或播放 generation 不匹配时必须 fail-closed，不得用不可信音频触发停止。取消请求绑定播放 generation，旧候选不能停止新一轮播放。

预卷以 candidate onset sequence 为中心保存确认前音频。可信来源优先为 AEC 输出、标量 echo-subtracted rescue 或受保护的双麦 restore；存在 gap 或来源不可信时拒绝对应窗口，而不是上传原始回声音频。主机测试已覆盖 onset 前 1.5 秒、序号回绕、gap 裁剪、onset 保留和不可信 overlap 拒绝。

## 6. AEC 内存与实时预算修复

AEC pool 已移动到 speaker manager 初始化之后、display/touch/LVGL/Wi-Fi/TLS 之前创建。ESP-SR 的大块内部 RAM 在堆尚未碎片化时一次性预留，并在每轮对话间复用。

OTA 首次启动不再跳过 AEC 初始化。启用 live AEC 的产品映像必须取得 `OTA_BOOT_HEALTH_LIVE_AEC` 才能通过 OTA boot health 并提交；否则保留回滚能力。

以下常驻任务栈迁至 PSRAM，共释放 24064 B internal RAM：

- battery service：4096 B；
- LED worker：2048 B；
- board GPIO inputs：2560 B；
- face cache preload：4096 B；
- USB provisioning control：3072 B；
- LVGL worker：8192 B。

flash/OTA、SW3 power、touch I2C、Wi-Fi fallback/NVS 等需要严格 cache/flash 安全边界的任务仍保留 internal stack。LVGL draw buffer仍优先 internal，避免 UI 渲染性能倒退。

## 7. 上行背压修复

正常对话和会议/监控使用不同可靠性策略：

- 正常对话实时队列为 96 帧，约 1.92 秒，位于 PSRAM。非终止帧零等待入队；饱和返回可恢复的 `ESP_ERR_NOT_FINISHED`，不能阻塞 20 ms capture/AEC 路径。
- 当前尾帧在瞬时饱和时保留；`finish()` 等待 FIFO 排空后补 END，避免尾部协议不完整。
- 会议和监控继续使用可靠队列和有界等待，不能因为正常对话低延迟策略而丢失完整录音。

## 9. 实机放行门槛

当前结论只能是“代码和构建已修复，等待新固件实机验收”，不能提前宣称四项声学能力全部生效。

启动和资源：

- `live AEC ... pooled=1 enabled=1 initialized=1`；
- 不得出现 AEC `ESP_ERR_NO_MEM`；
- AEC reserve 后 internal free >= 24576 B、largest >= 12288 B；
- DMA free >= 16384 B、largest >= 8192 B。

实时性和完整性：

- DSP p95 < 20 ms，目标 <= 15 ms；p99 <= 20 ms；
- `stale_capture=0`、`sequence_gaps=0`、capture drop=0；
- uplink `queue_full=0`、drop=0；
- 播放期 AEC active、reference locked、fallback=0。

声学和打断：

- 低/中/高音量 playback-only 各 20 轮，误打断 0/20；
- 低/中/高音量真人打断各 20 轮，成功 20/20；
- 用户起音到可闻停止 p95 <= 220 ms（0 至 75% 音量），高音量 <= 300 ms；
- 本地确认到首个上行帧 p95 <= 60 ms；
- 首音节损失 p95 <= 40 ms，前 100 ms 人声能量保留 >= 90%；
- 有效播放窗口 ERLE 目标 >= 12 dB，最低工程门槛 >= 6 dB，残余参考相关性 <= 0.10；
- 播放结束后等待预算约 120000 ms，稳定无声约 120 秒后才进入 sleep；
- 30 分钟多轮 soak：无 OOM、WDT、重连风暴或 heap 持续下降。

OTA 期间还必须并发检查 PSRAM task stack：battery/LED/GPIO/USB/UI 不得异常，UI 不得明显卡顿，所有 task high-water mark 必须保留足够余量。
