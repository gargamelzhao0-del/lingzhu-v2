## 1. 会议模式冻结时点

### 1.1 已完成的设备端代码

会议模式已独立放置在：

- `main/audio_modes/meeting/meeting_mode.c/.h`
- `main/audio_modes/meeting/meeting_processor.c/.h`
- `main/audio_modes/meeting/meeting_protocol.c/.h`
- `main/audio_modes/meeting/meeting_processor_host_check.c`

`main/CMakeLists.txt` 已将三个运行时源文件加入组件编译。

当前实现已经具备：

1. `disabled -> starting -> active -> stopping -> disabled/error` 状态机。
2. UI 开关请求和云端主动 `set_audio_mode` 请求。
3. 独立的 `NUWAX_MIC_OWNER_MEETING_CAPTURE` 麦克风所有权。
4. 进入会议模式前对普通播报执行约 200 ms 异步淡出，并清理普通对话的后续播放。
5. 会议期间停止普通唤醒词、ASR、TTS 事件对会议音频的干扰。
6. 连续读取麦克风并上传每个有效 PCM 帧；VAD 只作为元数据和静音计时依据，不删帧。
7. 弱人声的有界增益（默认约 +0.54 dB，最大约 +1.58 dB）。
8. 连续环境安静达到 30 分钟时发起本地停止。
9. WebSocket 断开时停止会议录音，不在离线状态继续采集。

当前 `sdkconfig` 的有效值为：

| 项目 | 当前值 |
| --- | ---: |
| 采样率 | 16 kHz |
| 设备上传通道 | 单声道 |

会议模式当前没有接入普通对话的完整 Live AEC 和硬件参考处理链，而是直接调用普通 `read_pcm16` 接口，再执行 `meeting_processor` 的保守处理。因此“持续上传全部音频”已经成立，但“会议模式的高质量降噪/AEC”还没有实现为独立能力。

### 1.3 状态机实际行为

#### 开启

1. UI 或云端命令进入 `starting`。
2. 如果扬声器仍有待播数据，调用异步淡出，等待最多 500 ms 让播放队列稳定。
3. 发送 `listen start`，其中 `mode=meeting` 和 `audio_session_id` 已带上。
4. 初始化会议专属麦克风和上行队列。
5. 进入 `active`，开始按 16 ms 帧读取、处理和上传。

当前实现的一个重要事实：发送 `listen start` 后没有等待并验证 `listen_ack`，而是继续初始化本地采集。只有当云端的 `audio_mode_request_ack` 被当作“接收器已准备好”时，这个行为才与简化协议一致。正式协议若要求 `listen_ack`，后续必须补齐。

#### 采集和上传

处理器做三件事：慢速 DC 去除、能量/峰值分类、弱人声的有界增益。默认阈值为 `avg_abs >= 280`、`peak >= 900`，静音计时使用 `quiet_margin_abs=110` 和 `quiet_peak=520`。处理器不会把帧清零，也不会因低能量丢帧。

采集使用一个待发送帧作为结束标志缓冲，因此正常结束时最后一帧可带 END；上行队列失败会记录丢帧并停止会话。

#### 停止

停止时的顺序是：结束当前帧、排空上行、发送 `listen stop`、释放麦克风所有权、回到 `disabled` 或 `error`。WebSocket 断开时不等待发送，直接释放本地资源。

## 3. 新板逐页硬件理解

### 3.1 麦克风板

FPC 连接器引出：

- `ADC_MIC1_P/N`
- `ADC_MIC2_P/N`
- `ADC_MICBIAS12`
- `TOUCH`
- `LED_G`
- `MCU_3V3`、数字地和模拟地

U1/U2 为两个麦克风偏置/前端稳压或耦合单元，图中每路使用 100 nF、10 uF 去耦，并通过 1 uF 耦合电容把差分信号送到主板。麦克风板本身没有 AEC 运算器，也没有第三路参考输入；第三路 `MIC3` 参考在主板上产生。

### 3.2 主板一

主板一主要是非音频外围：

- 电池充电器 `LGS4056HA`
- `MCU_3V3` DCDC
- `CODEC_3V3` DCDC
- 4G 升压/供电 `TPS61023...`
- Type-C 输入和 USB ESD/限流
- 4G、底座 UART、SD 卡接口
- 机械开关、LED 和固定螺母

关键结论是：编解码器使用独立命名的 `CODEC_3V3` 电源，而不是原理图中某个 ESP32 GPIO 控制的模拟电源。电源图没有出现 `CODEC_PWR` 这一网络。

### 3.3 主板二第 1 页：ESP32 和引脚

器件为 `ESP32-S3-WROOM-1-N32R8`。原理图给出的音频引脚是：

| 信号 | 新板 GPIO | 去向 |
| --- | ---: | --- |
| `I2S_MCLK` | 42 | ES8311/ES7210 MCLK |
| `I2S_DI` | 38 | ES7210 `SDOUT1/TDMOUT` 到 ESP32 |
| `I2S_WS` | 39 | 两个 codec 共用 LRCK/WS |
| `I2S_BCK` | 40 | 两个 codec 共用 SCLK/BCLK |
| `I2S_DO` | 41 | ESP32 到 ES8311 SDIN |
| `PA_CTRL` | 4 | NS4150B `CTRL` |

I2C 主控侧为 GPIO1/2：

- ES8311 地址 `0x18`
- ES7210 地址 `0x40`
- 触摸地址 `0x15`
- 电量计 `0x55`

新板的 4G 控制明确使用 GPIO15 (`4G_EN`)，这与当前软件把 GPIO15 当作 PA 控制的做法直接冲突。

### 3.4 主板二第 2 页：LCD、连接器和 PA 相关接口

该页显示 LCD、4G、底座和 B2B 连接器。LCD 相关 GPIO 与当前 7.0 配置也不同，例如图中 `LCD_SCL=GPIO14`、`LCD_BLK=GPIO3`、`LCD_RST=GPIO21`。当前工程配置是 `SCK=18`、`BL=44`、`RST=47`，因此 UI 引脚不能直接复用。

### 3.5 主板二第 3 页：codec、AEC 和功放

#### ES8311

ES8311 地址为 `0x18`，工作在 DAC 模式：

1. ESP32 的 `I2S_DO` 进入 ES8311。
2. ES8311 将数字音频变成差分模拟 `OUTP/OUTN`。
3. `OUTP/OUTN` 一路经 C44/C45（100 nF）和 R19/R20（100 kOhm）进入 NS4150B。
4. 同一对 `OUTP/OUTN` 在进入功放之前分出一条支路进入标注为 `AEC` 的无源网络。

#### ES7210

ES7210 地址为 `0x40`，使用 4-slot TDM：

- `MIC1P/N` 接麦克风板的 `ADC_MIC1_P/N`。
- `MIC2P/N` 接麦克风板的 `ADC_MIC2_P/N`。
- `MIC3P/N` 接 AEC 无源网络的 `ADC_MIC3_P/N`。
- `MIC4P/N` 没有接外部麦克风，周围只有参考/去耦网络，作为保持四槽 TDM 的 NC 通道。
- `SDOUT1/TDMOUT` 接 `I2S_DI`。
- `SDOUT2/TDMIN`、INT、DMIC_CLK 在图中未用于本音频链路。

## 4. 新板 AEC 音频链路推导

### 4.1 实际信号流

```text
ESP32 I2S_DO
    -> ES8311 DAC
    -> OUTP/OUTN 差分模拟
       -> C44/C45 + R19/R20 -> NS4150B -> VOP/VON -> 扬声器
       -> R7/R11、C7/C14、R8/R12、C10、R9/R13、R10、C11、C8/C15
          -> ADC_MIC3_P/N -> ES7210 MIC3 -> TDM slot2 -> ESP32 I2S_DI
麦克风 MIC1/MIC2 -> ES7210 -> TDM slot0/slot1 -> ESP32 I2S_DI
```

这是一条“电气播放参考”回采路径：参考取自 ES8311 的 DAC 输出，而不是扬声器端子 VOP/VON，也不是麦克风里混合后的声学回声。

### 4.2 无源 AEC 网络的元件作用

AEC 支路左右对称，主要元件为：

| 级 | 元件 | 作用判断 |
| --- | --- | --- |
| 输入串联 | R7/R11 = 2.2 kOhm | 限流和隔离 DAC 负载 |
| 首级跨线 | C9 = 10 nF | 高频差分/共模抑制 |
| AC 耦合 | C7/C14 = 470 nF | 去直流、形成低频高通 |
| 中间串联 | R8/R12 = 10 kOhm | 降幅和隔离 |
| 中间跨线 | C10 = 2.2 nF | 限制较高频率 |
| 末级串联 | R9/R13 = 20 kOhm | 与 R10 形成主要差分衰减 |
| 末级负载 | R10 = 4.3 kOhm | 差分负载/衰减，降低 MIC3 电平 |
| 末级跨线 | C11 = 100 pF | RF 抑制 |
| ADC 耦合 | C8/C15 = 220 nF | 进入 ES7210 前再次隔直 |

这个网络的设计意图明显是“把 DAC 播放信号变成幅度受控、带宽受限、差分对称的 MIC3 参考”。它不是 AEC 算法本身，也不能单独消除回声。

### 4.3 这块板是否真的带硬件 AEC

仅根据这三份原理图，结论应分成两层：

已确认：

- 有专用 `MIC3` 电气参考通道。
- ES7210 可以把该参考与 MIC1/MIC2 一起送入 TDM。
- 参考在功放前取样，避免把 NS4150B 的大电流开关节点直接接入 ADC。

不能从图中确认：

- 没有看到 JL7018、专用 DSP 或带 AEC 固件的独立处理器。
- 没有看到任何硬件自适应滤波、双讲检测或残余回声抑制模块。
- `AEC` 方框只是无源 RC 网络的名称，不能等价于“硬件已经完成 AEC”。

因此更准确的表述是：**新板提供了适合做 AEC 的硬件参考回路，但 AEC 算法仍然需要 ES7210 后面的 ESP32 软件或未提供的厂商固件完成。** 厂商演示程序若表现出完整 AEC，仍需通过固件行为和原始通道回采验证，不能只凭原理图下结论。

### 4.4 该参考对回声消除的优势和边界

优势：

1. 参考与麦克风由同一 ES7210 时钟域采样，天然避免独立 ADC 时钟漂移。
2. 参考从 DAC 输出直接取得，理论延迟短且波形干净，优于把网络下发 PCM 作为唯一参考。
3. 参考与 MIC1/MIC2 同一帧进入 TDM，帧级对齐更容易建立。
4. 无源网络左右对称，适合差分输入，能降低共模噪声。

边界：

1. 参考点在功放前，未包含 NS4150B 的增益、频响、削波、供电压缩和扬声器/腔体响应。
2. 房间反射和扬声器到麦克风的声学路径仍需自适应滤波器学习，电气参考不能直接代表麦克风中的全部回声。
3. R10=4.3 kOhm 等网络会把参考显著衰减；ES7210 增益、ADC 噪声和播放音量必须配套校准。
4. 若 TDM 槽序、I2S 边沿或参考延迟配置错误，slot2 即使有能量也可能不是可用参考。
5. 新板未提供实测的参考幅度、噪声、相位和延迟，不能直接沿用当前 7.0 的 840-sample 软件延迟。

## 5. 新板与当前 7.0 软件的兼容性审计

### 5.1 音频关键管脚差异

| 信号 | 新板原理图 | 当前 `esp_vocat_v1_0_pins.h` | 影响 |
| --- | ---: | ---: | --- |
| I2S MCLK | GPIO42 | GPIO42 | 一致 |
| I2S BCLK | GPIO40 | GPIO40 | 一致 |
| I2S WS/LRCK | GPIO39 | GPIO39 | 一致 |
| I2S DO 到 ES8311 | GPIO41 | GPIO41 | 一致 |
| I2S DI 从 ES7210 | **GPIO38** | **GPIO3** | 致命不一致，RX 读不到正确 TDM |
| PA_CTRL | **GPIO4** | **GPIO15** | 致命不一致，无法正确控制功放 |
| I2C SCL/SDA | GPIO1/2 | GPIO1/2 | 名义上一致，仍需验证电平转换链路 |
| codec 电源控制 | `CODEC_3V3` 电源网 | 软件驱动 GPIO48 | 原理图没有 GPIO48 电源开关，软件动作没有依据 |

### 5.2 两个直接的硬件风险

1. 当前软件把 GPIO15 交给 ES8311/PA 控制，而新板 GPIO15 是 `4G_EN`。这可能在播报启停时误开关 4G 电源，带来电源扰动和射频噪声，且 NS4150B 仍可能保持关闭。
2. 当前软件把 GPIO3 当作 ES7210 DIN，而新板 GPIO3 是 `LCD_BLK`。这会导致麦克风数据线悬空或错接，并可能干扰屏幕背光。

此外，当前非板级回退配置的 `CONFIG_NUWAX_MIC_I2S_DIN_GPIO=6` 在新板上又对应 `4G_RX`，同样不能作为新板临时修复。当前 LCD `SCK=18、BL=44、RST=47` 也与新板 `SCK=14、BL=3、RST=21` 不一致，因此即使音频修正，UI 也不能直接认为兼容。

### 5.3 当前代码已经具备的可复用部分

当前 `vocat_audio_board.c` 和 `mic_input.c` 已经实现了与新板拓扑相符的抽象：

- 单 I2S 全双工。
- ES7210 四槽 TDM 读取。
- slot0/slot1/slot2 分离读取。
- `MIC3` 作为硬件参考候选的健康检查。
- 软件参考和硬件参考 A/B 路径。

但是当前构建默认关闭 `CONFIG_NUWAX_VOCAT_SLOT2_AEC_REF_ENABLE`，且会议模式只读取 slot0。这些代码只能作为迁移基础，不能当作新板已经验证。

## 6. 新板迁移前必须确认的事实

在修改代码或烧录前，需要通过厂商、PCB 实物或示波器/逻辑分析仪确认：

1. ESP32 实际封装和 PCB 是否确实采用 GPIO38 作为 `I2S_DI`、GPIO4 作为 `PA_CTRL`。
2. `PA_CTRL` 的有效电平、R18 10 kOhm 下拉和 C49 1 uF 延时是否与 ES8311 驱动的 enable 逻辑一致。
3. `CODEC_3V3` 是否上电即有效，是否存在原理图未标出的负载开关；在没有确认前不能驱动 GPIO48。
4. ES7210 四槽的真实顺序是否为 slot0=MIC1、slot1=MIC2、slot2=MIC3、slot3=MIC4。必须用逐槽原始 TDM dump 验证，不能只看芯片符号位置。
5. AEC RC 网络的实际贴装值、误差、PCB 走线和 AGND 汇流点；原理图不显示实际贴装和布局。
6. 播放静音、1 kHz 单音和真实 TTS 时，MIC3 的 RMS、峰值、削波率、相对 MIC1 的相关性以及样本延迟。
7. ES8311/ES7210 的 I2C 电平转换器和上拉电压；GPIO1/2 总线 400 kHz 是否稳定。
8. NS4150B 的实际供电 VOUT、扬声器阻抗和最大音量，以确定参考衰减和声学回声范围。
9. 厂商所谓“硬件 AEC 已解决”究竟指 RC 参考回路、ESP32 固件 AEC，还是另有未提供的 DSP/二进制；需要固件版本和可观测接口佐证。

## 7. 推荐的新板验证顺序

这一部分是冻结后的下一阶段计划，不代表已经执行：

1. 先建立独立的新板 profile，禁止直接改写当前 `ESP-VOCAT` profile。
2. 只修正并验证引脚和电源初始化：`DIN=38`、`PA_CTRL=4`，暂不打开新 AEC 参数。
3. 做 I2C 扫描，确认 ES8311 `0x18`、ES7210 `0x40` 和 codec 电源状态。
4. 用逻辑分析仪确认 MCLK/BCLK/WS 频率和相位；16 kHz、256 fs 时 MCLK 应约为 4.096 MHz。
5. 读取原始四槽 TDM，确认 MIC1/MIC2/MIC3/MIC4 槽序和符号位宽。
6. 播放固定 1 kHz 音，测量 slot2 的幅度、削波、噪声和相关延迟；再做静音和真人双讲对照。
7. 只有 slot2 健康通过后，才在软件 AEC 中启用硬件参考，并与软件参考做 A/B，不要同时改变多个参数。
8. 最后再迁移 UI、会议模式和显示引脚，分别做音频、云端和 UI 回归。

## 8. 最终结论

会议模式在冻结时已经完成设备端主体框架并能编译，但还没有新固件真机闭环，仍属于实验版。当前代码和新板原理图不能直接视为同一硬件目标。

新板的最大价值是提供了一条结构清晰的 `ES8311 OUTP/OUTN -> RC AEC -> ES7210 MIC3 -> TDM slot2` 电气参考回路，这比只使用软件播放 PCM 作为参考更有希望改善实时 AEC 的对齐和稳定性。但原理图没有显示独立 AEC/DSP，不能据此断言硬件已经完成回声消除。

在新板上直接烧录当前 7.0 固件前，必须先解决并验证 `GPIO38` 音频输入、`GPIO4` 功放控制以及整套显示/外围引脚映射。会议模式冻结不影响后续迁移：会议模式代码可以保留，待新板 profile、TDM 原始数据和参考健康测试通过后再接入。
