# 500 KiB/s 补传目标：固定预读优先级与流水线修订

## 结论与实测边界

本轮修订针对已观测到的读取端调度等待，保留录音保护、内存余量、CRC 和持久化 ACK。代码与主机回归、整机构建完成后提供独立固件快照；500 KiB/s 仍须新固件实机验收，不能用主机测试或模型推算宣称达标。之前的延迟 Cache/MMU 重启也尚未证明根治。

## 历轮证据

网关速度均按同一会话的归档字节数 / 首次 begin 到最后持久化 commit 的时间计算。不同轮次的录音、推理和网络负载并不完全相同，不能作为严格 A/B。

| 会话尾号 | 网关平均 KiB/s | 标准段 SD 读取 ms | 标准段编码 ms | 主要变化 |
| --- | ---: | ---: | ---: | --- |
| 309152 | 280.50 | 1194 | 523 | 单次 read 5→6→5，分段编码 |
| 309565 | 309.85 | 1782 | 428 | 撤回逐次优先级切换，读发均为 5 |
| 310311 | 293.20 | 1939 | 222 | 显式 builtin 掩码生效，但读发等待增加 |

标准段为 1,048,412 字节，排除包含串行诊断探针的分段。上表是墙钟耗时，包含调度抢占，不等同于纯 CPU 时间或 SD 总线时间。

310311 的 11 个归档共 9,782,284 字节，14,686 帧完整，32.582 秒上传结束。读取加校验平均 2205 ms/标准段，仅约 464 KiB/s，尚未包含额外积压等待。读取侧保护等待累计 5.47 秒，发送侧 4.464 秒；二者及流水线等待有重叠，不能直接相加。网关 76 次窗口落盘累计 181 ms，未见发送短写或重试。SD 实际 40 MHz，读取错误为零。

因此，继续加大 TCP 窗口、缩短 RX 锁或提高 SD 时钟，不是当前证据指向的优先项。掩码已修正，双缓冲也已存在；重复添加同类机制不能解决读取端调度。

## 代码修订

### 1. 预读任务全程固定优先级 6

`offline_io_schedule.h` 单独定义 `OFFLINE_REPLAY_READER_PRIORITY=6`，只用于 core 0 的 `sd_prefetch`。测试网关发送任务、SD writer 仍为 5；正式补传任务维持原配置。

旧版本读发同核、同为 5。当发送器可运行时，SD ISR 唤醒同优先级预读任务，不保证立即抢占发送器。SDK 已经调用条件式 ISR yield，问题不是漏写 yield。改为预读 6 后，SD 完成可唤醒更高优先级任务，连续执行校验、复制和发布，再进入下一次阻塞读取。

这与先前失败尝试有明确区别：不在每次 read 前后执行 `vTaskPrioritySet`。旧 6→5 会请求调度，可能在数据尚未发布时把 CPU 让给等待这份数据的发送器。本轮任务从创建到退出保持同一优先级。

保留每 64 KiB 或累计 20 ms 处理工作的一个 tick 让出；保留 SD、空间信号量和 ACK 等阻塞。预读与显示 flush 同优先级，低于 LVGL 7、唤醒 10、采音 12 及网络任务。优先级调整仍可能影响动画和 PSRAM 竞争，须按实际日志验证，不能仅凭优先级关系证明没有影响。

### 2. 默认关闭串行诊断窗口

新增 `CONFIG_NUWAX_OFFLINE_AUDIO_REPLAY_LANE_PROBE`，默认关闭。此前每次补传第一个符合条件的 128 KiB 窗口会完整读完才发送，并等 ACK 后才读下一窗口，主动破坏双缓冲重叠。

该探针可在专门诊断时重新开启；关闭不影响逐段统计、UART 崩溃转储或生命周期堆检查。正常配置从第一个窗口起即可逐块发布和发送。它只消除一个窗口的额外开销，不把这一小项夸大为主要提速来源。

启动分段时打印实际配置：`reader_priority=6 sender_priority=5 lane_probe=0`（测试网关并行路径）。创建预读任务失败时仍走原串行退路，日志如实反映调用者优先级。

### 3. 将完整性与速度验收绑定

`audit-offline-session.js` 增加可选网关日志和目标参数，先重新校验实际 `.complete` 文件的 CRC、序号及预期帧数，再计算整段墙钟速度。

- 重复 commit 只计一次归档字节数；跨段间隔、重试停顿计入耗时。
- 缺少从 offset=0 开始的完整传输历史时，不拿整段文件大小除以续传尾部的时间。
- 网关 commit 的字节数、帧数、CRC 必须与真实文件一致。
- 音频完整性失败退出码 2；完整但速度不达标或历史不足退出码 3。
- 速度通过不代表唤醒、UI 和长期稳定性通过，这些须结合设备日志验收。

上一轮数据作为负向验收样本，仍应得到 293.199 KiB/s、`throughputTargetMet=false`。

## 保留的可靠性约束

内部 DMA 分配前后继续检查 16 KiB 空闲余量，缓冲仍按可用内存缩小并在每次读后释放。不开长期 DMA 占用，不提高内存不足时的准入风险。

唤醒积压仍在 >=60 ms 时暂停补传，下降至 <=30 ms 后恢复。新录音、取消、连接 epoch 变化仍在读/发边界检查。FILE 由单个读任务拥有，取消后必须 join 才能释放资源；窗口只有持久化 ACK 后才可复用，最终 commit ACK 后才删除归档。

不修改在线协议、离线归档、音频编码、会话 ID、ACK 语义、SD 时钟或 Wi-Fi 缓冲。不会通过压缩后的字节、裸 PCM 等效速度或局部峰值更换 500 KiB/s 的验收口径。

## 验证与新一轮验收

主机回归分别编译探针开/关路径，覆盖首窗口流式发布、读取失败、CRC 损坏、任意偏移续传、重复 ACK、错误 ACK、丢失 ACK、录音抢占、连接变化、分配失败及内存余量。主机线程并不模拟 ESP32 的真实调度时序，不能测出设备提速比例。

最终 ELF 继续验证掩码路径无逐字 ROM 调用、两个 RNNT 修复调用点存在；诊断版保留 UART 转储、独立转储栈及生命周期堆检查。构建产物和报告在各自不可覆盖的快照目录中关联 SHA。

建议使用诊断快照，避免再次丢失重启证据：

```powershell
powershell -ExecutionPolicy Bypass -File tools/flash-sd-replay-test.ps1 -Port COM11 -BuildDir C:\tmp\nuwax-replay-reader500-diagnostic-20260916
powershell -ExecutionPolicy Bypass -File tools/monitor-sd-replay-test.ps1 -Port COM11 -BuildDir C:\tmp\nuwax-replay-reader500-diagnostic-20260916
```

性能快照为 `C:\tmp\nuwax-replay-reader500-speed-20260916`，默认 build 目录也更新为该性能配置。两种配置的内部内存预算不同，应在各自配置内比较；不能把移除转储缓冲释放的内存误记为调度算法收益。

先测约 5 分钟离线会议，恢复后关闭会议，核对 session、完整帧数及以下数据：

1. `reader_priority=6 sender_priority=5 lane_probe=0`；启动 SHA 与快照一致。
2. `sd_read_ms`、`empty_lag_total_us`、`data_wait_ms` 下降；同时检查录音保护等待是否上升，不能只看读取单项。
3. 网关全程平均 >=500 KiB/s，CRC 正确、序号连续、无重复。以 310311 同样的数据量计算，耗时须 <=19.106 秒，当前基线为 32.582 秒。
4. 无新增采音丢块、序号断点、内存错误、持续心跳超时；观察 UI 响应。
5. 补传后继续待机至少 30 分钟，并继续多轮会议/监控切换与长录音测试。一次短测通过不能确认延迟重启或 8 小时运行稳定性。

验收命令（替换新会话、实际帧数、当轮网关日志）：

```powershell
node tools/protocol/audit-offline-session.js runtime-logs/sd-replay-test-20260911/archives SESSION EXPECTED_FRAMES tmp/session-acceptance.json GATEWAY_LOG 500
```

如果读取改善而保护等待上升或 UI 明显恶化，不进一步整体抬高优先级或放宽保护；下一步应根据这版实测分离推理/PSRAM 竞争。尚未实测前不承诺这两项改动必然使端到端达到 500 KiB/s。
