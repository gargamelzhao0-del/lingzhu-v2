## 任务编号：`P6-GRAYCONFIRM-003`

任务名称：实现灰度确认式智能打断最小闭环

优先级：最高

### 背景

`P6-DUALMIC-002` 已证明：当前 CyberVoc V1.2 双麦同帧 `corr/diff_ratio/level_delta` 简单特征无法可靠区分真人近端语音和播放残留。继续要求 `active_dual_mic_voice_ok=1` 会导致正常音量正向打断长期失败；直接绕过双麦让单麦硬 cancel 又会回到播放-only 误打断风险。

因此下一步采用两阶段灰度确认策略：

```text
p6_record_candidate -> gray_candidate -> ASR/云端确认 -> confirmed_cancel
```

本任务目标是在当前测试网关和设备代码中实现一个最小可验证闭环。注意：这是阶段 1，不是最终企业级云端方案。

### 产品目标

用户在设备已唤醒状态下，设备正在播报时，用户 50-100cm 正常音量只说一次：

```text
你好，打断一下，现在换一个话题，今天天气怎么样
```

期望体验：

- 设备不要求用户重复说。
- 设备应尽快降低旧播报音量，目标 0.5 秒级；首版可以接受先记录实际延迟。
- 确认用户确实说了新内容后，旧播报结束，进入用户新语音的 ASR 和回答链路。
- 播放-only 或回声残留不能触发新一轮对话。

### 设计原则

1. 不再把双麦简单特征作为硬 cancel 必要条件。
2. 不允许把 `p6_record_candidate=1` 直接升级为硬 cancel。
3. 必须区分三个状态：
   - `gray_candidate`：本地疑似用户插话，可以开始临时降音/采集。
   - `confirmed_cancel`：ASR/云端确认后，才真正取消上一轮。
   - `rejected_gray`：确认失败或超时，不能进入新一轮。
4. 旧 `p6-gray-cancel` 路径保留，用于对比和回归；新逻辑必须可开关、可回滚。

### 本轮实现范围

请优先实现最小闭环，不要做大范围重构。

建议实现一个独立模式或 endpoint，例如：

```text
/api/device/p6-gray-confirm

```

如复用现有 endpoint，也必须在日志中明确区分 `mode=gray_confirm`，不能和旧 `gray_cancel` 混在一起。

端侧建议：

- `p6_record_candidate=1` 且数据面健康时，产生 `gray_candidate=1`。
- `gray_candidate=1` 时不要立即发送硬 `cancel_turn`。
- 如现有 speaker 只有 `fade_cancel`，先评估能否新增短暂降音/duck 能力；首版可以先记录缺口，但不能把无法恢复的硬停播当作未确认动作。
- 收到确认后才执行完整淡出/停止旧播报，并发送或确认 `cancel_turn`。
- 确认失败或超时后，必须保证不会进入下一轮对话；如果做了本地降音，必须恢复或说明当前无法恢复的风险。

网关/云端测试服务建议：

- 收到 `gray_candidate` 后，对候选音频走 ASR。
- ASR 文本包含用户新内容时确认，例如包含以下任一关键词可先作为开发门槛：
  - `打断`
  - `停`
  - `换`
  - `天气`
  - `问题`
  - `没有理解`
- 确认前不得 abort 旧 LLM/TTS worker。
- 确认后才发送/接受硬 cancel，并进入下一轮用户输入处理。
- 确认超时建议先设为 1200-1500ms，具体值写入汇报。

### 背景
