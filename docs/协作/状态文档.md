## 状态枚举

### Codex / 技术总监状态

| 状态 | 含义 | 允许设置时机 |
| --- | --- | --- |
| 等待工程师 | 当前任务已下发，等待工程师开发、自测、汇报 | Codex 完成任务下发或评审后 |
| 评审中 | 工程师状态已变为“等待 Codex 评审”，Codex 正在查看代码、日志和文档 | Codex 开始评审前，必须先修改为此状态 |
| 下发任务中 | Codex 正在把评审结论、下一步任务写入协作文档 | Codex 评审后需要补充正式任务时 |
| 等待产品负责人真人测试 | 当前需要真人说话、操作设备、确认体验或执行硬件测试 | Codex 判断需要产品负责人参与实测时 |
| 等待产品负责人处理紧急事项 | 出现严重阻塞、重大风险、敏感配置泄露、硬件异常等必须产品负责人介入的问题 | Codex 判断不能继续安全推进时 |

### 工程师状态

| 状态 | 含义 | 允许设置时机 |
| --- | --- | --- |
| 等待执行任务 | 工程师尚未开始最新任务，或等待 Codex 下发新任务 | Codex 初始设置，或工程师确认无可执行任务时 |
| 开发中 | 工程师正在改代码、改配置或实现任务 | 工程师开始执行《任务指示文档》任务前 |
| 自测中 | 代码已写完，正在本地构建、host check、脚本测试或整理验证结果 | 工程师进入验证阶段时 |
| 更新文档中 | 工程师正在补充《工作汇报文档》或《技术讨论文档》 | 工程师完成测试后 |
| 等待 Codex 评审 | 工程师已完成代码、测试、汇报、讨论内容更新，等待 Codex 检查 | 工程师完成所有交付动作后的最后一步 |
| 等待产品负责人真人测试 | 任务需要产品负责人实测，工程师暂停等待 | 工程师确认缺少真人测试条件时 |
| 等待产品负责人处理紧急事项 | 工程师发现严重风险，不能继续推进 | 工程师确认存在重大阻塞或风险时 |

### 产品负责人状态

| 状态 | 含义 | 允许设置时机 |
| --- | --- | --- |
| 无需负责人真人测试 | 当前任务不需要产品负责人介入 | 默认状态；测试和评审都可由工程师/Codex完成 |

## 修改权限

| 修改人 | 可以修改的状态 | 不允许修改的状态 |
| --- | --- | --- |
| Codex | Codex 状态；产品负责人状态 | 工程师状态，除非初始化文档或产品负责人明确要求 |
| 工程师 | 工程师状态；产品负责人状态 | Codex 状态 |
| 产品负责人 | 三方全部状态 | 无限制，但建议保留最后更新人和原因 |

产品负责人状态只能在确实需要真人测试或出现重大事件时修改。不能因为普通等待、普通代码问题或一般讨论就设置为“等待产品负责人真人测试”。

## 决策复核与等待轮询规则

### Codex 决策复核

Codex 的任务拆分、技术判断、评审结论和实现裁决并不默认视为绝对正确。工程师在开发、测试、阅读代码或分析日志时，如果发现以下情况，应当主动提出：

- Codex 的判断与代码事实、日志事实或测试结果不一致。
- Codex 的任务边界遗漏了必要文件、必要测试或必要风险控制。
- Codex 的技术方案存在更低风险、更容易验证或更符合产品目标的替代方案。
- Codex 的评审结论可能导致误测、漏测、错误放行或错误阻塞。
- 当前任务指示与产品目标“正常音量一句话智能打断、低误触发、可恢复”发生冲突。

提出方式：

1. 工程师不要直接扩大代码改动范围。
2. 先在《技术讨论文档.md》顶部追加署名讨论内容，说明发现的问题、证据、影响范围和建议方案。
3. 如果问题会阻断当前任务，工程师状态保持或切换为“等待 Codex 评审”，下一步动作写明“等待 Codex 回复技术讨论”。
4. Codex 评审时必须读取该讨论并明确回复：采纳、不采纳、部分采纳或需要补充验证。
5. 只有 Codex 把结论写入《任务指示文档.md》后，讨论内容才转为正式任务。

### 等待状态轮询

当任一角色处于等待状态时，应按约定频率查看本状态文档，避免长时间错过对方状态变化。

| 角色 | 等待状态 | 查看频率 | 需要查看的内容 |
| --- | --- | --- | --- |
| Codex | 等待工程师 | 每 30 秒一次，或每次用户通知后立即查看 | 工程师状态、当前任务编号、下一步动作 |
| 工程师 | 等待 Codex 评审 / 等待执行任务 / 等待产品负责人真人测试 | 每 30 秒一次 | Codex 状态、产品负责人状态、当前任务编号、下一步动作 |
| 产品负责人 | 等待产品负责人真人测试 / 紧急严重事项 | 看到通知后尽快查看 | 测试要求、风险说明、下一步动作 |

如果等待期间发现对方状态已变化，应先按“标准流转”修改自己的状态，再继续查看对应的任务、汇报、讨论或代码内容。

## 标准流转

### 1. Codex 下发任务

1. Codex 在《任务指示文档》中写入正式任务。
2. Codex 在《技术讨论文档》中写入必要的裁决或背景。
3. Codex 最后把 Codex 状态改为“等待工程师”。
4. 如无需真人测试，产品负责人状态保持“无需负责人真人测试”。

### 2. 工程师执行任务

1. 工程师查看《状态文档》和《任务指示文档》。
2. 工程师开始前，把工程师状态改为“开发中”。
3. 代码完成后，把工程师状态改为“自测中”。
4. 测试完成后，把工程师状态改为“更新文档中”。
5. 工程师更新《工作汇报文档》，必要时更新《技术讨论文档》。
6. 所有交付内容完成后，工程师最后把工程师状态改为“等待 Codex 评审”。

### 3. Codex 评审

1. Codex 看到工程师状态为“等待 Codex 评审”。
2. Codex 先把 Codex 状态改为“评审中”。
3. Codex 查看《工作汇报文档》《技术讨论文档》《任务指示文档》和相关代码/日志。
4. Codex 在《技术讨论文档》中写入评审意见。
5. 如需要下一步任务，Codex 在《任务指示文档》中写入新任务。
6. Codex 最后把 Codex 状态改为“等待工程师”。

### 4. 需要产品负责人真人测试

当任务需要产品负责人说话、操作设备、观察体验或执行命令时：

1. 发起方先在对应汇报/讨论文档中说明需要测试的原因、测试命令、通过标准和风险。
2. 发起方把自己的状态改为“等待产品负责人真人测试”。
3. 发起方把产品负责人状态改为“等待产品负责人真人测试”。
4. 产品负责人完成测试后，把测试结果发给工程师或 Codex，由当前任务负责人写入《工作汇报文档》或《技术讨论文档》。
5. 测试结果记录完成后，产品负责人状态恢复为“无需负责人真人测试”。

### 5. 紧急严重事项

以下情况可以设置为“紧急严重事项”：

- 疑似明文泄露 token、API key、Wi-Fi 密码或用户隐私数据。
- 烧录、硬件、供电、串口、音频链路出现可能损坏设备或阻断后续测试的问题。
- 代码改动可能破坏主线功能且无法通过小补丁恢复。
- 工程师或 Codex 无法判断是否继续推进，且继续推进可能造成不可逆风险。

设置流程：

1. 发起方先在《技术讨论文档》中写明严重事项、影响范围、建议处理方式。
2. 发起方把自己的状态改为“等待产品负责人处理紧急事项”。
3. 发起方把产品负责人状态改为“紧急严重事项”。
4. 在产品负责人确认前，不继续扩大代码修改或烧录测试。

## 状态修改格式

修改状态时，只修改“当前三方状态”表格中对应角色的一行，并保持以下字段完整：

```text
当前状态:
当前任务编号:
下一步动作:
最后更新时间:
最后更新人:
```

如果状态变化原因复杂，原因不要写在状态表里，应写入《技术讨论文档》或《工作汇报文档》，状态表只放可快速扫描的信息。
