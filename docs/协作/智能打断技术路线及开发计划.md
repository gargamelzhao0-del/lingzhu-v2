## 2. 产品目标

最终目标不是“某个脚本能触发 cancel”，而是产品使用中的拟人化插话体验：

```text
设备处于唤醒状态后，用户在任意时间用正常音量说一句话，
无论设备正在播报还是暂时空闲，
设备都能快速感知用户真实插话/换题/补充意图，
在约 0.5-1.5 秒内让上一轮播报自然淡出，
继续完整接收用户当前这句话，
并基于这句话进入下一轮回答。
```

同时必须满足：

- 不被设备自己的 TTS 播报误打断。
- 不被电视/音乐/短视频等媒体声误打断。
- 不被周围旁人闲聊误打断。
- 不被键盘、敲击、摩擦、短促环境声误打断。
- 用户短句如“停一下”“换一个”不能因为太短而经常漏掉。
- 用户长句如“我觉得你没有理解我的意思，实际上是...”不能中途过早截断。
- 后续 ASR 文本不能明显混入上一轮 TTS 内容。

当前最高优先级是两个 P0 目标同时成立：

1. 用户正常音量一句话能打断。
2. 设备不被自身 TTS 打断。

如果二者冲突，不能为了提高正向灵敏度牺牲自身 TTS 反向安全。

## 3. 当前实现现状

当前主线是 P3/P5/P6 测试链路：

- P3：soft reference AEC / near-end candidate / P6 voice shape。
- P5：播放期间 overlap probe、capture/upload/overlap 检查。
- P6：gray cancel，满足条件后 fade 当前 TTS、发送 cancel、进入 follow-up ASR。

已经具备的能力：

- 播放中采集用户语音并上传。
- 有 playback-only 反向安全样本。
- 有 normalvoice 正向 smoke。
- 有 `cancel_sent`、`p6_record_candidate`、`p6_cancel_candidate`、`live_cancel_candidate` 等日志字段。
- 有淡出旧 TTS 的本地动作。
- 有 follow-up ASR 检查，能发现 ASR 污染。

当前主要问题：

1. 普通音量一句话打断不稳定。
2. 大声说话更容易成功，正常音量容易漏触发。
3. 有过 playback-only 误打断风险。
4. 有过 follow-up ASR 混入上一轮 TTS 的情况。
5. 当前仍偏向“测试命令驱动”，还不是完整产品态“唤醒后持续可插话”。
6. 当前对背景人声、媒体声、键盘声等负样本矩阵不足。

需要特别注意：

- `p3_nearend_candidate.c` 中 P3 cancel 判别器已允许窄 single-mic voice shape 参与，不再只有双麦硬门槛。
- 但 `conversation/p5_fullduplex_overlap_probe.c` 的 live fast path 当前仍要求 `active_dual_mic_voice_ok`，这可能导致 live fast 漏触发，然后退到较慢的 fallback P3 路径。

裁决：

- P3 与 P5 live fast 的判别器不一致，不应长期保留为默认设计。
- 但它也不能在没有 playback-only 反向数据时直接放宽。正确路径是：004-3A 后按结果决定是否进入 A/B 验证。
- 如果 playback-only 已误打断，先修自身 TTS 误触发；如果 playback-only 通过但 normalvoice 漏触发，再处理 live fast gate。

当前负样本基础不足，不能用“已有零星通过”替代矩阵验收。已知有过 playback-only 通过样本、媒体/背景声零星样本、normalvoice 成功和失败样本，但数量、场景、音量、距离、复现率都不足以形成产品结论。

## 4. `xiaozhi-esp32-main` 可参考内容

`xiaozhi-esp32-main` 不是现成智能打断答案，但有若干工程设计值得吸收。

### 4.1 状态机设计

参考点：

- `DeviceStateMachine` 明确区分 `Idle / Connecting / Listening / Speaking`。
- 状态转移受控，`Speaking -> Listening` 是合法转移。
- UI、音频、协议都围绕状态机响应，而不是到处散落布尔变量。

参考价值：

- 我们后续应把智能打断从“测试 endpoint/probe”收敛成产品状态机能力。
- 唤醒后应该进入明确的 `AwakeListening / SpeakingRealtime / Interrupting / FollowupListening` 等状态，而不是仅依赖测试脚本触发。

不应照搬：

- `xiaozhi` 的状态机没有我们的 P6 候选、灰区确认、ASR 去污染、误触发恢复逻辑。

### 4.2 Abort / Listen 协议语义

参考点：

- 设备通过 `{"type":"abort"}` 请求终止当前 TTS。
- 设备通过 `{"type":"listen","state":"start","mode":"realtime"}` 进入实时监听。
- `reason` 可标记为 `wake_word_detected`。

参考价值：

- 协议语义清晰，适合企业级网关继续抽象。
- 我们现有 `cancel_turn`、`return_to_listening_after_cancel` 可以借鉴这种简单明确的命令层：

```text
interrupt_candidate -> local_fade -> cancel_turn/abort -> followup_listen -> new_turn
```

不应照搬：

- 仅发送 abort 不等于产品级打断。我们还需要本地 fade、旧音频 stale drop、follow-up ASR 绑定、turn_id/audio_session_id/playback_id 一致性。

### 4.3 Realtime Listening 与 AEC 绑定

参考点：

- 默认 listening mode 与 AEC 状态绑定：AEC 开启时使用 `realtime`。
- 在 `Speaking` 状态下，如果 listening mode 是 `realtime`，不会关闭 voice processing。

参考价值：

- 这是产品级“边播边听”的核心方向，不只是普通参考项。
- 后续阶段 2 必须吸收这种 realtime listening 与 AEC 绑定的状态机思想。
- 我们后续不应只做一次性 P6 probe，而应实现唤醒态持续可插话。

不应照搬：

- `xiaozhi` 并没有在普通用户语音出现时自动本地打断。它主要依赖唤醒词或手动事件。

### 4.4 ESP-SR AFE / AEC / VAD 管线

参考点：

- AFE 输入格式按 `M...R` 构造，支持 mic + reference。
- 使用 `AFE_TYPE_VC` / `AFE_MODE_HIGH_PERF` / `AEC_MODE_VOIP_HIGH_PERF`。
- 支持 NS 模型和 VAD 模型。

参考价值：

- 可作为我们后续评估“官方 AFE AEC 路线”的参考实现。
- 可用于对比当前 P3 softref AEC 自研链路的效果和资源消耗。

不应照搬：

- 在设备 AEC 模式下，`xiaozhi` 的 AFE processor 会关闭 VAD；这与我们“播放中用 VAD/端点判断用户是否还在说话”的需求不完全一致。
- ESP32S3 资源有限，完整 AFE 高性能配置会带来 RAM/CPU 压力。
- 必须先验证当前 Vocat 实际参考通道、双麦通道、I2S/TDM 布局是否匹配。

硬件层预检要求：

- 明确 Vocat 的 mic0/mic1/ref 在当前 I2S/TDM 帧中的 slot 映射。
- 明确当前 P3 softref 与 ESP-SR AFE 的参考信号来源是否一致。
- 明确是否存在硬件回采 reference；若没有，只能使用软件 ref/播放缓冲 ref。
- 单独验证 AFE 输入格式 `M...R` 与当前 codec 输出的通道顺序。
- 任何 AFE 路线都必须先做 build、boot、heap、CPU、音频 underrun 验证，不允许直接替换主链路。

### 4.5 唤醒词打断与声纹数据上传

参考点：

- 设备在 `Speaking` 或 `Listening` 时检测到唤醒词，会发送 abort，并重新进入 listening。
- AFE wake word 会保存约 2 秒音频，可上传给服务端做声纹识别。

参考价值：

- 可作为保守兜底：当自然语音智能打断失败时，用户说唤醒词仍应能可靠打断。
- 声纹/说话人身份应优先放在服务端增强，而不是直接强压 ESP32S3 本地实现。

兜底边界：

- 唤醒词打断是 fallback，不是主路径。
- 唤醒词应允许在 `SpeakingRealtime` 中打断，作为自然语音插话失败时的保底入口。
- 唤醒词打断不应降低自然语言打断目标，不应要求用户每次插话前重复唤醒词。
- 如果自然语音候选进入灰区且 ASR/语义确认失败，系统可以提示或允许用户用唤醒词重新进入，但不应自动把所有背景唤醒词都当成产品级智能打断成功。

不应照搬：

- 我们的目标是不需要用户重复唤醒词，直接说“换一个问题，今天天气怎么样”即可打断。

### 4.6 音频任务拆分

参考点：

- 输入任务、输出任务、Opus codec 任务分离。
- 输入以 10ms feed 给 wake word / processor。
- Opus 以 60ms 帧上传。
- 播放队列和上传队列分离。

参考价值：

- 后续产品化时应保持音频链路职责清晰：
  - mic/read/AEC/VAD
  - Opus encode/uplink
  - TTS decode/playback
  - interruption/fade/stale-drop

不应照搬：

- 我们当前已有自己的音频链路和日志工具，不能大范围替换，除非单独立项验证。

## 5. 不建议直接移植的原因

1. `xiaozhi` 的“打断”主要是手动打断或唤醒词打断，不是任意自然语音打断。
2. 它没有我们当前需要的 near-end candidate、self-echo gate、gray cancel、ASR 去污染测试链。
3. 它没有完整负样本矩阵。
4. 它没有我们当前“设备回答中用户直接插话”的本地置信分层。
5. `esp-vocat` 板型代码需要编译验证，不能默认可用。
6. 它的服务端协议与我们的网关协议不同，不能简单替换。

因此，`xiaozhi` 应作为架构参考，不作为直接代码迁移对象。

如果后续数据证明必须引入 ESP-SR AFE 路线，迁移工作量初步按中型任务估计，不应低估：

- 硬件 slot/ref 映射验证：0.5-1 天。
- AFE 最小构建和 boot 验证：0.5-1 天。
- AFE 与当前播放/上传链路适配：1-2 天。
- heap/CPU/underrun 回归：1 天。
- 与 P6 日志和测试脚本打通：1-2 天。

合计粗估 4-7 个工程日，且不包含产品级负样本调参。

## 6. 推荐技术路线

### 6.1 设备端目标架构

设备端应形成以下闭环：

```text
唤醒态持续监听
→ 播放中保留 mic/ref 采集
→ 本地 AEC/相关性/能量/VAD 生成 interrupt_candidate
→ 按置信度分层:
    高置信: 立即 soft-duck/fade + cancel old turn + 持续录完整句话
    灰区: 先轻 duck 或继续采集, 等短窗口确认
    低置信: 不打断, 只记录诊断
→ 上传 follow-up audio
→ 等待 ASR/语义确认
→ 新 turn 回答或恢复/忽略误触发
```

关键原则：

- 本地声学/VAD 负责低延迟候选。
- ASR/语义负责确认用户意图，不作为所有场景的第一阶段硬前置。
- 本地先 fade，但不要过早结束用户录音。
- “停止旧 TTS”和“判断用户说完”必须是两个独立动作。
- 每个音频包必须能绑定 `turn_id / playback_id / audio_session_id / seq / timestamp`。

落地方式：

- 短期复用现有 P3/P5/P6 链路，不新建第二套并行打断链路。
- 先把 P5 live fast 与 P3 cancel 判别器的一致性、日志和 A/B 验证补齐。
- 再把一次性 probe 收敛到产品状态机。
- fade 的触发点是本地高置信 interrupt candidate；`cancel_sent` 是向服务端发出 cancel/abort 的结果；用户语音结束由后续 VAD/ASR endpoint 判断，三者不能混成一个事件。
- 不允许在没有 playback-only 反向验证前放宽 broad low-ref 或 high-ref strong shortcut。

### 6.2 网关/云端目标架构

企业级网关/云端需要承担：

- ASR 实时识别与端点判断。
- 语义意图确认：换题、否定、补充、停止、闲聊噪声。
- 旧 turn cancel/stale drop。
- 新 turn 创建与上下文切换。
- 背景人声/媒体声误触发恢复策略。
- Agent 切换与会话隔离。
- 情绪标签、UI 表情同步。
- 设备绑定、鉴权、日志脱敏。

设备端不应关心当前使用哪个智能体。只要网关协议稳定，切换智能体应由服务端完成。

工程边界：

- 上述内容属于企业级服务设计，工程师可以提出约束和字段需求，但不直接决定服务端产品形态。
- 设备端只要求协议稳定、turn/cancel/audio 绑定清晰、Agent 切换对固件透明。

### 6.3 协议建议

以下字段是产品级目标协议草案，不要求在当前 004/005 阶段一次实现。后续应拆出独立文档，例如 `docs/协议/智能打断协议v1.md`，由设备端、网关端和服务端共同维护。

## 7. 分阶段开发计划

### 阶段 0：当前 004-3A 最小 smoke

目标：

### 阶段 2：唤醒态持续可插话状态机

目标：

- 从测试 endpoint/probe 过渡到产品态状态机。

参考 `xiaozhi`，但必须拆成子任务：

#### 阶段 2A：状态定义与事件表

- 定义 `Idle / AwakeListening / SpeakingRealtime / Interrupting / FollowupListening / Recovering`。
- 定义事件：wake、tts_start、tts_stop、interrupt_candidate、fade_done、cancel_ack、asr_partial、asr_final、timeout。
- 只改文档和状态表，不急于改音频行为。

#### 阶段 2B：播放中持续采集生命周期

- 明确进入 `SpeakingRealtime` 后哪些 mic/ref 采集任务保持运行。
- 明确何时暂停普通监听、何时保持 interrupt detector。
- 明确播放完成后如何回到 `AwakeListening`。

#### 阶段 2C：Interrupting 与 FollowupListening

- interrupt candidate 命中后进入 `Interrupting`。
- 本地 fade 与服务端 cancel 分离记录。
- 进入 `FollowupListening` 后继续收完整用户句子。
- 旧 TTS audio 必须 stale drop，不得进入新 turn ASR。

#### 阶段 2D：恢复策略

- 灰区误触发后可以恢复 idle/listening。
- 服务端拒绝语义打断时不应造成死锁。
- 网络断开、cancel ack 超时、ASR 空文本都必须有恢复路径。

验收：

- 不依赖测试脚本一次性下发 candidate 命令。
- 唤醒后，在设备说话期间保持必要的 mic/ref 采集。
- 打断后旧 TTS 能 stale drop，不混入下一轮。

### 阶段 3：端点与完整收音

目标：

- 用户长句不被过早截断。
- 用户短句不因太短漏掉。

技术点：

- 打断触发与用户说完判断分离。
- 本地维护 pre-roll ring buffer。
- ASR partial/final 与本地 VAD 共同决定 end-of-utterance。
- 短句给最小保护窗口，长句给持续 VAD 延长。

RAM 评估：

- 16kHz / 16bit / mono PCM 约 32KB/s。
- 300ms pre-roll 约 9.6KB。
- 500ms pre-roll 约 16KB。
- 如果保存双麦 + ref 原始 PCM，内存会成倍增加，不应作为默认方案。
- 第一阶段只建议保存 AEC 后 mono 或上传前 mono ring buffer；是否保存 raw mic/ref 只能作为诊断开关。
- pre-roll buffer 必须评估 internal RAM、PSRAM、DMA 访问和 Opus 编码延迟，不允许凭经验直接加大。

验收：

- “停一下”可以触发。
- “我觉得你没有理解我的意思，实际上是...”不会中途结束。
- follow-up ASR 能包含完整用户意图。

### 阶段 4：负样本矩阵

目标：

- 证明不是只对正向样本灵敏，而是在真实环境可控。

矩阵：

1. playback-only 连续多轮。
2. 媒体声/电视/音乐/短视频。
3. 背景人声，旁人在远处说话但不是对设备说话。
4. 键盘/敲桌/摩擦/短促噪声。
5. 用户正常音量正向：换题、否定、补充、短句、长句。
6. ASR 去污染：旧 TTS 与用户语音重叠。

建议初始门槛：

- playback-only：0/20 误打断。
- 正常音量正向：至少 8/10 一句话成功。
- 媒体声：0/10 误打断。
- 键盘/敲击：0/10 误打断。
- 背景人声：第一轮先记录数据，但不能长期无门槛。

背景人声临时判据：

- 工程阶段：记录 10 条，误打断 > 2/10 必须停止正向灵敏度优化，转入语义/说话人/方向性增强讨论。

### 阶段 5：语义确认与恢复策略

目标：

- 不把 ASR 关键词作为所有打断的前置，但用 ASR/语义降低误触发后果。

策略：

- 高置信声学：先 fade，后语义确认。
- 灰区声学：轻 duck 或短延迟确认。
- ASR 显示为旧 TTS 污染：丢弃或重录。
- ASR 显示为背景闲聊：不创建新 turn，可恢复待机/继续。
- ASR 显示为明确插话：创建新 turn。

验收：

- 误触发不会导致上下文严重错乱。
- 用户真实插话不会被服务端忽略。

服务端前置改造清单：

- 支持 ASR partial/final 流式回传。
- 支持 interrupt intent 分类：明确打断、换题、补充、停止、背景闲聊、未知。
- 支持 `turn_id / playback_id / audio_session_id` 绑定。
- 支持旧 turn stale drop。
- 支持 cancel ack 或等价状态回执。
- 支持灰区误触发恢复：不创建新 turn、恢复 listening、或提示用户重说。
- 支持日志脱敏后的端到端 trace。

- 不把 `xiaozhi` 代码直接复制进主工程，除非单独立项、编译验证、资源评估和接口适配。
- 引入任何 AFE/声纹/DOA/服务端语义方案前，必须说明 CPU、RAM、延迟、准确率、误触发恢复策略。

每轮汇报至少包括：

```text
任务编号
修改文件
核心改动
构建结果
测试命令
日志路径
正向/反向样本结果
关键字段摘要
已知风险
下一步建议
```

---

## 11. 结论

`xiaozhi-esp32-main` 对我们最有价值的是：

- 产品状态机。
- realtime listening 与 AEC 绑定。
- abort/listen 协议语义。
- ESP-SR AFE 接入方式。
- 唤醒词打断兜底。
- 声纹数据上传思路。

但它没有解决我们当前最难的问题：

```text
不说唤醒词、不按按钮，
用户正常音量一句自然语言，
在设备播报中可靠插话，
同时不被自身 TTS、媒体声、背景人声、噪声误触发。
```

因此，后续路线应是：

```text
保留当前 P3/P5/P6 数据化验证
吸收 xiaozhi 的状态机和 realtime 架构
修正 live fast 漏触发
建立完整正反向矩阵
再逐步引入语义确认、服务端增强和产品级协议
```
