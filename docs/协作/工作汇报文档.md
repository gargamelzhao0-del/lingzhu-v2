### 3 项核心需求 vs 协议现状
| 服务端需求 | 协议规范章节 | 现状 | 备注 |
|---|---|---|---|
| **接收设备过滤后音频** | §6 `audio_chunk` + `audio_params` (上行 NA 二进制帧 + JSON) | ✅ 完整 | 服务端需按 `output_sample_rate` / `opus_bandwidth` 处理 |
| **下发播放音频** | §9 `playback_begin/end` + §10 下行 `NA` PCM16 二进制帧 | ✅ 完整 | 服务端需把 TTS 切成 PCM16 帧并逐段下发 |
| **下发状态消息** | §7.1 `device_command`(set_state / show_status) + §11 `audio_session` + §12 `text_response` | ⚠️ 部分 | 命令通路完整,**缺流式流状态**(没看到 stream_state / segment_state) |

### 只换 URL 不改协议可对接? —— §2.1.1 6 项条件
1. URL scheme 兼容 (`ws://` / `wss://`)—— ✅ 默认支持
2. TLS 证书兼容—— ⚠️ 自签或私有 CA 需设备增加 CA 配置
3. 鉴权兼容 (X-Bridge-Token 头)—— ⚠️ 服务端必须接受该头
4. 协议兼容 (JSON + NA 二进制帧)—— ✅ 默认
5. 音频参数兼容 (PCM16/Opus + 16k/24k)—— ✅ 默认
6. 轮次上下文兼容 (audio_session_id / turn_id / playback_id)—— ✅ 默认

### "状态消息" 维度细化(产品负责人隐含问题)
当前协议 §7.1 `device_command` 子类型中:
- ✅ `set_state`(写端到云状态指示)
- ✅ `show_status`(读端给云状态汇报)
- ❌ **缺"云→端流式状态广播"**:没看到 `stream_state` / `segment_state` / `connection_state` 之类的显式消息类

如果服务端需要主动推送"我正在播放第 3 段 / 我开始 ASR / 我识别结束"之类状态,当前协议**只通过 `playback_begin/end` + `asr_*` 间接表达**,**没有独立流式状态消息**。

### 双麦可分离性最终判断

**结论:当前 `corr/diff_ratio/level_delta` 三组简单特征在 CyberVoc V1.2 双麦硬件上**完全不足以分离近端人声与播放残差**。**

证据:
- **真人 vs 播放-only 的双麦指标几乎无法区分**:
  - 播放-only: corr 0.997-0.998, diff_ratio 0.072-0.081, level_delta 0.33-0.34
  - 真人 5 场景: corr 0.996-0.999, diff_ratio 0.068-0.099, level_delta 0.30-0.50
  - **两者分布完全重叠,没有任何阈值能切分**
- **真人场景之间无差异**:无论 30cm/50cm/100cm/左/右,`corr ≥ 0.996` 不变
- **MIC1 和 MIC2 在 CyberVoc V1.2 上物理位置极近**(根据 V1.2 引脚真值表,MIC1/MIC2 是 4 槽 TDM 的 slot0/slot1),亚波长距离,远场假设下相关性天然趋近 1
- **现有门限的"高差分 + 低相关性"分支**(`dual_mic_diff_ratio >= 0.40 && dual_mic_abs_corr <= 0.94`)在所有 7 个场景下都完全不满足 —— 实测 diff_ratio ≤ 0.099, corr ≥ 0.996

### 下一步建议(A/B/C/D 四选一,请 Codex 拍板)

**A. 物理结构改造** — 修改 PCB 让 MIC1/MIC2 物理距离 ≥ λ/2(声学波长的 1/2,即 ≥ 5cm),再做双麦 DOA。**否决原因**:硬件改动不属于本工程范围,且当前已量产 N16R8 模组。

**B. 切换到两阶段云端确认策略**(代码级可行,工作量 2-3 周)
- 端侧:`p6_record_candidate=1` 即触发 cancel(单麦 gate),但 cooldown 严格收紧(≥ 5s),且加 `gray` 标记
- 云端:收到 cancel_turn + gray 标记 → 不立即 abort 旧 LLM/TTS worker → 等 asr_final 含打断关键词(模糊匹配)"打断"/"停一下"/"换"等 → 再真 abort
- 优势:端侧简化,不依赖双麦;云端用 ASR 二次确认,误打断靠关键词过滤
- 风险:打断响应延迟 + 200ms(ASR first partial)+ 云端判断延迟,可能超过 0.5s 目标

**C. 引入时延/相位特征**(代码级可行,工作量 1-2 周)
- 端侧:加 GCC-PHAT(广义互相关)计算 MIC1/MIC2 时延差,真人 30cm 通常 ≥ 3 样本时延(约 0.19ms),而播放残差时延差接近 0(同源信号同时到达)
- 阈值:时延差 > 1.5 样本 ≈ 真人,≤ 0.5 样本 ≈ 播放残差
- 优势:不依赖相关性,直接测量物理到达差
- 风险:噪声环境 + 远场时延差变小(100cm < 0.5 样本),需要降级策略

**D. 取消双麦硬要求,改为单麦 + 强校验**(代码级可行,工作量 1 周)
- 端侧:`active_dual_mic_voice_ok` 不再是 cancel 必须条件
- 改为:`p6_record_candidate=1` + 至少一条 P6 voice class 命中(`p6_normal_voice_ok`/`p6_mid_ref_strong_voice_ok`/`p6_low_ref_normal_voice_ok`) → 即放行 cancel
- 优势:立即可解锁正向样本
- 风险:误触发率上升,需要更多反向 stress(尤其音乐、电视人声)

**我的推荐**:**D 先快速解锁正向通路**(1 周)+ **C 加时延特征做双保险**(1-2 周并行)。**B 留作 fallback**。
