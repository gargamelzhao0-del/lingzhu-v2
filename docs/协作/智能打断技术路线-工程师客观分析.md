## 1. 总体判断

**这份文档是 Codex 写过的、唯一一份真正"产品级"智能打断架构文档**。它不再是 endpoint 契约细化,而是回到产品目标、设备端/网关/服务端三层架构、可量化的正反向验收标准。这正是 003 系列反复细化缺失的"全局视角"。

**但在工程落地层面,文档有 6 处遗漏、3 处错误判断、2 处时间表过于乐观**。下面对每章节逐项分析。

---

## 2. 第 1-2 章(目的、产品目标):完全采纳

这两章写得最扎实:
- **目标描述准确**:"拟人化插话体验"、"不被自己打断",覆盖 P0 到 P2
- **冲突仲裁原则正确**:"为正向灵敏度牺牲自身 TTS 反向安全"——这正是 004-3A smoke 的核心
- **短句/长句双向保护**("停一下"和"理解错"长句)已写入目标

**工程师认可**:无修改。

---

## 3. 第 3 章(当前实现现状):4 处事实,4 处准确,1 处误导

Codex 列出 6 个主要问题,这 6 条**全部准确**。但有一处遗漏:

**遗漏**:Codex 说"P5 live fast path 当前仍要求 `active_dual_mic_voice_ok`"——这是对的,但 **Codex 没说明"当前 P3 已通过验收"`dual_mic_voice_ok` 解锁但 P5 没解锁"** 是 bug 还是 feature。从代码看,**两边应该同步**。需要 Codex 把这个"是否需要同步"明确化。

**遗漏**:"当前对背景人声、媒体声、键盘声等负样本矩阵不足"——这句话虽然正确,但**没量化**。"不足"到什么程度?当前已有多少样本?这些样本的边界在哪里?这关系到阶段 4 的目标可达成性。

---

## 4. 第 4 章(xiaozhi 参考):6 节中 4 节优秀,2 节低估

### 4.1 状态机:完全正确
"参考状态机,不应照搬"——这句话是关键技术判断。

### 4.2 Abort/Listen 协议语义:完全正确
"仅发送 abort 不等于产品级打断"——这是反 xiaozhi 朴素方案的关键论述。

### 4.3 Realtime Listening 与 AEC 绑定:**低估**

Codex 说"xiaozhi 没有在普通用户语音出现时自动本地打断"——这是对的,但 **xiaozhi 的 realtime listening 与 AEC 绑定策略,本质上是"边播边听"的产品架构基础**。Codex 给的评价是"参考价值",但**这其实是后续阶段 2 的核心思路来源**。我建议 Codex 把这一节评级从"参考"提升到"必须吸收"。

### 4.4 ESP-SR AFE:引用正确,但遗漏关键点

Codex 提到 ESP-SR AFE 的 AFE_TYPE_VC / AFE_MODE_HIGH_PERF / AEC_MODE_VOIP_HIGH_PERF,这是配置面。但 **Codex 没回答一个关键问题:我们的 Vocat 设备 mic / ref 通道在 AFE 框架下怎么映射?**——没有 mic 矩阵、ref 注入、TDM 布局评估,直接套 AFE 会跑不起来。

**这是 Stage 0/1 必须补的硬件层验证**。建议加入阶段 0 的预检任务。

### 4.5 唤醒词兜底 + 声纹:**技术矛盾**

Codex 同时给两个建议:
- 用 xiaozhi 的唤醒词兜底
- 我们的目标是"不需要重复唤醒词"

**这两者不冲突**——唤醒词是 fallback,主路径不变。但 **Codex 没指定"什么时候触发唤醒词兜底"**——是任意时候都允许唤醒词打断(降低体验),还是仅 ASR/语义失败时(more complex)?

**遗漏**:这个边界未明确。

### 4.6 音频任务拆分:正确但可简化

Codex 列了 5 个职责——但这其实是我们现有 P3/P5/P6 链路的"再描述"。**没有引入新信息**。建议 Codex 删除或合并到 6.1。

---

## 5. 第 5 章(不建议直接移植):4 条理由,1 条冗余

- "xiaozhi 是手动/唤醒词打断,不是自然语音打断"——核心论据,正确
- "没有 near-end candidate"——正确
- "没有负样本矩阵"——同 3 章那个遗漏
- "没有本置信分层"——正确
- "esp-vocat 需要编译验证"——**冗余**,这条对任何第三方代码都成立,不构成"不移植 xiaozhi" 的独有理由

**遗漏**:**没量化迁移工作量**。如果"阶段 0 数据出来后确定需要 AFE 路线",迁移到 xiaozhi AFE 需要多少人天?Codex 没给出估算。这意味着阶段 5-6 的"是否引入 AFE"决策缺乏预算依据。

---

## 6. 第 6 章(推荐技术路线):**6 条原则全对,但 3 处落地不清晰**

### 6.1 设备端架构:**架构图清晰,关键原则正确**

6 条原则**全部正确**,特别是:
- "本地声学负责低延迟,ASR/语义不作为硬前置"——这避免了我前一轮担心的 1s+ 延迟
- "打断触发和判断用户说完是两个独立动作"——分得很清楚
- "每个音频包必须绑定 turn_id / playback_id / audio_session_id / seq / timestamp"——这是 ASR 去污染的基础

**但缺少**:
- 没指定"链路复用还是新链路"——是在 P3/P5/P6 现有链路上插入 fade/状态机,还是新建一套?
- 没指定"什么时候开始 fade,什么时候决定 cancel_sent"——当前 P3-3 是 1200ms 完整窗口才 fire。这是瓶颈,文档没说怎么改。

### 6.2 网关/云端架构:**正确,但延伸超出工程师范围**

8 条全部正确,但有些是企业级架构决策(代理切换、token 管理),**超出工程师能决策范围**。建议 Codex 在工程师汇报中**只确认接收,不参与设计**。

### 6.3 协议建议:**正确但结构字段过多**

Codex 列了 16 个协议字段 + 14 个诊断字段,这相当于"产品级 API 草案"——是一个完整的设计。**评估**:这是工程级工作量,**不是路线文档该有的细致度**。建议拆出到 `docs/协议/智能打断协议 v1.md` 独立维护。

## 7. 第 7 章(分阶段开发计划):**6 个阶段,2 个时间表过于乐观,3 个验收指标缺失**

### 阶段 0(004-3A smoke):**完全正确**,可以立即执行

但 **Codex 没说明 smoke 失败路径**:
- 失败时,**只修一个最小补丁**(自我审查)还是允许重设阈值?
- 失败时,**由谁决定"是阈值问题还是链路问题"**——工程师还是 Codex?

**建议补**:阶段 0 必须**有显式失败处理 SOP**(查找最近变更 → 比对相邻版本 → 写技术讨论,而不是直接 patch 阈值)

### 阶段 1(live fast 与 P3 对齐):**正确且关键**

A/B 开关设计**清晰**:`active_dual_mic_voice_ok` vs `p6_single_mic_voice_shape_ok`。**这是我前一轮提到的关键风险点**,Codex 已准确识别。

但 **验收"明显早于 fallback P3"过于模糊**——`live_candidate_elapsed_ms` 应该是量化指标,**目标值是多少?**Codex 没给。

**建议**:写明目标:"live_candidate_elapsed_ms ≤ 250ms"(比 fallback P3 的 1000-1200ms 早 800ms+)。这样验收就有数字。

### 阶段 2(唤醒态持续可插话状态机):**关键遗漏**

Codex 状态机 `Idle / AwakeListening / SpeakingRealtime / Interrupting / FollowupListening` ——这很清晰,但**从 P3/P5/P6 测试链路迁移到产品态状态机**,工作量**远大于一个阶段**。Codex 这一阶段只列了验收,没列**任务分解**。

**建议**:这一阶段应该**拆成多个子任务**,而不是只放在阶段 2 一节。

### 阶段 3(端点与完整收音):**正确但低估**

"打断触发和用户说完判断分离" + "pre-roll ring buffer" + "ASR partial + VAD"——这三句话背后工作量很大,且 pre-roll ring buffer 设计**当前设备 RAM 不一定支持**(需要评估)。**Codex 没提 RAM 评估**。

### 阶段 4(负样本矩阵):**方向对,数字松**

- playback-only 0/20
- 正常音量 8/10
- 媒体声 0/10
- 键盘 0/10
- 背景人声**"先记录数据,不急于定门槛"** ← 这条是真问题

背景人声(不是 P0 也不是 P1)被推迟,**可能成为长期坑**。如果背景人声误触发率 30%,我们"不可接受"还是"暂时接受"——这必须在产品侧定决策,不能在工程师层面推迟。

### 阶段 5(语义确认与恢复策略):**正确**

但 **"服务端语义确认"是新增能力,需要服务端同步**——文档没提服务端需要哪些前置改造,容易后期阻塞。

### 阶段 6(企业级服务对接):**超出工程师范围**,同意延迟到中后期

---

## 8. 第 8 章(验收定义):**清晰,可量化**

P0/P1/P2 分级清晰。**P0 通过定义有 6 条**,这是合理的多维度要求,而不是单点"成功/失败"。

**遗漏**:P0 通过定义没说"必须满足所有 6 条"还是"满足其中 N 条算过"——**应该是全部 6 条**。Codex 没明说,但工程师默认理解为全部。

按 1-2-3-4-5 顺序推进,**逻辑清晰**。也明确"不立即大改架构"——这响应了我前一轮的担忧。

## 13. 工程师对最终路线方向的客观态度

我**强烈认可**这份路线的方向与原则。它把过去 003-X 反复细化失去的"全局视野"找回来了。

但**实际推进层面**,**工程师能在一周内交付的是**:
- 阶段 0 smoke(继续 004-3A)
- 阶段 1 live fast A/B 修正
- 阶段 4 负样本矩阵 build 脚本

**需要跨团队或多轮迭代的**:
- 阶段 2 状态机重设计(工程师不能独立做)
- 阶段 3 端点检测(需要 RAM 评估)
- 阶段 5 服务端改造(超出工程师能力)
- 阶段 6 企业级服务(需要产品负责人主导)

**建议**:Codex 把这份文档作为 v1.0 路线基线,**立即进入阶段 0**,不要等待"补完所有 7 处细节"再开始——否则永远等不到 v2.0。
