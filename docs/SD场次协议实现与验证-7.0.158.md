# 7.0.158 SD 场次上传实现与验证

协议入口：[SD 会议监控场次上传协议](SD会议监控场次上传协议.md)。

## 上传行为

- 每场正常上传只发送一次 `meeting_audio_begin` 或 `monitoring_audio_begin`，收到成功 ACK 后开始发送本场文件。
- 同一场次的 `audio_session_id` 不变。文件通过 `audio_session_id + segment_index` 寻址，每个文件发送完后单独 commit，携带长度与 CRC；确认可靠保存后，设备先持久化确认记录，再删除本地文件。
- 场次录制结束且可上传文件均确认后发送 `session_end`。空场次也执行 begin 和 session_end。
- 不增加 SD hello、能力协商、窗口确认或逐片 ACK。现有 App 模式控制和无卡设备实时上传流程保留。
- 会议在线、离线均录入 SD，结束后上传。监控继续边录边存边传，实时文件优先；历史文件可在同一连接被打断后续传。
- 录音封存规则没有改动：最大文件 4 MiB，在线监控通常 48 帧／960 ms，离线监控通常 1,500 帧／30 秒；停止及采集属性切换可提前封存。

## 断线和异常

设备在首次发送文件前持久化“已尝试上传”标记，保留原目录记录大小、CRC 双副本和音频归档格式。传输头改为协议中的场次 ID、文件编号、文件偏移布局。

连接变化、设备重启或失败重试时，通过场次 begin 的 resume 列表查询未确认文件；每批最多 16 项。网关只回报已可靠落盘的连续前缀。偏移等于文件长度时只重发 commit，不重传文件。正常首次上传不查询每个文件。

临时错误使用退避重试，失败不会删除源文件。网关报告 `invalid_argument` 或 `conflict` 时，设备持久化 `/sdcard/audio_sessions/<场次ID>.blocked`，保留该场次全部本地证据，其他场次继续处理。核对并解决内容／身份冲突后，移除该标记、重新挂载或重启才能重新纳入扫描；不能只清空网关或绕过 CRC 来冒充成功。

网关保留旧固件接收路径；已有归档和网页播放仍可使用。新固件使用新的 Binary 头，正式云端须按新协议接入，不能继续按旧逐文件 begin 解包。
