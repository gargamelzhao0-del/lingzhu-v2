# 有卡监控满文件上传：7.0.162

日期：2026-10-22。基线：7.0.161。音频继续上传到本机 SD 测试网关。

## 录制与上传

有卡监控不再按在线 960 ms、离线 30 秒封存。在线、离线采用相同文件容量规则：

1. 将采集到的音频持续写入当前 SD 文件。
2. 写完一帧后，若剩余容量不足容纳下一条完整记录，立即写入文件尾、同步并封存。
3. 在线时安排上传该文件，同时继续录制下一个文件；离线时保留文件，联网后补传。
4. 文件收到成功 commit ACK，并将确认状态持久化后，才允许清理本地文件。
5. 停止监控后封存尾文件；全部文件确认后发送场次结束消息。

上限为 4 MiB（4,194,304 字节）。当前 16 kHz、单声道 PCM16、20 ms 一帧，每条归档记录 666 字节；加上 128 字节文件头尾，一个满文件为 **4,193,930 字节、6,297 帧、125.94 秒音频**。不补零、不拆开音频记录，也不等下一帧到达后才封存。

以下情况仍会产生不足上限的文件：停止监控、静音暂停、在线／离线采集属性切换，以及原有异常收尾。已存的小文件保持原内容和编号，正常补传，不重新合并。

连续 120 秒未确认有效人声仍暂停保存，麦克风继续监听；确认约 200 ms 人声后恢复，最多保留 500 ms 前置音频，场次 ID 不变。因此安静环境可能在满文件之前先暂停并封存。持续保存时约两分钟形成一个满文件，云端处理还需等待上传和提交成功。

## 通信

协议、数据布局及实时／历史判定不变，不要求 App 或网关增加字段：

```text
首次有封存文件待传：monitoring_audio_begin → monitoring_audio_begin_ack
实时文件示例：Binary → monitoring_audio_realtime_commit → monitoring_audio_realtime_commit_ack
历史文件示例：Binary → monitoring_audio_history_commit → monitoring_audio_history_commit_ack
……
停止、尾文件确认后：monitoring_audio_session_end → monitoring_audio_session_end_ack
```

正常连接同场次只需一次 begin；断线或重启后按现有机制恢复原场次和可靠偏移。实时／历史在一次文件发送尝试开始时判断，传输时间超过 3 秒不会自动改变本次分类；重试时重新判断。完整协议见 [SD 会议监控场次上传协议](SD会议监控场次上传协议.md)。

会议仍在整场结束后上传；无卡路径、录音与上传任务优先级、内存预留及确认后删除规则保持现状。启动监控日志新增 `seal=file_limit segment_limit=4194304`，用于核对封存策略。

## 验证

9 个测试入口通过，记录见固件包 `checks/`：

- 实际 C 写入器在小容量边界和实际 4 MiB 配置下验证在线、离线各连续两个满文件及尾文件；逐帧核对 PCM、序号、时间戳和 CRC。
- 未封存文件不能被选择上传；满文件立即可选，下一文件可以继续录制；准确满文件停止不生成空文件。
- 在线／离线切换、暂停尾文件和恢复后的时间间隔正确；会议结束屏障、无卡模式及 ACK 后清理回归通过。
- 网关接收两个满监控文件及尾文件，实时／历史交错后逐字节一致，场次时长与文件清单正确；真实 WebSocket 仅返回 begin、commit 和 session_end ACK。
- 静音 120 秒暂停、200 ms 人声恢复、前置音频去重、重连续传、缓存、持久化失败及场次确认回归通过。八小时录音覆盖为主机模拟，不是新固件实机耐久测试。
