# 正常对话与双讲打断优化开发方案

日期：2026-07-31  
目标工程：`NuwaxAIPartner-v2`  
当前基线：`7.0.14` / `release_sequence=7000014`  
目标硬件：新版 V2.0 / ESP32-S3 / ES7210 + ES8311 + NS4150B

## 1. 结论

当前工程不是缺少正常对话和打断功能，而是已经具有完整主链路，但尚未完成“低延迟、全音量、防自打断、双讲保真人声”的产品级收口。

首要发布阻断不是继续调阈值，而是先证明 AEC 在目标固件上确实运行。2026-07-29 的旧版实机日志明确出现 `live AEC preflight enabled=1 allow=0`、内部空闲内存约 13-16 KB、`raw mono fallback active`。该日志来自旧的 16 ms 构建，不能直接代表当前 20 ms 基线，但已经证明“配置启用”不等于“运行时生效”；当前候选固件必须重新取得 AEC 初始化、持续处理、参考覆盖率和无静默降级的实机证据。

可行方案是保留正式云端协议和现有 20 ms PCM16 帧不变，依次完成：

1. 建立端到端延迟、队列、AEC 和打断判定的可测基线；
2. 清除普通对话中由本机造成的固定等待和积压；
3. 将播放中打断从固定门限改为“参考锁定 + 回声置信度 + 双麦近端证据 + 音量状态”的状态机；
4. 在确认打断后立即停止播放并上传修复后的起音预录，不再额外等待一段新语音；
5. 使用多音量、多距离、单讲和双讲录音回放及真人实机矩阵验收；
6. 每阶段独立 OTA、独立回退，会议模式和监控模式保持隔离。

不建议现在直接切换 Opus、直接缩小 I2S DMA，或仅按音量线性缩放 VAD 门限。这些做法不能单独解决双讲问题，并会扩大协议或硬件风险。

## 2. 本方案范围

### 2.1 包含

- 正常对话的麦克风采集、AEC/cleaner/VAD、上行发送和本地收尾；
- 云端下行 PCM 接收、排队、I2S 首帧播放和取消；
- 播放中用户说话的检测、播放停止、旧轮取消、新轮起音保存和上传；
- 音量 0% 至 100% 下的防自打断和用户打断；
- AEC 资源不足、参考失效、网络阻塞、队列积压时的降级和可观测性；
- 主机回放测试、正式云端兼容回归、实机声学验收和 OTA 灰度。

### 2.2 不包含

- 会议模式和监控模式协议或音频处理策略变更；
- 正式云端 ASR、LLM、TTS 内部性能改造；
- 在云端未确认前切换上行 Opus；
- 在设备没有 Opus 解码器和协议协商前接收 Opus 下行；
- 把 MIC3 直接认定为可靠硬件参考；
- SD 卡、底座 UART、4G 的验证。

## 3. 不允许变化的端云契约

第一至第四阶段必须保持以下内容逐字节兼容：

- `hello` 鉴权、设备 ID、密钥和正式云端兼容行为；
- `listen start`、二进制音频、`listen stop` 的顺序；
- `NA`、version 1、22 字节小端音频头；
- 16 kHz、单声道、PCM16、20 ms、每帧 320 个采样；
- START/END/VAD flags；
- 每个音频会话从 0 开始且连续递增的 sequence；
- 当前正式云端的 PCM16 下行；
- `barge_in`、`cancel_turn` 及现有 turn/playback/audio session 关联字段；
- BLE 配网、OTA、会议模式和监控模式现有协议。

任何 Opus 方案都必须作为后续协商能力，不能替换当前 PCM16 默认路径。

## 4. 当前代码事实

### 4.1 上行

- 当前实际配置是 16 kHz、单声道、20 ms、PCM16；不是 Opus。
- 实时采集任务与 DSP/发送任务已分离，采集优先级高于 DSP。
- 正常对话已启用低延迟发送，每个 WebSocket 音频消息为一个 20 ms 帧。
- PCM 上行 sender 也有 128 个 slot；低延迟模式下一次占用一个 20 ms 帧，因此实际仍可积压约 2.56 秒。普通入队等待约 80 ms 后会终止本轮，但稳态高水位仍应按毫秒受控。
- TCP 已启用 `TCP_NODELAY`。
- 手动/首次对话在采集前已经打开云端上传。
- 持续唤醒会话保持上行，由云端连续分句，本地 VAD 句界不会关闭上行。
- 非持续自动续听先在本地确认人声，再打开上传；预录可以保存起音，但云端在确认前不能提前处理这些音频。

主要代码入口：

- `main/nuwax_ai_partner_main.c`
- `main/conversation/audio_uplink.c`
- `main/conversation/audio_uplink.h`
- `main/ws_transport.c`

### 4.2 AEC 与打断

- 播放活动时，`live_aec` 使用播放参考处理麦克风重叠音频；播放不活动时清理 AEC 会话状态并保留正常麦克风链路。
- 软件参考来自实际送入 I2S 的、已经按音量缩放后的立体声数据，因此参考幅度会随音量变化。
- 软件参考延迟、动态 FIR 延迟、双麦近端保护、human rescue、残余回声抑制已经存在。
- 硬件参考只有通过运行时健康检查才会启用；失败时走软件播放参考。
- AEC 初始化失败或内部内存不足时，当前实现会降级到原始单声道，不会阻止对话。
- 旧版实机日志已经实际触发上述降级；当前 20 ms 候选尚缺少一组新的全音量运行证据，因此现阶段不能宣称 AEC 已经可用于产品级双讲。
- 当前打断判断使用固定能量、双麦差分、参考相关性和连续帧规则。
- 播放开始固定保护 32 帧，即 640 ms；这期间即使用户说话也不能本地确认打断。
- 本地确认后保留约 96 ms 播放尾音保护，并重新等待约 300 ms 新鲜语音才打开新上行。
- 当前低音量路径存在门禁不一致：AEC 的参考活性配置约为 `avg_abs >= 20` 或 `peak >= 60`，打断路径却使用约 `avg_abs >= 120` 或 `peak >= 500`，且近场分类器硬性要求 `ref_active=true`；低音量或 TTS 间隙会漏掉真实用户。
- 当前候选事件在采集线程同步发送，然后才进入本地停播；网络写阻塞会直接增加打断时延。确认后若上行启动失败，现有分支还可能对同一事件再发送 `rejected`，需要改为单一终态。
- 播放中形成的新轮当前使用 3500 ms 最短采集和 1200 ms 尾静音，若云端依赖设备 END，会显著拖慢新轮收尾。

主要代码入口：

- `main/conversation/live_aec.c`
- `main/conversation/barge_in_detector.c`
- `main/conversation/barge_in_detector.h`
- `main/nuwax_ai_partner_main.c`
- `main/conversation/session_dispatch.c`

### 4.3 下行与播放

- 当前只接受 `NA v1` PCM16；codec 2/Opus 会被跳过。
- WebSocket 接收回调内完成解析并把 PCM 复制到扬声器队列。
- 扬声器队列深度为 128 个 20 ms 帧，可积压 2.56 秒。
- 队列满时接收任务最多等待 3 秒，这会同时拖住文本命令、心跳和取消处理。
- 每个队列项内嵌一整帧 PCM，入队和出队都会复制。
- `speaker_output` 的写入函数支持首次 write 时扩展 mono-to-stereo 缓冲，但产品启动路径会通过 prepare/stop 写入一帧静音完成 320-sample 预热；正常启动后的首个标准音频帧通常不会再分配。该预热行为需要变成受测试保护的契约，而不是被视为当前主要瓶颈。
- 当前共享 I2S DMA 为 `6 x 240` frames，在 16 kHz 下容量约 90 ms。

主要代码入口：

- `main/ws_transport.c`
- `main/conversation/speaker_playback.c`
- `main/speaker_output.c`
- `main/board/vocat_audio_board.c`

## 5. 当前主要问题及优先级

| 优先级 | 问题 | 实际影响 |
| --- | --- | --- |
| P0 | 缺少完整的端到端分位数测量 | 无法判断每轮慢在设备、网络还是云端，也无法证明优化有效 |
| P0 | 640 ms 固定播放启动保护 | 用户在 TTS 起始阶段讲话无法及时打断 |
| P0 | 打断后约 96 ms + 300 ms 再确认 | 起音已保存但上传仍被推迟，影响下一轮 ASR 首包 |
| P0 | 播放中 3500/1200 ms 收尾参数 | 正式云端若等待 END，新轮会多等数秒 |
| P0 | AEC 失败静默退化为 raw mono | 高音量时存在严重自打断风险，却没有产品状态阻止激进本地取消 |
| P0 | 打断控制事件同步走 WebSocket | 候选发送或 socket 锁阻塞会推迟本地停播；同一事件还可能出现 confirmed/rejected 矛盾终态 |
| P0 | 低音量打断硬依赖较高的 `ref_active` 门槛 | TTS 音量低或参考瞬时安静时，真实用户即使出现也可能无法进入近场分类 |
| P1 | 采集、PCM 上行和播放队列都允许约 2.56 秒积压 | 过载时可能处理过期音频，表面不断流但交互已失去实时性 |
| P1 | 扬声器入队可阻塞 WebSocket RX 3 秒 | 取消、命令和心跳都可能被音频背压阻塞 |
| P1 | 所有发送共享一把锁和 4 秒 I/O deadline | 音频慢写可能延迟 `barge_in confirmed` 或 `cancel_turn` |
| P1 | 下行没有严格序号缺口/重复/乱序统计 | 播放卡顿不能定位到网络、云端还是设备 |
| P1 | 音量未成为打断策略的显式上下文 | 软件参考虽随音量变化，但声学路径、PA 非线性和削顶不会线性变化 |
| P2 | RX 每条消息分配释放内存 | 增加抖动和长期堆碎片风险 |
| P2 | 下行多次整帧复制；预热契约缺少直接回归 | 增加 CPU/内存带宽，异常启动路径仍可能触发首次动态分配 |
| P2 | DMA 约 90 ms | 增加停止播放后的物理尾音，但不是当前第一瓶颈 |

## 7. 目标数据流与状态机

### 7.1 普通对话与打断的双路径数据流

```text
I2S RX：MIC1 raw + MIC2 raw
  -> RT capture（只采集、校验序号和打时间戳）
  -> 同步帧环：MIC1/MIC2/processed/reference/metadata
       |-> 判定路径：raw 双麦 + 实际播放参考 + clipping/delay/AEC health
       |     -> barge controller -> generation-bound 本地停播
       |
       `-> 上传路径：AEC -> residual suppression -> human rescue/起音修复
             -> bounded uplink queue -> priority TX owner -> WebSocket

WebSocket RX
  -> header/sequence validation
  -> PCM buffer pool
  -> speaker pointer queue
  -> I2S TX
  -> post-volume software reference ring
```

判定路径不得使用已经被 human rescue 或 cleaner 改写后的音频作主要证据，避免形成“先保护人声、再用保护结果证明有人声”的循环依赖。上传路径负责音质，判定路径负责是否停播，两者共享同步时间线但职责独立。

### 7.2 打断状态机

```text
PLAYBACK_ARMING
  -> ECHO_TRACKING
  -> HUMAN_CANDIDATE
  -> STRICT_CONFIRMED
     或 AMBIGUOUS_PROBE -> STRICT_CONFIRMED / REJECTED
  -> LOCAL_STOPPING
  -> POST_STOP_TAIL
  -> UPLINK_ACTIVE

任意状态：
  ref/AEC/时序失效 -> DEGRADED_REF / DEGRADED_AEC
  TTS-only 判定 -> 回到 ECHO_TRACKING
  generation 改变 -> 清理旧候选并绑定新播放代次
```

关键规则：

- `PLAYBACK_ARMING` 不再固定为 640 ms；由最小保护时间、匹配的播放 generation 和 AEC/reference lock 共同决定；
- `HUMAN_CANDIDATE` 只发送诊断或现有 candidate 事件，不立即破坏播放；
- `STRICT_CONFIRMED` 立即使旧播放 generation 失效，本地停止不等待云端 ACK；
- `LOCAL_STOPPING` 保留已修复的起音预录，同时将高相关回声尾帧替换为等长静音，保持序号连续；
- 观察到 I2S/软件参考停止边界后立即进入 `UPLINK_ACTIVE`，不再强制等待额外 300 ms 人声；
- 若 AEC degraded，只允许更严格的双麦强近场确认，或放弃本地早停并交给云端，绝不能按 raw VAD 直接停 TTS。
- 本地停播必须先于并且独立于网络 I/O；`candidate -> confirmed/rejected` 仍按现有协议有序异步发送，同一事件只能产生一个终态。上行后来失败应报告音频会话错误，不能把已经 confirmed 的打断改写为 rejected。

## 8. 分阶段实施方案

### 阶段 0：测量基线，不改变用户行为

新增统一单调时钟时间点：

- `mic_read_done_us`
- `dsp_done_us`
- `vad_onset_us`
- `uplink_enqueue_us`
- `uplink_socket_done_us`
- `endpoint_us`
- `end_socket_done_us`
- `downlink_handler_us`
- `speaker_enqueue_us`
- `first_i2s_begin_us`
- `barge_candidate_us`
- `barge_confirm_us`
- `speaker_stop_request_us`
- `speaker_last_i2s_us`
- `barge_first_uplink_us`

同步记录：

- capture、uplink、speaker 队列当前深度和最大深度，统一换算为毫秒；
- DSP 每帧耗时 p50/p95/p99/max；
- WebSocket 每次写耗时、锁等待耗时和超时；
- AEC reference active/lock、相关性、估计增益、残差、delay、clip ratio；
- 下行 sequence gap/duplicate/out-of-order；
- 打断判定各分支计数和拒绝原因。

同时完成 AEC 内存审计：统计启动各阶段内部 RAM/最大连续块，确认 AFE/AEC 所需内存在启动早期预留；把可放入 PSRAM 的队列、历史和任务栈移出内部 RAM；对话热路径不得重复创建/销毁 AEC。若当前候选仍出现 `raw mono fallback active`，阶段 0 直接判定失败，不进入打断策略调参。

实现文件：

- 新增 `main/conversation/conversation_metrics.[ch]`；
- 接入 `nuwax_ai_partner_main.c`、`audio_uplink.c`、`speaker_playback.c`、`speaker_output.c`、`ws_transport.c`；
- 新增主机统计测试，验证计数溢出、重置、分位数和 generation 隔离。

阶段门：至少采集 20 轮正常对话、每个音量 10 轮 TTS-only 和 10 轮真人打断基线。未形成基线，不进入调参。

### 阶段 1：无协议风险的实时路径整理

1. 固化并测试现有扬声器 prepare/stop 预热契约；必要时改为显式分配最大单帧 mono-to-stereo 缓冲，确保任何产品启动分支都不会在真实首帧触发 `realloc`。这是一项抖动防护，不作为主要延迟收益计算。
2. 将扬声器大结构体队列改为固定 PCM buffer pool + 指针/索引队列，避免每帧多次整块复制。
3. WebSocket RX 不得等待扬声器队列 3 秒：
   - 正常入队等待预算不超过 20 ms；
   - 队列持续满视为播放实时性失败，取消当前播放并记录明确原因；
   - RX 任务继续处理控制帧和心跳。
4. 保留物理队列容量作为突发保护，但设置实时软上限：
   - capture 目标高水位 5 帧/100 ms；
   - speaker 目标高水位 5 帧/100 ms；
   - 超过 8 帧/160 ms 进入故障策略，不能默默播放或上传旧音频。
5. 增加下行序号跟踪；重复和乱序丢弃，缺口记录并按等长静音或取消播放的已定义策略处理。
6. 将 `speaker_output`、PCM pool、AEC 大块内存在启动阶段预留并验证，避免对话中堆碎片。

阶段门：协议字节完全相同；30 分钟上下行无采集缺口、无正常条件掉帧、队列稳态不超过 100 ms。

### 阶段 2：普通对话收尾提速

先通过 Kconfig/运行时策略引入参数组，首轮推荐值：

| 参数 | 当前 | 首轮候选 | 说明 |
| --- | ---: | ---: | --- |
| 自动续听人声确认 | 180 ms | 120 ms | 仍使用预录，不影响手动/持续会话 |
| 非持续尾静音 | 450 ms | 320 ms | 先在短句和尾音数据集验证 |
| 非持续最短采集 | 700 ms | 500 ms | 防止极短噪声轮，不用于持续会话 |
| 预录有效窗口 | 已有 256 帧环 | 实际发送 300-500 ms | 环容量无需全部发送 |

约束：

- 手动/首次监听继续立即上传，不增加 120 ms 等待；
- 持续唤醒会话继续保持上行，忽略本地句界；
- 自动续听确认前的语音由预录补发，sequence 必须从 0 连续；
- 参数必须可单独回退，不与 AEC 调参捆绑；
- 使用短尾音词、轻声、停顿句、数字和中英文混合语料验证，不凭主观听感直接定值。

阶段门：非持续轮 `真实停说 -> END/listen stop` p95 不高于 350 ms，短句截断率不高于基线。

### 阶段 3：动态音量 AEC 与参考健康状态

新增只读声学健康快照 `nuwax_aec_runtime_context_t`，每个 20 ms 帧更新，并汇总为 `GREEN/YELLOW/RED`：

- 当前音量百分比和音量 generation；
- 软件参考 RMS/peak/clip ratio；
- mic1/mic2 RMS/peak 和差分能量；
- mic-ref correlation、投影 gain、残余回声比；
- 当前 delay、delay 稳定度和 reference generation；
- AEC 状态：`WARMUP/FAR_ONLY/DOUBLE_TALK/HOLD/DEGRADED`；
- `reference_locked` 和连续稳定帧数。

处理原则：

1. 音量仅作为先验，不直接按百分比线性放大能量门限。实际依据是 post-volume 软件参考和麦克风中的回声底噪。
2. 低音量时降低“参考必须很强”的要求，但仍要求 reference generation 连续；高音量时提高削顶、残差和自相关防护。
3. 只在可信 `FAR_ONLY` 帧更新回声路径、动态 delay 和自适应增益；近端候选或双讲时冻结自适应，避免把用户声音学进回声滤波器。
4. AEC 失败、参考断代、内存降级或 delay 不稳定时设置 `DEGRADED`，同时关闭高召回本地早停。
5. MIC3 只有在独立健康检查、通道映射、与播放高度相关且与 MIC1/MIC2 人声行为不同均通过后，才允许参与正式 AEC。未通过时继续以软件播放参考为权威。
6. 音量改变后保留会话，但清除短期 lock/echo floor，重新经过最小锁定窗口。
7. 音量百分比只作先验，实测参考覆盖率、残余相关性、ERLE、双麦空间证据和削顶率才是最终依据；音量档切换采用 200-300 ms 滞回，避免边界抖动。

建议首轮音量策略：

- `0-5%` 或参考确实不活动：不再硬性要求 `ref_active`，使用普通 VAD 加强双麦独立人声证据；
- `6-30%`：要求 2-3 个连续人声证据帧，并重点防止 TTS 间隙漏检；
- `31-75%`：健康为 GREEN 时允许 2-3 帧严格本地确认；
- `76-100%`、存在削顶或健康为 YELLOW：单帧高召回证据只能形成候选，至少需要两类独立证据才允许停播；
- 健康为 RED：禁止激进本地停播，记录原因并走保守策略。

阶段门：所有音量的纯 TTS 数据中 AEC lock 稳定，raw mono fallback 可检测、可上报且不会进入激进早停。

### 阶段 4：双讲打断状态机收口

1. 用 `minimum_guard + reference_locked` 替代固定 32 帧：
   - 绝对最小保护先取 4 帧，即 80 ms；
   - 正常目标在 80-160 ms 内完成锁定，连续 3-5 帧参考稳定后允许判定；
   - 300 ms 内仍未锁定则进入 `DEGRADED_GUARD`，而不是无条件开放。
2. 候选确认：
   - 非对称近场强证据：连续 2 帧，约 40 ms；
   - 对称正面人声：连续 3 帧，约 60 ms；
   - 高相关或 echo candidate 不能单独确认；缺少独立双麦/语音证据时拒绝，证据冲突时进入探测分支；
   - AEC degraded 时使用更严格的双麦强证据，禁止单麦 raw VAD 早停。
   - 高音量且证据冲突时，可在独立 feature flag 下进行 60-100 ms、12-18 dB 的瞬时降音探测；麦克风能量同步下降则判为回声，独立双麦人声仍存在才确认。探测结束恢复当前 generation 的瞬时增益，不改变用户保存的音量。
3. 确认后立即执行本地动作：
   - 推进 speaker generation，停止接受旧轮 PCM；
   - 立即请求 I2S 停止/清 DMA；
   - 发送现有 `barge_in confirmed`/`cancel_turn`，进入控制消息高优先级队列；
   - 本地停播不等待云端 ACK。
4. 起音保护：
   - 保留确认前 300-500 ms mic1/mic2/ref/aec_out；
   - 对可由 human rescue/双麦证据支持的用户帧进行恢复；
   - 对 reference 高相关且无法可靠分离的播放尾帧替换等长静音；
   - 保持新音频 session 的 sequence 连续。
5. 新轮启动：
   - 首轮先保留约 96 ms 安全尾保护；
   - 一旦 speaker generation 停止且软件参考 generation 已跨过尾部，立即上传修复后的起音；
   - 移除当前必须再积累约 300 ms fresh speech 的条件；
   - 后续可把固定 96 ms 改为实际 DMA stop/reference drain 边界。
6. 打断新轮收尾首轮候选值：
   - 最短采集 600-800 ms；
   - 尾静音 400-500 ms；
   - 不再使用 3500/1200 ms；
   - 最终数值必须结合正式云端是否流式 endpoint 决定，但不改变协议格式。

阶段门：在所有音量、距离和指定噪声下同时达到防自打断与真人打断指标，不能只优化其中一个。

### 阶段 5：发送控制优先级与下行抖动治理

1. 所有 WebSocket 出站消息进入单一 TX owner，避免多个任务直接竞争 socket 生命周期锁。
2. 至少分为 control、terminal、audio 三类优先级：
   - `cancel_turn`、`barge_in confirmed`、ping/close 为最高；
   - listen stop/END 为次高；
   - 普通音频为正常。
3. 控制消息必须能越过尚未开始发送的音频；已经阻塞的底层 write 不能真正抢占，因此音频 write deadline 也要缩短。超过实时预算应断开重连，不能占锁 4 秒。
4. RX 使用复用缓冲或 buffer pool，去掉每消息 malloc/free；解析与扬声器消费解耦。
5. 下行不做大预缓冲。首包满足 START 和格式校验后即可入 I2S，稳态队列目标小于 100 ms。

阶段门：人工制造网络背压时，本地停播仍按时发生；控制帧不会被 2.56 秒 PCM 队列或 4 秒发送锁阻塞。

### 阶段 6：高风险可选优化

仅在阶段 0-5 全部通过后考虑：

- 将 I2S DMA 从约 90 ms 调到 40-60 ms，验证 30 分钟无 underrun、capture gap 和爆音；
- 云端明确确认 Opus 上行后，启用现有 32 kbps/20 ms Opus 并测编码 p99；
- 增加协商式 Opus 下行和持久 decoder，同时保留 PCM fallback 和丢包 PLC；
- MIC3 硬件参考通过实测后做软件参考/硬件参考 A/B，而不是直接替换。

## 10. 测试体系

### 10.1 主机自动测试

- 正常对话状态：首次监听、自动续听、持续会话、超时、短音频和取消；
- uplink：START/END、sequence、首批一帧、队列满、发送失败、final flush；
- downlink：START/END、缺口、重复、乱序、旧 generation、并发 cancel；
- 打断：startup guard、reference lock、非对称近场、对称近场、纯 TTS、AEC degraded；
- preroll：起点定位、修复、静音替换、sequence 连续、旧轮隔离；
- 协议：hello、listen、二进制帧、正式云端兼容、会议和监控模式无变化；
- 30 分钟合成压力：队列高水位、内存泄漏、堆碎片、任务栈和 watchdog。

现有源代码模式检查只能防止已知结构被误删，不能代替真实 DSP、延迟和回放测试。必须新增用真实录音驱动算法的可重复测试。

### 10.2 离线 WAV 数据集

每条样本应同步保存：

- mic1 raw；
- mic2 raw；
- 软件参考；
- 可选 MIC3；
- AEC output；
- 设备原始 TTS PCM；
- 音量、距离、噪声、用户起音真值和预期是否打断。

至少覆盖：

- TTS-only：音量 0/10/30/50/70/90/100%；
- near-end only：轻声、正常声、较大声；
- double-talk：TTS 开始后 0/100/300/600/1500 ms 起说；
- 距离 0.5/1/2 m；
- 正面、侧面；
- 安静、稳定风扇噪声、多人背景声；
- 单音节、短句、长句、爆破音开头、轻声开头；
- 播放过程中调节音量。

### 10.3 实机验收顺序

1. 纯 TTS 防自打断；
2. 停播但保持监听的 near-end only；
3. 固定句双讲；
4. 随机起说双讲；
5. 连续 20 轮正常问答；
6. 连续 100 轮 TTS-only；
7. 30 分钟混合压力；
8. 正式云端协议和体验回归；
9. 会议模式、监控模式、BLE、OTA 冒烟回归。

## 11. 验收指标

### 11.1 实时性

| 指标 | 目标 |
| --- | ---: |
| 每 20 ms 帧 DSP | p99 <= 15 ms，max 不持续超过 20 ms |
| 手动/立即监听：真实语音首样本到首个 binary send 完成 | p95 <= 50 ms |
| 自动续听：真实语音首样本到首个 binary send 完成 | p95 <= 140 ms |
| 非持续会话：真实停说到 END/listen stop | p95 <= 350 ms |
| 下行 handler 进入到首个 I2S write begin | p95 <= 20 ms，p99 <= 40 ms |
| capture 稳态积压 | <= 100 ms |
| speaker 稳态积压 | <= 100 ms |
| 用户起音到最后可闻播放停止，音量 0-75% | p95 <= 220 ms |
| 用户起音到最后可闻播放停止，音量 76-100% | p95 <= 300 ms |
| 本地确认到新轮首个上行帧 | p95 <= 60 ms |

上表只测设备自身时间。云端 ASR/LLM/TTS 和公网时间必须另列，不能混成一个“总响应时间”后归因给设备。

### 11.2 完整性

- 30 分钟采集：gap/drop/duplicate/out-of-order 均为 0；
- 正常网络下 uplink 和 downlink sequence 均连续；
- START/END 各一次且顺序正确；
- 旧 playback END、旧 cancel ACK 不改变新 generation；
- 队列超过实时软上限时必须产生明确失败，不允许静默处理旧音频；
- AEC degraded 必须可观测，不能伪报 AEC 正常。

### 11.3 声学与打断

- 每个音量至少 100 次 TTS-only，设备本地误停 0 次；
- 安静环境真人打断成功率 >= 95%；
- 规定噪声环境真人打断成功率 >= 90%；
- 0.5/1 m 必须达标，2 m 单独记录，不用近场门限强行承诺；
- 打断起始音节可懂度不得低于 near-end-only 基线，首音节损失 p95 <= 40 ms，前 100 ms 能量保留率 >= 90%；
- far-end only 的 AEC 输出相对 raw mic 回声能量中位下降：10-70% 音量目标 >= 18 dB，90-100% 音量目标 >= 15 dB；
- 双讲时用户语音能量相对 near-end-only 参考衰减 < 3 dB，STOI 下降 <= 0.08，并同时记录 ASR 字错率；
- 任何音量都不得通过“把麦克风整体压低”来换取防自打断。

声学 dB 指标需要同一摆位、同一播放文件和校准音量；未校准录音只能用于相对 A/B，不能作为绝对硬件结论。

## 12. 发布和回退策略

建议按以下 OTA 版本逐步发布，每版只跨一个主要风险面：

1. 指标版：只增加观测，不改行为；
2. 实时队列版：预分配、PCM pool、序号和软上限；
3. 普通对话 endpoint 版；
4. AEC runtime state/reference lock 版；
5. 双讲状态机版；
6. TX 优先级和 RX buffer pool 版；
7. 可选 DMA/Opus 实验版。

每版均要求：

- 递增版本和 release sequence；
- fresh build；
- 全部 host checks；
- 镜像 size/SHA/HTTPS 回读；
- OTA `accepted -> staged -> reboot -> pending_verify -> committed`；
- 正式云端至少 20 轮正常问答；
- 会议、监控模式协议及完整录音冒烟；
- 保留前一版 OTA 回退镜像和串口救援路径。

最终候选还必须完成 8 小时混合稳定性测试：无重启、watchdog、I2S underrun、队列溢出、序号异常和持续内存下降。

## 13. 明确禁止的实现方式

- 只按扬声器音量百分比线性放大 VAD 阈值；
- 只靠单麦能量判断打断；
- AEC 失败后仍开放高召回本地取消；
- 为避免自打断而整体压低或静音用户麦克风；
- 在确认打断后丢弃确认前全部音频；
- 让 WebSocket RX 为保存 PCM 阻塞数秒；
- 让旧轮 END/cancel ACK 终止新轮；
- 未经云端确认直接切换 Opus；
- 未经 MIC3 通道和健康实测直接把商家代码中的第二通道当硬件参考；
- 一次 OTA 同时改 VAD、AEC、DMA、codec 和协议，导致无法定位回归。

商家工程可参考的是“连续全双工采集、独立 AFE/AEC 处理和播放参考”这一架构，不可直接复制其通道假设。商家 V2.0 路径把第二输入通道当 reference，但现有代码与板级资料不能证明该通道就是可靠电回采，并且与双麦用途存在冲突；在 MIC3/slot 映射、连通性和健康指标实测通过前，本工程继续以实际 I2S 播放 PCM 的软件参考为主，硬件参考保持 fail-closed。

软件方案也存在物理边界：PA、扬声器、空气路径或 ADC 一旦严重非线性/削顶，软件参考无法重建已经丢失的波形，因此不能承诺“100% 音量下永不自打断且任何轻声都能打断”。若高音量矩阵仍不达标，应按实测依次评估输出 limiter、把 ES7210 固定模拟增益从当前 30 dB 调低至 27/24 dB 后补数字增益、修复硬件参考，最后才考虑硬件改版；不得随播放音量动态切换模拟麦克风增益，以免破坏 AEC 收敛。

## 14. 推荐执行顺序

当前下一步应只实施阶段 0，并在实机上获得可比较基线。第一批代码不要修改 AEC 数学参数和打断门限。

基线完成后按以下判定推进：

- 普通对话主要慢在 450/700 ms：进入阶段 2；
- 首包慢在队列/内存/锁：先完成阶段 1 和阶段 5 对应部分；
- 高音量纯 TTS 出现 candidate：先完成阶段 3，不直接提高人声阈值；
- 用户打断识别正确但停播慢：优化 generation/I2S stop 和控制发送；
- 用户打断后首字丢失：优化 preroll repair 和尾帧 sanitize；
- AEC 经常 degraded：先解决内存、参考连续性和 delay lock，暂不开放激进早停。

只有阶段 0-5 的量化指标同时通过，才能将“正常对话快速响应、全音量防自打断、双讲保留用户声音”标记为完成。
