全程日志均为实际 SD 时钟 40000 kHz、fallback_latched=0；两场合计 4998 次 SD 读取，错误 0。不能再将慢归因于仍跑 20 MHz。

800 KiB/s 要求 128 KiB 窗口约 160 ms；当前两路单独运行均未达到，单纯加大窗口或增加预读缓冲不足以解决。

## 稳定性和边界

- 截取中未见 panic、看门狗或重启，但设备最后仅运行到约 10 分 18 秒，补传后观察约 10 秒，尚不能证明长期稳定。
- 补传期间 UI 从 21.3 降到 19.3、18.0 fps，目标 40 fps；解码耗时峰值 413.84 ms，已有明显流畅性代价。离线时 paused=1 / fps=0 属于暂停状态，和补传期间掉帧需分开。
- wake input partial_reads/timeouts 从 0 增至 6，但独立 capture 的 partial_reads/timeouts/queue_drops/invariant_faults 为 0，input_gaps/partial_samples_dropped 也为 0。代码表明前者来自推理任务读取采集队列，不应等同 DMA 丢音。补传后超时计数没有继续增长，推理均值降至约 18.2 ms。
- 5 次正式云端应用心跳延后，后续仍有 pong，无此期间断线重连证据；提示后台补传资源竞争。
- internal_min=63 是历史最低水位指标，当前 internal=28059、largest=11776；不能判定现在只剩 63 字节，但仍应定位历史低水位来源，避免用扩大内部缓冲换吞吐。
- 断网时 TLS read error 和未发送帧报错与 UI 主动关闭连接相邻，随后离线交接、接纳帧数和网关连续性验证均成功。OTA 被 audio_busy 拒绝为录音保护生效。
- 没有启动 SHA，测量日志证明新诊断路径生效，不能仅凭该截取核对完整固件 SHA。

## 下一步建议

优先分离设备端 CPU 实际工作与被抢占时间，检查 SD 完成后任务恢复、PSRAM 校验/组帧/掩码拷贝和网络发送路径。保留唤醒采集优先级、录音抢占和 CRC，避免单纯提高补传优先级进一步压低 UI 帧率。利用相同归档做受控对照：先优化复制/缓存访问和调度等待，再决定是否有必要调整 CPU 绑定或窗口。

现有证据说明尚有可优化开销，但没有证据承诺稳定达到 800 KiB/s。下一轮验收应同时看网关完整性、端到端吞吐、UI 帧率、唤醒丢帧和心跳延后次数。
