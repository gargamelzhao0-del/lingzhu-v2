## 结论

正常路径的 8 组相关回归通过，但仍有两处设备端异常／长时间运行问题，以及一处已测出的网关性能问题。不能据此认定功能已经没有缺陷，或已经达到 500.0 KiB/s。

本轮范围为模式控制、有卡／无卡路由、录音写入、场次目录、上传调度、协议收发、确认删除、断电恢复、网关落盘与收尾。不是对充电、配网、唤醒等全部产品模块重新做验收。

## 1. P2：确认记录同步失败，目录扫描仍可能清理音频

代码位置：

- `main/sd_audio_catalog.c:352`：`sd_audio_catalog_ack()` 写确认标志并检查同步结果。
- `main/sd_audio_catalog.c:627`：`catalog_next_impl()` 读到 acknowledged 后直接删除音频，没有确认该次索引写入是否同步成功。
- `main/offline_audio_spool.c:4598`：正常上传清理路径会检查确认记录写入结果；问题位于后续目录扫描的清理分支。

复现步骤：创建一场已结束、尚未确认的录音；模拟云端文件 ACK 到达后的本地确认写入；让这次 fsync 返回 EIO；调用真实目录选择函数。结果：确认函数返回失败，但后续扫描删除了源文件，并选中了场次结束操作，期间没有再次调用 fsync。

随后模拟失败的索引更新在断电中丢失，恢复旧索引内容，再调用真实恢复函数，得到 `missing=true、complete=false`。复现结果：

```json
{
  "ack_error": -1,
  "audio_removed_after_failed_fsync": true,
  "syncs_before_cleanup": 0,
  "selected_session_end": true,
  "after_simulated_reset_missing": true,
  "after_simulated_reset_complete": false
}
```

影响：本地“确认持久化后才能删除”的约束有一个绕行入口。异常断电恢复时，可能把原来完整的场次标为不完整。这里云端已经返回文件成功 ACK，**不能把此结果说成云端已经丢失音频**。

证据边界：使用真实目录 C 实现进行主机故障注入；旧索引恢复是模拟掉电，不是已经完成实卡断电复现。ESP-IDF 的 FatFs 关闭文件也可能再次尝试同步，因此一次物理 fsync 故障不等于每次都会出现上述最终结果；代码仍不应把失败返回后的可读 ACK 自动当作持久化成功。

建议：统一所有删除入口的确认条件。清理尚存在的源文件前，必须取得可靠的已持久化确认依据；失败后应重新持久化确认记录，并检查写入和关闭结果，失败则保留文件。不要只在重新打开的未修改文件上调用一次 fsync 来代替确认重写。正常已确认并删除的文件仍可沿用游标快路径，避免每次扫描都增加同步开销。

复现源码及结果：`tmp/sd-chain-audit-20261021/ack_fsync.c`、`ack_fsync-result.json`。

## 2. P2：连续在线约 24.9 天后，新监控音频被判为历史

代码位置：

- `main/sd_audio_session_storage.inc:38`：最近上线时间仅在离线转在线时更新。
- `main/offline_audio_spool.c:2488`：采集帧在线属性使用有符号 32 位时间差。
- `main/sd_audio_catalog.c:506`：上传实时性判断使用同类时间差。

`(int32_t)(采集时间低32位 - 最近上线时间)` 只有时间差小于 2³¹ ms 时适合判断先后。持续在线达到 2,147,483,648 ms，约 24 天 20 小时 31 分，差值变为负数。新开启监控也不会重置最近上线时间。

调用真实 `sd_audio_segment_realtime()`，保持相同开机、在线标记、封存有效、末帧仅距当前 100 ms，结果：

| 持续在线时间 | realtime |
| --- | --- |
| 1 天 | true |
| 2³¹ − 1 ms | true |
| 2³¹ ms | false |
| 25 天 | false |

影响：设备仍能录音和上传，但新声音被作为 history，云端按约定不产生实时告警。采集侧也可能进入非实时文件封存条件。长期插电使用会遇到这一边界，不能只测一次 8 小时离线录音来覆盖。

建议：设备内部使用同一基准的 64 位上线时间与采集时间；对 NA 帧的低 32 位时间在有明确近时约束的地方展开。采集属性判断和上传分类一起修改。网络协议中的帧格式、场次 ID、消息名无需改变。

复现源码及结果：`tmp/sd-chain-audit-20261021/long_uptime.c`、`long_uptime-result.json`。

## 3. P2：测试网关在文件 ACK 前同步重写所有历史统计

代码位置：

- `tools/protocol/sd-scene-receiver.js:267`：提交成功返回 ACK 前调用 `persistReport()`。
- `tools/protocol/offline-audio-replay-gateway.js:969`：把不断增长的全部 archives 放入报告。
- `tools/protocol/offline-audio-replay-gateway.js:979`：主线程 JSON 序列化并同步写整份报告。

本轮从现行网关源码提取原 `persistReport` 函数，使用真实 SceneReceiver 提交路径；分别预置 0 和 30,000 条历史统计，各提交 6 个真实格式的 32,096 字节文件。统计列表是合成数据，没有拿真实用户录音做变更。

| 测量项 | 无历史统计 | 30,000 条历史统计 |
| --- | ---: | ---: |
| 报告大小，最后一次 | 3,830 B | 16,923,832 B |
| commit 耗时中位数 | 14.37 ms | 80.75 ms |
| 其中报告处理中位数 | 1.18 ms | 64.03 ms |

30,000 个 960 ms 文件对应连续保存约 8 小时的在线监控。该规模也可能由多场录音、同一个网关进程长期运行累积形成。若 PC 网关不可达而普通云端仍在线，设备还可能积压这种小文件。

影响：上传文件越多，统计处理越慢，并占住网络事件循环。对于本次模拟的 32,096 B 小文件，单凭 80.75 ms 的提交耗时，串行“传文件、等确认”处理速度上界就约 388 KiB/s，尚未算 SD 读取、设备发送和网络耗时。

**此数值不是实机吞吐量，也不是所有场景的上限。** 4 MiB 文件把同样提交开销分摊到更多数据上，受影响小得多；正式云端如果有不同实现，也不能套用此结论。

建议：音频、文件索引及幂等状态仍需可靠保存后才 ACK；统计报告从 ACK 的必要路径移出，使用合并更新、后台写入。内存中保留累计计数与有界近期记录，历史明细另行查询，不在每次提交时序列化全部历史。不能简单把大文件同步写入移到另一个主线程定时器就认为阻塞已经消失。

复现源码及结果：`tmp/sd-chain-audit-20261021/report-load.js`、`report-load-result.json`。

## 下一步顺序及验收

1. 修正确认失败后的清理入口，加入确认写入／关闭失败和重启恢复回归。
2. 同步修正采集与上传的长时间运行判断，覆盖 2³¹ ms、2³² ms、重连及旧文件分类。
3. 移出网关 ACK 路径中的历史报告写入，在相同 30,000 条记录条件下比较修改前后数据。
4. 实机分别测已结束会议的 4 MiB 文件、监控积压小文件，以及实时监控与历史补传并行；按新增确认字节除以完整耗时计算速度，另记录断线、麦克风丢帧、最小堆、看门狗及复位。
