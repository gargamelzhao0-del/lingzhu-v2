# AU03 音频重复初始化边界修复

## 结论与范围

本轮继续 W05 音频资源所有权。Wi-Fi 间歇认证/关联失败按用户要求暂缓，不标为已解决；UI 提帧、SD 提速、正常 no_speech 均不在本轮范围。

AU03 旧行为已通过实际生产函数故障注入确认：对活 MIC 对象重复 init 会在 owner 拒绝前清空字段；复用活 channel lease 作为 acquire 输出会丢失 token。未发现正常业务必然重复初始化的路径，也没有实机故障证明用户此前异常由此引起。属于 API 异常调用边界的真实风险，不能描述为已发生的常规 MIC 泄漏。

## 修复

- MIC：把对象清零移入 acquire_owner，在全局 owner 锁内确认空闲后执行。重复初始化、另一 owner 竞争、锁超时均不改变调用方对象；不读取未初始化对象字段来判断是否 busy。
- channel lease：明确先零初始化、只移动活租约的契约。acquire 在改写租约或 handle 之前拒绝非零 token；同通道和跨通道重用均保留原资源。
- 调用点检查：会议、监控、普通对话、唤醒、离线采集、AEC 诊断的局部 MIC 均零初始化；speaker 初始化会清零实例；板级自检和 codec 临时租约零初始化；主程序三处 diagnostic owner 均为 `{0}`。
- 不支持同时对同一对象执行 init/deinit；调用者仍须串行管理生命周期。离线交接保留现有 move 语义。

成功路径仍执行相同板级初始化和通道获取，不改变协议、任务优先级、采样、播放、发送算法；无新增动态分配。

## 验证与证明边界

1. test-mic-init-owner.py 提取生产 acquire_owner/release_owner 和 init 的准入前缀：验证重复同 owner、不同 owner、独立实例竞争、锁超时、释放和重新初始化。旧的 clear-before-admission 变异被拒绝；硬件初始化部分不在这个单测范围。
2. audit-audio-teardown.py 使用实际板级 acquire/release、MIC/speaker deinit：补充租约重复申请不破坏原 owner，并验证原租约可以释放；原 AU01/AU02 部分关闭、跨代重试、引用容量及回绕场景保留。5 个变异必须失败。
3. 产品、对话、音频生命周期及正式构建结果见审计目录。软件测试不等同于真实 I2S 故障注入或 72 小时稳定性验收。

## AU04/AU05 复核进度

- AU04：destroy_owned 移交失败仍保留指针，而调用端部分忽略返回值；队列 1 个指针与 sender 单例限制仍成立。未证明正常唯一 owner 会遇到队列满。本轮不重构 reaper，不把假设当作已发生泄漏；后续须注入移交拒绝和重复清理并验证调用方责任。
- AU05：reaper 的关闭与 90 秒兜底仍受 heartbeat_healthy 约束。健康心跳不证明本地 sender 有进度，条件风险仍在。后续需生产循环故障注入和 epoch 隔离测试，再决定恢复策略；本轮不增加可能误断线的超时。
