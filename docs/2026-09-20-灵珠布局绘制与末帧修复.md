# 灵珠布局绘制与末帧修复

## 证据与判断边界

用户日志 `2fac4d23-cc07-4503-8987-bfb70dfc753c/已粘贴的文本.txt` 中，同级切页约 9.5～14.9 FPS；12 次有效详情动画均只有 2～4 帧，耗时 225～305 ms。46.289 秒窗口中，绘制及其他调度占 80.6%，缓存合成占 5.6%，显示资源等待占 13.8%。继续单独优化缓存 memcpy 无法消除主要卡顿。

此次代码追踪确认并修复下列两条低效路径。它们的存在及消除可以在主机上复现；各自占实机耗时的比例、修改后的实机 FPS，仍需新固件日志确认，不能由回调次数推算。

## 1. 透明布局节点仍执行通用绘制

`make_reveal_clip()`、抽屉根节点、页面根节点和 surface 都用于布局及裁剪，本身没有背景、边框、滚动条等可见内容。但它们是普通 `lv_obj`，每个刷新分块仍会进入默认 `lv_obj_draw()`：解析矩形、模糊和滚动条等样式。对象和样式位于项目的 PSRAM 优先分配器中。内容树隐藏、改用缓存后，这些外围布局节点仍存在。

修复：为这些明确的纯布局节点添加 `LV_EVENT_PREPROCESS` 回调，跳过 `DRAW_MAIN`、`DRAW_MAIN_END`、`DRAW_POST` 的默认绘制；保留 LVGL 的几何裁剪、子节点遍历、透明度传播及非绘制事件。背景节点仍执行原有黑色背景绘制回调。没有修改通用 LVGL 控件行为。

实际生产控件的主机追踪：测试版缓存同级切页和缓存详情滑动的一次整屏刷新，进入默认绘制的 `DRAW_MAIN` 回调由 52 次降为 16 次；关闭测试页时为 12 次。该数字是回调次数，不是 FPS，也不是绘图任务总数。稳态页面与上一交付版本逐像素一致。

## 2. 动画结束早于末帧绘制，缓存提前退出

原 `page_transition_completed()`、`reveal_completed()`、`sheet_completed()` 在动画完成回调中立即退出缓存并恢复真实控件树。LVGL 尚未处理末帧的刷新区域，此时恢复真实树，会使末帧重新绘制文字和卡片。详情页取消/复位坐标还会追加失效区域。

修复：缓存动画完成后先登记待交接状态；末帧继续走缓存路径，直到 `LV_EVENT_REFR_READY` 再恢复真实控件。交接时暂停无效区域提交，只对分页选择状态或动画期间发生变化的数据补刷。这里的“已刷新”指 LVGL 完成该帧绘制和 flush 提交，最后一个异步显示任务仍由原显示管线管理。

关闭、反向切换和销毁会清理待交接状态；缓存不可用时保留原即时切换行为。未绕过显示管线，没有新增整屏缓存或提高任务优先级。

## 新增诊断

`ui sw draw` 按填充、边框、文字、图像、图层、矩形蒙版、其他绘制任务记录累计耗时、任务数及最大单任务耗时，同时明确打印 `buffers=internal/none` 等绘图缓冲位置。

计时仅在 ESP 平台、性能日志启用且 LVGL 无 OS 绘制线程的现有配置中启用，热路径不分配内存、不输出逐任务日志。计时值包括任务运行期间的抢占等待，且可能包含本窗口缓存预热的绘制，不能直接当作纯 CPU 时间，也不能与 `ui stages` 各项简单相加。

`lvgl_internal=0` 只表示 LVGL 自定义分配器的内部内存用量；它不代表绘图缓冲位于 PSRAM。原日志已经显示第二块内部绘图缓冲因内存余量不足而释放，本轮保留该保护机制。
