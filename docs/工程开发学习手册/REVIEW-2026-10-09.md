复核日期：2026-10-09。目标是完善知栈中的 Nuwax AI Partner／灵珠开发实录。依据为本机固件工作树、30 章现有教材、相关协议与故障记录，以及知栈的导入、校验和更新实现。本文不是设备验收报告，也没有逐行审计全部第三方库。

## 一、结论与本轮修订

这份资料已经覆盖产品主要技术链路，适合作为有一定 C/RTOS 基础的工程导读。它的价值在于记录真实资源交接、故障证据和适用边界；不足在于章节普遍偏重概念与入口说明，初学者仍需要更多完整推导、源码阅读步骤、实验输入和可判定的结果。继续完善应围绕真实链路展开，避免用通用概念堆长篇幅。

本轮先完成基线修订和一个深入教学样板：

- 第 00、03 章和目录对齐默认版本 7.0.113、发布序列 7000113。

- 重新生成知栈内置正文和附件，使阅读内容与其引用源码一致。手机安装包与服务端发布不属于本轮复核交付。

## 三、全工程应该怎样理解

灵珠是运行在 ESP32-S3 / ESP-IDF / FreeRTOS 上的语音终端；知栈是承载教材的 Android/Web 应用。两者的版本、发布链和测试结果需要分别管理。本固件不是嵌入式 Linux 系统，不能把 Linux 的进程隔离、驱动模型或 systemd 服务直接套在 FreeRTOS 任务上。

### 3.1 从底层到产品的责任链

| 层次 | 实际入口 | 教材必须讲清的关键问题 |
| --- | --- | --- |
| 启动与电源 | bootloader power hold、`board/nuwax_power_ctrl.c` | 应用运行之前怎样保持供电；正常关机与突然掉电的差别 |
| 板级驱动 | 引脚头文件、I²C manager、音频板、SD、display | 总线、地址、时钟、超时、输出有效性和共享访问 |
| 运行资源 | mic owner、任务/队列、内存策略 | 谁拥有缓冲和设备，何时可转交，何时可释放 |
| 声音输入 | `mic_input.c`、`wake_word_detector.c`、conversation | TDM 槽位到 PCM，统计到候选，候选到事件 |
| 业务编排 | `nuwax_ai_partner_main.c`、audio_modes | 当前模式、连接代次、请求身份和停止优先级 |
| 网络输出 | `audio_uplink.c`、`session_protocol.c`、`ws_transport.c` | 实时期限、半帧失败、ACK 归属和重连 |
| 本地保存 | `offline_audio_spool.c` 及 replay 实现文件 | 队列、writer、封存、恢复、补传、确认后删除 |
| 声音输出 | playback、jitter、terminal guard | BEGIN、首 PCM、首 I²S、END、排空是不同事件 |
| 用户界面 | state bridge、LVGL port、drawer、emotion | 业务快照如何变成画面，旧合成任务怎样退休 |
| 设备交付 | provisioning、NVS、OTA、diagnostics | 绑定提交、回滚、产物身份和证据留存 |

源码导航见 [第 02 章](02-architecture.md) 与 [第 25 章](25-reference.md)。目录只是导航；构建列表、有效配置和生产调用共同决定实际启用能力。

### 3.2 需要串起来的六条完整链路

**唤醒到欢迎音**：I²S 采样 → capture 队列 → MultiNet 候选 → 近期声学检查 → 唤醒事件 → 主控请求与轮次归属 → 下行首 PCM → 播放输出 → 播放结束后倾听。提高阈值只改变其中的准入部分，不直接缩短云端等待。第 10 章本轮已补完整计算样板。

**会议跨断网**：模式接受 → 麦克风 owner → 连续音频 → 网络失效后本地保存 → 恢复时发起新的控制 request_id → 延续原 audio_session_id → 实时流与历史归档按身份、采集序号/时间归并。同一逻辑会话的条件是原模式仍存续；主动停止、八小时上限退出后再开属于新的开启，不能无条件沿用旧会话。在线 listen 序号与归档采集序号也不能混作同一条计数器。

**监控暂停后的保存**：云端上传暂停不等于用户退出监控；本地仍依语音确认、preroll 和尾部保留形成语音段。它与会议连续录音不同，不能用文件时长直接等同于离线墙钟时长。用户可见 SD 状态仍是有意暂缓的需求。

**补传完整性**：`.open` 恢复/封存 → `.ready` → begin → 分片与偏移确认 → commit ACK → 删除。socket 写成功、分片 ACK、云端完整持久化、设备删除是不同边界。正式 v1 与测试 v2 的窗口和 ACK 策略不同；“500 KiB/s”应按完整会话提交口径评估，不能从测试网关瞬时速度推导正式云端能力。

**配网与绑定**：BLE 安全会话 → APP 获取并下发绑定材料 → pending NVS → Wi-Fi GOT_IP → active 配置提交 → WebSocket 鉴权。Wi-Fi 可用与密钥有效是两层状态；pending 已持久化，不能教材简写为“仅内存暂存”。自动 NVS 恢复有擦除默认分区的分支，也不能承诺任何异常下凭据永不丢失。

**充电与 OTA 界面**：电流/FC 的有效证据经电池服务形成充电快照，再驱动图标与 GPIO18 策略；20 mA 是显示判据，不是充电器电流设置。OTA 接管则要同步退休菜单动画和 flush 合成缓存；新建顶层对象不足以避免之后的缓存覆盖。两类案例都体现“显示异常要追到数据和资源来源”。

## 四、已有内容的价值和不足

应保留三类内容：单位和容量的准确口径；owner/epoch/commit 等可靠性边界；真实故障中对确认事实、推断和缺失证据的区分。例如 RNNT 静态缺陷修复不等于证明所有历史重启消失，后来的 Cache/MMU 现场也不能自动归为同一根因。这些是工程经验的核心。

当前需要补足的不是更多术语，而是中间推导。比如读者知道“队列要有界”，仍可能不知道如何把 20 ms、128 帧和 SD 抖动预算联系起来；知道“重连用 epoch”，仍可能不会画出迟到 ACK 被拒绝的具体时间线；知道“充电器与电量计不同”，仍需要一组寄存器、有效性和 UI 输出的逐步演算。

源码附件解决“能打开代码”，不等于解决“能读懂代码”。每条附件入口应配一个搜索符号、一组输入、一条正常路径、一条失败路径和可观察结果。无需把几万行主控直接塞进手机正文。

## 六、适合知栈的学习组织

建议将现有章节组成六个学习阶段。阶段顺序补足前置知识，不必为重排而改变文章 ID：

1. **认清工程与硬件**：00、01、02、04、05、26。成果：画出硬件链路并解释 ready 与 degraded。
2. **掌握运行与数据**：06、07、08、09。成果：算清 PCM、帧和队列预算，解释所有权交接。
3. **完成一次交互**：10、11、12、18。成果：追踪从唤醒到首声、结束倾听的完整时间线。
4. **保存并恢复音频**：13、14、15、16。成果：验证同会话恢复、归档完整性与真实吞吐。
5. **实现可恢复交付**：17、27、28、19、03。成果：解释绑定/更新各提交点，识别错误产物。
6. **独立排障与维护**：20、21、22、23、24、25、29。成果：提交一份可复核故障分析和验证记录。

知栈已有阶段路径组件，但当前配置与界面条件面向 course 类资料；开发实录是 project 类，不能仅添加一份 JSON 就声称完成界面接入。接入时需要保留目录、收藏、笔记、进度和内部跳转，并检查手机小屏表现。当前轮次未改这些界面条件。

每个深入章节宜包含：学习目标与前置知识；问题或现象；原理推导；源码入口与真实参数；一个正常例子和一个边界例子；实验输入与预期输出；自测答案；版本和证据范围。篇幅由问题复杂度决定，不按字数验收。

## 七、质量和更新门槛

**事实门槛**：当前默认行为必须能追到生产调用和有效配置。历史速度、重启、误唤醒结果应绑定原测试，不得换个日期后当作新版本结果。公式必须给单位；合成样本显式标注；外部云端不能从设备代码反推出已部署能力。

**教学门槛**：学员应能独立复算、执行、观察、解释失败。新增目标/练习/答案几个词只能通过结构筛查，不能证明教学优秀；不能为了修检查而批量添加同一句空泛练习。

**资料门槛**：正文引用与打包附件同步，校验实际字节摘要，目录不能冒充文件。文章 ID `handbook-00`～`handbook-29` 保持稳定，资料版号与应用版号分开。知栈现有更新流程对用户已编辑文章保留原文并处理新版副本，附件变化也有独立身份，更新时应跑相关回归。

**展示门槛**：手机正文优先短段落、带说明的图和有限宽度的例子。协议宽表可以横向查看，但应先给能直接读懂的关键字段说明。动态图仅用于解释队列、水位或状态变化，不给长文增加无关动画。

**发布门槛**：源教材维护检查 → 知栈导入 → 引用/摘要校验 → 本地编辑保护回归 → 手机阅读检查 → 应用发布。只改电脑 `public/seed` 不会更新已安装 APK 内的资源，本轮不将源码同步描述成手机端已经更新。

## 八、验证边界与下一批顺序

本轮验证记录见 [修订后记录](evidence/review-2026-10-09-after.json) 和 [教材维护检查](evidence/document-validation.json)。修订前后均不涉及重新烧录、实际八小时录音、云端部署或手机安装验收。文中教学策略输入的主机执行不等于声学准确率测试。

下一批应先扩展第 07、08、13～16 章：这些章节既承载本项目最有辨识度的经验，也有明确的算例和可验证协议边界。之后完善配网、NVS、OTA、电池与 UI，最后统一日志案例、实验入口和阶段路径。C++／嵌入式 Linux 课程可引用这些实践作概念对照，但须明确 FreeRTOS 与 Linux 的机制差异。
