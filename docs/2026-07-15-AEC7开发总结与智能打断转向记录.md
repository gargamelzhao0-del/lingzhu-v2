## 2. 最终业务目标

原 AEC 开发目标：

> 设备播报期间用户说话，在保证用户人声清晰、完整、音量正常的前提下，尽可能削减或消除设备声及其他杂音，使上传云端的音频尽可能接近干净用户音频。

开发后期确认的优先级是：

1. 不缺字，尤其不能丢失句首。
2. 人声音量连续、稳定，不得忽大忽小或出现异常静音。
3. 人声频谱和听感尽量自然，不因 AEC 产生电音、尖锐感或明显失真。
4. 在前三项成立的前提下，再尽可能压低设备声。

不能为了更低的设备声，把真人也当作回声压低。S22 的听感证明“设备声很低但句首和大部分人声被压低”不满足目标；S48 的反馈证明“人声完整但设备声较大”更接近正确优先级，但仍未完成。

## 4. 硬件和音频格式

目标设备为 ESP32-S3，当前板级路径是 ESP-VOCAT V1.0。

采集侧主要事实：

- ES7210 以 4-slot TDM 输出。
- slot0：MIC1，当前主上传麦克风。
- slot1：MIC2，主要用于空间差分、平衡度和真人提示。
- slot2：硬件播放参考候选，但当前有效配置未将其作为 Live AEC 主参考。
- slot3：未使用。
- MIC 模拟增益：30 dB。
- MIC1 数字输入增益：`32768`，即 1.0 倍。
- 采样率：16 kHz。
- 单帧：16 ms，即 256 个 PCM16 样本。
- 当前上行：单声道 PCM16。

播放侧主要事实：

- 云端下发 PCM 音频帧。
- `speaker_playback` 维护播放队列、播放 generation、当前 turn/playback ID。
- 软件播放参考由实际下发或播放数据写入软件参考环形缓冲。
- 采集线程按连续参考 cursor 读取延迟后的软件参考。

## 5. 当前音频线程和数据流

### 5.1 播放路径

主要文件：

- `main/conversation/speaker_playback.c`
- `main/p3_software_ref.c`
- `main/speaker_output.c`

主要流程：

1. 网关发送 `playback_begin` 和二进制 PCM 帧。
2. `speaker_playback` 记录 `turn_id`、`playback_id` 和 playback generation。
3. PCM 帧进入播放队列。
4. 播放任务输出到扬声器，同时维护供 AEC 使用的软件参考。
5. 播放结束或取消时清理当前播放上下文。

当前取消能力：

- `nuwax_speaker_playback_cancel_now()` 会清空播放队列、增加 generation、停止输出并建立旧流丢弃窗口。
- `nuwax_speaker_playback_fade_cancel()` 已存在，但通过每隔约 40 ms 修改硬件音量并同步等待，调用期间会阻塞当前任务，不适合直接从音频采集线程使用。
- 智能打断新增 `nuwax_speaker_playback_request_fade_cancel()`：命令线程只登记 200 ms 请求，扬声器任务对实际 PCM 做线性包络；截止时间到、旧流 END 或包络完成后再调用立即取消，不修改用户持久音量。

### 5.2 采集路径

主要文件：

- `main/nuwax_ai_partner_main.c`
- `main/mic_input.c`
- `main/conversation/audio_uplink.c`

主要流程：

1. `rt_capture_task` 独立从 ES7210 读取 MIC1、MIC2、slot2 参考和软件参考快照。
2. 实时采集队列深度为 64 帧，约 1.024 秒。
3. DSP 任务从队列读取每个 16 ms 帧。
4. 计算双麦、MIC/ref 相关性和播放状态特征。
5. 设置 Live AEC 人声保护提示。
6. 执行 Live AEC。
7. 执行 Audio Cleaner。
8. 在播放中先写入预卷；真人确认后才启动云端上行。
9. `audio_uplink` 以每批 4 帧、32 批队列异步发送。

采集队列和上行队列分离是后期的重要修复，避免 WebSocket 发送、预卷补发或 DSP 计算直接阻塞 I2S 读取。

### 5.3 播放中预监听

TTS 开始时，`speaker_callback_on_tts_start()` 调用 `arm_during_playback_capture("tts_start")`。

因此设备在播报时并不是等用户按键后才打开麦克风，而是持续执行：

- 采集 MIC1/MIC2。
- 获取软件参考。
- 执行 AEC 和人声判别。
- 保存预卷。
- 在确认真人前不上传普通会话音频。

预卷容量为 256 帧：

```text
256 帧 * 16 ms = 4096 ms
```

每个预卷帧保存：

- 最终待上传样本。
- Cleaner 前样本。
- human rescue 源。
- reference 样本。
- Cleaner 的状态快照。
- playback 标志、人声标志和 capture sequence。

当前代码在确认后会修复候选起点附近的人声预卷，但发送阶段仍会发送整个 ring 中的全部帧。这是智能打断阶段需要修改的内容。

## 6. 当前 Live AEC 配置

| 固定参考延迟 | 840 samples | 16 kHz 下约 52.5 ms |

| Near-end blend | 开启 | 检测近端时恢复部分原始成分 |

## 7. 当前 Audio Cleaner 配置

当前 Cleaner 仍开启高通和 100 Hz notch，但播放期多数衰减参数已经回到 unity：

| 配置 | 当前值 | 结论 |
| --- | ---: | --- |
| Quiet zero | 关闭 | 不再把安静帧直接清零 |
| Quiet attenuation | 32768 | 1.0 倍 |
| Playback quiet attenuation | 32768 | 1.0 倍 |
| Playback unprotected attenuation | 32768 | 1.0 倍 |
| Playback impulse attenuation | 32768 | 1.0 倍 |
| Protected gain/AGC | 关闭 | 不再主动抬高受保护人声 |
| Protected limiter | 开启，峰值 24000 | 仅防止极高峰值削波 |

因此当前听到的人声忽大忽小，不能简单归因于 Cleaner 的固定增益。更主要的变化来自：

- 人声 seed/anchor 时有时无。
- Live AEC、human rescue、dual restore 和残余消除之间的路径切换。
- 播放参考相关性和软件参考对齐变化。
- 播放停止后仍存在的 AEC hangover。

## 8. 播放状态和 AEC 生命周期

当前 `playback_active` 不只等于“扬声器正在写数据”。它由以下状态组合得到：

- `speaker_pending`。
- playback session gap。
- during-playback AEC hangover。

关键时间：

- playback session gap：1500 ms。
- playback hangover：700 ms。

当 `playback_active=false` 时，`live_aec_process_internal()` 会清理 pending/FIR session 状态并直接返回，不改写当前 MIC1 样本。因此非播放状态本身已经具备人声保真旁路。

智能打断后不应继续维持 700 ms 的完整播放处理。建议在本地静音后只保留约 80 至 160 ms 的扬声器尾响处理，然后切到非播放旁路。

## 9. 人声检测和保护现状

当前播放中人声判别不是单一 VAD，而是组合以下证据：

- MIC1 原始能量和峰值。
- MIC2 能量和峰值。
- 双麦差分能量、差分峰值和 level balance。
- MIC/ref 相关性。
- AEC 后输出能量。
- echo veto。
- spatial anchor、low-level anchor、voice anchor、exceptional anchor。
- provisional、fast、confirmed 三层人声保护。
- seed 和多个 hangover。

主要正向成果：

- 能在检测到真人迹象时冻结或降低 AEC 自适应，减少把真人学进回声模型。
- 能保存候选起点 sequence，并回修候选前后的预卷。
- S48 等轮次已经出现“人声完整、不缺字”的主观结果。

主要缺陷：

- `NUWAX_PLAYBACK_HUMAN_SEED_HANGOVER_FRAMES=256`，约 4.096 秒。
- weak continuity hangover 为 80 帧，约 1.28 秒。
- candidate 最大间隙为 48 帧，约 768 ms。
- 一次错误空间 anchor 可能让设备声在数秒内持续继承“真人上下文”。
- 上传 VAD 的 dual candidate 路径可以依赖 seed/hangover，不要求当前帧重新满足有效人声能量。

这解释了为什么当前判别逻辑适合做“保护提示”，但还不能直接作为自动打断授权。

### 11.9 智能打断淡出/采集保留 S2 和 S3

S2 请求和日志：

```text
barge_fade_preserve_faronly_20260715_s2
runtime-logs/nuwax7-barge-fade-preserve-faronly-s2-20260715-172258.log
```

S2 通过直接下发 `stop_playback mode=barge_in`，在不需要真人讲话的条件下验证控制路径：

- 设备 ACK：`stopped capture_preserved=1`。
- `speaker async PCM fade cancel armed ... fade_ms=200 samples=3200`。
- 约 200 ms 后执行实际 `speaker local stop`。
- 没有出现 `prelisten stopped by session command`。

S2 同时发现旧代码的 active drop window 只有 2500 ms；若网关没有同步 abort，极晚旧 TTS 分段可能在窗口过期后重新被接受。每个丢弃帧还会打印 INFO 并重复触发恢复回调。

最终修复：

- active stale drop window 从 2500 ms 延长到 30000 ms。
- 新的不同 `playback_id` 到达时仍可立即解除旧流窗口，不会延迟新回复。
- 丢弃日志只记录首帧、每 50 帧和 END。
- `return_to_listening_after_cancel` 只在第一帧通知；设备主回调再次检查 active `during_playback`/`barge_in` capture，禁止重建预监听覆盖当前采集。

S3 请求和日志：

```text

runtime-logs/nuwax7-barge-fade-drop-faronly-s3-20260715-172630.log
```

S3 最终结果：

- 没有出现预监听被 session command 终止。

该测试证明控制状态机和迟到旧流策略成立；因为没有真人讲话，它仍未证明“停止播报后真人音频持续无缺字上传”。

## 12. 历史开发阶段总结

### 12.1 2026-07-07 至 2026-07-08：建立真实全双工采集基线

主要工作：

- 建立播放中验收采集和 WAV 保存。
- 比较无人/真人双讲。
- 试验 delay 1280、1600 等早期参考延迟。
- 区分 ref inactive、dual hint、hint hangover。
- 将双麦差异用于近端提示，而不是直接混合两路麦克风。

主要教训：

- 单看 VAD 无法区分设备声和真人。
- 参考存在不等于参考对齐。
- 无人和真人必须成对测试，否则无法识别“设备声降低是因为整条音频被压低”。

### 12.2 2026-07-08 至 2026-07-09：Near-end blend、dual restore 和 Cleaner

主要工作：

- 引入或调整 near-end raw mix。
- 增加 dual restore 和空间 restore guard。
- 收紧 Cleaner 的播放期 gate。
- 试验 protected gain、limiter 和 human-first 参数。
- 将多数主动衰减参数逐步恢复到 unity。

主要教训：

- protected gain 会放大设备残余或造成音量跳变。
- 仅靠输出电平无法判断被 AEC 削弱的人声。
- 设备声和真人同时存在时，固定增益或固定阈值会在两者之间做错误取舍。

### 12.3 2026-07-09 至 2026-07-10：实时队列、软件参考和 echo veto

主要工作：

- 将实时 I2S 采集与网络/DSP 解耦。
- 修复 reference snapshot、连续 cursor 和 external-ref 切换导致的 FIFO 问题。
- 区分给 AEC 的参考和给 Cleaner/检测器的提示。
- 增加 echo veto、continuity 和 onset guard。

主要教训：

- 软件参考 cursor 必须连续，不能每帧重新从“最新位置”读取。
- external ref 模式变化会破坏 AEC FIFO 连续性。
- echo veto 可以降低设备声误保护，但过强时同样会误伤真人句首。

### 12.4 2026-07-11：固定 AEC 路径和 delay sweep

主要工作：

- 在固定实现上进行 far-only 与 double-talk 对比。
- 扫描 delay 240、360、480、600、720、840、960、1080 samples。
- 最终选择 840 samples 作为有效构建和板级默认延迟。

结论：

- 840 samples 是当前硬件、软件参考链路和分帧条件下的工程基线。
- 该值不是不可改变的物理常数；播放驱动、缓冲深度或采样链路改变后必须重测。

### 12.5 2026-07-13：人声优先和统一增益

主要工作：

- 从 S22 的设备声抑制结果出发，修复人声句首被压低。
- 试验 dual restore、provisional gate、continuity、far gate、diff 特征。
- 关闭或回退会造成音量跳变的增益路径。
- 形成 S35 “设备声可接受但人声忽大忽小”的阶段性结果。

主要教训：

- 保护建立得晚会丢句首。
- 保护建立得早、保持得长会把设备声当真人保护。
- 单纯增加 hangover 能改善字间断裂，但会显著提高 far-only 误触风险。

### 12.6 2026-07-13 至 2026-07-15：预卷修复、human rescue、FIR 和 ref epoch

主要工作：

- 增加预卷中的 preclean、rescue source、ref 和 Cleaner state。
- 候选确认后回修历史帧，保护检测前已被削弱的句首。
- 引入两阶段 anchor、seed refresh、voice anchor。
- 增加 post-blend residual。
- 训练 FIR human rescue，并试验不同 lag、warmup、validation span。
- 处理软件参考 generation、cursor reanchor、epoch validation 和 retrain。
- 最终在 S83 使用真实 Nuwax 分段回复验证。

主要教训：

- 回修预卷可以改善句首，但不能解决 detector 本身的真假人声分类。
- FIR rescue 的训练、验证和 ref cursor 必须在播放 session 边界上保持一致。
- 保护机制越复杂，状态之间的长 hangover 越容易制造 far-only 假阳性。

## 13. 已经证明无效或风险较高的方向

以下方案不应在没有新证据时重复：

1. 直接提高 AEC 强度以追求更低设备声。
   结果通常是人声同时被削弱，尤其是句首。

2. 用单一能量 VAD 直接授权打断。
   设备播报本身会进入麦克风，far-only 可满足能量条件。

3. 用一次空间 anchor 加很长 hangover 保持真人状态。
   S80 已证明会在低电平设备残余上错误确认。

4. 对受保护帧做自动增益。
   容易导致忽大忽小，并可能放大设备残余。

5. 在采集线程同步执行 `fade_cancel()`。
   会阻塞采集或命令处理，增加丢帧概率。
   当前智能打断路径已经改用扬声器任务内的异步 PCM fade；旧 P6 手工路径仍保留原同步 API，恢复时不要混用。

6. 确认后发送完整 4.096 秒预卷。
   会把大量旧 TTS 送入 ASR，并瞬时挤压上行队列。

7. 直接开启网关 `interrupt.enabled`。
   当前 `listen start -> cancelTurn -> stop_playback` 会覆盖 `s_prelisten.capture_active`，导致正在上传的真人整句被截断。

## 14. 当前上行可靠性

`audio_uplink` 的基础机制较完整：

- 独立发送任务。
- 每批 4 帧。
- 32 批发送队列。
- 普通队列背压等待 80 ms。
- final slot 等待 180 ms。
- finish 超时和发送失败会显式报错。
- queue full 会增加 `dropped_frames` 和 `queue_full_events`，不是静默丢弃。

S83 retry 已出现：

```text

sent=1814
dropped=0
queue_full=0
```

当前不具备跨 WebSocket 重连的 ACK/replay。如果采集期间连接断开，无法保证重连后继续同一音频会话。这属于第二阶段可靠性问题，不应阻塞首版智能打断。

## 15. 当前网关换轮能力

网关原有基础：

- 每个 text turn 使用 `AbortController`。
- Nuwax API 请求接收 abort signal。
- streaming TTS 和 prepared TTS 发送循环检查 signal 和 `isCurrentTurn()`。
- `cancelTurn()` 会使旧 turn 失效、停止 provider 工作并下发 `stop_playback`。
- 迟到的旧 Nuwax/PC/TTS 响应大多会被 stale 检查丢弃。
- `playback_end` 按 playback ID 结束对应播放，不会直接清除不同 ID 的新播放。

2026-07-15 已补齐的智能打断基础：

- 正式支持 `barge_in` 的 `candidate`、`confirmed`、`rejected` 三种消息。
- 每个事件绑定 `event_id`、`parent_turn_id`、`playback_id`、`audio_session_id`。
- 已确认事件重复到达时返回第一次产生的同一个 `new_turn_id`，不重复取消旧轮。
- 同一 `event_id` 携带不同 turn/playback/audio session 时返回 `event_context_mismatch`。
- confirmed 只允许当前 parent turn、当前 playback 和当前 uplink audio session。
- `cancelTurn(..., {sendIdle:false})` 停止旧播放时不再强制设备进入 idle。
- `listen start` 的 `barge_in`/`during_playback` 模式不再隐式取消旧 turn。
- 相同 `audio_session_id` 的重复 start 幂等成功；不同 ID 不再静默覆盖当前会话。
- `listen stop` 校验 `audio_session_id`；迟到的旧 stop 不能结束新会话。

仍未完成：

- 自动取消开关尚未开放，设备目前只发 candidate。
- 云端流式 ASR 证据虽已接入影子判定，但尚无真实流式 ASR + 设备板级统计。
- 智能打断路径已接入异步 PCM 包络，但尚未经过板级听感和时延验收。
- WebSocket 断线后仍不能续传同一个 audio session。

当前网关配置仍为：

```text
interrupt.enabled = false
interrupt.level = 0
```

当前设备测试网关仍为：

```text
ws://192.168.31.180:8799/api/device/ws
```

## 16. 为什么转向智能打断

全程双讲 AEC 要同时解决：

- 设备扬声器到两个麦克风的非线性声学路径。
- 动态播放音量和设备结构反射。
- 软件参考延迟变化。
- 人声与设备声频谱重叠。
- 近端人声保护和残余回声消除之间的冲突。

现有代码已经证明可以把设备声压低，也可以把人声保护完整，但两项同时达到目标仍需要大量声学调参。

智能打断把困难问题限制在用户开口后的短窗口：

1. 播放期间持续采集和保存预卷。
2. 检测到候选真人后先降低设备音量。
3. 本地高置信度或云端流式 ASR 确认后，取消旧轮并淡出设备声。
4. 静音后快速退出 AEC，主体句子走人声保真路径。
5. 完成 ASR 后交给 Nuwax 智能体产生新回复。

这样第一段约几百毫秒仍需要 AEC，但用户句子的主体不再长期承受双讲 AEC 的误伤。

## 17. 智能打断目标状态机

建议建立独立 `barge_in_controller`：

```text
IDLE
  -> MONITORING
  -> CANDIDATE
  -> CONFIRMED
  -> FADING_AND_UPLOADING
  -> CAPTURING_NEW_TURN
  -> COMMITTING_ASR
  -> IDLE
```

每个事件必须锁存：

- `barge_event_id`
- `parent_turn_id`
- `playback_id`
- `audio_session_id`
- `candidate_onset_sequence`
- `confirmed_sequence`
- detector evidence 和 confidence
- 当前 generation

控制原则：

- `stop_playback` 只控制播放，不得结束当前 barge-in capture。
- capture 的生命周期由 barge-in controller 或用户/VAD endpoint 控制。
- 同一个 `barge_event_id` 重复到达必须返回同一结果。
- 旧 turn 的任何迟到状态、TTS 或 playback end 不得覆盖新 capture。
- 新回复必须绑定新 turn generation。

## 18. 建议的两级确认策略

### 18.1 Candidate

设备连续 160 至 300 ms 满足以下组合时进入 candidate：

- 当前 MIC1 或 AEC 后能量达到最低语音阈值。
- 与参考的相关性不足以解释为纯设备回声，或存在稳定空间差异。
- 双麦差分/平衡特征在滑窗中持续成立。
- 不是单个冲击帧。

进入 candidate 后：

- 保存 onset sequence。
- 只补 onset 前约 300 ms 预卷。
- 开始或继续流式上行。
- 设备声异步降低到约 30% 至 50%。
- 不立即取消旧轮，除非达到高置信度快速路径。

### 18.2 Confirmed

满足任一条件后确认：

- 本地高置信度真人证据持续成立。
- 云端流式 ASR 产生有效非空 partial，并通过基础语音/文本检查。

确认后：

- 幂等 abort 旧 Nuwax/TTS turn。
- 设备端在 160 至 240 ms 内淡出到零。
- 丢弃旧播放队列。
- 保持同一个 audio session 连续上传。
- 静音后 80 至 160 ms 退出 AEC hangover。

若 candidate 被拒绝：

- 平滑恢复设备音量。
- 不建立新 turn。
- 保存 shadow 诊断供后续调参。

## 19. 定向预卷实现

当前代码使用以下序列依据：

- VAD 连续语音窗口首帧 `vad_candidate_start_sequence`。
- 人声历史回修起点 `playback_human_candidate_start_sequence` 和 `repair_actual_start_sequence`。
- 每个采集帧的连续 `capture_sequence`。

`send_auto_followup_preroll()` 已改为按 sequence 发送：

```text
send_start = candidate_onset_sequence - 约 19 帧
send_end   = 确认前最后一个已存储帧
```

19 帧约等于 304 ms。

当前参数：

- `NUWAX_BARGE_IN_PREROLL_LEAD_FRAMES=19`，即候选前 304 ms。
- 180 ms VAD 确认在 16 ms 帧下向上取整为 12 帧。
- 正常连续条件下通常发送 31 帧，约 496 ms，而不是原来的 256 帧/4.096 秒。
- 找不到 onset 时，最多回退发送最近 31 帧。

已经落实的连续性约束：

- 第一帧带 START。
- sequence 保持单调连续，不重新编号。
- 预卷尾部与实时第一帧之间 gap=0、duplicate=0。
- 补发帧数应显著小于 256，避免占满发送队列。
- ASR 不再接收确认前数秒的纯 TTS 残余。
- 环形缓冲中若存在 sequence gap，只保留能连续连接实时帧的尾部。
- 若预卷最后一帧不能满足 `last_sequence + 1 == live_sequence`，整段预卷跳过，当前实时帧直接带 START，禁止制造人为 gap/duplicate。
- `uint32_t` sequence 回绕已经由主机测试覆盖。

## 22. 量化验收标准

首版智能打断至少满足：

1. far-only 连续 30 分钟：自动取消次数为 0。
2. 20 次真人打断：命中至少 19 次。
3. 人声句首：20 次中至少 19 次无可听缺字。
4. 有声段内无超过 32 ms 的异常数字静音或非自然断流。
5. 上传 `capture sequence gap=0`。
6. `queued_frames=sent_frames`。
7. `dropped_frames=0`、`queue_full_events=0`。
8. 确认后 300 ms 内不再播放旧 turn 音频。
9. 设备静音后的真人 RMS 与普通非播放录音相比尽量保持在 +/-2 dB。
10. 新 ASR 结果只触发一次新 Nuwax turn。

目标体感：

- 用户开口后立即感知设备声音下降。
- 通常 0.4 至 1.0 秒内旧播放淡出停止。
- 网络或 ASR 较慢时不超过约 1.5 秒完成确认。
- 用户完整说完后，设备基于新请求生成新回复。

### 25.4 S4 的关键失败：前级实时采集丢帧

S4 末尾日志：

```text
rt capture stopped read=1077 dropped_no_slot=0 dropped_oldest=48 ready_full=0 dropped_samples=12288 max_ready=64
I2S microphone stream done ... frames=730 queued=730 sent=730 dropped=0 queue_full=0 ... realtime=96%
```

同时出现 25 次 `capture sequence gap` 日志，累计缺口正好为 48 帧。每帧 256 samples、16 ms，因此：

```text
48 frames * 16 ms = 768 ms
48 frames * 256 samples = 12288 samples
```

根因不是网络上行队列；`audio_uplink` 的 730 帧全部发送成功。丢失发生在更前面的 `nuwax_mic_rx` 实时采集环形队列：

1. 原队列深度为 64 帧，仅能缓冲 1.024 秒。
2. DSP 主任务在真人双讲时同时执行 AEC、双麦特征、Cleaner、候选判断、预卷启动和上行打包。
3. `playback human strong` 与 `audio clean` 在若干状态下逐帧输出长串口日志；S4 内分别出现 94 行和 73 行。
4. 消费侧最终只有 96% 实时速度，队列达到 64/64 后，高优先级采集任务立即复用最老 ready slot，形成分散的 sequence gap。
5. 因为缺帧在上传打包前发生，网关 WAV 会时间压缩而不是出现等长零洞，可能造成听感断续或缺字。

这条证据修正了此前“`queued=sent` 即代表整条采集链完整”的不充分判断。后续验收必须同时检查：

```text
rtcap_drop_oldest=0
rtcap_drop_samples=0
rtcap_gap_frames=0
queued_frames=sent_frames
dropped_frames=0
```

### 25.5 修复内容

`main/nuwax_ai_partner_main.c` 已完成以下修改：

- `NUWAX_RT_CAPTURE_QUEUE_DEPTH` 从 64 增至 128，缓冲窗口从 1.024 秒增至 2.048 秒。
- free slot 暂时不可用时先阻塞 10 ms，让较低优先级 DSP 消费者释放 slot；只有一个 tick 后仍无 slot 才执行原有丢最老帧兜底。
- 增加 `backpressure_recovers/backpressure_waits` 统计，区分短暂背压恢复与真正丢帧。
- `playback human strong` 最多每 64 帧记录一次。
- 连续 limiter 诊断最多每 32 帧抽样一次，冲击等真正异常仍立即记录。
- sequence gap 日志记录累计事件和累计缺帧，只在首次、较大单次 gap 或每 16 次事件输出，避免错误日志本身继续拖慢 DSP。

### 28.1 设备端授权规则

代码现在区分“保护人声”和“有权打断”：

- 旧 separated/exceptional/low-level/voice anchor 仍可用于短时 AEC human protection，避免直接删除已有保真能力。
- 旧 anchor 不再设置 `playback_human_confirmation_anchor`，单帧播放瞬态无权启动上传或停播。
- 只有 `nuwax_barge_in_nearfield_tracker_update()` 输出的 temporal nearfield anchor 才能建立正式 human seed。
- temporal nearfield 仍要求 64 帧内至少两个合格 potential；S5 真人代表帧满足单帧特征，S5a/S6 的单次或零次反例不能确认。

候选确认后设备执行以下顺序：

```text
1. 发送 barge_in candidate，confidence_q15=28672
2. 发送 listen start，建立 barge_audio 会话
3. 发送 barge_in confirmed
4. 发送 onset 前 304 ms 定向预卷
5. 连续发送 live 音频
```

必须先建立音频会话再发 confirmed，因为网关会校验 `parent_turn_id + playback_id + audio_session_id` 都仍是当前上下文。相同 WebSocket 上消息有序，网关处理 confirmed 时会话已经存在。

### 28.2 停播与人声连续性

网关收到 confirmed 后取消旧 turn，并下发带 barge 上下文的 `stop_playback`。设备端：

- `session_dispatch_preserve_capture_on_stop_playback()` 识别 active `during_playback/barge_in` capture。
- 不取消麦克风任务，不清理预监听状态。
- `nuwax_speaker_playback_request_fade_cancel()` 在 speaker PCM 消费路径上做 200 ms 逐样本线性衰减。
- 衰减完成后取消旧 generation，30 秒 stale window 丢弃迟到的旧 TTS 帧。
- 扬声器停止后，麦克风继续采集；播放 gate 的 700 ms hangover 结束后，处理链回到非播放的人声路径。

预期体感是：真人起声后约数百毫秒内开始淡出，200 ms 内设备声降到 0；用户起声前 304 ms、淡出期间以及之后的声音保持在同一连续音频会话中。只有开头短窗口需要 AEC 处理，后续主体不再与设备声重叠。

时间跟踪器同时保存 `first_candidate_sequence`。即使第二个 potential 在 1.024 秒窗口末端才出现，定向预卷也以第一个 potential 为 onset，而不是以第二次确认后的 VAD 帧为 onset；256 帧环形缓存足以覆盖“64 帧确认窗口 + 19 帧前导 + 12 帧 VAD 确认”。这消除了旧时序中理论上可能遗漏用户最早约 0.7–1 秒的风险。

扬声器完全停止并结束 700 ms playback hangover 后，`during_playback_post_candidate` 改回 `nuwax_mic_level_is_speech()` 的普通人声阈值（当前 400/1500），不再使用较高的 900/2500 双阈值。播放存在时仍由严格 playback gate 控制，因此该调整只保护淡出后的较轻人声和句间连续性。

### 28.3 网关最终提交闸门

`finishAudioSession()` 现在对 `during_playback/barge_in` 模式执行独立提交判定：

```text
barge event 必须存在
event.state 必须为 confirmed
最终 ASR evidence 必须存在且 final=true
最终 evidence 必须 eligible=true 且 reason=new_speech
同一 event 不得已经 relayCommitted
```

任一条件不满足时：

- 记录 `bargeInAudioRelaySuppressed` 和具体原因。
- 不调用 `handleDeviceTextRequest()`。
- 不创建 Nuwax 请求，不生成自回复。
- 已停播的误确认会话完成后最多发送一次 idle，采集中途不会强制 idle。

确认通过时沿用 barge cancel 创建的 `newTurnId`，只提交一次，并记录 `relayCommittedAt/relayRequestId`。普通非 barge 音频仍保持原自动转发行为。

流式 evidence 在 event 已进入 `confirmed` 后仍继续更新，因此早期 partial confirmation 不再决定最终是否提交。最终 `echo_like` 可以否决提交。默认 echo containment 阈值由 `0.72` 收紧到 `0.60`，S6 的两个 `0.667` 假 partial 现在也不会触发云端确认。

网关协议测试已验证：

- 未验证的 barge 音频产生 0 个第二智能体请求。
- 重复 confirmed 只产生 1 个 stop command。
- candidate/confirmed 的 event、turn、playback、audio session 不匹配时拒绝。
- capture active 时 stop playback 不发送 idle。
- 最终 rejected/echo/mock evidence 不提交。
- 已提交 event 再次判定为 duplicate。
- 普通 ASR auto relay 路径保持可用。

```text

2. 下发 set_volume=70 且等待设备 ACK
```

`acceptance_capture` 是诊断音频模式，网关不会把这些音频送入 ASR 或自动转发给智能体，因此不会形成设备自回复。原始长录音、TTS 数字参考、逐段指标、拒绝原因、哈希和最终核验结果都保存在单次数据集目录；大体积数据集由 `.gitignore` 排除，不污染源码仓库。

首轮正式采集还确认了一个容量边界：当前网关每个调试音频会话最多保存 `2097152` 字节 PCM，即 16 kHz 单声道下恰好 `65.536` 秒。智能体首轮回复实际播报约 87 秒，设备上传序列仍从 `0` 连续到 `5613`，但网关只把前 `1048576` 个样本写入 WAV 并标记 `truncated=true`。该标志表示“后续样本没有继续存盘”，不表示已经保存的前缀存在丢帧或损坏。因此采集器保留并切分这段连续前缀，同时在清单写入容量告警；采样率错误、声道错误、codec 错误或序列间隙仍会整轮拒绝。

70% 实际扬声器音量下，板载原始麦克风存在一定饱和，这是部署环境本身的一部分。质量门拒绝单段中绝对满幅样本超过 3% 的窗口；3% 以下的轻度饱和保留为真实设备声正样本，超过该比例则视为过度失真。后续训练清单必须使用逐段 `clipped_ratio`，分别统计低削波和高削波子集，不能把所有片段视为同等质量。

目标文件命名为：

```text
zh_female_daimengchuanmei_moon_bigtts_vol070_dist100cm_sent_001.wav
...
zh_female_daimengchuanmei_moon_bigtts_vol070_dist100cm_sent_225.wav
```

需要特别说明：本次声音由设备自身麦克风采集，`dist100cm` 是用户指定的文件名和训练元数据标签，不自动等于设备扬声器到板载麦克风的真实几何距离。采集清单默认记录 `distance_label_verified=false`，避免以后把命名标签误当作实测条件。

### 29.5 当前训练框架的已知阻塞项

这批纯设备声数据有价值，但现有 `device_voiceprint_trainer` 还不能直接作为可上线训练闭环：

- `record_dataset.py`、`verify_dataset.py` 与 `evaluate.py` 的模块字符串未闭合，当前文件不能正常执行。
- `train.py` 导入 `extract.goertzel_256`，但 `extract.py` 只实现了 `goertzel_single`，训练入口当前会导入失败。
- 当前 Goertzel 字典每个 WAV 只生成一个 8 频点模板，而设备端每 256 样本判一次；两者的时间统计合同尚未统一。
- 设备端 `p3_device_voiceprint_goertzel.c` 将 `2*cos(w)*32768` 强制写入 `int16_t s_coeff_q15[]`，但该系数范围是 `[-65536, 65536]`，并不适合 int16 Q15。例如 bin 6 的理论整数系数约为 `64826`，转换后成为 `-710`；bin 128 的 `-65536` 转换后成为 `0`。8 个频点中多个系数因此符号或幅度错误。后续必须改成足够位宽的系数或统一为 Q14，并做 PC/ESP 逐帧一致性测试。
- 字典结构保存了 `distance_cm`，但当前 `match_dict()` 只按 `tts_id` 和 `volume` 过滤，距离字段没有参与运行时匹配；不能把 `dist100cm` 命名理解为当前算法已经具备距离泛化能力。
- 运行时中等相似度直接将整帧衰减 50%，高相似度再减 30% software reference。若字典只含设备女声，没有真人负样本和双讲混合样本，很容易把频谱相近的真人音素误判并削弱。

因此 225 段数据可以作为“设备声正样本第一批”，适合建立设备声检测或残余回声估计的基础，但不能单独证明“干净用户声提取”。后续训练至少还需要：独立真人负样本、真人加设备声的多信噪比混合、同步播放参考、未见文本/说话人验证集，以及以人声保真为硬约束的 false-positive 指标。
