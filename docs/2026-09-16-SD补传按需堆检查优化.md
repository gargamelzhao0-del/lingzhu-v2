# SD 补传按需堆检查优化

## 实测基线

上一版自适应读取固件会话 `meeting_20260916_76f279a7_301892`：8371 帧、8 个分段共 5,576,110 字节，网关从第一条 begin 到最后一条 commit 用时 17.036 秒，平均 **319.64 KiB/s**。归档 CRC、序列和设备记录的总帧数一致，设备收到全部 ACK 并删除对应分段。

全部音频读取使用内部缓冲，未发生缩块或回退，因此该轮没有验证长时间运行后的碎片压力分支。每个完整分段的 SD 读取平均 1796.8 ms，校验 305.4 ms，内存准备 171 ms。后者为墙钟计时，含任务被调度挂起的时间，不能等同于分配器 CPU 时间。

## 代码依据

原路径每次读取都调用 `heap_caps_get_largest_free_block`。本地 ESP-IDF 的 `heap_caps.c` 将该查询转入 `heap_caps_get_info`；`multi_heap.c` 的 `multi_heap_get_info_impl` 持锁执行 `tlsf_walk_pool`，遍历匹配堆内的块。每个约 1 MiB 归档通常有 128 次读取，因此存在可直接消除的重复遍历。

`heap_caps_get_free_size` 读取各匹配堆的空闲计数，不使用这条全堆遍历路径。保留它进行每次实际分配前、后的 16 KiB 余量检查。

## 本次修改

- 正常路径按实时空闲量计算扇区对齐容量，直接尝试有界分配，不再预先查询最大连续块。
- 分配失败时，每次读取最多查询一次连续空间，并据此缩小下一次尝试；一次读取仍最多尝试 3 次分配。
- 得到的碎片容量仅作为接下来 32 次对齐读取的上限提示，之后重新尝试当前内存允许的大块；每个归档重新初始化提示。提示只保存数值，不保存内存指针，也不能替代实时余量检查。
- 连一个扇区也放不下时，短期使用原有 PSRAM/SD 适配路径，并按同样规则重新尝试恢复。`fragment_fallback` 单独统计该提示导致的回退，避免误报为真实总余量不足。
- 仍只在一次读取和校验期间持有内部缓冲。事件等待、网络 ACK、采音压力等待和主动让步前均已释放。
- 继续使用最大 8 KiB 单次读取、16 KiB 内部余量、原采音保护和工作预算；协议、CRC、持久化 ACK、窗口所有权和取消清理规则不变。

新增观测行：

```text
offline replay heap policy=on_failure largest_scans=0 largest_scan_ms=0 hinted_reads=0 fragment_fallback=0
```

正常场景预期 `largest_scans=0`。碎片场景应出现少量查询与提示命中；内存恢复后应重新使用大块，不能无限停留在降级状态。
